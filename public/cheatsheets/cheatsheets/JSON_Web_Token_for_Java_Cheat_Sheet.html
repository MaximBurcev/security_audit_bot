    Шпаргалка по JSON Web Token для Java¶

    Введение¶

    Многие приложения используют JSON Web Tokens (JWT) для того, чтобы клиент мог подтвердить свою идентичность при последующих обменах данными после аутентификации.

    Из JWT.IO:

    JSON Web Token (JWT) — открытый стандарт (RFC 7519), определяющий компактный и самодостаточный способ безопасной передачи информации между участниками в виде JSON-объекта. Эта информация может быть верифицирована и признана достоверной, поскольку является цифровой подписью. JWT могут быть подписаны с использованием секрета (с алгоритмом HMAC) или пары открытого/закрытого ключей RSA.

    JWT используются для передачи информации об идентичности и характеристиках (утверждениях) клиента. Эта информация подписывается сервером, чтобы гарантировать её неизменность после отправки клиенту. Это не позволяет злоумышленнику изменить идентичность или характеристики — например, изменить роль с обычного пользователя на администратора или изменить логин клиента.

    Токен создаётся в процессе аутентификации (выпускается при успешной аутентификации) и проверяется сервером перед любой обработкой. Приложения используют токен, чтобы клиент мог предъявить серверу своеобразное «удостоверение личности». Сервер может безопасно проверить валидность и целостность токена. Такой подход является stateless и переносимым — он работает с различными клиентскими и серверными технологиями, а также по различным транспортным каналам, хотя наиболее часто используется HTTP.

    Структура токена¶

    Пример структуры токена взят с JWT.IO:

    [Base64(HEADER)].[Base64(PAYLOAD)].[Base64(SIGNATURE)]

    eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWV9.
TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ

    Часть 1: Header

    {
  "alg": "HS256",
  "typ": "JWT"
}

    Часть 2: Payload

    {
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true
}

    Часть 3: Signature

    HMACSHA256( base64UrlEncode(header) + "." + base64UrlEncode(payload), KEY )

    Цель¶

    Данная шпаргалка содержит советы по предотвращению типичных проблем безопасности при использовании JSON Web Tokens (JWT) с Java.

    Советы, приведённые в этой статье, являются частью Java-проекта, созданного для демонстрации правильного способа создания и валидации JSON Web Tokens.

    Java-проект можно найти здесь; он использует официальную библиотеку JWT.

    В остальной части статьи термин токен относится к JSON Web Tokens (JWT).

    Соображения об использовании JWT¶

    Хотя JWT «прост» в использовании и позволяет предоставлять сервисы (преимущественно в стиле REST) без сохранения состояния, он не является решением, подходящим для всех приложений, поскольку имеет ряд нюансов — например, вопрос хранения токена (рассматривается в этой шпаргалке) и другие.

    Если вашему приложению не нужно быть полностью stateless, можно рассмотреть использование традиционной системы сессий, предоставляемой всеми web-фреймворками, и следовать советам из специализированной шпаргалки по управлению сессиями. Однако для stateless-приложений при правильной реализации JWT является хорошим кандидатом.

    Проблемы¶

    Алгоритм хеширования None¶

    Симптом¶

    Эта атака, описанная здесь, происходит когда злоумышленник изменяет токен и меняет алгоритм хеширования на none, указывая тем самым, что целостность токена уже была проверена. Как объяснено по ссылке выше, некоторые библиотеки обрабатывали токены, подписанные алгоритмом none, как валидные токены с проверенной подписью, поэтому злоумышленник может изменить утверждения токена и изменённый токен по-прежнему будет доверенным для приложения.

    Как предотвратить¶

    Прежде всего, используйте JWT-библиотеку, не подверженную этой уязвимости.

    Далее, при валидации токена явно требуйте использования ожидаемого алгоритма.

    Пример реализации¶

    // HMAC ключ — запрет сериализации и хранения в виде String в памяти JVM
private transient byte[] keyHMAC = ...;

...

// Создание контекста верификации токена с явным указанием
// использования алгоритма хеширования HMAC-256
JWTVerifier verifier = JWT.require(Algorithm.HMAC256(keyHMAC)).build();

// Верификация токена; если проверка не прошла — выбрасывается исключение
DecodedJWT decodedToken = verifier.verify(token);

    Перехват токена (Token Sidejacking)¶

    Симптом¶

    Эта атака происходит когда токен был перехвачен или похищен злоумышленником, и он использует его для получения доступа к системе под видом целевого пользователя.

    Как предотвратить¶

    Один из способов предотвращения — добавить «контекст пользователя» к токену. Контекст пользователя должен включать:

    • Случайную строку, сгенерированную на этапе аутентификации. Эта строка отправляется клиенту в виде защищённого cookie (со следующими флагами: HttpOnly + Secure, SameSite, Max-Age и префиксы cookie). Избегайте установки заголовка expires, чтобы cookie удалялся при закрытии браузера. Устанавливайте Max-Age равным времени жизни JWT или меньше — но никогда больше.
    • SHA256-хеш случайной строки хранится в токене (вместо исходного значения), чтобы предотвратить возможность чтения случайной строки через XSS и установки ожидаемого cookie злоумышленником.

    Избегайте использования IP-адресов в качестве части контекста. IP-адреса могут изменяться в течение одной сессии по законным причинам — например, когда пользователь получает доступ к приложению с мобильного устройства и переключается между провайдерами. Кроме того, отслеживание IP может вызывать вопросы, связанные с соответствием GDPR в ЕС.

    При валидации токена, если полученный токен не содержит правильного контекста (например, если он воспроизводится злоумышленником), он должен быть отклонён.

    Пример реализации¶

    Код создания токена после успешной аутентификации.

    // HMAC ключ — запрет сериализации и хранения в виде String в памяти JVM
private transient byte[] keyHMAC = ...;
// Генератор случайных данных
private SecureRandom secureRandom = new SecureRandom();

...

// Генерация случайной строки, составляющей отпечаток для данного пользователя
byte[] randomFgp = new byte[50];
secureRandom.nextBytes(randomFgp);
String userFingerprint = DatatypeConverter.printHexBinary(randomFgp);

// Добавление отпечатка в защищённый cookie — добавление cookie вручную, поскольку
// атрибут SameSite не поддерживается классом javax.servlet.http.Cookie
String fingerprintCookie = "__Secure-Fgp=" + userFingerprint
                           + "; SameSite=Strict; HttpOnly; Secure";
response.addHeader("Set-Cookie", fingerprintCookie);

// Вычисление SHA256-хеша отпечатка для хранения
// хеша отпечатка (вместо исходного значения) в токене,
// чтобы XSS не мог прочитать отпечаток и
// самостоятельно установить ожидаемый cookie
MessageDigest digest = MessageDigest.getInstance("SHA-256");
byte[] userFingerprintDigest = digest.digest(userFingerprint.getBytes("utf-8"));
String userFingerprintHash = DatatypeConverter.printHexBinary(userFingerprintDigest);

// Создание токена со сроком действия 15 минут и информацией о контексте клиента (отпечатке)
Calendar c = Calendar.getInstance();
Date now = c.getTime();
c.add(Calendar.MINUTE, 15);
Date expirationDate = c.getTime();
Map<String, Object> headerClaims = new HashMap<>();
headerClaims.put("typ", "JWT");
String token = JWT.create().withSubject(login)
   .withExpiresAt(expirationDate)
   .withIssuer(this.issuerID)
   .withIssuedAt(now)
   .withNotBefore(now)
   .withClaim("userFingerprint", userFingerprintHash)
   .withHeader(headerClaims)
   .sign(Algorithm.HMAC256(this.keyHMAC));

    Код валидации токена.

    // HMAC ключ — запрет сериализации и хранения в виде String в памяти JVM
private transient byte[] keyHMAC = ...;

...

// Получение отпечатка пользователя из специального cookie
String userFingerprint = null;
if (request.getCookies() != null && request.getCookies().length > 0) {
 List<Cookie> cookies = Arrays.stream(request.getCookies()).collect(Collectors.toList());
 Optional<Cookie> cookie = cookies.stream().filter(c -> "__Secure-Fgp"
                                            .equals(c.getName())).findFirst();
 if (cookie.isPresent()) {
   userFingerprint = cookie.get().getValue();
 }
}

// Вычисление SHA256-хеша отпечатка из cookie для сравнения
// с хешем отпечатка, хранящимся в токене
MessageDigest digest = MessageDigest.getInstance("SHA-256");
byte[] userFingerprintDigest = digest.digest(userFingerprint.getBytes("utf-8"));
String userFingerprintHash = DatatypeConverter.printHexBinary(userFingerprintDigest);

// Создание контекста верификации токена
JWTVerifier verifier = JWT.require(Algorithm.HMAC256(keyHMAC))
                              .withIssuer(issuerID)
                              .withClaim("userFingerprint", userFingerprintHash)
                              .build();

// Верификация токена; если проверка не прошла — выбрасывается исключение
DecodedJWT decodedToken = verifier.verify(token);

    Отсутствие встроенного механизма отзыва токена пользователем¶

    Симптом¶

    Эта проблема присуща JWT, поскольку токен становится недействительным только при истечении срока действия. Пользователь не имеет встроенного инструмента для явного отзыва валидности токена. Это означает, что если токен похищен, пользователь не может отозвать его, заблокировав тем самым злоумышленника.

    Как предотвратить¶

    Поскольку JWT являются stateless, сервер(ы), обслуживающий(е) запросы клиентов, не поддерживает(ют) сессию. Следовательно, нет сессии для инвалидации на стороне сервера. Хорошо реализованное решение Token Sidejacking (как описано выше) должно устранить необходимость ведения списка запрещённых токенов на стороне сервера. Это обусловлено тем, что защищённый cookie, используемый в Token Sidejacking, можно считать столь же безопасным, как идентификатор сессии в традиционной системе сессий, и если не перехвачены одновременно и cookie, и JWT, JWT становится бесполезным. Таким образом, «выход из системы» можно «имитировать», удалив JWT из session storage. Если пользователь закрывает браузер, и cookie, и sessionStorage автоматически очищаются.

    Другой способ защиты — реализация списка запрещённых токенов, который будет использоваться для имитации функции «выхода из системы», существующей в традиционных системах управления сессиями.

    Список запрещённых токенов будет хранить дайджест (SHA-256, закодированный в HEX) токена с датой отзыва. Эта запись должна существовать как минимум до истечения срока действия токена.

    Когда пользователь хочет «выйти из системы», он вызывает специальный сервис, который добавляет предоставленный токен в список запрещённых, что немедленно инвалидирует токен для дальнейшего использования в приложении.

    Пример реализации¶

    Хранилище списка заблокированных¶

    В качестве централизованного хранилища списка запрещённых токенов будет использована таблица базы данных следующей структуры.

    create table if not exists revoked_token(jwt_token_digest varchar(255) primary key,
revocation_date timestamp default now());
    Управление отзывом токенов¶

    Код, отвечающий за добавление токена в список запрещённых и проверку статуса отзыва токена.

    /**
* Обработка отзыва токена (выхода из системы).
* Используется БД для возможности проверки отозванных токенов
* несколькими экземплярами и централизованной очистки на уровне БД.
*/
public class TokenRevoker {

 /** Подключение к БД */
 @Resource("jdbc/storeDS")
 private DataSource storeDS;

 /**
  * Проверяет наличие дайджеста зашифрованного токена в HEX
  * в таблице отзыва
  *
  * @param jwtInHex Токен, закодированный в HEX
  * @return Флаг наличия
  * @throws Exception При возникновении проблем при взаимодействии с БД
  */
 public boolean isTokenRevoked(String jwtInHex) throws Exception {
     boolean tokenIsPresent = false;
     if (jwtInHex != null && !jwtInHex.trim().isEmpty()) {
         // Декодирование зашифрованного токена
         byte[] cipheredToken = DatatypeConverter.parseHexBinary(jwtInHex);

         // Вычисление SHA256 зашифрованного токена
         MessageDigest digest = MessageDigest.getInstance("SHA-256");
         byte[] cipheredTokenDigest = digest.digest(cipheredToken);
         String jwtTokenDigestInHex = DatatypeConverter.printHexBinary(cipheredTokenDigest);

         // Поиск дайджеста токена в HEX в БД
         try (Connection con = this.storeDS.getConnection()) {
             String query = "select jwt_token_digest from revoked_token where jwt_token_digest = ?";
             try (PreparedStatement pStatement = con.prepareStatement(query)) {
                 pStatement.setString(1, jwtTokenDigestInHex);
                 try (ResultSet rSet = pStatement.executeQuery()) {
                     tokenIsPresent = rSet.next();
                 }
             }
         }
     }

     return tokenIsPresent;
 }


 /**
  * Добавляет дайджест зашифрованного токена в HEX в таблицу отозванных токенов
  *
  * @param jwtInHex Токен, закодированный в HEX
  * @throws Exception При возникновении проблем при взаимодействии с БД
  */
 public void revokeToken(String jwtInHex) throws Exception {
     if (jwtInHex != null && !jwtInHex.trim().isEmpty()) {
         // Декодирование зашифрованного токена
         byte[] cipheredToken = DatatypeConverter.parseHexBinary(jwtInHex);

         // Вычисление SHA256 зашифрованного токена
         MessageDigest digest = MessageDigest.getInstance("SHA-256");
         byte[] cipheredTokenDigest = digest.digest(cipheredToken);
         String jwtTokenDigestInHex = DatatypeConverter.printHexBinary(cipheredTokenDigest);

         // Проверка наличия дайджеста токена в HEX в БД и добавление при отсутствии
         if (!this.isTokenRevoked(jwtInHex)) {
             try (Connection con = this.storeDS.getConnection()) {
                 String query = "insert into revoked_token(jwt_token_digest) values(?)";
                 int insertedRecordCount;
                 try (PreparedStatement pStatement = con.prepareStatement(query)) {
                     pStatement.setString(1, jwtTokenDigestInHex);
                     insertedRecordCount = pStatement.executeUpdate();
                 }
                 if (insertedRecordCount != 1) {
                     throw new IllegalStateException("Number of inserted record is invalid," +
                     " 1 expected but is " + insertedRecordCount);
                 }
             }
         }

     }
 }

    Раскрытие информации токена¶

    Симптом¶

    Эта атака происходит когда злоумышленник получает доступ к токену (или набору токенов) и извлекает хранящуюся в нём информацию (содержимое JWT кодируется в base64, но по умолчанию не шифруется), чтобы получить сведения о системе. Информация может включать, например, роли безопасности, формат логина и т.д.

    Как предотвратить¶

    Один из способов защиты от этой атаки — шифрование токена с использованием, например, симметричного алгоритма.

    Также важно защитить зашифрованные данные от атак, таких как Padding Oracle или любых других атак с использованием криптоанализа.

    Для достижения всех этих целей используется алгоритм AES-GCM, обеспечивающий аутентифицированное шифрование со связанными данными.

    Подробнее здесь:

    AEAD primitive (Authenticated Encryption with Associated Data) provides functionality of symmetric
authenticated encryption.

Implementations of this primitive are secure against adaptive chosen ciphertext attacks.

When encrypting a plaintext one can optionally provide associated data that should be authenticated
but not encrypted.

That is, the encryption with associated data ensures authenticity (ie. who the sender is) and
integrity (ie. data has not been tampered with) of that data, but not its secrecy.

See RFC5116: https://tools.ietf.org/html/rfc5116

    Примечание:

    Здесь шифрование добавляется главным образом для сокрытия внутренней информации, но очень важно помнить, что первичная защита JWT от подделки — это подпись. Поэтому подпись токена и её верификация должны присутствовать всегда.

    Пример реализации¶

    Шифрование токена¶

    Код, управляющий шифрованием. Для выполнения операций шифрования используется специализированная криптографическая библиотека Google Tink, чтобы применять встроенные лучшие практики, предоставляемые этой библиотекой.

    /**
 * Управление шифрованием и дешифрованием токена с использованием AES-GCM.
 *
 * @see "https://github.com/google/tink/blob/master/docs/JAVA-HOWTO.md"
 */
public class TokenCipher {

    /**
     * Конструктор — регистрация конфигурации AEAD
     *
     * @throws Exception При возникновении проблем во время регистрации конфигурации AEAD
     */
    public TokenCipher() throws Exception {
        AeadConfig.register();
    }

    /**
     * Шифрование JWT
     *
     * @param jwt          Токен для шифрования
     * @param keysetHandle Указатель на дескриптор набора ключей
     * @return Зашифрованная версия токена, закодированная в HEX
     * @throws Exception При возникновении проблем во время операции шифрования токена
     */
    public String cipherToken(String jwt, KeysetHandle keysetHandle) throws Exception {
        // Проверка параметров
        if (jwt == null || jwt.isEmpty() || keysetHandle == null) {
            throw new IllegalArgumentException("Both parameters must be specified!");
        }

        // Получение примитива
        Aead aead = AeadFactory.getPrimitive(keysetHandle);

        // Шифрование токена
        byte[] cipheredToken = aead.encrypt(jwt.getBytes(), null);

        return DatatypeConverter.printHexBinary(cipheredToken);
    }

    /**
     * Дешифрование JWT
     *
     * @param jwtInHex     Токен для дешифрования, закодированный в HEX
     * @param keysetHandle Указатель на дескриптор набора ключей
     * @return Токен в открытом виде
     * @throws Exception При возникновении проблем во время операции дешифрования токена
     */
    public String decipherToken(String jwtInHex, KeysetHandle keysetHandle) throws Exception {
        // Проверка параметров
        if (jwtInHex == null || jwtInHex.isEmpty() || keysetHandle == null) {
            throw new IllegalArgumentException("Both parameters must be specified !");
        }

        // Декодирование зашифрованного токена
        byte[] cipheredToken = DatatypeConverter.parseHexBinary(jwtInHex);

        // Получение примитива
        Aead aead = AeadFactory.getPrimitive(keysetHandle);

        // Дешифрование токена
        byte[] decipheredToken = aead.decrypt(cipheredToken, null);

        return new String(decipheredToken);
    }
}

    Хранение токена на стороне клиента¶

    Симптом¶

    Это происходит когда приложение хранит токен способом, демонстрирующим следующее поведение:

    • Автоматически отправляется браузером (хранение в Cookie).
    • Сохраняется при перезапуске браузера (использование контейнера браузера localStorage).
    • Доступен в случае XSS-уязвимости (Cookie доступен для JavaScript-кода или токен хранится в local/session storage браузера).

    Как предотвратить¶

    1. Хранить токен в контейнере браузера sessionStorage или использовать JavaScript замыкания с приватными переменными.
    2. Добавлять его как HTTP-заголовок Bearer Authentication через JavaScript при вызове сервисов.
    3. Добавлять информацию об отпечатке в токен.

    Хранение токена в контейнере браузера sessionStorage подвергает его риску кражи через XSS-атаку. Однако отпечатки, добавленные к токену, предотвращают повторное использование похищенного токена злоумышленником на его машине. Для максимального сужения поверхности атаки добавьте в браузер Content Security Policy, чтобы ужесточить контекст выполнения.

    Однако sessionStorage не всегда удобен из-за ограниченной области видимости (одна вкладка), и метод хранения токенов должен соблюдать баланс между безопасностью и удобством использования.

    LocalStorage лучше sessionStorage с точки зрения удобства, поскольку позволяет сессии сохраняться между перезапусками браузера и между вкладками, но необходимо применять строгие меры безопасности:

    • Токены, хранящиеся в localStorage, должны иметь короткое время истечения (например, тайм-аут бездействия 15–30 минут, абсолютный тайм-аут 8 часов).
    • Реализуйте механизмы ротации токенов и refresh токенов для минимизации рисков.

    Если требуется сохранение сессии между вкладками при использовании sessionStorage, рассмотрите применение BroadcastChannel API или Single Sign-On (SSO) для автоматической повторной аутентификации пользователей при открытии новых вкладок.

    Альтернативой хранению токена в браузерном sessionStorage или localStorage является использование приватных переменных JavaScript или замыканий. В этом случае все web-запросы маршрутизируются через JavaScript-модуль, инкапсулирующий токен в приватной переменной, недоступной извне модуля.

    Примечание:

    • Оставшийся случай — когда злоумышленник использует контекст браузера пользователя как прокси для обращения к целевому приложению через легитимного пользователя. Content Security Policy может предотвратить взаимодействие с неожидаемыми доменами.
    • Также можно реализовать сервис аутентификации таким образом, чтобы токен выпускался в виде защищённого cookie. Однако в этом случае необходимо реализовать защиту от атак Cross-Site Request Forgery.

    Слабый секрет токена¶

    Симптом¶

    Когда токен защищён алгоритмом на основе HMAC, безопасность токена полностью зависит от надёжности секрета, используемого с HMAC. Если злоумышленник может получить действительный JWT, он может провести офлайн-атаку и попытаться взломать секрет с помощью инструментов, таких как John the Ripper или Hashcat.

    В случае успеха злоумышленник сможет изменить токен и повторно подписать его полученным ключом. Это может позволить ему повысить привилегии, скомпрометировать аккаунты других пользователей или выполнить другие действия в зависимости от содержимого JWT.

    Существует ряд руководств, подробно описывающих этот процесс.

    Как предотвратить¶

    Простейший способ предотвратить эту атаку — убедиться, что секрет для подписи JWT является надёжным и уникальным, чтобы затруднить его взлом злоумышленником. Поскольку этот секрет никогда не нужно вводить вручную, он должен содержать не менее 64 символов и генерироваться с использованием безопасного источника случайности.

    В качестве альтернативы рассмотрите использование токенов, подписанных с помощью RSA, вместо использования HMAC и секретного ключа.
