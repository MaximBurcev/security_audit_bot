    Лучшие практики безопасности NPM¶

    Следующая шпаргалка охватывает несколько лучших практик безопасности и советов по повышению производительности при работе с npm, полезных для разработчиков JavaScript и Node.js. Этот список изначально основан на статье 10 лучших практик безопасности npm из блога Snyk.

    1) Избегайте публикации секретов в реестр npm¶

    Независимо от того, используете ли вы API-ключи, пароли или другие секреты, они очень легко могут попасть в систему контроля версий или даже в опубликованный пакет в публичном реестре npm. Секреты могут находиться в вашем рабочем каталоге в специальных файлах, например .env, который следует добавить в .gitignore, чтобы не фиксировать его в SCM. Но что происходит, когда вы публикуете пакет npm из каталога проекта?

    npm CLI упаковывает проект в tar-архив (tarball), чтобы отправить его в реестр. Следующие критерии определяют, какие файлы и каталоги добавляются в tarball:

    • Если присутствует файл .gitignore или .npmignore, его содержимое используется как шаблон игнорирования при подготовке пакета к публикации.
    • Если оба файла существуют, в реестр публикуется всё, что не указано в .npmignore. Это условие является распространённым источником путаницы и может привести к утечке секретов.

    Разработчики могут обновить .gitignore, но забыть обновить .npmignore, что может привести к тому, что потенциально чувствительный файл не попадёт в систему контроля версий, но всё равно будет включён в npm-пакет.

    Ещё одной хорошей практикой является использование свойства files в package.json, которое работает как allowlist и определяет массив файлов, включаемых в создаваемый и устанавливаемый пакет (тогда как файл игнорирования работает как denylist). Свойство files и файл игнорирования могут использоваться вместе, чтобы явно определить, какие файлы должны быть включены, а какие исключены из пакета. При совместном использовании свойство files в package.json имеет приоритет над файлом игнорирования.

    При публикации пакета npm CLI подробно отображает создаваемый архив. Для дополнительной осторожности добавьте аргумент --dry-run к команде публикации, чтобы сначала проверить, как создаётся tarball, не публикуя его фактически в реестр.

    Подробности об отзыве токенов доступа см. в официальной документации: Revocation access tokens.

    2) Соблюдайте lockfile¶

    Мы с радостью встретили появление lockfile-файлов для пакетов, которые обеспечили: детерминированные установки в разных средах и согласованные ожидания относительно зависимостей при командной работе. Жизнь прекрасна! Или так казалось... что было бы, если бы я внёс изменение в файл package.json проекта, но забыл зафиксировать lockfile вместе с ним?

    Yarn и npm ведут себя одинаково при установке зависимостей. При обнаружении несоответствия между package.json проекта и lockfile они компенсируют это изменение, устанавливая версии, указанные в package.json, а не те, что записаны в lockfile.

    Такая ситуация может быть опасна для сборочных и производственных сред, так как могут быть загружены непредусмотренные версии пакетов, что делает использование lockfile бессмысленным.

    К счастью, есть способ указать Yarn и npm строго придерживаться указанного набора зависимостей и их версий, ссылаясь на lockfile. При любом несоответствии установка будет прервана. Используйте следующие команды:

    • Если вы используете Yarn, запустите yarn install --frozen-lockfile.
    • Если вы используете npm, запустите npm ci.

    3) Минимизируйте поверхность атаки, игнорируя run-scripts¶

    npm CLI работает со скриптами запуска пакетов. Если вы когда-либо запускали npm start или npm test, вы тоже использовали скрипты запуска пакетов. npm CLI опирается на скрипты, которые пакет может объявить, и позволяет пакетам определять скрипты для запуска в определённые точки входа во время установки пакета в проекте. Например, некоторые из этих хуков скриптов могут быть скриптами postinstall, которые выполняет устанавливаемый пакет для выполнения служебных задач.

    С помощью этой возможности злоумышленники могут создавать или изменять пакеты для выполнения вредоносных действий, запуская произвольные команды при установке пакета. Несколько случаев, когда это уже происходило: известный инцидент с eslint-scope, который собирал npm-токены, и инцидент с crossenv вместе с 36 другими пакетами, использовавшими typosquatting-атаку на реестр npm.

    Применяйте следующие лучшие практики безопасности npm для минимизации поверхности атаки вредоносных модулей:

    • Всегда проверяйте и анализируйте сторонние модули, которые вы устанавливаете, чтобы убедиться в их надёжности и достоверности.
    • Не спешите с обновлением до новых версий; дайте новым версиям пакетов немного времени до того, как начнёте их использовать.
    • Перед обновлением обязательно просмотрите changelog и примечания к выпуску для обновляемой версии.
    • При установке пакетов добавляйте суффикс --ignore-scripts, чтобы отключить выполнение скриптов сторонними пакетами.
    • Рассмотрите возможность добавления ignore-scripts в файл .npmrc вашего проекта или в глобальную конфигурацию npm.

    Использование allowlist для lifecycle-скриптов¶

    Отключение lifecycle-скриптов по умолчанию путём добавления ignore-script в файл .npmrc является наиболее безопасным вариантом. Если вы используете пакеты, которые зависят от lifecycle-скриптов по законным причинам, можно использовать плагин @lavamoat/allow-scripts для создания allowlist пакетов, которым разрешено запускать lifecycle-скрипты.

    Вот как будет выглядеть allowlist в файле package.json для проекта, использующего популярный пакет обработки изображений sharp:

    {
  "lavamoat": {
    "allowScripts": {
      "sharp": true
    }
  }
}

    4) Оценивайте состояние npm-проекта¶

    Команда npm outdated¶

    Постоянно обновлять зависимости до последних версий — не обязательно хорошая практика, если это делается без изучения примечаний к выпуску, изменений кода и тщательного тестирования новых обновлений. Тем не менее отставание в обновлениях и отказ от них вовсе или длительная задержка с обновлением — тоже источник проблем.

    npm CLI может предоставить информацию об актуальности используемых вами зависимостей с точки зрения их семантической версии. Запустив npm outdated, вы увидите, какие пакеты устарели. Зависимости, выделенные жёлтым, соответствуют семантической версии, указанной в манифесте package.json, а выделенные красным означают, что доступно обновление. Кроме того, вывод показывает последнюю версию каждой зависимости.

    Команда npm doctor¶

    Как среди разнообразия менеджеров пакетов Node.js, так и при наличии разных версий Node.js на вашем компьютере, как убедиться в том, что установка npm работает корректно? Независимо от того, работаете ли вы с npm CLI в среде разработки или в CI, важно убедиться, что всё функционирует должным образом.

    Вызовите доктора! npm CLI включает инструмент диагностики окружения для корректной работы npm. Запустите npm doctor для проверки вашей конфигурации npm:

    • Проверяет доступность официального реестра npm и отображает текущий настроенный реестр.
    • Проверяет доступность Git.
    • Просматривает установленные версии npm и Node.js.
    • Выполняет проверку прав доступа для различных папок, таких как локальный и глобальный node_modules, а также папки, используемой для кэша пакетов.
    • Проверяет локальный кэш npm-модулей на корректность контрольных сумм.

    5) Проводите аудит уязвимостей в зависимостях с открытым исходным кодом¶

    Экосистема npm является крупнейшим репозиторием библиотек приложений среди всех других языковых экосистем. Реестр и находящиеся в нём библиотеки являются основой для разработчиков JavaScript, позволяя им использовать чужие наработки и включать их в свой код. Вместе с тем растущее использование библиотек с открытым исходным кодом в приложениях влечёт за собой повышенный риск внесения уязвимостей безопасности.

    Многие популярные npm-пакеты оказались уязвимыми и могут представлять значительный риск без надлежащего аудита безопасности зависимостей вашего проекта. Примеры: npm-пакеты request, superagent, mongoose и даже пакеты, связанные с безопасностью, такие как jsonwebtoken и validator.

    Безопасность не заканчивается сканированием на уязвимости при установке пакета — её необходимо встроить в рабочий процесс разработчиков, чтобы она эффективно применялась на протяжении всего жизненного цикла разработки программного обеспечения, и вести непрерывный мониторинг при развёртывании кода:

    • Сканируйте на уязвимости безопасности в сторонних проектах с открытым исходным кодом
    • Отслеживайте снимки манифестов вашего проекта, чтобы получать оповещения при появлении новых CVE, влияющих на них: OWASP Dependency-Track

    6) Управление артефактами и защита цепочки поставок¶

    Используйте локальный npm-прокси¶

    Реестр npm — крупнейшая коллекция пакетов для всех JavaScript-разработчиков, а также основное место хранения большинства проектов с открытым исходным кодом для веб-разработчиков. Однако иногда могут возникнуть различные требования с точки зрения безопасности, развёртывания или производительности. В таких случаях npm позволяет переключиться на другой реестр:

    При запуске npm install автоматически устанавливается связь с главным реестром для разрешения всех зависимостей. Если вы хотите использовать другой реестр, это тоже просто:

    • Установите npm set registry для настройки реестра по умолчанию.
    • Используйте аргумент --registry для одного конкретного реестра.

    Verdaccio — это простой лёгкий частный реестр без необходимости настройки, установить его так же просто: $ npm install --global verdaccio.

    Размещать собственный реестр никогда не было так просто! Рассмотрим наиболее важные возможности этого инструмента:

    • Поддерживает формат реестра npm, включая функции приватных пакетов, поддержку областей видимости (scope), управление доступом к пакетам и аутентифицированных пользователей в веб-интерфейсе.
    • Предоставляет возможности для взаимодействия с удалёнными реестрами и маршрутизации каждой зависимости в разные реестры с кэшированием tarball-архивов. Для снижения дублирования загрузок и экономии полосы пропускания на локальных серверах разработки и CI следует проксировать все зависимости.
    • В качестве провайдера аутентификации по умолчанию использует htpasswd, но также поддерживает Gitlab, Bitbucket, LDAP. Можно использовать и собственный провайдер.
    • Легко масштабируется с использованием различных провайдеров хранилища.
    • Если ваш проект основан на Docker, использование официального образа — лучший выбор.
    • Обеспечивает очень быстрый запуск тестовых сред и удобен для тестирования крупных монорепозиторных проектов.

    Управление и этапы верификации¶

    Атаки на цепочку поставок всё чаще нацелены на артефакты сборки, реестры и учётные данные CI. Добавьте облегчённые шаги управления и верификации для снижения риска и улучшения времени реагирования:

    • Отслеживайте происхождение и создавайте SBOM для сборок (CycloneDX/SPDX), чтобы можно было отследить, что было собрано и откуда поступили входные данные.

    Пример CycloneDX:

    # Генерация SBOM
npm install @cyclonedx/cyclonedx-npm
npx @cyclonedx/cyclonedx-npm --validate > sbom.json # Используйте флаг `--omit dev` для исключения dev-зависимостей из SBOM при необходимости
    • Подписывайте артефакты и подтверждения происхождения сборки (например, используйте Sigstore / cosign или аналогичные инструменты подписи), чтобы потребители могли проверить целостность перед установкой.

    Пример Sigstore:

    // sign-and-verify.js
// npm install sigstore fs

import * as fs from 'fs';
import * as sigstore from 'sigstore';

// Путь к собранному npm-пакету (через `npm pack`)
const artifact = 'my-lib-1.0.0.tgz';

// --- Подпись ---
const payload = fs.readFileSync(artifact);
const bundle = await sigstore.sign(payload);
fs.writeFileSync(`${artifact}.sigstore.json`, JSON.stringify(bundle, null, 2));
console.log('Подписано:', artifact);

// --- Верификация ---
await sigstore.verify(payload, bundle);
console.log('Верификация прошла успешно!');
    • Отдавайте предпочтение неизменяемым реестрам с контролем доступа или проверенным зеркалам (приватные реестры, Verdaccio с кэшем вышестоящего реестра или одобренные зеркала) и включайте политики хранения/неизменяемости там, где это доступно.
    • Ограничивайте, разграничивайте и ротируйте токены CI и публикующих пользователей. Привязывайте токены публикации к рабочим процессам или диапазонам IP-адресов и минимизируйте привилегии.
    • Верифицируйте пакеты во время CI: проверяйте подписи или происхождение, валидируйте SBOM, запускайте SCA и статический анализ и устанавливайте из зафиксированных версий lockfile.
    • Автоматизируйте мониторинг и оповещения о необычных публикациях, использовании токенов или изменениях зависимостей, а также ведите документированный план реагирования (отзыв токенов, депрекация/удаление скомпрометированных пакетов, публикация исправлений и уведомление потребителей).

    Эти меры постепенны и не несут рисков при внедрении. В совокупности они делают атаки на цепочку поставок сложнее и ускоряют обнаружение и восстановление в случае компрометации.

    7) Ответственно раскрывайте уязвимости безопасности¶

    Когда обнаруживаются уязвимости безопасности, они представляют потенциально серьёзную угрозу, если публикуются без предварительного предупреждения или соответствующих мер по устранению для пользователей, которые не могут защитить себя самостоятельно.

    Рекомендуется, чтобы исследователи безопасности следовали программе ответственного раскрытия — набору процессов и руководящих принципов, направленных на установление связи между исследователями и поставщиком или сопровождающим уязвимого актива для передачи информации об уязвимости, её влиянии и применимости. После правильной сортировки уязвимости поставщик и исследователь координируют исправление и дату публикации уязвимости, стремясь предоставить путь обновления или устранения для затронутых пользователей до того, как проблема безопасности станет общедоступной.

    8) Включите 2FA¶

    Включение двухфакторной аутентификации (2FA) является критически важной лучшей практикой безопасности npm. Реестр npm поддерживает два режима включения 2FA для учётной записи пользователя:

    • Только авторизация — когда пользователь входит в npm через веб-сайт или CLI или выполняет другие действия, такие как изменение информации профиля.
    • Авторизация и режим записи — действия с профилем и входом, а также операции записи, такие как управление токенами и пакетами, и ограниченная поддержка информации о видимости команды и пакетов.

    Для начала работы см. официальную документацию: Requiring 2FA.

    Оснастите себя приложением аутентификации, например Google Authentication, которое можно установить на мобильное устройство, и вы готовы к работе. Один простой способ начать расширенную защиту 2FA для вашей учётной записи — через пользовательский интерфейс npm, который позволяет очень легко её включить. Если вы предпочитаете командную строку, включить 2FA также легко при использовании поддерживаемой версии npm-клиента (>=5.5.1):

    npm profile enable-2fa auth-and-writes

    Следуйте инструкциям командной строки для включения 2FA и сохранения аварийных кодов аутентификации. Если вы хотите включить режим 2FA только для входа и изменений профиля, вы можете заменить auth-and-writes на auth-only в приведённой выше команде.

    9) Используйте токены авторов npm¶

    Каждый раз, когда вы входите с помощью npm CLI, для вашего пользователя генерируется токен, который аутентифицирует вас в реестре npm. Токены упрощают выполнение действий, связанных с реестром npm, в процессе CI и автоматизированных процедур, таких как доступ к приватным модулям в реестре или публикация новых версий на этапе сборки.

    Токенами можно управлять через веб-сайт реестра npm, а также с помощью npm-клиента командной строки. Пример использования CLI для создания токена только для чтения, ограниченного определённым диапазоном адресов IPv4:

    npm token create --read-only --cidr=192.0.2.0/24

    Для проверки созданных токенов или отзыва токенов в экстренных случаях можно использовать npm token list или npm token revoke соответственно.

    Убедитесь, что вы следуете этой лучшей практике безопасности npm, защищая и минимизируя раскрытие своих npm-токенов.

    10) Понимание атак typosquatting и slopsquatting¶

    Атаки typosquatting¶

    Typosquatting — это атака, основанная на ошибках пользователей, таких как опечатки. При typosquatting злоумышленники публикуют вредоносные модули в реестр npm с именами, очень похожими на существующие популярные модули. Эти вредоносные пакеты эксплуатируют распространённые ошибки при вводе или визуальное сходство, чтобы обманом заставить разработчиков установить их вместо легитимных пакетов.

    Команда безопасности Snyk отслеживала десятки вредоносных пакетов в экосистеме npm, использовавших typosquatting для обмана пользователей; аналогичные атаки наблюдались и в реестре Python PyPi. Среди наиболее известных инцидентов: cross-env, event-stream и eslint-scope.

    Одной из основных целей атак typosquatting являются учётные данные пользователей, поскольку любой пакет имеет доступ к переменным окружения через глобальную переменную process.env. Другие примеры включают случай с event-stream, когда злоумышленники нацелились на разработчиков с целью внедрения вредоносного кода в исходный код приложения.

    Атаки slopsquatting¶

    Slopsquatting — более новый вектор атаки, эксплуатирующий AI-помощников по написанию кода и большие языковые модели (LLM). Когда разработчики используют AI-инструменты для генерации кода или рекомендаций по пакетам, эти модели иногда могут «галлюцинировать» названия пакетов, которых на самом деле не существует. Злоумышленники отслеживают такие галлюцинации и создают вредоносные пакеты с именно такими именами, зная, что разработчики могут слепо доверять и устанавливать пакеты, предложенные их AI-помощниками.

    Для защиты от slopsquatting:

    • Всегда проверяйте, что пакеты, предложенные AI-инструментами, действительно существуют и являются легитимными
    • Проверяйте репозиторий пакета, статистику загрузок и информацию о сопровождающих
    • Сверяйте предложения AI с официальной документацией
    • С осторожностью относитесь к пакетам с очень малым количеством загрузок или недавними датами создания
    • Изучайте исходный код пакета перед установкой, особенно для пакетов, предложенных AI

    11) Используйте доверенных публикаторов для безопасной публикации пакетов¶

    Традиционная публикация в npm основана на долгосрочных токенах, которые могут быть скомпрометированы или случайно раскрыты. Trusted publishing с использованием OpenID Connect (OIDC) предоставляет более безопасную альтернативу, используя краткосрочные, специфичные для рабочего процесса учётные данные, автоматически генерируемые во время CI/CD-процессов. В настоящее время trusted publishing поддерживает GitHub Actions и GitLab CI/CD Pipelines.

    Как работает trusted publishing¶

    Trusted publishing создаёт отношение доверия между npm и вашим CI/CD-провайдером с использованием OIDC. При настройке доверенного публикатора для вашего пакета npm будет принимать публикации из конкретного рабочего процесса, который вы авторизовали, в дополнение к традиционным методам аутентификации, таким как npm-токены и ручная публикация. npm CLI автоматически обнаруживает OIDC-окружения и использует их для аутентификации, прежде чем переходить к традиционным токенам.

    Этот подход устраняет риски безопасности, связанные с долгосрочными токенами записи, которые могут быть скомпрометированы, случайно раскрыты в логах или требуют ручной ротации. Вместо этого каждая публикация использует краткосрочные, криптографически подписанные токены, специфичные для вашего рабочего процесса, которые не могут быть извлечены или повторно использованы.

    Автоматическая генерация подтверждений происхождения¶

    При публикации через trusted publishing npm автоматически генерирует подтверждения происхождения (provenance attestations), которые предоставляют криптографическое доказательство подлинности пакета. Это помогает пользователям убедиться, что пакеты поступают из законных источников и не были подделаны.

    Дополнительную информацию см. в документации по npm trusted publishing.

    Итоговые рекомендации¶

    В заключение списка лучших практик безопасности npm приведём следующие советы для снижения риска подобных атак:

    • Будьте особенно внимательны при копировании команд установки пакетов в терминал. Убедитесь, что проверили репозиторий исходного кода и реестр npm, что именно этот пакет вы намерены установить. Вы можете проверить метаданные пакета с помощью npm info, чтобы получить дополнительную информацию о контрибьюторах и последних версиях.
    • По умолчанию работайте с npm без авторизации в повседневных задачах, чтобы ваши учётные данные не стали слабым местом, ведущим к компрометации аккаунта.
    • При установке пакетов добавляйте --ignore-scripts для снижения риска выполнения произвольных команд. Например: npm install my-malicious-package --ignore-scripts
