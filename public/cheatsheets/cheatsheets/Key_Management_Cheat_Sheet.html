    Шпаргалка по управлению ключами¶

    Введение¶

    Данная шпаргалка по управлению ключами предоставляет разработчикам руководство по реализации управления криптографическими ключами в приложении безопасным образом. Важно документировать и согласовывать правила и практики по следующим темам:

    1. Управление жизненным циклом ключей (генерация, распределение, уничтожение)
    2. Компрометация, восстановление и обнуление ключей
    3. Хранение ключей
    4. Соглашение о ключах

    Общие руководящие принципы и соображения¶

    Разработайте план общей криптографической стратегии организации, который будет руководить разработчиками, работающими над различными приложениями, и обеспечит соответствие криптографических возможностей каждого приложения минимальным требованиям и лучшим практикам.

    Определите криптографические требования и требования к управлению ключами для вашего приложения и составьте карту всех компонентов, обрабатывающих или хранящих криптографический ключевой материал.

    Выбор ключей¶

    Выбор криптографических алгоритмов и алгоритмов управления ключами для конкретного приложения должен начинаться с понимания целей приложения.

    Например, если приложению необходимо безопасно хранить данные, разработчик должен выбрать набор алгоритмов, поддерживающих цель защиты данных в состоянии покоя. Приложения, которым требуется передача и получение данных, выберут набор алгоритмов, поддерживающих цель защиты данных при передаче.

    Мы предоставили рекомендации по выбору криптографических наборов в приложении на основе целей приложения и безопасности. Разработчики приложений зачастую начинают разработку криптографических возможностей и управления ключами с изучения того, что доступно в библиотеке.

    Однако следует провести анализ реальных потребностей приложения, чтобы определить оптимальный подход к управлению ключами. Начните с понимания целей безопасности приложения, что затем определит выбор наиболее подходящих криптографических протоколов. Например, приложению может потребоваться:

    1. Конфиденциальность данных в состоянии покоя и конфиденциальность данных при передаче.
    2. Подлинность конечного устройства.
    3. Подлинность источника данных.
    4. Целостность данных при передаче.
    5. Ключи для создания ключей шифрования данных.

    После понимания потребностей безопасности приложения разработчики могут определить, какие протоколы и алгоритмы необходимы. После определения протоколов и алгоритмов можно начать определение различных типов ключей, которые будут поддерживать цели приложения.

    Существует разнообразный набор типов ключей и сертификатов для рассмотрения, например:

    1. Шифрование: Симметричные ключи шифрования, Асимметричные ключи шифрования (открытые и закрытые).
    2. Аутентификация конечных устройств: Предварительно распределённые симметричные ключи, доверенные сертификаты, якоря доверия.
    3. Аутентификация источника данных: HMAC.
    4. Защита целостности: Коды аутентификации сообщений (MAC).
    5. Ключи шифрования ключей.

    Алгоритмы и протоколы¶

    Согласно NIST SP 800-57 Part 1, многие алгоритмы и схемы, предоставляющие услугу безопасности, используют хеш-функцию в качестве компонента алгоритма.

    Хеш-функции используются в алгоритмах цифровой подписи (FIPS186), кодах аутентификации сообщений с ключом (HMAC) (FIPS198), функциях/методах получения ключей (NIST Special Publications (SP) 800-56A, 800-56B, 800-56C и 800-108) и генераторах случайных чисел (NIST SP 800-90A). Утверждённые хеш-функции определены в FIPS180.

    NIST SP 800-57 Part 1 выделяет три основных класса утверждённых криптографических алгоритмов: хеш-функции, симметричные алгоритмы и асимметричные алгоритмы. Классы определяются количеством криптографических ключей, используемых в сочетании с алгоритмом.

    АНБ опубликовало отчёт Commercial National Security Algorithm Suite 2.0, в котором перечислены криптографические алгоритмы, ожидающиеся стойкими даже при достижениях в области квантовых вычислений.

    Криптографические хеш-функции¶

    Криптографические хеш-функции не требуют ключей. Хеш-функции генерируют относительно небольшой дайджест (хеш-значение) из (возможно) большого входного значения так, что обратное вычисление принципиально затруднено (т.е. сложно найти входное значение, которое даст заданный результат). Хеш-функции используются как строительные блоки для управления ключами, например:

    1. Для обеспечения аутентификации данных и служб обеспечения целостности (Раздел 4.2.3) — хеш-функция используется с ключом для генерации кода аутентификации сообщения.
    2. Для сжатия сообщений при генерации и проверке цифровых подписей (Раздел 4.2.4).
    3. Для получения ключей в алгоритмах установления ключей (Раздел 4.2.5).
    4. Для генерации детерминированных случайных чисел (Раздел 4.2.7).

    Алгоритмы с симметричными ключами¶

    Алгоритмы с симметричными ключами (иногда называемые алгоритмами с секретными ключами) преобразуют данные так, что обратное преобразование принципиально затруднено без знания секретного ключа. Ключ «симметричен», поскольку один и тот же ключ используется для криптографической операции и её обратной операции (например, шифрования и дешифрования).

    Симметричные ключи часто известны более чем одной стороне; однако ключ не должен раскрываться сторонам, не имеющим авторизованного доступа к данным, защищённым этим алгоритмом и ключом. Алгоритмы с симметричными ключами используются, например:

    1. Для обеспечения конфиденциальности данных (Раздел 4.2.2); один и тот же ключ используется для шифрования и дешифрования данных.
    2. Для обеспечения аутентификации и служб обеспечения целостности (Раздел 4.2.3) в форме кодов аутентификации сообщений (MAC); один и тот же ключ используется для генерации MAC и его проверки. MAC обычно используют либо алгоритм симметричного шифрования, либо криптографическую хеш-функцию в качестве криптографического примитива.
    3. Как часть процесса установления ключей (Раздел 4.2.5).
    4. Для генерации детерминированных случайных чисел (Раздел 4.2.7).

    Алгоритмы с асимметричными ключами¶

    Алгоритмы с асимметричными ключами, широко известные как алгоритмы с открытым ключом, используют два связанных ключа (т.е. пару ключей) для выполнения своих функций: открытый ключ и закрытый ключ. Открытый ключ может быть известен любому; закрытый ключ должен находиться под исключительным контролем стороны, «владеющей» парой ключей. Несмотря на то, что открытый и закрытый ключи пары ключей связаны, знание открытого ключа не позволяет раскрыть закрытый ключ. Асимметричные алгоритмы используются, например:

    1. Для вычисления цифровых подписей (Раздел 4.2.4).
    2. Для установления криптографического ключевого материала (Раздел 4.2.5).
    3. Для генерации случайных чисел (Раздел 4.2.7).

    Коды аутентификации сообщений (MAC)¶

    Коды аутентификации сообщений (MAC) обеспечивают аутентификацию данных и целостность. MAC — это криптографическая контрольная сумма данных, используемая для обеспечения уверенности в том, что данные не изменились и что MAC был вычислен ожидаемой стороной.

    Хотя целостность сообщений часто обеспечивается с помощью некриптографических методов, известных как коды обнаружения ошибок, эти коды могут быть изменены злоумышленником в его интересах. Использование утверждённого криптографического механизма, такого как MAC, позволяет решить эту проблему.

    Кроме того, MAC может предоставить получателю уверенность в том, что источник данных является держателем ключа (т.е. стороной, авторизованной для обладания ключом). MAC часто используются для аутентификации отправителя перед получателем, когда только эти две стороны разделяют ключ MAC.

    Цифровые подписи¶

    Цифровые подписи используются для обеспечения аутентификации, целостности и неотказуемости. Цифровые подписи используются в сочетании с хеш-функциями и вычисляются на данных любой длины (до предела, определяемого хеш-функцией).

    FIPS186 определяет алгоритмы, утверждённые для вычисления цифровых подписей.

    Ключи шифрования ключей¶

    Симметричные ключи оборачивания ключей используются для шифрования других ключей с помощью алгоритмов симметричного ключа. Ключи оборачивания ключей также известны как ключи шифрования ключей.

    Стойкость ключей¶

    Ознакомьтесь с NIST SP 800-57 (Рекомендация по управлению ключами) для получения рекомендуемых руководящих принципов по стойкости ключей для конкретных реализаций алгоритмов. Также рассмотрите следующие лучшие практики:

    1. Установите минимальную вычислительную стойкость приложения к атакам. Понимание минимальной вычислительной стойкости к атакам должно учитывать изощрённость злоумышленников, как долго необходимо защищать данные, где данные хранятся и подвергаются ли они воздействию. Определение вычислительной стойкости к атакам позволит инженерам узнать минимальную длину криптографического ключа, необходимую для защиты данных в течение их жизненного цикла. Обратитесь к NIST SP 800-131a для получения дополнительных рекомендаций по определению соответствующих длин ключей для выбранного алгоритма.
    2. При шифровании ключей для хранения или распределения всегда шифруйте криптографический ключ другим ключом равной или большей криптографической стойкости.
    3. При переходе на алгоритмы на основе эллиптических кривых выбирайте длину ключа, равную или превосходящую сравнимую стойкость других алгоритмов, используемых в вашей системе. Обратитесь к NIST SP 800-57 Таблица 2.
    4. Разработайте стратегию общей криптографической стратегии организации, которая будет руководить разработчиками, работающими над различными приложениями, и обеспечит соответствие криптографических возможностей каждого приложения минимальным требованиям и лучшим практикам.

    Соображения об управлении памятью¶

    Ключи, хранящиеся в памяти в течение длительного времени, могут «отпечататься». Это можно смягчить путём разбиения ключа на компоненты, которые часто обновляются (NIST SP 800-57).

    Потеря или повреждение носителя памяти, на котором хранятся ключи и/или сертификаты, и планирование восстановления согласно NIST SP 800-57.

    Планируйте восстановление после возможного повреждения носителя памяти, необходимого для систем, подсистем или компонентов генерации, регистрации и/или распределения ключей или сертификатов, как рекомендовано в NIST SP 800-57.

    Совершенная прямая секретность¶

    Эфемерные ключи могут обеспечить защиту совершенной прямой секретности, что означает: компрометация долгосрочного ключа подписи сервера не компрометирует конфиденциальность прошлых сессий. Обратитесь к шпаргалке по TLS.

    Использование ключей¶

    Согласно NIST, в целом один ключ должен использоваться только для одной цели (например, шифрования, аутентификации, оборачивания ключей, генерации случайных чисел или цифровых подписей).

    Существует несколько причин для этого:

    1. Использование одного и того же ключа для двух различных криптографических процессов может ослабить безопасность, обеспечиваемую одним или обоими процессами.
    2. Ограничение использования ключа ограничивает ущерб, который мог бы быть причинён в случае его компрометации.
    3. Некоторые варианты использования ключей мешают друг другу. Например, время, в течение которого ключ может потребоваться для каждого использования и цели. Требования к хранению данных могут различаться для разных типов данных.

    Темы по криптографическим модулям¶

    Согласно NIST SP 800-133, криптографические модули — это набор аппаратного обеспечения, программного обеспечения и/или встроенного программного обеспечения, реализующего функции безопасности (включая криптографические алгоритмы и генерацию ключей) и содержащегося в пределах криптографического модуля для обеспечения защиты ключей.

    Лучшие практики жизненного цикла управления ключами¶

    Генерация¶

    Криптографические ключи должны генерироваться в криптографическом модуле с соответствием как минимум FIPS 140-2 или 140-3. Для пояснительных целей рассматривайте криптографический модуль, в котором генерируется ключ, как модуль генерации ключей.

    Любое случайное значение, необходимое модулю генерации ключей, должно генерироваться внутри этого модуля; то есть генератор случайных битов, генерирующий случайное значение, должен быть реализован в криптографическом модуле с соответствием как минимум FIPS 140-2 или 140-3, генерирующем ключ.

    Аппаратные криптографические модули предпочтительнее программных криптографических модулей для защиты.

    Распределение¶

    Сгенерированные ключи должны передаваться (при необходимости) по защищённым каналам и использоваться соответствующим криптографическим алгоритмом как минимум в криптографических модулях, соответствующих FIPS 140-2 или 140-3. Для получения дополнительных сведений о рекомендациях этого раздела обратитесь к NIST Special Paper 800-133.

    Хранение¶

    1. Разработчики должны понимать, где в приложении хранятся криптографические ключи. Определите, на каких устройствах памяти хранятся ключи.
    2. Ключи должны быть защищены как в энергозависимой, так и в постоянной памяти, в идеале обрабатываясь в безопасных криптографических модулях.
    3. Ключи никогда не должны храниться в открытом виде.
    4. Убедитесь, что все ключи хранятся в криптографическом хранилище, таком как аппаратный модуль безопасности (HSM) или изолированный криптографический сервис.
    5. Если вы планируете хранить ключи на автономных устройствах/базах данных, зашифруйте ключи с использованием ключей шифрования ключей (KEK) перед экспортом ключевого материала. Длина (и алгоритм) KEK должна быть эквивалентна или превосходить стойкость защищаемых ключей.
    6. Обеспечьте применение защиты целостности к ключам при хранении (рассмотрите алгоритмы двойного назначения, поддерживающие шифрование и MAC).
    7. Убедитесь, что стандартный код на уровне приложения никогда не читает криптографические ключи и не использует их напрямую — используйте библиотеки управления ключами.
    8. Убедитесь, что ключи и криптографические операции выполняются внутри защищённого хранилища.
    9. Вся работа должна выполняться в хранилище (например, доступ к ключам, шифрование, дешифрование, подписание и т.д.).

    Для более полного руководства по хранению конфиденциальной информации, такой как ключи, см. Шпаргалку по управлению секретами.

    Депонирование и резервное копирование¶

    Данные, зашифрованные с использованием утраченных криптографических ключей, никогда не будут восстановлены. Поэтому приложение обязательно должно включать безопасную возможность резервного копирования ключей, особенно для приложений, поддерживающих шифрование данных в состоянии покоя для долгосрочных хранилищ данных.

    При резервном копировании ключей убедитесь, что база данных, используемая для хранения ключей, зашифрована с использованием как минимум валидированного модуля FIPS 140-2 или 140-3. Иногда полезно депонировать ключевой материал для использования в расследованиях и для повторного предоставления ключевого материала пользователям в случае утери или повреждения ключа.

    Никогда не депонируйте ключи, используемые для создания цифровых подписей, но рассматривайте необходимость депонирования ключей, поддерживающих шифрование. Зачастую депонирование может выполняться Центром сертификации (CA) или системой управления ключами, предоставляющей сертификаты и ключи; однако в некоторых случаях необходимо реализовать отдельные API, чтобы система могла выполнять депонирование для приложения.

    Подотчётность и аудит¶

    Подотчётность подразумевает идентификацию тех, кто имеет доступ к криптографическим ключам или контролирует их на протяжении их жизненного цикла. Подотчётность может быть эффективным инструментом для предотвращения компрометации ключей и снижения воздействия компрометации после её обнаружения.

    Хотя предпочтительно, чтобы ни один человек не мог видеть ключи, как минимум система управления ключами должна учитывать всех лиц, способных видеть криптографические ключи в открытом виде.

    Кроме того, более сложные системы управления ключами могут учитывать всех лиц, авторизованных для доступа к любым криптографическим ключам или управления ими — как в открытом, так и в зашифрованном виде.

    Подотчётность обеспечивает три значительных преимущества:

    1. Помогает определить, когда могла произойти компрометация и какие лица могли быть причастны.
    2. Защищает от компрометации, поскольку лица, имеющие доступ к ключу, знают, что их доступ к ключу зафиксирован.
    3. Очень полезна при восстановлении после обнаруженной компрометации ключа для определения, где использовался ключ и какие данные или другие ключи были защищены скомпрометированным ключом.

    Определённые принципы оказались полезными для обеспечения подотчётности криптографических ключей. Эти принципы могут применяться не ко всем системам или всем типам ключей.

    Некоторые принципы, применимые к долгосрочным ключам, контролируемым людьми, включают:

    1. Уникальная идентификация ключей.
    2. Идентификация пользователя ключа.
    3. Идентификация дат и времени использования ключа, а также защищаемых данных.
    4. Идентификация других ключей, защищённых симметричным или закрытым ключом.

    Для систем управления ключами должны проводиться два типа аудита:

    1. План безопасности и процедуры, разработанные для его поддержки, должны периодически проверяться, чтобы убедиться, что они по-прежнему поддерживают политику управления ключами (NIST SP 800-57 Part 2).
    2. Применяемые защитные механизмы должны периодически переоцениваться с точки зрения уровня безопасности, который они обеспечивают и ожидается обеспечить в будущем, а также правильно и эффективно ли они поддерживают соответствующие политики.

    Следует учитывать новые технологические разработки и атаки. На более регулярной основе действия людей, использующих, эксплуатирующих и обслуживающих систему, должны проверяться для подтверждения соблюдения установленных процедур безопасности.

    Сильные криптографические системы могут быть скомпрометированы небрежными и неадекватными действиями людей. Крайне необычные события должны фиксироваться и проверяться как возможные индикаторы попыток атак на систему.

    Компрометация и восстановление ключа¶

    Компрометация ключа имеет следующие последствия:

    1. В целом, несанкционированное раскрытие ключа, используемого для обеспечения защиты конфиденциальности (т.е. посредством шифрования), означает, что все данные, зашифрованные этим ключом, могут быть раскрыты или стать известными несанкционированным сторонам. Раскрытие закрытого ключа подписи Центра сертификации означает, что злоумышленник может создавать мошеннические сертификаты и списки отзыва сертификатов (CRL).
    2. Компрометация целостности ключа означает, что ключ неверен — либо ключ был изменён (намеренно или случайно), либо был подменён другим ключом; это включает удаление (недоступность) ключа. Подмена или модификация ключа, используемого для обеспечения целостности, ставит под сомнение целостность всей информации, защищённой этим ключом. Эта информация могла быть предоставлена или изменена несанкционированной стороной, знающей ключ. Подмена открытого или секретного ключа, который будет использоваться (в будущем) для шифрования данных, может позволить несанкционированной стороне (знающей ключ дешифрования) дешифровать данные, зашифрованные с использованием ключа шифрования.
    3. Компрометация связи ключа с его использованием или приложением означает, что ключ может использоваться для неправильной цели (например, для установления ключей вместо цифровых подписей) или для неправильного приложения, что может привести к компрометации информации, защищённой ключом.
    4. Компрометация связи ключа с владельцем или другой стороной означает, что личность другой стороны не может быть удостоверена (т.е. неизвестно, кто в действительности является другой стороной) или что информация не может быть обработана правильно (например, дешифрована с правильным ключом).
    5. Компрометация связи ключа с другой информацией означает, что связи нет вообще или что связь установлена с неправильной «информацией». Это может привести к сбою криптографических служб, потере информации или компрометации безопасности информации. Аналогично воздействию программ-вымогателей, за исключением того, что нельзя заплатить выкуп и вернуть ключ.

    Обычно задействуются следующие процедуры:

    1. Ограничение времени нахождения симметричного или закрытого ключа в открытом виде.
    2. Предотвращение просмотра людьми симметричных и закрытых ключей в открытом виде.
    3. Ограничение симметричных и закрытых ключей в открытом виде физически защищёнными контейнерами. Это включает генераторы ключей, устройства транспортировки ключей, загрузчики ключей, криптографические модули и устройства хранения ключей.
    4. Использование проверок целостности для обеспечения сохранности ключа или его связи с другими данными. Например, ключи могут оборачиваться (т.е. шифроваться) таким образом, что несанкционированные изменения оборачивания или связей будут обнаружены.
    5. Применение подтверждения ключа (см. NIST SP 800-57 Part 1 Раздел 4.2.5.5) для обеспечения уверенности в том, что правильный ключ действительно был установлен.
    6. Создание системы подотчётности, отслеживающей каждый доступ к симметричным и закрытым ключам в открытом виде.
    7. Обеспечение криптографической проверки целостности ключа (например, с использованием MAC или цифровой подписи).
    8. Использование доверенных временных меток для подписанных данных. Уничтожение ключей сразу после того, как они больше не нужны.
    9. Создание плана восстановления после компрометации, особенно в случае компрометации CA.

    План восстановления после компрометации необходим для восстановления криптографических служб безопасности в случае компрометации ключа. План восстановления после компрометации должен быть задокументирован и легко доступен.

    План восстановления после компрометации должен содержать:

    1. Идентификацию и контактную информацию персонала для уведомления.
    2. Идентификацию и контактную информацию персонала для выполнения действий по восстановлению.
    3. Метод замены ключей.
    4. Инвентарь всех криптографических ключей и их использование (например, расположение всех сертификатов в системе).
    5. Обучение всего соответствующего персонала процедурам восстановления.
    6. Идентификацию и контактную информацию всего персонала, необходимого для поддержки процедур восстановления.
    7. Политики обязательной проверки отзыва ключей (для минимизации последствий компрометации).
    8. Мониторинг операций по замене ключей (для обеспечения выполнения всех необходимых операций для всех затронутых ключей).
    9. Любые другие процедуры восстановления, которые могут включать:
      1. Физическую проверку оборудования.
      2. Идентификацию всей информации, которая могла быть скомпрометирована в результате инцидента.
      3. Идентификацию всех подписей, которые могут быть недействительными из-за компрометации ключа подписи.
      4. Распределение нового ключевого материала при необходимости.

    Хранилища доверия¶

    1. Разработайте меры контроля для защиты хранилища доверия от внедрения корневых сертификатов третьих сторон. Управление доступом реализуется и применяется на уровне каждой стороны и приложения.
    2. Реализуйте средства контроля целостности объектов, хранящихся в хранилище доверия.
    3. Не допускайте экспорта ключей из хранилища доверия без аутентификации и авторизации.
    4. Установите строгие политики и процедуры для экспорта ключевого материала из приложений в сетевые приложения и другие компоненты.
    5. Реализуйте безопасный процесс обновления хранилища доверия.

    Библиотеки управления криптографическими ключами¶

    Используйте только авторитетные криптографические библиотеки, которые хорошо поддерживаются, обновляются и протестированы и валидированы сторонними организациями (например, NIST/FIPS).
