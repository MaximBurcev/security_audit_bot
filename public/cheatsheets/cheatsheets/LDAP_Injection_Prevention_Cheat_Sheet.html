    Шпаргалка по предотвращению LDAP-инъекций¶

    Введение¶

    Протокол LDAP (Lightweight Directory Access Protocol) позволяет приложению удалённо выполнять операции, такие как поиск и изменение записей в каталогах. LDAP-инъекция возникает из-за недостаточной санации и валидации входных данных и позволяет вредоносным пользователям получать ограниченную информацию с использованием службы каталогов. Общую информацию о LDAP можно найти на странице протокол LDAP.

    LDAP-инъекция — это атака, используемая для эксплуатации web-приложений, формирующих операторы LDAP на основе пользовательского ввода. Когда приложение не выполняет надлежащую санацию пользовательского ввода, возможна модификация операторов LDAP с помощью методов, аналогичных SQL-инъекции.

    Данная шпаргалка сосредоточена на предоставлении чётких, простых, практически применимых рекомендаций по предотвращению уязвимостей LDAP-инъекций в приложениях. LDAP-инъекции распространены по двум причинам:

    1. Отсутствие более безопасных, параметризованных интерфейсов запросов LDAP
    2. Широкое использование LDAP для аутентификации пользователей в системах.

    Атаки LDAP-инъекций могут привести к предоставлению разрешений на несанкционированные запросы и модификации контента в дереве LDAP.

    Основные меры защиты:

    • Экранирование всех переменных с использованием правильной функции кодирования LDAP
    • Использование фреймворка, который экранирует автоматически.

    Дополнительные меры защиты:

    • Принцип минимальных привилегий
    • Валидация входных данных по допустимому списку

    Основные меры защиты¶

    Вариант защиты 1: Экранирование всех переменных с использованием правильной функции кодирования LDAP¶

    Экранирование различительных имён (DN)¶

    Основной способ хранения имён в LDAP основан на DN (Distinguished Name — различительное имя). Можно думать о нём как об уникальном идентификаторе. Иногда они используются для доступа к ресурсам, например как имя пользователя.

    DN может выглядеть следующим образом:

    cn=Richard Feynman, ou=Physics Department, dc=Caltech, dc=edu

    или

    uid=inewton, ou=Mathematics Department, dc=Cambridge, dc=com

    Для ограничения входных данных допустимым списком допустимых символов можно использовать allowlist. Символы и последовательности символов, которые должны быть исключены из allowlist — включая метасимволы Java Naming and Directory Interface (JNDI) и специальные символы LDAP — перечислены в следующем списке.

    Исчерпывающий список: \ # + < > , ; " = и начальные или завершающие пробелы.

    Некоторые «специальные» символы, разрешённые в Distinguished Names и не требующие экранирования, включают:

    * ( ) . & - _ [ ] ` ~ | @ $ % ^ ? : { } ! '

    Экранирование поискового фильтра¶

    Каждый DN указывает ровно на 1 запись, которую можно рассматривать как строку в СУБД. Для каждой записи будет 1 или более атрибутов, аналогичных столбцам СУБД. Для поиска в LDAP пользователей с определёнными атрибутами можно использовать поисковые фильтры.

    В поисковом фильтре можно использовать стандартную булеву логику для получения списка пользователей, соответствующих произвольному ограничению. Поисковые фильтры записываются в польской нотации (префиксная нотация).

    Пример:

    (&(ou=Physics)(|
(manager=cn=Freeman Dyson,ou=Physics,dc=Caltech,dc=edu)
(manager=cn=Albert Einstein,ou=Physics,dc=Princeton,dc=edu)
))

    При построении LDAP-запросов в коде приложения НЕОБХОДИМО экранировать все ненадёжные данные, добавляемые в LDAP-запрос. Существуют две формы экранирования LDAP. Кодирование для поиска LDAP и кодирование для DN (Distinguished Name) LDAP. Правильное экранирование зависит от того, санируете ли вы входные данные для поискового фильтра или используете DN в качестве учётных данных, подобных имени пользователя, для доступа к ресурсам.

    Некоторые «специальные» символы, разрешённые в поисковых фильтрах и требующие экранирования:

    * ( ) \ NUL

    Дополнительную информацию об экранировании поисковых фильтров см. в RFC4515.

    Безопасный пример экранирования на Java¶

    Следующее решение использует allowlist для санации пользовательского ввода, чтобы строка фильтра содержала только допустимые символы. В этом коде userSN может содержать только буквы и пробелы.

    // String userSN = "Sherlock Holmes"; // Допустимо
// ... начало LDAPInjection.searchRecord()...
sc.setSearchScope(SearchControls.SUBTREE_SCOPE);
String base = "dc=example,dc=com";

if (!userSN.matches("[\\w\\s]*")) {
 throw new IllegalArgumentException("Invalid input");
}

String filter = "(sn = " + userSN + ")";
// ... остаток LDAPInjection.searchRecord()...

    Когда поле базы данных должно включать специальные символы, критически важно обеспечить хранение подлинных данных в санированной форме в базе данных, а также нормализацию любого пользовательского ввода до выполнения валидации или сравнения. Использование символов, имеющих особое значение в JNDI и LDAP, без полной нормализации и процедуры на основе allowlist не рекомендуется. Специальные символы должны быть преобразованы в санированные, безопасные значения до их добавления в выражение allowlist, по которому будут проверяться входные данные. Аналогично, нормализация пользовательского ввода должна выполняться до этапа валидации (источник: Prevent LDAP injection).

    Дополнительную информацию см. в OWASP ESAPI Java Encoder Project, включающем encodeForLDAP(String) и encodeForDN(String).

    Небезопасное и безопасное построение LDAP-запросов на Java¶

    ❌ Небезопасный пример (уязвим к LDAP-инъекции)

    // Пользовательский ввод напрямую конкатенируется в фильтр
String filter = "(&(uid=" + userInput + ")(objectClass=person))";
NamingEnumeration<SearchResult> results =
    ctx.search("ou=users,dc=example,dc=com", filter, controls);


✅ Безопасный пример (использование параметризованного фильтра)

// Пользовательский ввод безопасно передаётся как параметр
String filter = "(&(uid={0})(objectClass=person))";
NamingEnumeration<SearchResult> results =
    ctx.search("ou=users,dc=example,dc=com", filter, new Object[]{ userInput }, controls);

    Безопасный пример для C# .NET¶

    .NET AntiXSS (теперь класс Encoder) имеет функции кодирования LDAP, включая Encoder.LdapFilterEncode(string), Encoder.LdapDistinguishedNameEncode(string) и Encoder.LdapDistinguishedNameEncode(string, bool, bool).

    Encoder.LdapFilterEncode кодирует входные данные согласно RFC4515, где небезопасные значения преобразуются в \XX, где XX — представление небезопасного символа.

    Encoder.LdapDistinguishedNameEncode кодирует входные данные согласно RFC2253, где небезопасные символы преобразуются в #XX, где XX — представление небезопасного символа, а запятая, плюс, кавычка, косая черта, знаки «меньше» и «больше» экранируются с использованием нотации с косой чертой (\X). Кроме того, пробел или октоторп (#) в начале входной строки экранируется \, как и пробел в конце строки.

    LdapDistinguishedNameEncode(string, bool, bool) также предоставляется, чтобы можно было отключить правила экранирования начального или конечного символа — например, при конкатенации экранированного фрагмента DN в середину полного DN.

    Вариант защиты 2: Использование фреймворков, автоматически защищающих от LDAP-инъекций¶

    Безопасный пример для .NET¶

    Рекомендуется использовать LINQ to LDAP (для .NET Framework 4.5 и ниже до обновления) в DotNet. Он обеспечивает автоматическое кодирование LDAP при построении LDAP-запросов. Обратитесь к файлу Readme в репозитории проекта.

    Дополнительные меры защиты¶

    Помимо принятия одной из двух основных мер защиты, рекомендуется также принять все следующие дополнительные меры для обеспечения глубокоэшелонированной защиты. Эти дополнительные меры:

    • Принцип минимальных привилегий
    • Валидация входных данных по допустимому списку

    Принцип минимальных привилегий¶

    Для минимизации потенциального ущерба от успешной атаки LDAP-инъекции следует минимизировать привилегии, назначенные учётной записи привязки LDAP в вашей среде.

    Включение аутентификации привязки¶

    Если протокол LDAP настроен с аутентификацией привязки, злоумышленники не смогут проводить атаки LDAP-инъекций из-за проверок верификации и авторизации, выполняемых против допустимых учётных данных, предоставленных пользователем. Злоумышленник всё ещё может обойти аутентификацию привязки через анонимное подключение или путём использования неаутентифицированной привязки: Anonymous Bind (LDAP) и Unauthenticated Bind (LDAP).

    Валидация входных данных по допустимому списку¶

    Валидация входных данных может использоваться для обнаружения несанкционированного ввода до его передачи в LDAP-запрос. Дополнительную информацию см. в Шпаргалке по валидации входных данных.
