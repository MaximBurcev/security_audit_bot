    Шпаргалка по предотвращению DOM-based XSS¶

    Введение¶

    При рассмотрении XSS (межсайтового скриптинга) существует три общепризнанных формы XSS:

    • Отражённый или хранимый
    • DOM-based XSS.

    Шпаргалка по предотвращению XSS отлично рассматривает отражённый и хранимый XSS. Данная шпаргалка посвящена XSS на основе DOM (объектной модели документа) и является расширением Шпаргалки по предотвращению XSS (и предполагает её понимание).

    Для понимания DOM-based XSS необходимо увидеть принципиальное отличие между отражённым и хранимым XSS и DOM-based XSS. Основное отличие заключается в том, где атака внедряется в приложение.

    Отражённый и хранимый XSS — проблемы внедрения на стороне сервера, тогда как DOM-based XSS — проблема внедрения на стороне клиента (браузера).

    Весь этот код происходит с сервера, что означает, что ответственность за его защиту от XSS лежит на владельце приложения, независимо от типа уязвимости XSS. Кроме того, атаки XSS всегда выполняются в браузере.

    Разница между отражённым/хранимым XSS заключается в том, где атака добавляется или внедряется в приложение. При отражённом/хранимом XSS атака внедряется в приложение в процессе серверной обработки запросов, где ненадёжные входные данные динамически добавляются в HTML. При DOM XSS атака внедряется в приложение непосредственно во время выполнения на стороне клиента.

    Когда браузер отображает HTML и любой связанный контент, такой как CSS или JavaScript, он определяет различные контексты отображения для разных видов входных данных и следует разным правилам для каждого контекста. Контекст отображения связан с разбором HTML-тегов и их атрибутов.

    • HTML-парсер контекста отображения определяет, как данные представляются и располагаются на странице, и может быть дополнительно разделён на стандартные контексты HTML, атрибута HTML, URL и CSS.
    • JavaScript- или VBScript-парсер контекста выполнения связан с разбором и выполнением кода скриптов. Каждый парсер имеет отдельную семантику в том, как он может выполнять код скриптов, что затрудняет создание согласованных правил для устранения уязвимостей в различных контекстах. Сложность усугубляется различными значениями и обработкой закодированных значений в каждом подконтексте (HTML, атрибут HTML, URL и CSS) в рамках контекста выполнения.

    Для целей данной статьи мы называем контексты HTML, атрибута HTML, URL и CSS подконтекстами, поскольку каждый из них может быть достигнут и установлен в контексте выполнения JavaScript.

    В коде JavaScript основным контекстом является JavaScript, но с правильными тегами и символами закрытия контекста злоумышленник может попытаться атаковать другие 4 контекста с использованием эквивалентных DOM-методов JavaScript.

    Ниже приведён пример уязвимости, возникающей в контексте JavaScript и подконтексте HTML:

     <script>
 var x = '<%= taintedVar %>';
 var d = document.createElement('div');
 d.innerHTML = x;
 document.body.appendChild(d);
 </script>

    Рассмотрим отдельные подконтексты контекста выполнения по очереди.

    ПРАВИЛО #1 - HTML-кодирование, затем JavaScript-кодирование перед вставкой ненадёжных данных в HTML-подконтекст в контексте выполнения¶

    Существует несколько методов и атрибутов, которые можно использовать для непосредственного отображения HTML-контента в JavaScript. Эти методы составляют HTML-подконтекст в контексте выполнения. Если этим методам передаются ненадёжные данные, может возникнуть уязвимость XSS. Например:

    Примеры опасных HTML-методов¶

    Атрибуты¶

     element.innerHTML = "<HTML> Tags and markup";
 element.outerHTML = "<HTML> Tags and markup";

    Методы¶

     document.write("<HTML> Tags and markup");
 document.writeln("<HTML> Tags and markup");

    Рекомендация¶

    Для безопасного динамического обновления HTML в DOM рекомендуется:

    1. HTML-кодирование, затем
    2. JavaScript-кодирование всех ненадёжных входных данных, как показано в следующих примерах:
     var ESAPI = require('node-esapi');
 element.innerHTML = "<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForHTML(untrustedData))%>";
 element.outerHTML = "<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForHTML(untrustedData))%>";

     var ESAPI = require('node-esapi');
 document.write("<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForHTML(untrustedData))%>");
 document.writeln("<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForHTML(untrustedData))%>");

    ПРАВИЛО #2 - JavaScript-кодирование перед вставкой ненадёжных данных в подконтекст атрибутов HTML в контексте выполнения¶

    HTML-атрибутный подконтекст в контексте выполнения отличается от стандартных правил кодирования. Это объясняется тем, что правило кодирования HTML-атрибутов в контексте отображения HTML-атрибутов необходимо для предотвращения атак, пытающихся выйти из HTML-атрибутов или добавить дополнительные атрибуты, которые могут привести к XSS.

    Когда вы находитесь в контексте выполнения DOM, вам нужно только JavaScript-кодировать HTML-атрибуты, которые не выполняют код (атрибуты, отличные от обработчиков событий, CSS и URL-атрибутов).

    Например, общее правило — HTML-атрибутное кодирование ненадёжных данных (данных из базы данных, HTTP-запроса, пользователя, серверной системы и т.д.), помещаемых в HTML-атрибут. Это необходимый шаг при выводе данных в контексте отображения, однако использование HTML-атрибутного кодирования в контексте выполнения нарушит отображение данных приложением.

    БЕЗОПАСНЫЙ, но НЕРАБОТАЮЩИЙ пример¶

     var ESAPI = require('node-esapi');
 var x = document.createElement("input");
 x.setAttribute("name", "company_name");
 // В следующей строке кода companyName представляет ненадёжный ввод пользователя
 // ESAPI.encoder().encodeForHTMLAttribute() не нужен и вызывает двойное кодирование
 x.setAttribute("value", '<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForHTMLAttribute(companyName))%>');
 var form1 = document.forms[0];
 form1.appendChild(x);

    Проблема в том, что если companyName имело значение "Johnson & Johnson". В текстовом поле ввода отобразилось бы "Johnson &amp; Johnson". Правильным кодированием в приведённом случае было бы только JavaScript-кодирование, чтобы запретить злоумышленнику закрывать одинарные кавычки и встраивать код, или экранирование в HTML и открытие нового тега script.

    БЕЗОПАСНЫЙ и ФУНКЦИОНАЛЬНО КОРРЕКТНЫЙ пример¶

     var ESAPI = require('node-esapi');
 var x = document.createElement("input");
 x.setAttribute("name", "company_name");
 x.setAttribute("value", '<%=ESAPI.encoder().encodeForJavascript(companyName)%>');
 var form1 = document.forms[0];
 form1.appendChild(x);

    Важно отметить, что при установке HTML-атрибута, не выполняющего код, значение устанавливается непосредственно в атрибуте объекта HTML-элемента, поэтому нет опасений относительно внедрения снаружи.

    ПРАВИЛО #3 - Будьте осторожны при вставке ненадёжных данных в подконтекст обработчиков событий и кода JavaScript в контексте выполнения¶

    Размещение динамических данных в коде JavaScript особенно опасно, поскольку JavaScript-кодирование имеет различную семантику для закодированных данных JavaScript по сравнению с другими видами кодирования. Во многих случаях JavaScript-кодирование не останавливает атаки в контексте выполнения. Например, JavaScript-закодированная строка будет выполнена, даже если она закодирована в JavaScript.

    Поэтому основная рекомендация — избегать включения ненадёжных данных в этот контекст. Если это необходимо, следующие примеры описывают подходы, которые работают и не работают.

    var x = document.createElement("a");
x.href="#";
// В следующей строке кода закодированные данные справа (второй аргумент setAttribute)
// являются примером ненадёжных данных, которые были правильно закодированы в JavaScript, но всё равно выполняются.
x.setAttribute("onclick", "\u0061\u006c\u0065\u0072\u0074\u0028\u0032\u0032\u0029");
var y = document.createTextNode("Click To Test");
x.appendChild(y);
document.body.appendChild(x);

    Метод setAttribute(name_string,value_string) опасен, поскольку он неявно преобразует value_string в тип данных DOM-атрибута name_string.

    В приведённом выше случае имя атрибута является обработчиком событий JavaScript, поэтому значение атрибута неявно преобразуется в код JavaScript и вычисляется. В этом случае JavaScript-кодирование не защищает от DOM-based XSS.

    Другие методы JavaScript, принимающие код в виде строкового типа, будут иметь аналогичную проблему, описанную выше (setTimeout, setInterval, new Function и т.д.). Это резко контрастирует с JavaScript-кодированием в атрибуте обработчика событий HTML-тега (HTML-парсер), где JavaScript-кодирование защищает от XSS.

    <!-- НЕ работает  -->
<a id="bb" href="#" onclick="\u0061\u006c\u0065\u0072\u0074\u0028\u0031\u0029"> Test Me</a>

    Альтернативой использованию Element.setAttribute(...) для установки DOM-атрибутов является прямая установка атрибута. Прямая установка атрибутов обработчиков событий позволит JavaScript-кодированию защитить от DOM-based XSS. Обратите внимание, что прямое помещение ненадёжных данных в контекст выполнения команд всегда является опасным решением.

    <a id="bb" href="#"> Test Me</a>

    // Следующее НЕ работает, поскольку обработчик события устанавливается в строку.
// "alert(7)" закодировано в JavaScript.
document.getElementById("bb").onclick = "\u0061\u006c\u0065\u0072\u0074\u0028\u0037\u0029";

// Следующее НЕ работает, поскольку обработчик события устанавливается в строку.
document.getElementById("bb").onmouseover = "testIt";

// Следующее НЕ работает из-за закодированных "(" и ")".
// "alert(77)" закодировано в JavaScript.
document.getElementById("bb").onmouseover = \u0061\u006c\u0065\u0072\u0074\u0028\u0037\u0037\u0029;

// Следующий пример хитрый
// сначала testIt будет присвоен как обработчик события onmousehover, второй testIt выполнится при разборе.
// это происходит потому, что второй testIt — отдельный оператор js
// это происходит из-за разделителя ;
// "testIt;testIt" закодировано в JavaScript.
document.getElementById("bb").onmouseover = \u0074\u0065\u0073\u0074\u0049\u0074\u003b\u0074\u0065\u0073
                                            \u0074\u0049\u0074;

// Следующее РАБОТАЕТ, поскольку закодированное значение является допустимым именем переменной или ссылкой на функцию.
// "testIt" закодировано в JavaScript
document.getElementById("bb").onmouseover = \u0074\u0065\u0073\u0074\u0049\u0074;

function testIt() {
   alert("I was called.");
}

    Существуют и другие места в JavaScript, где JavaScript-кодирование принимается как допустимый исполняемый код.

     for(var \u0062=0; \u0062 < 10; \u0062++){
     \u0064\u006f\u0063\u0075\u006d\u0065\u006e\u0074
     .\u0077\u0072\u0069\u0074\u0065\u006c\u006e
     ("\u0048\u0065\u006c\u006c\u006f\u0020\u0057\u006f\u0072\u006c\u0064");
 }
 \u0077\u0069\u006e\u0064\u006f\u0077
 .\u0065\u0076\u0061\u006c
 \u0064\u006f\u0063\u0075\u006d\u0065\u006e\u0074
 .\u0077\u0072\u0069\u0074\u0065(111111111);

    или

     var s = "\u0065\u0076\u0061\u006c";
 var t = "\u0061\u006c\u0065\u0072\u0074\u0028\u0031\u0031\u0029";
 window[s](t);

    Поскольку JavaScript основан на международном стандарте (ECMAScript), JavaScript-кодирование обеспечивает поддержку международных символов в конструкциях программирования и переменных, а также альтернативных представлений строк (строковых экранирований).

    Однако обратное верно для HTML-кодирования. HTML-теги хорошо определены и не поддерживают альтернативных представлений одного и того же тега. Таким образом, HTML-кодирование не может использоваться для того, чтобы разработчик имел альтернативные представления тега <a>, например.

    Нейтрализующая природа HTML-кодирования¶

    В целом HTML-кодирование служит для нейтрализации HTML-тегов, помещаемых в HTML и контексты HTML-атрибутов. Рабочий пример (без HTML-кодирования):

    <a href="..." >

    Обычно закодированный пример (не работает — НР):

    &#x3c;a href=... &#x3e;

    Пример HTML-кодирования для выделения принципиального отличия от значений JavaScript-кодирования (НР):

    <&#x61; href=...>

    Если бы HTML-кодирование следовало той же семантике, что и JavaScript-кодирование, строка выше могла бы отобразить ссылку. Это отличие делает JavaScript-кодирование менее эффективным оружием в борьбе с XSS.

    ПРАВИЛО #4 - JavaScript-кодирование перед вставкой ненадёжных данных в подконтекст CSS-атрибутов в контексте выполнения¶

    Обычно выполнение JavaScript из CSS-контекста требовало либо передачи javascript:attackCode() CSS-методу url(), либо вызова CSS-метода expression(), передавая JavaScript-код для непосредственного выполнения.

    Из практики вызов функции expression() из контекста выполнения (JavaScript) был отключён. Для защиты от CSS-метода url() убедитесь, что данные, передаваемые CSS-методу url(), URL-закодированы.

    var ESAPI = require('node-esapi');
document.body.style.backgroundImage = "url(<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForURL(companyName))%>)";

    ПРАВИЛО #5 - URL-кодирование, затем JavaScript-кодирование перед вставкой ненадёжных данных в подконтекст URL-атрибутов в контексте выполнения¶

    Логика разбора URL как в контекстах выполнения, так и в контекстах отображения выглядит одинаковой. Поэтому правила кодирования для URL-атрибутов в контексте выполнения (DOM) практически не изменяются.

    var ESAPI = require('node-esapi');
var x = document.createElement("a");
x.setAttribute("href", '<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForURL(userRelativePath))%>');
var y = document.createTextElement("Click Me To Test");
x.appendChild(y);
document.body.appendChild(x);

    Если вы используете полностью квалифицированные URL, это нарушит ссылки, поскольку двоеточие в идентификаторе протокола (http: или javascript:) будет URL-закодировано, что предотвратит вызов протоколов http и javascript.

    ПРАВИЛО #6 - Заполняйте DOM с использованием безопасных функций или свойств JavaScript¶

    Наиболее фундаментальный безопасный способ заполнения DOM ненадёжными данными — использование безопасного свойства присвоения textContent.

    Ниже приведён пример безопасного использования.

    <script>
element.textContent = untrustedData;  // не выполняет код
</script>

    ПРАВИЛО #7 - Исправление уязвимостей DOM-based межсайтового скриптинга¶

    Лучший способ устранить DOM-based межсайтовый скриптинг — использовать правильный метод вывода (приёмник). Например, если вы хотите использовать пользовательский ввод для записи в элемент div, не используйте innerHtml — используйте innerText или textContent. Это решит проблему, и это правильный способ устранения уязвимостей DOM-based XSS.

    Использование контролируемых пользователем входных данных в опасных источниках, таких как eval, — всегда плохая идея. В 99% случаев это признак плохой или ленивой практики программирования, поэтому просто не делайте этого, вместо того чтобы пытаться санитизировать входные данные.

    Наконец, для устранения проблемы в нашем начальном коде вместо попытки правильно закодировать вывод, что хлопотно и легко сделать с ошибкой, мы просто используем element.textContent для записи в содержимое следующим образом:

    <b>Current URL:</b> <span id="contentholder"></span>
...
<script>
document.getElementById("contentholder").textContent = document.baseURI;
</script>

    Это делает то же самое, но на этот раз не уязвимо к DOM-based межсайтовому скриптингу.

    Рекомендации по разработке безопасных приложений на JavaScript¶

    DOM-based XSS чрезвычайно сложно устранить из-за большой поверхности атаки и отсутствия стандартизации в разных браузерах.

    Приведённые ниже рекомендации являются попыткой предоставить руководство для разработчиков при создании веб-приложений на JavaScript (Web 2.0), чтобы они могли избежать XSS.

    РЕКОМЕНДАЦИЯ #1 - Ненадёжные данные следует рассматривать только как отображаемый текст¶

    Избегайте обработки ненадёжных данных как кода или разметки в коде JavaScript.

    РЕКОМЕНДАЦИЯ #2 - Всегда применяйте JavaScript-кодирование и ограничивайте ненадёжные данные кавычками как строки при вводе в приложение при построении шаблонного JavaScript¶

    Всегда применяйте JavaScript-кодирование и ограничивайте ненадёжные данные кавычками как строки при вводе в приложение, как показано в следующем примере.

    var x = "<%= Encode.forJavaScript(untrustedData) %>";

    РЕКОМЕНДАЦИЯ #3 - Используйте document.createElement("..."), element.setAttribute("...","value"), element.appendChild(...) и аналогичные методы для создания динамических интерфейсов¶

    document.createElement("..."), element.setAttribute("...","value"), element.appendChild(...) и аналогичные методы — безопасные способы создания динамических интерфейсов.

    Обратите внимание, что element.setAttribute безопасен только для ограниченного числа атрибутов.

    Опасные атрибуты включают любой атрибут, являющийся контекстом выполнения команды, такой как onclick или onblur.

    Примеры безопасных атрибутов включают: align, alink, alt, bgcolor, border, cellpadding, cellspacing, class, color, cols, colspan, coords, dir, face, height, hspace, ismap, lang, marginheight, marginwidth, multiple, nohref, noresize, noshade, nowrap, ref, rel, rev, rows, rowspan, scrolling, shape, span, summary, tabindex, title, usemap, valign, value, vlink, vspace, width.

    РЕКОМЕНДАЦИЯ #4 - Избегайте отправки ненадёжных данных в HTML-методы отображения¶

    Избегайте заполнения следующих методов ненадёжными данными.

    1. element.innerHTML = "...";
    2. element.outerHTML = "...";
    3. document.write(...);
    4. document.writeln(...);

    РЕКОМЕНДАЦИЯ #5 - Избегайте многочисленных методов, которые неявно вызывают eval() для переданных данных¶

    Существует множество методов, которые неявно вызывают eval() для переданных данных, которых необходимо избегать.

    Убедитесь, что любые ненадёжные данные, передаваемые этим методам:

    1. Ограничены строковыми разделителями
    2. Заключены в замыкание или JavaScript-закодированы до N-уровней в зависимости от использования
    3. Обёрнуты в пользовательскую функцию.

    Убедитесь, что вы следуете шагу 3, чтобы убедиться, что ненадёжные данные не отправляются опасным методам внутри пользовательской функции, или обрабатывайте это, добавив дополнительный уровень кодирования.

    Использование замыкания (как предложил Газ)¶

    Следующий пример иллюстрирует использование замыканий для избежания двойного JavaScript-кодирования.

     var ESAPI = require('node-esapi');
 setTimeout((function(param) { return function() {
          customFunction(param);
        }
 })("<%=ESAPI.encoder().encodeForJavascript(untrustedData)%>"), y);

    Другой альтернативой является использование N-уровней кодирования.

    N-уровней кодирования¶

    Если ваш код выглядит следующим образом, вам нужно только двойное JavaScript-кодирование входных данных.

    setTimeout("customFunction('<%=doubleJavaScriptEncodedData%>', y)");
function customFunction (firstName, lastName)
     alert("Hello" + firstName + " " + lastNam);
}

    doubleJavaScriptEncodedData имеет первый слой JavaScript-кодирования, обратимый (при выполнении) в одинарных кавычках.

    Затем неявный вызов eval из setTimeout обращает ещё один слой JavaScript-кодирования для передачи правильного значения в customFunction.

    Причина, по которой нужно только двойное JavaScript-кодирование, заключается в том, что функция customFunction сама не передала входные данные другому методу, неявно или явно вызывающему eval. Если firstName передавался бы другому JavaScript-методу, неявно или явно вызывающему eval(), то <%=doubleJavaScriptEncodedData%> выше нужно было бы изменить на <%=tripleJavaScriptEncodedData%>.

    Важное замечание по реализации: если JavaScript-код пытается использовать двойно- или трижды закодированные данные в сравнениях строк, значение может интерпретироваться по-разному в зависимости от того, сколько раз eval() применялся к данным перед передачей в сравнение if и сколько раз значение было JavaScript-закодировано.

    Если A дважды закодировано в JavaScript, следующая проверка if вернёт false.

     var x = "doubleJavaScriptEncodedA";  //\u005c\u0075\u0030\u0030\u0034\u0031
 if (x == "A") {
    alert("x is A");
 } else if (x == "\u0041") {
    alert("This is what pops");
 }

    Это поднимает интересный момент проектирования. В идеале правильный способ применения кодирования и избежания описанной проблемы — это серверное кодирование для контекста вывода, в который данные вводятся в приложение.

    Затем клиентское кодирование (с использованием библиотеки JavaScript-кодирования, такой как node-esapi) для отдельного подконтекста (DOM-методов), которому передаются ненадёжные данные.

    Вот несколько примеров их использования:

    // серверное кодирование
var ESAPI = require('node-esapi');
var input = "<%=ESAPI.encoder().encodeForJavascript(untrustedData)%>";

    // HTML-кодирование выполняется в JavaScript
var ESAPI = require('node-esapi');
document.writeln(ESAPI.encoder().encodeForHTML(input));

    Один из вариантов — использовать неизменяемые свойства ECMAScript 5 в JavaScript-библиотеке. Другой вариант, предложенный Газ (Gareth), — использовать специфическую конструкцию кода для ограничения изменчивости с анонимными замыканиями.

    Пример:

    function escapeHTML(str) {
     str = str + "''";
     var out = "''";
     for(var i=0; i<str.length; i++) {
         if(str[i] === '<') {
             out += '&lt;';
         } else if(str[i] === '>') {
             out += '&gt;';
         } else if(str[i] === "'") {
             out += '&#39;';
         } else if(str[i] === '"') {
             out += '&quot;';
         } else {
             out += str[i];
         }
     }
     return out;
}

    РЕКОМЕНДАЦИЯ #6 - Используйте ненадёжные данные только в правой части выражения¶

    Используйте ненадёжные данные только в правой части выражения, особенно данные, которые выглядят как код и могут передаваться в приложение (например, location и eval()).

    window[userDataOnLeftSide] = "userDataOnRightSide";

    Использование ненадёжных пользовательских данных в левой части выражения позволяет злоумышленнику подменять внутренние и внешние атрибуты объекта window, тогда как использование пользовательского ввода в правой части выражения не допускает прямой манипуляции.

    РЕКОМЕНДАЦИЯ #7 - При URL-кодировании в DOM учитывайте проблемы с набором символов¶

    При URL-кодировании в DOM учитывайте проблемы с набором символов, поскольку набор символов в JavaScript DOM чётко не определён (Майк Сэмюэл).

    РЕКОМЕНДАЦИЯ #8 - Ограничивайте доступ к свойствам объектов при использовании аксессоров object[x]¶

    Ограничивайте доступ к свойствам объектов при использовании аксессоров object[x] (Майк Сэмюэл). Иными словами, добавляйте уровень косвенности между ненадёжными входными данными и указанными свойствами объектов.

    Вот пример проблемы с использованием типов карт:

    var myMapType = {};
myMapType[<%=untrustedData%>] = "moreUntrustedData";

    Разработчик, пишущий код выше, пытался добавить дополнительные ключевые элементы в объект myMapType. Однако злоумышленник мог бы использовать это для подмены внутренних и внешних атрибутов объекта myMapType.

    Лучшим подходом было бы использование следующего:

    if (untrustedData === 'location') {
  myMapType.location = "moreUntrustedData";
}

    Типичные проблемы при устранении DOM-based XSS¶

    Сложные контексты¶

    Во многих случаях контекст не всегда очевиден.

    <a href="javascript:myFunction('<%=untrustedData%>', 'test');">Click Me</a>
 ...
<script>
Function myFunction (url,name) {
    window.location = url;
}
</script>

    В приведённом выше примере ненадёжные данные начинались в контексте отображения URL (атрибут href тега a), затем перешли в контекст выполнения JavaScript (обработчик протокола javascript:), который передал ненадёжные данные в URL-подконтекст выполнения (window.location в myFunction).

    Поскольку данные были введены в код JavaScript и переданы в URL-подконтекст, соответствующим серверным кодированием было бы следующее:

    <a href="javascript:myFunction('<%=ESAPI.encoder().encodeForJavascript(ESAPI.encoder().encodeForURL(untrustedData)) %>', 'test');">
Click Me</a>
 ...

    Или если вы использовали ECMAScript 5 с неизменяемыми клиентскими библиотеками JavaScript-кодирования, вы могли бы сделать следующее:

    <!-- серверное URL-кодирование удалено. Теперь только JavaScript-кодирование на стороне сервера. -->
<a href="javascript:myFunction('<%=ESAPI.encoder().encodeForJavascript(untrustedData)%>', 'test');">Click Me</a>
 ...
<script>
Function myFunction (url,name) {
    var encodedURL = ESAPI.encoder().encodeForURL(url);  // URL-кодирование с помощью клиентских скриптов
    window.location = encodedURL;
}
</script>

    Непоследовательность библиотек кодирования¶

    Существует ряд библиотек кодирования с открытым исходным кодом:

    1. OWASP ESAPI
    2. OWASP Java Encoder
    3. Apache Commons Text StringEscapeUtils, замена из Apache Commons Lang3
    4. Jtidy
    5. Пользовательская реализация вашей компании.

    Некоторые работают на основе списка запретов, другие игнорируют важные символы, такие как "<" и ">".

    Java Encoder — активный проект, поддерживающий HTML, CSS и JavaScript-кодирование.

    ESAPI — один из немногих, работающих на основе списка разрешений и кодирующих все небуквенно-цифровые символы. Важно использовать библиотеку кодирования, которая понимает, какие символы могут использоваться для эксплуатации уязвимостей в соответствующих контекстах. Вокруг правильного кодирования существует масса заблуждений.

    Заблуждения относительно кодирования¶

    Многие учебные программы и статьи по безопасности пропагандируют слепое использование HTML-кодирования для решения проблемы XSS.

    Логически это выглядит разумным советом, поскольку JavaScript-парсер не понимает HTML-кодирование.

    Однако если страницы, возвращаемые вашим веб-приложением, используют тип содержимого text/xhtml или расширение файла *.xhtml, то HTML-кодирование может не работать для защиты от XSS.

    Например:

    <script>
&#x61;lert(1);
</script>

    Вышеприведённое HTML-закодированное значение всё равно выполняется. Если этого недостаточно для запоминания, стоит помнить, что кодирования теряются при их получении с помощью атрибута value элемента DOM.

    Рассмотрим пример страницы и скрипта:

    <form name="myForm" ...>
  <input type="text" name="lName" value="<%=ESAPI.encoder().encodeForHTML(last_name)%>">
 ...
</form>
<script>
  var x = document.myForm.lName.value;  // при получении значения кодирование отменяется
  document.writeln(x);  // любой код, переданный в lName, теперь выполняем.
</script>

    Наконец, существует проблема, что некоторые методы в JavaScript, которые обычно безопасны, могут быть небезопасны в определённых контекстах.

    Обычно безопасные методы¶

    Один из примеров атрибута, считающегося безопасным, — innerText.

    Некоторые статьи или руководства рекомендуют его использование как альтернативу innerHTML для защиты от XSS в innerHTML. Однако в зависимости от тега, к которому применяется innerText, код может выполняться.

    <script>
 var tag = document.createElement("script");
 tag.innerText = "<%=untrustedData%>";  // выполняет код
</script>

    Функция innerText была изначально введена Internet Explorer и официально включена в стандарт HTML в 2016 году после принятия всеми основными производителями браузеров.

    Обнаружение DOM XSS с помощью вариантного анализа¶

    Уязвимый код:

    <script>
var x = location.hash.split("#")[1];
document.write(x);
</script>

    Правило Semgrep для выявления указанного выше DOM XSS ссылка.
