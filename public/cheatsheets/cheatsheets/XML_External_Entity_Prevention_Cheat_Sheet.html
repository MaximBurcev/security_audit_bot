    XML External Entity Prevention Cheat Sheet¶

    Введение¶

    XML eXternal Entity injection (XXE), которая входит в OWASP Top 10 под пунктом A4, — это атака на приложения, обрабатывающие XML-ввод. Проблема зарегистрирована под идентификатором 611 в реестре Common Weakness Enumeration. XXE-атака происходит, когда ненадёжный XML-ввод, содержащий ссылку на внешнюю сущность, обрабатывается слабо настроенным XML-парсером, и эта атака может использоваться для проведения различных инцидентов, в том числе:

    • Атака типа «отказ в обслуживании» (DoS) на систему
    • Атака Server Side Request Forgery (SSRF)
    • Сканирование портов с машины, на которой расположен парсер
    • Другие воздействия на систему.

    Данная шпаргалка поможет вам предотвратить эту уязвимость.

    Дополнительную информацию об XXE см. на странице XML External Entity (XXE).

    Общие рекомендации¶

    Самый безопасный способ предотвратить XXE — всегда полностью отключать DTD (внешние сущности). В зависимости от парсера метод должен выглядеть примерно так:

    factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);

    Отключение DTD также защищает парсер от атак типа «отказ в обслуживании» (DoS), таких как Billion Laughs. Если полностью отключить DTD невозможно, то внешние сущности и внешние объявления типов документа должны быть отключены способом, специфичным для каждого парсера.

    Матрица функций безопасности XML-парсеров¶

    Функция безопасности По умолчанию (зависит от парсера) Назначение Что произойдёт при отсутствии?
    Внешние сущности отключены Обычно отключены (безопасно) Блокирует загрузку внешних ресурсов Полноценная XXE → SSRF, раскрытие файлов, внутреннее сканирование
    Запрет объявления DOCTYPE Зависит от парсера Предотвращает определения ENTITY Классические XXE-payload становятся полностью работоспособными
    Отключение загрузки внешних DTD Обычно отключена Останавливает загрузку удалённых DTD Открывает Blind XXE, SSRF за межсетевыми экранами
    Режим безопасной обработки Зависит от парсера Ограничивает рекурсию, сетевой доступ, раскрытие сущностей Billion Laughs DoS и истощение ресурсов становятся возможными
    Отключение параметрических сущностей Зависит от парсера Предотвращает инъекции %entity; Продвинутые XXE-payload обходят простые защиты
    XInclude отключён Обычно отключён Предотвращает включение внешних файлов Чтение файлов через file:// и SSRF становятся возможными
    Ограничение количества раскрытий сущностей Обычно включено Предотвращает злоупотребление рекурсивными сущностями Исчерпание памяти → DoS парсера или сервера
    Валидация схемы без внешних запросов Обычно безопасна Гарантирует, что валидация не обращается к внешним URL Скрытые внешние HTTP-запросы инициируются в процессе валидации

    Матрица быстрого воздействия (что произойдёт при отсутствии?)¶

    Отсутствующий контроль Возникающая уязвимость
    DOCTYPE не отключён Стандартная XXE полностью эксплуатируема
    Внешние сущности включены SSRF, кража файлов, сканирование портов
    Загрузка внешних DTD разрешена Blind XXE → скрытые SSRF-атаки
    Нет ограничений на раскрытие сущностей Billion Laughs DoS
    XInclude включён Раскрытие локальных файлов + SSRF
    Безопасная обработка отключена Критические защиты обходятся
    Валидация схемы обращается к внешним URL Приложение делает нежелательные исходящие запросы

    Минимальные правила усиления защиты XML¶

    • Отключить DOCTYPE
    • Отключить внешние сущности
    • Отключить загрузку внешних DTD
    • Включить режим безопасной обработки
    • Отключить XInclude
    • Ограничить раскрытие сущностей
    • Не использовать устаревшие XML-парсеры
    • Никогда не обрабатывать ненадёжный XML с настройками по умолчанию

    Подробное руководство по предотвращению XXE приведено ниже для нескольких языков (C++, Cold Fusion, Java, .NET, iOS, PHP, Python, правила Semgrep) и часто используемых XML-парсеров.

    C/C++¶

    libxml2¶

    Перечисление xmlParserOption не должно включать следующие параметры:

    • XML_PARSE_NOENT: Раскрывает сущности и заменяет их заменяющим текстом
    • XML_PARSE_DTDLOAD: Загружает внешний DTD

    Примечание:

    Согласно этой записи, начиная с libxml2 версии 2.9 XXE по умолчанию отключён, что было зафиксировано следующим патчем.

    Проверьте, используются ли следующие API, и убедитесь, что в параметрах не определены XML_PARSE_NOENT и XML_PARSE_DTDLOAD:

    • xmlCtxtReadDoc
    • xmlCtxtReadFd
    • xmlCtxtReadFile
    • xmlCtxtReadIO
    • xmlCtxtReadMemory
    • xmlCtxtUseOptions
    • xmlParseInNodeContext
    • xmlReadDoc
    • xmlReadFd
    • xmlReadFile
    • xmlReadIO
    • xmlReadMemory

    libxerces-c¶

    При использовании XercesDOMParser выполните следующее для предотвращения XXE:

    XercesDOMParser *parser = new XercesDOMParser;
parser->setCreateEntityReferenceNodes(true);
parser->setDisableDefaultEntityResolution(true);

    При использовании SAXParser выполните следующее для предотвращения XXE:

    SAXParser* parser = new SAXParser;
parser->setDisableDefaultEntityResolution(true);

    При использовании SAX2XMLReader выполните следующее для предотвращения XXE:

    SAX2XMLReader* reader = XMLReaderFactory::createXMLReader();
parser->setFeature(XMLUni::fgXercesDisableDefaultEntityResolution, true);

    ColdFusion¶

    Согласно этой записи в блоге, и Adobe ColdFusion, и Lucee имеют встроенные механизмы для отключения поддержки внешних XML-сущностей.

    Adobe ColdFusion¶

    Начиная с ColdFusion 2018 Update 14 и ColdFusion 2021 Update 4, все встроенные функции ColdFusion, обрабатывающие XML, имеют аргумент XML-парсера, который отключает поддержку внешних XML-сущностей. Поскольку глобальной настройки для отключения внешних сущностей не существует, разработчики должны убедиться, что каждый вызов XML-функции использует правильные параметры безопасности.

    Согласно документации функции XmlParse(), вы можете отключить XXE с помощью следующего кода:

    <cfset parseroptions = structnew()>
<cfset parseroptions.ALLOWEXTERNALENTITIES = false>
<cfscript>
a = XmlParse("xml.xml", false, parseroptions);
writeDump(a);
</cfscript>

    Структуру "parseroptions", показанную выше, можно также передавать в качестве аргумента для защиты других функций обработки XML, например:

    XxmlSearch(xmldoc, xpath,parseroptions);

XmlTransform(xmldoc,xslt,parseroptions);

isXML(xmldoc,parseroptions);

    Lucee¶

    Начиная с Lucee 5.3.4.51 и выше, вы можете отключить поддержку внешних XML-сущностей, добавив следующее в ваш Application.cfc:

    this.xmlFeatures = {
     externalGeneralEntities: false,
     secure: true,
     disallowDoctypeDecl: true
};

    Поддержка внешних XML-сущностей отключена по умолчанию начиная с Lucee 5.4.2.10 и Lucee 6.0.0.514.

    Java¶

    Поскольку большинство Java XML-парсеров по умолчанию включают XXE, этот язык особенно уязвим к XXE-атакам, поэтому необходимо явно отключать XXE для безопасного использования этих парсеров. В данном разделе описывается, как отключить XXE в наиболее часто используемых Java XML-парсерах.

    JAXP DocumentBuilderFactory, SAXParserFactory и DOM4J¶

    Парсеры DocumentBuilderFactory, SAXParserFactory и DOM4J XML могут быть защищены от XXE-атак одними и теми же методами.

    Для краткости мы покажем только, как защитить парсер DocumentBuilderFactory. Дополнительные инструкции по защите этого парсера включены в пример кода

    Метод JAXP DocumentBuilderFactory setFeature позволяет разработчику управлять тем, какие зависимые от реализации функции XML-процессора включены или отключены.

    Эти функции могут быть установлены как на фабрике, так и через метод setFeature нижележащего XMLReader.

    Каждая реализация XML-процессора имеет собственные функции, управляющие обработкой DTD и внешних сущностей. Полное отключение обработки DTD позволяет предотвратить большинство XXE-атак, хотя также необходимо отключить или убедиться, что XInclude не включён.

    Начиная с JDK 6, флаг FEATURE_SECURE_PROCESSING может использоваться для указания реализации парсера обрабатывать XML безопасно. Его поведение зависит от реализации. Он может помочь с истощением ресурсов, но не всегда предотвращает раскрытие сущностей. Подробнее об этом флаге можно узнать здесь.

    Пример кода с подсветкой синтаксиса для SAXParserFactory можно найти здесь. Пример кода с полным отключением DTD (doctypes):

    import javax.xml.parsers.DocumentBuilderFactory;
import javax.xml.parsers.ParserConfigurationException; // catching unsupported features
import javax.xml.XMLConstants;

...

DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
String FEATURE = null;
try {
    // This is the PRIMARY defense. If DTDs (doctypes) are disallowed, almost all
    // XML entity attacks are prevented
    // Xerces 2 only - http://xerces.apache.org/xerces2-j/features.html#disallow-doctype-decl
    FEATURE = "http://apache.org/xml/features/disallow-doctype-decl";
    dbf.setFeature(FEATURE, true);

    // and these as well, per Timothy Morgan's 2014 paper: "XML Schema, DTD, and Entity Attacks"
    dbf.setXIncludeAware(false);

    // remaining parser logic
    ...
} catch (ParserConfigurationException e) {
    // This should catch a failed setFeature feature
    // NOTE: Each call to setFeature() should be in its own try/catch otherwise subsequent calls will be skipped.
    // This is only important if you're ignoring errors for multi-provider support.
    logger.info("ParserConfigurationException was thrown. The feature '" + FEATURE
    + "' is not supported by your XML processor.");
    ...
} catch (SAXException e) {
    // On Apache, this should be thrown when disallowing DOCTYPE
    logger.warning("A DOCTYPE was passed into the XML document");
    ...
} catch (IOException e) {
    // XXE that points to a file that doesn't exist
    logger.error("IOException occurred, XXE may still possible: " + e.getMessage());
    ...
}

// Load XML file or stream using a XXE agnostic configured parser...
DocumentBuilder safebuilder = dbf.newDocumentBuilder();

    Если полностью отключить DTD невозможно:

    import javax.xml.parsers.DocumentBuilderFactory;
import javax.xml.parsers.ParserConfigurationException; // catching unsupported features
import javax.xml.XMLConstants;

...

DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();

String[] featuresToDisable = {
    // Xerces 1 - http://xerces.apache.org/xerces-j/features.html#external-general-entities
    // Xerces 2 - http://xerces.apache.org/xerces2-j/features.html#external-general-entities
    // JDK7+ - http://xml.org/sax/features/external-general-entities
    //This feature has to be used together with the following one, otherwise it will not protect you from XXE for sure
    "http://xml.org/sax/features/external-general-entities",

    // Xerces 1 - http://xerces.apache.org/xerces-j/features.html#external-parameter-entities
    // Xerces 2 - http://xerces.apache.org/xerces2-j/features.html#external-parameter-entities
    // JDK7+ - http://xml.org/sax/features/external-parameter-entities
    //This feature has to be used together with the previous one, otherwise it will not protect you from XXE for sure
    "http://xml.org/sax/features/external-parameter-entities",

    // Disable external DTDs as well
    "http://apache.org/xml/features/nonvalidating/load-external-dtd"
}

for (String feature : featuresToDisable) {
    try {
        dbf.setFeature(feature, false);
    } catch (ParserConfigurationException e) {
        // This should catch a failed setFeature feature
        logger.info("ParserConfigurationException was thrown. The feature '" + feature
        + "' is probably not supported by your XML processor.");
        ...
    }
}

try {
    // Add these as per Timothy Morgan's 2014 paper: "XML Schema, DTD, and Entity Attacks"
    dbf.setXIncludeAware(false);
    dbf.setExpandEntityReferences(false);

    // As stated in the documentation, "Feature for Secure Processing (FSP)" is the central mechanism that will
    // help you safeguard XML processing. It instructs XML processors, such as parsers, validators,
    // and transformers, to try and process XML securely, and the FSP can be used as an alternative to
    // dbf.setExpandEntityReferences(false); to allow some safe level of Entity Expansion
    // Exists from JDK6.
    dbf.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);

    // And, per Timothy Morgan: "If for some reason support for inline DOCTYPEs are a requirement, then
    // ensure the entity settings are disabled (as shown above) and beware that SSRF attacks
    // (http://cwe.mitre.org/data/definitions/918.html) and denial
    // of service attacks (such as billion laughs or decompression bombs via "jar:") are a risk."

    // remaining parser logic
    ...
} catch (ParserConfigurationException e) {
    // This should catch a failed setFeature feature
    logger.info("ParserConfigurationException was thrown. The feature 'XMLConstants.FEATURE_SECURE_PROCESSING'"
    + " is probably not supported by your XML processor.");
    ...
} catch (SAXException e) {
    // On Apache, this should be thrown when disallowing DOCTYPE
    logger.warning("A DOCTYPE was passed into the XML document");
    ...
} catch (IOException e) {
    // XXE that points to a file that doesn't exist
    logger.error("IOException occurred, XXE may still possible: " + e.getMessage());
    ...
}

// Load XML file or stream using a XXE agnostic configured parser...
DocumentBuilder safebuilder = dbf.newDocumentBuilder();

    Xerces 1 Функции:

    • Не включать внешние сущности, установив эту функцию в false.
    • Не включать параметрические сущности, установив эту функцию в false.
    • Не включать внешние DTD, установив эту функцию в false.

    Xerces 2 Функции:

    • Запретить встроенный DTD, установив эту функцию в true.
    • Не включать внешние сущности, установив эту функцию в false.
    • Не включать параметрические сущности, установив эту функцию в false.
    • Не включать внешние DTD, установив эту функцию в false.

    Примечание: Приведённые выше меры защиты требуют Java 7 update 67, Java 8 update 20 или выше, поскольку меры противодействия для DocumentBuilderFactory и SAXParserFactory не работают в более ранних версиях Java согласно: CVE-2014-6517.

    XMLInputFactory (парсер StAX)¶

    Парсеры StAX, такие как XMLInputFactory, позволяют задавать различные свойства и функции.

    Для защиты Java XMLInputFactory от XXE полностью отключите DTD (doctypes):

    // This disables DTDs entirely for that factory
xmlInputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);

    или, если полностью отключить DTD невозможно:

    // This causes XMLStreamException to be thrown if external DTDs are accessed.
xmlInputFactory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
// disable external entities
xmlInputFactory.setProperty("javax.xml.stream.isSupportingExternalEntities", false);

    Параметр xmlInputFactory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, ""); не является обязательным, так как XMLInputFactory зависит от Validator при выполнении валидации XML по схемам. См. раздел Validator для конкретной конфигурации.

    Oracle DOM Parser¶

    Следуйте рекомендациям Oracle, например:

        // Extend oracle.xml.parser.v2.XMLParser
    DOMParser domParser = new DOMParser();

    // Do not expand entity references
    domParser.setAttribute(DOMParser.EXPAND_ENTITYREF, false);

    // dtdObj is an instance of oracle.xml.parser.v2.DTD
    domParser.setAttribute(DOMParser.DTD_OBJECT, dtdObj);

    // Do not allow more than 11 levels of entity expansion
    domParser.setAttribute(DOMParser.ENTITY_EXPANSION_DEPTH, 12);

    TransformerFactory¶

    Для защиты javax.xml.transform.TransformerFactory от XXE выполните следующее:

    TransformerFactory tf = TransformerFactory.newInstance();
tf.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
tf.setAttribute(XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "");

    Validator¶

    Для защиты javax.xml.validation.Validator от XXE выполните следующее:

    SchemaFactory factory = SchemaFactory.newInstance("http://www.w3.org/2001/XMLSchema");
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
Schema schema = factory.newSchema();
Validator validator = schema.newValidator();
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");

    Для защиты javax.xml.validation.SchemaFactory от XXE выполните следующее:

    SchemaFactory factory = SchemaFactory.newInstance("http://www.w3.org/2001/XMLSchema");
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
Schema schema = factory.newSchema(Source);

    SAXTransformerFactory¶

    Для защиты javax.xml.transform.sax.SAXTransformerFactory от XXE выполните следующее:

sf.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
sf.setAttribute(XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "");
sf.newXMLFilter(Source);

    • javax.xml.XMLConstants.ACCESS_EXTERNAL_SCHEMA
    • javax.xml.XMLConstants.ACCESS_EXTERNAL_STYLESHEET

    XMLReader¶

    Для защиты Java org.xml.sax.XMLReader от XXE-атаки выполните следующее:

    XMLReader reader = XMLReaderFactory.createXMLReader();
reader.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
// This may not be strictly required as DTDs shouldn't be allowed at all, per previous line.
reader.setFeature("http://apache.org/xml/features/nonvalidating/load-external-dtd", false);
reader.setFeature("http://xml.org/sax/features/external-general-entities", false);
reader.setFeature("http://xml.org/sax/features/external-parameter-entities", false);

    SAXReader¶

    Для защиты Java org.dom4j.io.SAXReader от XXE-атаки выполните следующее:

    saxReader.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
saxReader.setFeature("http://xml.org/sax/features/external-general-entities", false);
saxReader.setFeature("http://xml.org/sax/features/external-parameter-entities", false);

    Если в вашем коде отсутствуют все эти строки, вы можете быть уязвимы к XXE-атаке.

    SAXBuilder¶

    Для защиты Java org.jdom2.input.SAXBuilder от XXE-атаки полностью запретите DTD (doctypes):

    SAXBuilder builder = new SAXBuilder();
builder.setFeature("http://apache.org/xml/features/disallow-doctype-decl",true);
Document doc = builder.build(new File(fileName));

    Если полностью отключить DTD невозможно, отключите внешние сущности и раскрытие сущностей:

    SAXBuilder builder = new SAXBuilder();
builder.setFeature("http://xml.org/sax/features/external-general-entities", false);
builder.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
builder.setFeature("http://apache.org/xml/features/nonvalidating/load-external-dtd", false);
builder.setExpandEntities(false);
Document doc = builder.build(new File(fileName));

    No-op EntityResolver¶

    Для API, принимающих EntityResolver, вы можете нейтрализовать способность XML-парсера разрешать сущности, предоставив реализацию-заглушку:

    public final class NoOpEntityResolver implements EntityResolver {
    public InputSource resolveEntity(String publicId, String systemId) {
        return new InputSource(new StringReader(""));
    }
}

// ...

xmlReader.setEntityResolver(new NoOpEntityResolver());
documentBuilder.setEntityResolver(new NoOpEntityResolver());

    или, более кратко:

    EntityResolver noop = (publicId, systemId) -> new InputSource(new StringReader(""));
xmlReader.setEntityResolver(noop);
documentBuilder.setEntityResolver(noop);

    JAXB Unmarshaller¶

    Необходимо убедиться, что источником для функции unmarshal класса javax.xml.bind.Unmarshaller является javax.xml.stream.XMLStreamReader, созданный с помощью javax.xml.stream.XMLInputFactory с безопасными свойствами, то есть XMLInputFactory.SUPPORT_DTD и XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES установлены в false. Например:

    File file = new File(xmlPath);
XMLInputFactory xif = XMLInputFactory.newFactory();
xif.setProperty(XMLInputFactory.SUPPORT_DTD, false);
xif.setProperty(XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES, false);
XMLStreamReader xsr = null;
try {
    xsr = xif.createXMLStreamReader(new StreamSource(file));
} catch (XMLStreamException e) {
    throw new RuntimeException(e);
}
Unmarshaller um = jc.createUnmarshaller();
um.unmarshal(xsr);

    Обратите внимание, что методы createXMLStreamReader и unmarshal имеют несколько перегрузок с различными типами источников, поэтому необходимо выбрать подходящий и при необходимости выполнить конвертацию.

    XPathExpression¶

    Поскольку javax.xml.xpath.XPathExpression не может быть безопасно настроен сам по себе, ненадёжные данные должны сначала быть обработаны другим защищённым XML-парсером.

    Например:

    DocumentBuilderFactory df = DocumentBuilderFactory.newInstance();
df.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
df.setAttribute(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
DocumentBuilder builder = df.newDocumentBuilder();
String result = new XPathExpression().evaluate( builder.parse(
                            new ByteArrayInputStream(xml.getBytes())) );

    java.beans.XMLDecoder¶

    Метод readObject() этого класса является принципиально небезопасным.

    XML, который он обрабатывает, подвержен не только XXE, но и сам метод может использоваться для создания любого Java-объекта и выполнения произвольного кода, как описано здесь.

    И не существует способа сделать использование этого класса безопасным, кроме как доверять или должным образом проверять передаваемые в него данные.

    Поэтому мы настоятельно рекомендуем полностью избегать использования этого класса и заменить его безопасным или правильно настроенным XML-парсером, как описано в других разделах данной шпаргалки.

    Другие XML-парсеры¶

    Существует множество сторонних библиотек, обрабатывающих XML напрямую или через другие библиотеки. Пожалуйста, протестируйте и убедитесь, что их XML-парсер защищён от XXE по умолчанию. Если парсер не является безопасным по умолчанию, поищите флаги, поддерживаемые парсером, для отключения всех возможных включений внешних ресурсов, как в примерах выше. Если возможности управления не предоставлены извне, убедитесь, что ненадёжный контент сначала проходит через безопасный парсер, а затем передаётся в небезопасный сторонний парсер — аналогично тому, как обеспечивается безопасность Unmarshaller.

    XXE-уязвимости Spring Framework MVC/OXM¶

    **Некоторые XXE-уязвимости были обнаружены в Spring OXM и Spring MVC. Следующие версии Spring Framework уязвимы к XXE:

    • 3.0.0 по 3.2.3 (Spring OXM & Spring MVC)
    • 4.0.0.M1 (Spring OXM)
    • 4.0.0.M1-4.0.0.M2 (Spring MVC)

    Были и другие проблемы, исправленные позже, поэтому для полного устранения этих проблем Spring рекомендует обновиться до Spring Framework 3.2.8+ или 4.0.2+.

    Для Spring OXM речь идёт об использовании org.springframework.oxm.jaxb.Jaxb2Marshaller. Обратите внимание, что CVE для Spring OXM явно указывает, что две ситуации с разбором XML остаются в зоне ответственности разработчика, а ещё две — в зоне ответственности Spring и были исправлены для устранения этой CVE.

    Вот что они говорят:

    Две ситуации, которые должны обработать разработчики:

    • Для DOMSource XML уже был разобран пользовательским кодом, и именно он несёт ответственность за защиту от XXE.
    • Для StAXSource XMLStreamReader уже был создан пользовательским кодом, и именно он несёт ответственность за защиту от XXE.

    Проблема, исправленная Spring:

    Для экземпляров SAXSource и StreamSource Spring по умолчанию обрабатывал внешние сущности, тем самым создавая эту уязвимость.

    Вот пример использования StreamSource, которая была уязвимой, но теперь является безопасной при использовании исправленной версии Spring OXM или Spring MVC:

    import org.springframework.oxm.Jaxb2Marshaller;
import org.springframework.oxm.jaxb.Jaxb2Marshaller;

Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
// Must cast return Object to whatever type you are unmarshalling
marshaller.unmarshal(new StreamSource(new StringReader(some_string_containing_XML));

    Таким образом, согласно описанию CVE Spring OXM, приведённый выше код теперь безопасен. Но если вы используете DOMSource или StAXSource, ответственность за их безопасную настройку от XXE лежит на вас.

    Castor¶

    Castor — это фреймворк привязки данных для Java, позволяющий конвертировать данные между Java-объектами, XML и реляционными таблицами. XML-функции в Castor до версии 1.3.3 уязвимы к XXE, поэтому следует обновиться до последней версии. Дополнительную информацию см. в официальном файле конфигурации XML

    .NET¶

    Актуальная информация о XXE-инъекции в .NET взята непосредственно из веб-приложения с юнит-тестами Dean Fleming, охватывающего все поддерживаемые в настоящее время .NET XML-парсеры, с тест-кейсами, демонстрирующими их безопасность или уязвимость к XXE-инъекциям, однако эти тесты проводятся только с инъекцией из файла, но не с прямым DTD (используемым при DoS-атаках).

    Для DoS-атак с использованием прямого DTD (например, атака Billion laughs) было создано отдельное тестовое приложение Josh Grossman из Bounce Security, чтобы подтвердить, что .NET >=4.5.2 защищён от этих атак.

    Ранее эта информация основывалась на ряде более старых статей, которые могут быть не на 100% точны, включая:

    • Отличная статья James Jardine о .NET XXE.
    • Руководство Microsoft по предотвращению XXE и XML-атак типа «отказ в обслуживании» в .NET.

    Обзор уровней безопасности .NET-парсеров¶

    **Ниже представлен обзор всех поддерживаемых .NET XML-парсеров и их уровней безопасности по умолчанию. Подробнее о каждом парсере рассказывается после этого списка.

    **XDocument (LINQ to XML)

    Этот парсер защищён от внешних сущностей начиная с .NET Framework версии 4.5.2 и защищён от Billion Laughs начиная с версии 4.5.2 и выше, однако неизвестно, защищён ли этот парсер от Billion Laughs в версиях до 4.5.2.

    Уровни безопасности XmlDocument, XmlTextReader, XPathNavigator по умолчанию¶

    Эти парсеры уязвимы к атакам на внешние сущности и Billion Laughs в версиях ниже 4.5.2, но защищены в версиях 4.5.2 и выше.

    Уровни безопасности XmlDictionaryReader, XmlNodeReader, XmlReader по умолчанию¶

    Эти парсеры не уязвимы к атакам на внешние сущности или Billion Laughs ни до, ни после версии 4.5.2. Кроме того, начиная с версии ≥4.5.2 эти библиотеки по умолчанию не будут обрабатывать встроенный DTD. Даже если изменить настройку по умолчанию для разрешения обработки DTD, при попытке DoS-атаки всё равно будет выброшено исключение, как описано выше.

    ASP.NET¶

    Приложения ASP.NET версии ≥ .NET 4.5.2 также должны убедиться, что в Web.config установлен <httpRuntime targetFramework="..." /> версии ≥4.5.2, иначе они могут оставаться уязвимыми вне зависимости от фактической версии .NET. Отсутствие этого тега также приведёт к небезопасному поведению по умолчанию.

    Для понимания приведённой выше таблицы .NET Framework Version для ASP.NET-приложений — это либо версия .NET, с которой было собрано приложение, либо targetFramework httpRuntime (Web.config), в зависимости от того, что меньше.

    Этот тег конфигурации не следует путать с похожим тегом: <compilation targetFramework="..." /> или targetFramework сборок/проектов, которые не являются достаточными для достижения безопасного поведения по умолчанию, указанного в приведённой выше таблице.

    LINQ to XML¶

    Объекты XElement и XDocument библиотеки System.Xml.Linq по умолчанию защищены от XXE-инъекции из внешнего файла и DoS-атаки. XElement обрабатывает только элементы внутри XML-файла, поэтому DTD полностью игнорируются. XDocument имеет XmlResolver, отключённый по умолчанию, поэтому защищён от SSRF. Несмотря на то что DTD включены по умолчанию, начиная с Framework версий ≥4.5.2 он не уязвим к DoS, как указано выше, но может быть уязвим в более ранних версиях Framework. Дополнительную информацию см. в руководстве Microsoft по предотвращению XXE и XML-атак типа «отказ в обслуживании» в .NET

    XmlDictionaryReader¶

    System.Xml.XmlDictionaryReader безопасен по умолчанию: при попытке разобрать DTD компилятор выбрасывает исключение с сообщением о том, что «CData elements not valid at top level of an XML document». Он становится небезопасным, если создан с использованием другого небезопасного XML-парсера.

    XmlDocument¶

    В версиях .NET Framework до 4.5.2 System.Xml.XmlDocument небезопасен по умолчанию. Объект XmlDocument содержит объект XmlResolver, который необходимо устанавливать в null в версиях до 4.5.2. В версиях 4.5.2 и выше этот XmlResolver по умолчанию установлен в null.

    Следующий пример показывает, как обеспечить его безопасность:

     static void LoadXML()
 {
   string xxePayload = "<!DOCTYPE doc [<!ENTITY win SYSTEM 'file:///C:/Users/testdata2.txt'>]>"
                     + "<doc>&win;</doc>";
   string xml = "<?xml version='1.0' ?>" + xxePayload;

   XmlDocument xmlDoc = new XmlDocument();
   // Setting this to NULL disables DTDs - Its NOT null by default.
   xmlDoc.XmlResolver = null;
   xmlDoc.LoadXml(xml);
   Console.WriteLine(xmlDoc.InnerText);
   Console.ReadLine();
 }

    Для .NET Framework версии ≥4.5.2 он безопасен по умолчанию.

    XmlDocument может стать небезопасным, если создать собственный ненулевой XmlResolver с настройками по умолчанию или небезопасными настройками. Если необходимо включить обработку DTD, инструкции по безопасному выполнению этого подробно описаны в указанной статье MSDN.

    XmlNodeReader¶

    Объекты System.Xml.XmlNodeReader безопасны по умолчанию и будут игнорировать DTD даже при создании с небезопасным парсером или при оборачивании в другой небезопасный парсер.

    XmlReader¶

    Объекты System.Xml.XmlReader безопасны по умолчанию.

    По умолчанию их свойство ProhibitDtd установлено в false в версиях .NET Framework 4.0 и более ранних, или свойство DtdProcessing установлено в Prohibit в версиях .NET 4.0 и выше.

    Кроме того, в версиях .NET 4.5.2 и выше XmlReaderSettings, принадлежащий XmlReader, по умолчанию имеет XmlResolver, установленный в null, что обеспечивает дополнительный уровень защиты.

    Поэтому объекты XmlReader станут небезопасными в версии 4.5.2 и выше только в том случае, если одновременно свойство DtdProcessing установлено в Parse и XmlResolver в XmlReaderSetting установлен в ненулевой XmlResolver с настройками по умолчанию или небезопасными настройками. Если необходимо включить обработку DTD, инструкции по безопасному выполнению этого подробно описаны в указанной статье MSDN.

    XmlTextReader¶

    System.Xml.XmlTextReader небезопасен по умолчанию в версиях .NET Framework до 4.5.2. Вот как обеспечить его безопасность в различных версиях .NET:

    До .NET 4.0¶

    В версиях .NET Framework до 4.0 поведение разбора DTD для объектов XmlReader, таких как XmlTextReader, управляется булевым свойством ProhibitDtd, находящимся в классах System.Xml.XmlReaderSettings и System.Xml.XmlTextReader.

    Установите эти значения в true, чтобы полностью отключить встроенные DTD.

    XmlTextReader reader = new XmlTextReader(stream);
// NEEDED because the default is FALSE!!
reader.ProhibitDtd = true;

    .NET 4.0 — .NET 4.5.2¶

    В .NET Framework версии 4.0 поведение разбора DTD было изменено. Свойство ProhibitDtd было объявлено устаревшим в пользу нового свойства DtdProcessing.

    Однако настройки по умолчанию не изменились, поэтому XmlTextReader по-прежнему уязвим к XXE по умолчанию.

    Установка DtdProcessing в Prohibit приводит к тому, что среда выполнения выбрасывает исключение при обнаружении элемента <!DOCTYPE> в XML.

    Чтобы установить это значение вручную:

    XmlTextReader reader = new XmlTextReader(stream);
// NEEDED because the default is Parse!!
reader.DtdProcessing = DtdProcessing.Prohibit;

    Также можно установить свойство DtdProcessing в Ignore, что не будет выбрасывать исключение при обнаружении элемента <!DOCTYPE>, а просто пропустит его без обработки. Наконец, можно установить DtdProcessing в Parse, если нужно разрешить и обрабатывать встроенные DTD.

    .NET 4.5.2 и выше¶

    В версиях .NET Framework 4.5.2 и выше внутренний XmlResolver у XmlTextReader по умолчанию установлен в null, что заставляет XmlTextReader по умолчанию игнорировать DTD. XmlTextReader может стать небезопасным, если создать собственный ненулевой XmlResolver с настройками по умолчанию или небезопасными настройками.

    XPathNavigator¶

    System.Xml.XPath.XPathNavigator небезопасен по умолчанию в версиях .NET Framework до 4.5.2.

    Это связано с тем, что он реализует объекты IXPathNavigable, такие как XmlDocument, которые также небезопасны по умолчанию в версиях до 4.5.2.

    Вы можете сделать XPathNavigator безопасным, передав ему безопасный парсер, например XmlReader (который безопасен по умолчанию), в конструктор XPathDocument.

    Пример:

    XmlReader reader = XmlReader.Create("example.xml");
XPathDocument doc = new XPathDocument(reader);
XPathNavigator nav = doc.CreateNavigator();
string xml = nav.InnerXml.ToString();

    Для .NET Framework версии ≥4.5.2 XPathNavigator безопасен по умолчанию.

    XslCompiledTransform¶

    System.Xml.Xsl.XslCompiledTransform (XML-трансформер) безопасен по умолчанию при условии, что передаваемый ему парсер тоже безопасен.

    Он безопасен по умолчанию, потому что парсер по умолчанию для методов Transform() — это XmlReader, который безопасен по умолчанию (см. выше).

    Исходный код этого метода находится здесь.

    Некоторые методы Transform() принимают XmlReader или IXPathNavigable (например, XmlDocument) в качестве входных данных, и если передать небезопасный XML-парсер, то Transform также будет небезопасным.

    iOS¶

    libxml2¶

    iOS включает библиотеку C/C++ libxml2, описанную выше, поэтому приведённые там рекомендации применимы при непосредственном использовании libxml2.

    Однако версия libxml2, поставляемая вплоть до iOS6, является версией до 2.9 libxml2 (которая защищает от XXE по умолчанию).

    NSXMLDocument¶

    iOS также предоставляет тип NSXMLDocument, построенный поверх libxml2.

    Однако NSXMLDocument предоставляет некоторую дополнительную защиту от XXE, недоступную непосредственно в libxml2.

    Согласно разделу «NSXMLDocument External Entity Restriction API» на этой странице:

    • iOS4 и более ранние: все внешние сущности загружаются по умолчанию.
    • iOS5 и более поздние: загружаются только сущности, не требующие сетевого доступа. (что безопаснее)

    Однако для полного отключения XXE в NSXMLDocument в любой версии iOS достаточно указать NSXMLNodeLoadExternalEntitiesNever при создании NSXMLDocument.

    PHP¶

    При использовании парсера XML по умолчанию (основанного на libxml2), PHP 8.0 и более новые версии предотвращают XXE по умолчанию.

    Для версий PHP до 8.0, согласно документации PHP, при использовании PHP XML-парсера по умолчанию для предотвращения XXE следует установить следующее:

    libxml_set_external_entity_loader(null);

    Описание того, как злоупотребить этим в PHP, представлено в хорошей статье SensePost, описывающей интересную XXE-уязвимость на основе PHP, которая была исправлена в Facebook.
