    Шпаргалка по десериализации¶

    Введение¶

    Эта статья сосредоточена на предоставлении чётких и практических рекомендаций по безопасной десериализации недоверенных данных в ваших приложениях.

    Что такое десериализация¶

    Сериализация — это процесс преобразования некоторого объекта в формат данных, который можно восстановить позже. Люди часто сериализуют объекты для сохранения на хранение или для отправки в составе сообщений.

    Десериализация — это обратный процесс: принятие данных в некотором формате и воссоздание из них объекта. Сегодня наиболее популярным форматом данных для сериализации является JSON. До него таковым был XML.

    Однако многие языки программирования имеют нативные способы сериализации объектов. Эти нативные форматы обычно предлагают больше возможностей, чем JSON или XML, включая настройку процесса сериализации.

    К сожалению, возможности этих нативных механизмов десериализации иногда могут быть использованы в злонамеренных целях при работе с недоверенными данными. Атаки на десериализаторы могут позволить отказ в обслуживании, обход контроля доступа или атаки с удалённым выполнением кода (RCE).

    Рекомендации по безопасной десериализации объектов¶

    Следующие рекомендации, специфичные для языков программирования, перечисляют безопасные методологии десериализации данных, которым нельзя доверять.

    PHP¶

    Анализ с доступом к коду (Clear-box Review)¶

    Проверяйте использование функции unserialize() и анализируйте, как принимаются внешние параметры. Используйте безопасный, стандартный формат обмена данными, такой как JSON (через json_decode() и json_encode()), если нужно передавать сериализованные данные пользователю.

    Python¶

    Анализ без доступа к коду (Opaque-box Review)¶

    Если данные трафика содержат символ точки . в конце, весьма вероятно, что данные были отправлены в сериализованном виде. Это справедливо только если данные не закодированы в схемах Base64 или Hexadecimal. Если данные закодированы, лучше проверить наличие сериализации, взглянув на начальные символы значения параметра. Например, если данные закодированы в Base64, они, скорее всего, начинаются с gASV.

    Анализ с доступом к коду (Clear-box Review)¶

    Следующие API в Python будут уязвимы к атаке на сериализацию. Ищите в коде следующие паттерны.

    1. Использование pickle/c_pickle/_pickle с load/loads:
    import pickle
data = """ cos.system(S'dir')tR. """
pickle.loads(data)
    1. Использование PyYAML с load:
    import yaml
document = "!!python/object/apply:os.system ['ipconfig']"
print(yaml.load(document))
    1. Использование jsonpickle с методами encode или store.

    Java¶

    Все следующие техники подходят для предотвращения атак на десериализацию Java Serializable формата.

    Рекомендации по реализации:

    • В коде переопределяйте метод ObjectInputStream#resolveClass() для предотвращения десериализации произвольных классов. Это безопасное поведение можно обернуть в библиотеку, например SerialKiller.
    • Используйте безопасную замену для универсального метода readObject(), как показано здесь. Обратите внимание, что это решает атаки типа "billion laughs" путём проверки длины входных данных и количества десериализованных объектов.

    Анализ с доступом к коду (Clear-box Review)¶

    Следите за следующими использованиями Java API на предмет потенциальных уязвимостей сериализации.

    1. XMLdecoder с внешними пользовательскими параметрами

    2. XStream с методом fromXML (версия xstream <= v1.4.6 уязвима к проблеме сериализации)

    3. ObjectInputStream с readObject

    4. Использование readObject, readObjectNoData, readResolve или readExternal

    5. ObjectInputStream.readUnshared

    6. Serializable

    Анализ без доступа к коду (Opaque-box Review)¶

    Если захваченные данные трафика включают следующие паттерны, это может указывать на то, что данные были отправлены в потоках Java-сериализации:

    • AC ED 00 05 в шестнадцатеричном формате
    • rO0 в Base64
    • Заголовок Content-type HTTP-ответа установлен на application/x-java-serialized-object

    Предотвращение утечки данных и подмены доверенных полей¶

    Если есть члены данных объекта, которые никогда не должны контролироваться конечными пользователями при десериализации или раскрываться пользователям при сериализации, их следует объявить с ключевым словом transient (раздел Protecting Sensitive Information).

    Для класса, определённого как Serializable, чувствительная переменная должна быть объявлена как private transient.

    Например, для класса myAccount переменные 'profit' и 'margin' объявлены как transient, чтобы предотвратить их сериализацию.

    public class myAccount implements Serializable
{
    private transient double profit; // объявлено transient

    private transient double margin; // объявлено transient
    ....

    Предотвращение десериализации доменных объектов¶

    Некоторые объекты приложения могут быть вынуждены реализовывать Serializable из-за своей иерархии. Чтобы гарантировать невозможность десериализации объектов вашего приложения, следует объявить метод readObject() (с модификатором final), который всегда выбрасывает исключение:

    private final void readObject(ObjectInputStream in) throws java.io.IOException {
    throw new java.io.IOException("Cannot be deserialized");
}

    Усиление защиты java.io.ObjectInputStream¶

    Класс java.io.ObjectInputStream используется для десериализации объектов. Его поведение можно усилить, создав подкласс. Это лучшее решение если:

    • вы можете изменить код, выполняющий десериализацию;
    • вы знаете, какие классы ожидаете десериализовать.

    Общая идея — переопределить ObjectInputStream.html#resolveClass() для ограничения допустимых для десериализации классов.

    Поскольку этот вызов происходит до вызова readObject(), вы можете быть уверены, что никакая активность десериализации не произойдёт, если тип не является одним из разрешённых.

    Простой пример показан ниже, где класс LookAheadObjectInputStream гарантированно не десериализует никакой тип, кроме класса Bicycle:

    public class LookAheadObjectInputStream extends ObjectInputStream {

    public LookAheadObjectInputStream(InputStream inputStream) throws IOException {
        super(inputStream);
    }

    /**
    * Десериализовать только экземпляры ожидаемого класса Bicycle
    */
    @Override
    protected Class<?> resolveClass(ObjectStreamClass desc) throws IOException, ClassNotFoundException {
        if (!desc.getName().equals(Bicycle.class.getName())) {
            throw new InvalidClassException("Unauthorized deserialization attempt", desc.getName());
        }
        return super.resolveClass(desc);
    }
}

    Более полные реализации этого подхода были предложены различными членами сообщества:

    • NibbleSec - библиотека, позволяющая создавать списки классов, разрешённых для десериализации
    • IBM - оригинальная защита, написанная за годы до того, как были предусмотрены наиболее разрушительные сценарии эксплуатации.
    • Apache Commons IO classes

    Усиление всех использований java.io.ObjectInputStream с помощью агента¶

    Как упоминалось выше, класс java.io.ObjectInputStream используется для десериализации объектов. Его поведение можно усилить, создав подкласс. Однако если вы не владеете кодом или не можете ждать патча, использование агента для внедрения защиты в java.io.ObjectInputStream является лучшим решением.

    Глобальное изменение ObjectInputStream безопасно только для блокировки известных вредоносных типов, поскольку невозможно знать для всех приложений, какие классы ожидаются для десериализации. К счастью, для защиты от всех известных векторов атак сегодня в список запрещённых нужно добавить очень мало классов.

    Неизбежно будут обнаружены новые классы "гаджетов", которые можно злоупотребить. Однако сегодня огромное количество уязвимого программного обеспечения нуждается в исправлении. В некоторых случаях "исправление" уязвимости может включать перепроектирование систем обмена сообщениями и нарушение обратной совместимости, когда разработчики переходят к отказу от приёма сериализованных объектов.

    Чтобы включить эти агенты, добавьте новый параметр JVM:

    -javaagent:name-of-agent.jar

    Агенты с таким подходом выпущены различными членами сообщества:

    • rO0 by Contrast Security

    Похожий, но менее масштабируемый подход — вручную патчить и бутстрапить ObjectInputStream вашей JVM. Руководство по этому подходу доступно здесь.

    Другие библиотеки и форматы десериализации¶

    Хотя приведённые выше рекомендации сосредоточены на Java Serializable формате, существует ряд других библиотек, использующих другие форматы для десериализации. Многие из этих библиотек могут иметь аналогичные проблемы безопасности при неправильной настройке. В этом разделе перечислены некоторые из этих библиотек и рекомендуемые параметры конфигурации для предотвращения проблем безопасности при десериализации недоверенных данных:

    Безопасны при конфигурации по умолчанию:

    Следующие библиотеки можно использовать безопасно при конфигурации по умолчанию:

    • fastjson2 (JSON) - можно использовать безопасно, пока не включена опция autotype
    • jackson-databind (JSON) - можно использовать безопасно, пока не используется полиморфизм (см. статью)
    • Kryo v5.0.0+ (пользовательский формат) - можно использовать безопасно, пока регистрация классов не отключена (см. документацию и эту проблему)
    • YamlBeans v1.16+ (YAML) - можно использовать безопасно, пока не используется класс UnsafeYamlConfig (см. этот коммит)
      • ПРИМЕЧАНИЕ: поскольку эти версии недоступны в Maven Central, существует форк, который можно использовать вместо.
    • XStream v1.4.17+ (JSON и XML) - можно использовать безопасно, пока allowlist и другие средства контроля безопасности не ослаблены (см. документацию)

    Требуют настройки перед безопасным использованием:

    Следующие библиотеки требуют установки параметров конфигурации перед безопасным использованием:

    • fastjson v1.2.68+ (JSON) - нельзя использовать безопасно без включения опции safemode, которая отключает десериализацию любого класса (см. документацию). Предыдущие версии небезопасны.
    • json-io (JSON) - нельзя использовать безопасно, поскольку использование свойства @type в JSON позволяет десериализацию любого класса. Можно использовать безопасно только в следующих ситуациях:
      • В нетипизированном режиме с настройкой JsonReader.USE_MAPS, которая отключает десериализацию общих объектов
      • С пользовательским десериализатором, контролирующим, какие классы десериализуются
    • Kryo < v5.0.0 (пользовательский формат) - нельзя использовать безопасно без включения регистрации классов, которая отключает десериализацию любого класса (см. документацию и эту проблему)
      • ПРИМЕЧАНИЕ: существуют другие обёртки вокруг Kryo, например Chill, в которых регистрация классов также может не требоваться по умолчанию, независимо от базовой версии Kryo
    • SnakeYAML (YAML) - нельзя использовать безопасно без использования класса org.yaml.snakeyaml.constructor.SafeConstructor, который отключает десериализацию любого класса (см. документацию)

    Нельзя использовать безопасно:

    Следующие библиотеки либо больше не поддерживаются, либо не могут безопасно использоваться с недоверенными входными данными:

    • Castor (XML) - похоже, заброшен, без коммитов с 2016 года
    • fastjson < v1.2.68 (JSON) - эти версии допускают десериализацию любого класса (см. документацию)
    • XMLDecoder в JDK (XML) - "почти невозможно безопасно десериализовать объекты Java в этом формате из недоверенных входных данных" ("Red Hat Defensive Coding Guide", конец раздела 2.6.5)
    • XStream < v1.4.17 (JSON и XML) - эти версии допускают десериализацию любого класса (см. документацию)
    • YamlBeans < v1.16 (YAML) - эти версии допускают десериализацию любого класса (см. этот документ)

    .Net CSharp¶

    Анализ с доступом к коду (Clear-box Review)¶

    Ищите в исходном коде следующие термины:

    1. TypeNameHandling
    2. JavaScriptTypeResolver

    Ищите сериализаторы, где тип задаётся переменной, контролируемой пользователем.

    Анализ без доступа к коду (Opaque-box Review)¶

    Ищите содержимое, закодированное в Base64, начинающееся с:

    AAEAAAD/////

    Ищите содержимое со следующим текстом:

    1. TypeObject
    2. $type:

    Общие меры предосторожности¶

    Microsoft заявила, что тип BinaryFormatter опасен и не может быть защищён. Поэтому его не следует использовать. Полные сведения в руководстве по безопасности BinaryFormatter.

    Не позволяйте потоку данных определять тип объекта, в который будет выполняться десериализация потока. Это можно предотвратить, например, используя DataContractSerializer или XmlSerializer, если это возможно.

    Если используется JSON.Net, убедитесь, что TypeNameHandling установлен только в None.

    TypeNameHandling = TypeNameHandling.None

    Если используется JavaScriptSerializer, не используйте его с JavaScriptTypeResolver.

    Если необходимо десериализовывать потоки данных, определяющие свой тип, ограничьте допустимые типы. Следует учитывать, что это всё ещё рискованно, поскольку многие нативные типы .Net потенциально опасны сами по себе. Например:

    System.IO.FileInfo

    Объекты FileInfo, ссылающиеся на файлы, реально существующие на сервере, при десериализации могут изменять их свойства, например, устанавливать права только для чтения, создавая потенциальную атаку типа "отказ в обслуживании".

    Даже если вы ограничили типы для десериализации, помните, что у некоторых типов есть рискованные свойства. Например, System.ComponentModel.DataAnnotations.ValidationException имеет свойство Value типа Object. Если этот тип разрешён для десериализации, злоумышленник может установить свойство Value для любого типа объекта.

    Злоумышленников следует предотвращать от управления типом, который будет создан. Если это возможно, даже DataContractSerializer или XmlSerializer могут быть обойдены, например:

    // Действие ниже опасно, если злоумышленник может изменить данные в базе данных
var typename = GetTransactionTypeFromDatabase();

var serializer = new DataContractJsonSerializer(Type.GetType(typename));

var obj = serializer.ReadObject(ms);

    Выполнение может произойти в рамках определённых типов .Net во время десериализации. Создание такого контроля, как показано ниже, неэффективно.

    var suspectObject = myBinaryFormatter.Deserialize(untrustedData);

//Проверка ниже слишком поздна! Выполнение уже могло произойти.
if (suspectObject is SomeDangerousObjectType)
{
    //генерировать предупреждения и утилизировать suspectObject
}

    Для JSON.Net можно создать более безопасную форму контроля allowlist с использованием пользовательского SerializationBinder.

    Старайтесь быть в курсе известных небезопасных .Net гаджетов десериализации и уделяйте особое внимание тому, где такие типы могут создаваться вашими процессами десериализации. Десериализатор может создавать экземпляры только тех типов, о которых он знает.

    Старайтесь держать любой код, который может создавать потенциальные гаджеты, отдельно от любого кода, имеющего интернет-соединение. Например, System.Windows.Data.ObjectDataProvider, используемый в WPF-приложениях, является известным гаджетом, допускающим произвольный вызов методов. Было бы рискованно иметь ссылку на эту сборку в проекте REST-сервиса, выполняющего десериализацию недоверенных данных.

    Использование альтернативных форматов данных¶

    Значительное снижение риска достигается за счёт отказа от нативных форматов (де)сериализации. Переход на чистый формат данных, такой как JSON или XML, уменьшает вероятность того, что пользовательская логика десериализации будет использована в злонамеренных целях.

    Многие приложения полагаются на шаблон объекта передачи данных, который предполагает создание отдельного домена объектов с явной целью передачи данных. Конечно, приложение всё равно может допустить ошибки безопасности после разбора чистого объекта данных.

    Десериализация только подписанных данных¶

    Если приложение знает заранее, какие сообщения нужно обработать, оно может подписывать их как часть процесса сериализации. Затем приложение может не десериализовывать сообщения, не имеющие аутентифицированной подписи.
