    Шпаргалка по предотвращению DOM Clobbering¶

    Введение¶

    DOM Clobbering — это тип атаки повторного использования кода на основе только HTML-инъекции, при которой злоумышленники вводят в заблуждение веб-приложение, внедряя HTML-элементы, чьи атрибуты id или name совпадают с именами чувствительных к безопасности переменных или браузерных API, таких как переменные для загрузки удалённого контента (например, src скриптов), замещая их значения.

    Это особенно актуально, когда внедрение скриптов невозможно, например когда оно отфильтровано HTML-санитайзерами или предотвращено запретом или контролем выполнения скриптов. В таких сценариях злоумышленники всё ещё могут внедрять не-скриптовую HTML-разметку на веб-страницы и превращать изначально безопасную разметку в исполняемый код, добиваясь XSS (межсайтового скриптинга).

    Данная шпаргалка — список рекомендаций, паттернов безопасного кодирования и практик для предотвращения или ограничения воздействия DOM Clobbering в вашем веб-приложении.

    Предпосылки¶

    Прежде чем погрузиться в DOM Clobbering, освежим некоторые базовые знания о веб.

    Когда веб-страница загружается, браузер создаёт DOM-дерево, представляющее структуру и содержимое страницы, и JavaScript-код имеет доступ на чтение и запись в это дерево.

    При создании DOM-дерева браузеры также создают атрибут для (некоторых) именованных HTML-элементов на объектах window и document. Именованными HTML-элементами являются те, у которых есть атрибут id или name. Например, разметка:

    <form id=x></a>

    приведёт к тому, что браузеры создадут ссылки на этот элемент формы через атрибут x объектов window и document:

    var obj1 = document.getElementById('x');
var obj2 = document.x;
var obj3 = document.x;
var obj4 = window.x;
var obj5 = x; // по умолчанию объекты принадлежат глобальному Window, поэтому x то же самое, что window.x
console.log(
 obj1 === obj2 && obj2 === obj3 &&
 obj3 === obj4 && obj4 === obj5
); // true

    При обращении к атрибуту объектов window и document ссылки на именованные HTML-элементы стоят перед поиском встроенных API и других атрибутов window и document, определённых разработчиками — это также известно как доступ к именованным свойствам. Разработчики, не осведомлённые о таком поведении, могут использовать содержимое атрибутов window/document для чувствительных операций, таких как URL для загрузки удалённого контента, и злоумышленники могут эксплуатировать это, внедряя разметку с конфликтующими именами. Аналогично пользовательским атрибутам/переменным, встроенные браузерные API могут быть замещены через DOM Clobbering.

    Если злоумышленники могут внедрить (не-скриптовую) HTML-разметку в DOM-дерево, это может изменить значение переменной, на которую опирается веб-приложение, из-за доступа к именованным свойствам, что приведёт к некорректной работе, раскрытию конфиденциальных данных или выполнению скриптов под управлением злоумышленника. DOM Clobbering работает, используя это (унаследованное) поведение, вызывая коллизию пространств имён между средой выполнения (объектами window и document) и JavaScript-кодом.

    Пример атаки 1¶

    let redirectTo = window.redirectTo || '/profile/';
location.assign(redirectTo);

    Злоумышленник может:

    • внедрить разметку <a id=redirectTo href='javascript:alert(1)' и получить XSS.
    • внедрить разметку <a id=redirectTo href='phishing.com' и получить открытое перенаправление.

    Пример атаки 2¶

    var script = document.createElement('script');
let src = window.config.url || 'script.js';
s.src = src;
document.body.appendChild(s);

    Злоумышленник может внедрить разметку <a id=config><a id=config name=url href='malicious.js'> для загрузки дополнительного JavaScript-кода и получить произвольное выполнение кода на стороне клиента.

    Техники снижения рисков¶

    #1: HTML-санитизация¶

    Надёжные HTML-санитайзеры могут предотвращать или ограничивать риск DOM Clobbering. Они могут делать это несколькими способами. Например:

    • полностью удалять именованные свойства, такие как id и name. Хотя это эффективно, это может снизить удобство использования, когда именованные свойства нужны для законных функций.
    • изоляция пространства имён, которая может представлять собой, например, добавление префикса к значению именованных свойств в виде постоянной строки для ограничения риска коллизий имён.
    • динамическая проверка того, коллидируют ли именованные свойства входной разметки с существующим DOM-деревом, и если это так — удаление именованных свойств входной разметки.

    OWASP рекомендует DOMPurify или Sanitizer API для HTML-санитизации.

    Санитайзер DOMPurify¶

    По умолчанию DOMPurify удаляет все коллизии подмены с встроенными API и свойствами (с помощью включённой по умолчанию опции конфигурации SANITIZE_DOM).

    Для защиты также от подмены пользовательских переменных и свойств необходимо включить конфигурацию SANITIZE_NAMED_PROPS:

    var clean = DOMPurify.sanitize(dirty, {SANITIZE_NAMED_PROPS: true});

    Это изолирует пространство имён именованных свойств и JavaScript-переменных, добавляя к ним префикс строки user-content-.

    Sanitizer API¶

    Новый Sanitizer API, встроенный в браузер, не предотвращает DOM Clobbering в своих настройках по умолчанию, но может быть настроен для удаления именованных свойств:

    const sanitizerInstance = new Sanitizer({
  blockAttributes: [
    {'name': 'id', elements: '*'},
    {'name': 'name', elements: '*'}
  ]
});
containerDOMElement.setHTML(input, {sanitizer: sanitizerInstance});

    #2: Content-Security Policy¶

    Content-Security Policy (CSP) — набор правил, определяющих браузеру, какие ресурсы разрешено загружать на веб-странице. Ограничивая источники JavaScript-файлов (например, с помощью директивы script-src), CSP может предотвратить внедрение вредоносного кода на страницу.

    Примечание: CSP может снижать риски только некоторых вариантов атак DOM Clobbering, например когда злоумышленники пытаются загрузить новые скрипты путём замены источников скриптов, но не тогда, когда уже присутствующий код может быть использован для выполнения кода, например при замене параметров конструкций вычисления кода, таких как eval().

    #3: Замораживание чувствительных DOM-объектов¶

    Простым способом снижения рисков DOM Clobbering для отдельных объектов может быть замораживание чувствительных DOM-объектов и их свойств, например с помощью метода Object.freeze().

    Примечание: Замораживание свойств объектов предотвращает их перезапись именованными DOM-элементами. Однако определение всех объектов и свойств объектов, которые необходимо заморозить, может оказаться непростой задачей, что ограничивает полезность этого подхода.

    Рекомендации по безопасному кодированию¶

    DOM Clobbering можно избежать с помощью защитного программирования и соблюдения нескольких паттернов и рекомендаций по кодированию.

    #4: Валидируйте все входные данные в DOM-дерево¶

    Перед вставкой любой разметки в DOM-дерево веб-страницы санитизируйте атрибуты id и name (см. HTML-санитизацию).

    #5: Используйте явные объявления переменных¶

    При инициализации переменных всегда используйте декларатор переменной, такой как var, let или const, что предотвращает подмену переменной.

    Примечание: Объявление переменной с помощью let не создаёт свойство на window, в отличие от var. Поэтому window.VARNAME всё равно может быть подменено (при условии, что VARNAME — имя переменной).

    #6: Не используйте Document и Window для глобальных переменных¶

    Избегайте использования объектов, таких как document и window, для хранения глобальных переменных, поскольку ими легко манипулировать (см., например, здесь).

    #7: Не доверяйте встроенным API Document без валидации¶

    Свойства Document, включая встроенные, всегда замещаются DOM Clobbering, даже сразу после присвоения им значения.

    Подсказка: Это связано с так называемым алгоритмом видимости именованных свойств, где ссылки на именованные HTML-элементы стоят перед поиском встроенных API и других атрибутов на document.

    #8: Обеспечьте проверку типов¶

    Всегда проверяйте тип свойств document и window перед использованием в чувствительных операциях, например с помощью оператора instanceof.

    Подсказка: Когда объект подменяется, он ссылается на экземпляр Element, который может быть не ожидаемым типом.

    #9: Используйте строгий режим¶

    Используйте строгий режим (strict), чтобы предотвратить непреднамеренное создание глобальных переменных и генерировать ошибку при попытке перезаписи свойств только для чтения.

    #10: Применяйте определение возможностей браузера¶

    Вместо того чтобы полагаться на специфические функции или свойства браузера, используйте определение возможностей, чтобы проверить, поддерживается ли функция, прежде чем её использовать. Это поможет предотвратить ошибки и DOM Clobbering, которые могут возникнуть при использовании этих функций в неподдерживаемых браузерах.

    Подсказка: Неподдерживаемые API возможностей могут выступать как неопределённая переменная/свойство в неподдерживаемых браузерах, делая их уязвимыми для подмены.

    #11: Ограничивайте переменные локальной областью видимости¶

    Глобальные переменные более подвержены перезаписи через DOM Clobbering. По возможности используйте локальные переменные и свойства объектов.

    #12: Используйте уникальные имена переменных в продуктивной среде¶

    Использование уникальных имён переменных может помочь предотвратить коллизии имён, которые могут приводить к случайным перезаписям.

    #13: Используйте техники ООП, такие как инкапсуляция¶

    Инкапсуляция переменных и функций внутри объектов или классов помогает предотвратить их перезапись. Сделав их приватными, к ним нельзя получить доступ извне объекта, что делает их менее уязвимыми для DOM Clobbering.
