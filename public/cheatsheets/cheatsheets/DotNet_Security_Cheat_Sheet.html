    Памятка по безопасности DotNet¶

    Введение¶

    Эта страница содержит краткие базовые советы по безопасности .NET для разработчиков.

    .NET Framework¶

    .NET Framework — основная платформа Microsoft для корпоративной разработки. Это поддерживающий API для ASP.NET, настольных приложений Windows, служб Windows Communication Foundation, SharePoint, Visual Studio Tools for Office и других технологий.

    .NET Framework представляет собой набор API, обеспечивающих использование продвинутой системы типов, управление данными, графикой, сетью, файловыми операциями и многим другим — охватывая практически все требования к разработке корпоративных приложений в экосистеме Microsoft. Это почти повсеместно используемая библиотека со строгой именовкой и версионированием на уровне сборки.

    Обновление Framework¶

    .NET Framework обновляется Microsoft через службу Windows Update. Разработчикам, как правило, не нужно выполнять отдельные обновления Framework. Windows Update доступен по адресу Windows Update или через программу Windows Update на компьютере с Windows.

    Отдельные фреймворки можно поддерживать в актуальном состоянии с помощью NuGet. Поскольку Visual Studio запрашивает обновления, включите это в свой жизненный цикл разработки.

    Помните, что сторонние библиотеки нужно обновлять отдельно, и не все из них используют NuGet. Например, ELMAH требует отдельных усилий по обновлению.

    Уведомления безопасности¶

    Получайте уведомления безопасности, нажав кнопку "Watch" в следующих репозиториях:

    • Уведомления безопасности .NET Core
    • Уведомления безопасности ASP.NET Core и Entity Framework Core

    Общие рекомендации по .NET¶

    Этот раздел содержит общие рекомендации для приложений .NET. Они применимы ко всем приложениям .NET, включая ASP.NET, WPF, WinForms и другие.

    OWASP Top 10 перечисляет наиболее распространённые и опасные угрозы веб-безопасности в современном мире и пересматривается каждые несколько лет с обновлением данных об актуальных угрозах. Этот раздел памятки основан на данном списке. Подход к обеспечению безопасности веб-приложения следует начинать с верхней угрозы A1 и двигаться вниз; это гарантирует наиболее эффективное использование времени, уделённого безопасности: сначала закрываются главные угрозы, затем — менее значимые. После покрытия Top 10 в целом рекомендуется оценить другие угрозы или заказать профессиональный тест на проникновение.

    A01 Нарушение контроля доступа¶

    Слабое управление учётными записями¶

    Убедитесь, что cookie передаются с флагом HttpOnly, чтобы клиентские скрипты не могли получить доступ к cookie:

    CookieHttpOnly = true,

    Сократите период, в течение которого может быть украдена сессия, уменьшив таймаут сессии и отключив скользящее истечение:

    Решение о применении скользящего истечения зависит от модели угроз вашего приложения. Установка SlidingExpiration в false обеспечивает абсолютный срок жизни сессии, что ограничивает время повторного использования украденной сессии за счёт снижения удобства для долгосрочных интерактивных сессий. Для некоторых приложений включение скользящего истечения (true) может быть предпочтительным с точки зрения удобства пользователя, так как сессия остаётся активной пока пользователь активен. Это удобство сопряжено с повышенным риском при компрометации сессии.

    ExpireTimeSpan = TimeSpan.FromMinutes(60),
SlidingExpiration = false

    Полный пример кода запуска смотрите здесь.

    Убедитесь, что cookie передаются только по HTTPS в продакшне. Это должно быть закреплено в трансформациях конфигурации:

    <httpCookies requireSSL="true" />
<authentication>
    <forms requireSSL="true" />
</authentication>

    Защитите методы входа, регистрации и сброса пароля от атак перебором, ограничивая частоту запросов (см. код ниже). Рассмотрите также использование ReCaptcha.

    [HttpPost]
[AllowAnonymous]
[ValidateAntiForgeryToken]
[AllowXRequestsEveryXSecondsAttribute(Name = "LogOn",
Message = "You have performed this action more than {x} times in the last {n} seconds.",
Requests = 3, Seconds = 60)]
public async Task<ActionResult> LogOn(LogOnViewModel model, string returnUrl)

    НЕ ДЕЛАЙТЕ: Реализуйте собственную аутентификацию или управление сессиями. Используйте ту, что предоставляет .NET.

    НЕ ДЕЛАЙТЕ: Сообщайте пользователю, существует ли аккаунт при входе, регистрации или сбросе пароля. Говорите что-то вроде «Имя пользователя или пароль неверны» или «Если этот аккаунт существует, токен сброса будет отправлен на зарегистрированный адрес электронной почты». Это защищает от перечисления аккаунтов.

    Ответ пользователю должен быть одинаковым независимо от того, существует аккаунт или нет, — как по содержанию, так и по поведению. Например, если ответ занимает на 50% больше времени для реальных аккаунтов, информацию о членстве можно угадать и проверить.

    Отсутствие контроля доступа на уровне функций¶

    ДЕЛАЙТЕ: Авторизуйте пользователей на всех внешних конечных точках. .NET framework предоставляет множество способов авторизации пользователя, используйте их на уровне метода:

    [Authorize(Roles = "Admin")]
[HttpGet]
public ActionResult Index(int page = 1)

    или, что ещё лучше, на уровне контроллера:

    [Authorize]
public class UserController

    Вы также можете проверять роли в коде, используя функции идентификации в .NET: System.Web.Security.Roles.IsUserInRole(userName, roleName)

    Дополнительную информацию можно найти в Памятке по авторизации и Памятке по автоматизации тестирования авторизации.

    Небезопасные прямые ссылки на объекты¶

    Когда у вас есть ресурс (объект), к которому можно получить доступ по ссылке (в примере ниже это id), необходимо убедиться, что пользователь действительно должен иметь доступ к этому ресурсу.

    // Небезопасно
public ActionResult Edit(int id)
{
  var user = _context.Users.FirstOrDefault(e => e.Id == id);
  return View("Details", new UserViewModel(user);
}

// Безопасно
public ActionResult Edit(int id)
{
  var user = _context.Users.FirstOrDefault(e => e.Id == id);
  // Проверяем, что пользователь имеет право редактировать эти данные
  if (user.Id != _userIdentity.GetUserId())
  {
        HandleErrorInfo error = new HandleErrorInfo(
            new Exception("INFO: You do not have permission to edit these details"));
        return View("Error", error);
  }
  return View("Edit", new UserViewModel(user);
}

    Дополнительную информацию можно найти в Памятке по предотвращению небезопасных прямых ссылок на объекты.

    A02 Криптографические сбои¶

    Общие рекомендации по криптографии¶

    • Никогда, ни при каких обстоятельствах не пишите собственные криптографические функции.
    • По возможности избегайте написания любого криптографического кода вообще. Вместо этого попробуйте использовать готовые решения для управления секретами или решение, предоставляемое вашим облачным провайдером. Для получения дополнительной информации см. Памятку OWASP по управлению секретами.
    • Если вы не можете использовать готовое решение для управления секретами, попробуйте использовать проверенную и хорошо известную библиотеку реализации, а не библиотеки, встроенные в .NET, так как с ними слишком легко допустить криптографические ошибки.
    • Убедитесь, что ваше приложение или протокол может легко поддерживать будущую смену криптографических алгоритмов.

    Хэширование¶

    ДЕЛАЙТЕ: Используйте надёжный алгоритм хэширования.

    • В .NET (Framework и Core) наиболее надёжным алгоритмом хэширования для общих требований является System.Security.Cryptography.SHA512.
    • В .NET Framework 4.6 и более ранних версиях наиболее надёжным алгоритмом для хэширования паролей является PBKDF2, реализованный как System.Security.Cryptography.Rfc2898DeriveBytes.
    • В .NET Framework 4.6.1 и более поздних версиях и .NET Core наиболее надёжным алгоритмом для хэширования паролей является PBKDF2, реализованный как Microsoft.AspNetCore.Cryptography.KeyDerivation.Pbkdf2, который имеет несколько существенных преимуществ перед Rfc2898DeriveBytes.
    • При использовании функции хэширования для хэширования неуникальных входных данных, таких как пароли, добавляйте значение соли к исходному значению перед хэшированием.
    • Обратитесь к Памятке по хранению паролей для получения дополнительной информации.

    Пароли¶

    ДЕЛАЙТЕ: Применяйте политику паролей с минимальной сложностью, выдерживающей атаку по словарю, то есть более длинные пароли, использующие полный набор символов (цифры, спецсимволы и буквы) для увеличения энтропии.

    Шифрование¶

    ДЕЛАЙТЕ: Используйте надёжный алгоритм шифрования, например AES-512, там, где персональные данные необходимо восстановить в исходном формате.

    ДЕЛАЙТЕ: Защищайте ключи шифрования лучше, чем любые другие активы. Дополнительную информацию о хранении ключей шифрования в состоянии покоя можно найти в Памятке по управлению ключами.

    ДЕЛАЙТЕ: Используйте TLS 1.2+ для всего сайта. Получите бесплатный сертификат на LetsEncrypt.org и автоматизируйте продление.

    НЕ ДЕЛАЙТЕ: Разрешайте SSL — этот протокол уже устарел.

    ДЕЛАЙТЕ: Придерживайтесь строгой политики TLS (см. Лучшие практики SSL), везде, где возможно, используйте TLS 1.2+. Затем проверьте конфигурацию с помощью SSL Test или TestSSL.

    Дополнительную информацию о защите транспортного уровня можно найти в Памятке по безопасности транспортного уровня.

    ДЕЛАЙТЕ: Убедитесь, что заголовки не раскрывают информацию о вашем приложении. См. HttpHeaders.cs, Dionach StripHeaders, отключите через web.config или Startup.cs.

    Пример Web.config

    <system.web>
    <httpRuntime enableVersionHeader="false"/>
</system.web>
<system.webServer>
    <security>
        <requestFiltering removeServerHeader="true" />
    </security>
    <httpProtocol>
        <customHeaders>
            <add name="X-Content-Type-Options" value="nosniff" />
            <add name="X-Frame-Options" value="DENY" />
            <add name="X-Permitted-Cross-Domain-Policies" value="master-only"/>
            <add name="X-XSS-Protection" value="0"/>
            <remove name="X-Powered-By"/>
        </customHeaders>
    </httpProtocol>
</system.webServer>

    Пример Startup.cs

    app.UseHsts(hsts => hsts.MaxAge(365).IncludeSubdomains());
app.UseXContentTypeOptions();
app.UseReferrerPolicy(opts => opts.NoReferrer());
app.UseXXssProtection(options => options.FilterDisabled());
app.UseXfo(options => options.Deny());

app.UseCsp(opts => opts
 .BlockAllMixedContent()
 .StyleSources(s => s.Self())
 .StyleSources(s => s.UnsafeInline())
 .FontSources(s => s.Self())
 .FormActions(s => s.Self())
 .FrameAncestors(s => s.Self())
 .ImageSources(s => s.Self())

 );

    Шифрование для хранения¶

    • Используйте Windows Data Protection API (DPAPI) для безопасного локального хранения конфиденциальных данных.
    • Там, где DPAPI использовать невозможно, следуйте рекомендациям по алгоритмам в Памятке OWASP по криптографическому хранению.

    Следующий фрагмент кода демонстрирует пример использования AES-GCM для выполнения шифрования/дешифрования данных. Настоятельно рекомендуется привлечь эксперта по криптографии для проверки окончательного дизайна и кода, так как даже самая незначительная ошибка может серьёзно ослабить шифрование.

    Код основан на примере отсюда: https://www.scottbrady91.com/c-sharp/aes-gcm-dotnet

    Несколько ограничений/подводных камней этого кода:

    • Он не учитывает ротацию ключей или управление ими, что само по себе является отдельной темой.
    • Важно использовать разный nonce для каждой операции шифрования, даже если используется один и тот же ключ.
    • Ключ необходимо хранить в безопасном месте.
    Нажмите здесь, чтобы просмотреть фрагмент кода «Симметричное шифрование AES-GCM». 
    // Код основан на примере отсюда:
// https://www.scottbrady91.com/c-sharp/aes-gcm-dotnet

public class AesGcmSimpleTest
{
    public static void Main()
    {

        // Ключ длиной 32 байта / 256 бит для AES
        var key = new byte[32];
        RandomNumberGenerator.Fill(key);

        // MaxSize = 12 байт / 96 бит, и этот размер следует использовать всегда.
        var nonce = new byte[AesGcm.NonceByteSizes.MaxSize];
        RandomNumberGenerator.Fill(nonce);

        // Тег для аутентифицированного шифрования
        var tag = new byte[AesGcm.TagByteSizes.MaxSize];

        var message = "This message to be encrypted";
        Console.WriteLine(message);

        // Зашифровать сообщение
        var cipherText = AesGcmSimple.Encrypt(message, nonce, out tag, key);
        Console.WriteLine(Convert.ToBase64String(cipherText));

        // Расшифровать сообщение
        var message2 = AesGcmSimple.Decrypt(cipherText, nonce, tag, key);
        Console.WriteLine(message2);


    }
}


public static class AesGcmSimple
{

    public static byte[] Encrypt(string plaintext, byte[] nonce, out byte[] tag, byte[] key)
    {
        using(var aes = new AesGcm(key))
        {
            // Тег для аутентифицированного шифрования
            tag = new byte[AesGcm.TagByteSizes.MaxSize];

            // Создать массив байт из шифруемого сообщения
            var plaintextBytes = Encoding.UTF8.GetBytes(plaintext);

            // Шифртекст будет той же длины в байтах, что и открытый текст
            var ciphertext = new byte[plaintextBytes.Length];

            // Выполнить само шифрование
            aes.Encrypt(nonce, plaintextBytes, ciphertext, tag);
            return ciphertext;
        }
    }

    public static string Decrypt(byte[] ciphertext, byte[] nonce, byte[] tag, byte[] key)
    {
        using(var aes = new AesGcm(key))
        {
            // Открытый текст будет той же длины в байтах, что и шифртекст
            var plaintextBytes = new byte[ciphertext.Length];

            // Выполнить само дешифрование
            aes.Decrypt(nonce, ciphertext, tag, plaintextBytes);

            return Encoding.UTF8.GetString(plaintextBytes);
        }
    }
}

    Шифрование для передачи¶

    Следующий фрагмент кода демонстрирует пример использования Elliptic Curve/Diffie Hellman (ECDH) совместно с AES-GCM для выполнения шифрования/дешифрования данных между двумя сторонами без необходимости передавать симметричный ключ между ними. Вместо этого стороны обмениваются публичными ключами и могут использовать ECDH для генерации общего секрета, который можно использовать для симметричного шифрования.

    Снова настоятельно рекомендуется привлечь эксперта по криптографии для проверки окончательного дизайна и кода.

    Обратите внимание, что этот образец кода опирается на класс AesGcmSimple из предыдущего раздела.

    Несколько ограничений/подводных камней этого кода:

    • Он не учитывает ротацию ключей или управление ими.
    • Код намеренно обеспечивает новый nonce для каждой операции шифрования, но им нужно управлять как отдельным элементом данных наряду с шифртекстом.
    • Приватные ключи необходимо хранить в безопасном месте.
    • Код не рассматривает проверку публичных ключей перед использованием.
    • В целом, код не предусматривает проверку подлинности между двумя сторонами.
    Нажмите здесь, чтобы просмотреть фрагмент кода «Асимметричное шифрование ECDH». 
    public class ECDHSimpleTest
{
    public static void Main()
    {
        // Генерируем пару ECC ключей для Alice
        var alice = new ECDHSimple();
        byte[] alicePublicKey = alice.PublicKey;

        // Генерируем пару ECC ключей для Bob
        var bob = new ECDHSimple();
        byte[] bobPublicKey = bob.PublicKey;

        string plaintext = "Hello, Bob! How are you?";
        Console.WriteLine("Secret being sent from Alice to Bob: " + plaintext);

        // Обратите внимание, что новый nonce генерируется при каждой операции шифрования
        // в соответствии с моделью безопасности AES GCM
        byte[] tag;
        byte[] nonce;
        var cipherText = alice.Encrypt(bobPublicKey, plaintext, out nonce, out tag);
        Console.WriteLine("Ciphertext, nonce, and tag being sent from Alice to Bob: " + Convert.ToBase64String(cipherText) + " " + Convert.ToBase64String(nonce) + " " + Convert.ToBase64String(tag));

        var decrypted = bob.Decrypt(alicePublicKey, cipherText, nonce, tag);
        Console.WriteLine("Secret received by Bob from Alice: " + decrypted);

        Console.WriteLine();

        string plaintext2 = "Hello, Alice! I'm good, how are you?";
        Console.WriteLine("Secret being sent from Bob to Alice: " + plaintext2);

        byte[] tag2;
        byte[] nonce2;
        var cipherText2 = bob.Encrypt(alicePublicKey, plaintext2, out nonce2, out tag2);
        Console.WriteLine("Ciphertext, nonce, and tag being sent from Bob to Alice: " + Convert.ToBase64String(cipherText2) + " " + Convert.ToBase64String(nonce2) + " " + Convert.ToBase64String(tag2));

        var decrypted2 = alice.Decrypt(bobPublicKey, cipherText2, nonce2, tag2);
        Console.WriteLine("Secret received by Alice from Bob: " + decrypted2);
    }
}


public class ECDHSimple
{

    private ECDiffieHellmanCng ecdh = new ECDiffieHellmanCng();

    public byte[] PublicKey
    {
        get
        {
            return ecdh.PublicKey.ToByteArray();
        }
    }

    public byte[] Encrypt(byte[] partnerPublicKey, string message, out byte[] nonce, out byte[] tag)
    {
        // Генерируем AES ключ и Nonce
        var aesKey = GenerateAESKey(partnerPublicKey);

        // Тег для аутентифицированного шифрования
        tag = new byte[AesGcm.TagByteSizes.MaxSize];

        // MaxSize = 12 байт / 96 бит, и этот размер следует использовать всегда.
        // Новый nonce генерируется при каждой операции шифрования в соответствии
        // с моделью безопасности AES GCM
        nonce = new byte[AesGcm.NonceByteSizes.MaxSize];
        RandomNumberGenerator.Fill(nonce);

        // Возвращаем зашифрованное значение
        return AesGcmSimple.Encrypt(message, nonce, out tag, aesKey);
    }


    public string Decrypt(byte[] partnerPublicKey, byte[] ciphertext, byte[] nonce, byte[] tag)
    {
        // Генерируем AES ключ и Nonce
        var aesKey = GenerateAESKey(partnerPublicKey);

        // Возвращаем расшифрованное значение
        return AesGcmSimple.Decrypt(ciphertext, nonce, tag, aesKey);
    }

    private byte[] GenerateAESKey(byte[] partnerPublicKey)
    {
        // Получаем секрет на основе приватного ключа этой стороны и публичного ключа другой стороны
        byte[] secret = ecdh.DeriveKeyMaterial(CngKey.Import(partnerPublicKey, CngKeyBlobFormat.EccPublicBlob));

        byte[] aesKey = new byte[32]; // 256-битный ключ AES
        Array.Copy(secret, 0, aesKey, 0, 32); // Копируем первые 32 байта в качестве ключа

        return aesKey;
    }
}

    A03 Инъекции¶

    SQL Injection¶

    ДЕЛАЙТЕ: Использование объектно-реляционного маппера (ORM) или хранимых процедур — наиболее эффективный способ защиты от уязвимости SQL Injection.

    ДЕЛАЙТЕ: Используйте параметризованные запросы там, где необходимо использовать прямой SQL-запрос. Дополнительную информацию можно найти в Памятке по параметризации запросов.

    Например, с использованием Entity Framework:

    var sql = @"Update [User] SET FirstName = @FirstName WHERE Id = @Id";
context.Database.ExecuteSqlCommand(
    sql,
    new SqlParameter("@FirstName", firstname),
    new SqlParameter("@Id", id));

    НЕ ДЕЛАЙТЕ: Конкатенируйте строки где угодно в коде и выполняйте их против базы данных (известно как динамический SQL).

    Примечание: С ORM или хранимыми процедурами это всё равно можно случайно сделать, поэтому проверяйте везде. Например:

    string sql = "SELECT * FROM Users WHERE UserName='" + txtUser.Text + "' AND Password='"
                + txtPassword.Text + "'";
context.Database.ExecuteSqlCommand(sql); // Уязвимость SQL Injection!

    ДЕЛАЙТЕ: Применяйте принцип наименьших привилегий — подключайтесь к базе данных, используя учётную запись с минимальным набором разрешений, необходимых для её работы, а не учётную запись администратора базы данных.

    OS Injection¶

    Общие рекомендации по OS Injection можно найти в Памятке по защите от инъекций OS-команд.

    ДЕЛАЙТЕ: Используйте System.Diagnostics.Process.Start для вызова функций базовой ОС.

    Например:

    var process = new System.Diagnostics.Process();
var startInfo = new System.Diagnostics.ProcessStartInfo();
startInfo.FileName = "validatedCommand";
startInfo.Arguments = "validatedArg1 validatedArg2 validatedArg3";
process.StartInfo = startInfo;
process.Start();

    НЕ ДЕЛАЙТЕ: Предполагайте, что этот механизм защитит от вредоносного ввода, разработанного для выхода из одного аргумента и последующего изменения другого аргумента процесса. Это по-прежнему возможно.

    ДЕЛАЙТЕ: Применяйте валидацию с использованием белых списков ко всем пользовательским данным везде, где это возможно. Валидация ввода предотвращает попадание неправильно оформленных данных в информационную систему. Дополнительную информацию см. в Памятке по валидации ввода.

  // Отображаем адрес в стандартной нотации.
  return address.ToString();
 }
 else
 {
  //ipAddress не является типом IPAddress
  ...
 }
    ...
}

    ДЕЛАЙТЕ: Старайтесь принимать только простые буквенно-цифровые символы.

    НЕ ДЕЛАЙТЕ: Предполагайте, что можно обеззаразить специальные символы, не удаляя их фактически. Различные комбинации \, ' и @ могут неожиданно повлиять на попытки обеззараживания.

    НЕ ДЕЛАЙТЕ: Полагайтесь на методы без гарантии безопасности.

    Например, .NET Core 2.2 и выше, и .NET 5 и выше поддерживают ProcessStartInfo.ArgumentList, который выполняет некоторое экранирование символов, но объект включает предупреждение о небезопасности с ненадёжными входными данными.

    ДЕЛАЙТЕ: Рассмотрите альтернативы передаче необработанных ненадёжных аргументов через параметры командной строки, например кодирование с помощью Base64 (которое безопасно закодирует любые специальные символы), а затем декодирование параметров в принимающем приложении.

    LDAP injection¶

    Практически любые символы могут использоваться в Distinguished Names. Однако некоторые из них необходимо экранировать с помощью обратного слеша \. Таблицу символов, которые следует экранировать для Active Directory, можно найти в Памятке по предотвращению LDAP Injection.

    Примечание: Пробел необходимо экранировать только в том случае, если он является первым или последним символом в имени компонента, например в Common Name. Внутренние пробелы экранировать не нужно.

    • При использовании SQL Server предпочитайте интегрированную аутентификацию вместо SQL-аутентификации.
    • Используйте Always Encrypted там, где это возможно, для конфиденциальных данных (SQL Server 2016+ и Azure SQL)

    Если вы не используете Viewstate, обратитесь к главной странице по умолчанию шаблона ASP.NET Web Forms для получения ручного anti-CSRF токена с использованием двойной отправки cookie.

    private const string AntiXsrfTokenKey = "__AntiXsrfToken";
private const string AntiXsrfUserNameKey = "__AntiXsrfUserName";
private string _antiXsrfTokenValue;
protected void Page_Init(object sender, EventArgs e)
{
    // Код ниже помогает защититься от XSRF-атак
    var requestCookie = Request.Cookies[AntiXsrfTokenKey];
    Guid requestCookieGuidValue;
    if (requestCookie != null && Guid.TryParse(requestCookie.Value, out requestCookieGuidValue))
    {
       // Используем Anti-XSRF токен из cookie
       _antiXsrfTokenValue = requestCookie.Value;
       Page.ViewStateUserKey = _antiXsrfTokenValue;
    }
    else
    {
       // Генерируем новый Anti-XSRF токен и сохраняем в cookie
       _antiXsrfTokenValue = Guid.NewGuid().ToString("N");
       Page.ViewStateUserKey = _antiXsrfTokenValue;
       var responseCookie = new HttpCookie(AntiXsrfTokenKey)
       {
          HttpOnly = true,
          Value = _antiXsrfTokenValue
       };
       if (FormsAuthentication.RequireSSL && Request.IsSecureConnection)
       {
          responseCookie.Secure = true;
       }
       Response.Cookies.Set(responseCookie);
    }
    Page.PreLoad += master_Page_PreLoad;
}
protected void master_Page_PreLoad(object sender, EventArgs e)
{
    if (!IsPostBack)
    {
       // Устанавливаем Anti-XSRF токен
       ViewState[AntiXsrfTokenKey] = Page.ViewStateUserKey;
       ViewState[AntiXsrfUserNameKey] = Context.User.Identity.Name ?? String.Empty;
    }
    else
    {
       // Проверяем Anti-XSRF токен
       if ((string)ViewState[AntiXsrfTokenKey] != _antiXsrfTokenValue ||
          (string)ViewState[AntiXsrfUserNameKey] != (Context.User.Identity.Name ?? String.Empty))
       {
          throw new InvalidOperationException("Validation of Anti-XSRF token failed.");
       }
    }
}

    Валидация и кодирование HTTP¶

    • Не отключайте validateRequest в web.config или в настройках страницы.     • Версия 4.5 .NET Framework включает библиотеку AntiXssEncoder, которая содержит исчерпывающую библиотеку кодирования ввода для предотвращения XSS. Используйте её.

    • Проверяйте формат URI с помощью Uri.IsWellFormedUriString.

    Аутентификация через формы¶

    • По возможности используйте cookie для постоянства. Аутентификация без cookie по умолчанию будет использовать UseDeviceProfile.
    • Не доверяйте URI запроса для постоянства сессии или авторизации. Его можно легко подделать.
    • Уменьшите таймаут Forms Authentication с 20 минут по умолчанию до кратчайшего периода, подходящего для вашего приложения. Если используется slidingExpiration, этот таймаут сбрасывается после каждого запроса, поэтому активные пользователи не пострадают.
    • Если HTTPS не используется, slidingExpiration следует отключить. Рассмотрите отключение slidingExpiration даже при использовании HTTPS.
    • Всегда реализуйте надлежащий контроль доступа.
      • Сравнивайте имя пользователя, предоставленное пользователем, с User.Identity.Name.
      • Проверяйте роли по User.Identity.IsInRole.
    • Используйте провайдер членства ASP.NET и провайдер ролей, но проверяйте хранение паролей. Хранилище по умолчанию хэширует пароль с одной итерацией SHA-1, что является довольно слабым. Шаблон ASP.NET MVC4 использует ASP.NET Identity вместо ASP.NET Membership, а ASP.NET Identity по умолчанию использует PBKDF2, что лучше. Для получения дополнительной информации ознакомьтесь с Памяткой OWASP по хранению паролей.
    • Явно авторизуйте запросы ресурсов.
    • Используйте авторизацию на основе ролей через User.Identity.IsInRole.

    • По возможности используйте частичное доверие. Частично доверенные Windows-приложения уменьшают поверхность атаки приложения. Ведите список разрешений, которые должно использовать ваше приложение, и которые оно может использовать, а затем делайте запрос на эти разрешения декларативно во время выполнения.
    • Используйте развёртывание ClickOnce. Для расширенных разрешений используйте повышение привилегий во время выполнения или развёртывание доверенных приложений во время установки.

    Руководство по WCF¶

    • Имейте в виду, что единственный безопасный способ передачи запроса в RESTful-сервисах — через HTTP POST с включённым TLS. Использование HTTP GET требует помещения данных в URL (например, в строку запроса), которая видна пользователю и будет записана и сохранена в истории его браузера.
    • Избегайте BasicHttpBinding. У него нет конфигурации безопасности по умолчанию. Вместо него используйте WSHttpBinding.
    • Используйте как минимум два режима безопасности для вашей привязки. Message security включает положения безопасности в заголовках. Transport security означает использование SSL. TransportWithMessageCredential сочетает оба.
    • Тестируйте вашу реализацию WCF с помощью фаззера, например ZAP.
