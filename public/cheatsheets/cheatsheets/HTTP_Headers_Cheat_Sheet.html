    Шпаргалка по HTTP-заголовкам безопасности ответов¶

    Введение¶

    HTTP-заголовки — отличный инструмент повышения веб-безопасности, простой в реализации. Правильные заголовки HTTP-ответов помогают предотвращать уязвимости безопасности, такие как межсайтовый скриптинг, кликджекинг, раскрытие информации и многое другое.

    В этой шпаргалке мы рассмотрим все HTTP-заголовки, связанные с безопасностью, рекомендуемые конфигурации и ссылки на другие источники для сложных заголовков.

    Заголовки безопасности¶

    X-Frame-Options¶

    HTTP-заголовок ответа X-Frame-Options может использоваться для указания, должен ли браузер разрешать отображение страницы в <frame>, <iframe>, <embed> или <object>. Сайты могут использовать это для защиты от атак кликджекинга, гарантируя, что их контент не встраивается в другие сайты.

    Директива frame-ancestors политики Content Security Policy (CSP) устаревает X-Frame-Options для поддерживающих браузеров (источник).

    Заголовок X-Frame-Options полезен только тогда, когда HTTP-ответ, в котором он включён, содержит что-то для взаимодействия (например, ссылки, кнопки). Если HTTP-ответ является перенаправлением или API, возвращающим данные JSON, X-Frame-Options не обеспечивает никакой безопасности.

    Рекомендация¶

    По возможности используйте директиву frame-ancestors политики Content Security Policy (CSP).

    Запретить отображение страницы в фрейме.

    X-Frame-Options: DENY

    X-XSS-Protection¶

    HTTP-заголовок ответа X-XSS-Protection — функция Internet Explorer, Chrome и Safari, которая останавливает загрузку страниц при обнаружении отражённых атак межсайтового скриптинга (XSS).

    ВНИМАНИЕ: Несмотря на то что этот заголовок может защищать пользователей более старых браузеров, ещё не поддерживающих CSP, в некоторых случаях он может создавать уязвимости XSS на иначе безопасных сайтах (источник).

    Рекомендация¶

    Используйте Content Security Policy (CSP), отключающую использование встроенного JavaScript.

    Не устанавливайте этот заголовок или явно отключите его.

    X-XSS-Protection: 0

    Подробности см. в документации Mozilla X-XSS-Protection.

    X-Content-Type-Options¶

    HTTP-заголовок ответа X-Content-Type-Options используется сервером для указания браузерам следовать MIME-типам, объявленным в заголовках Content-Type, а не угадывать их.

    Этот заголовок используется для блокировки сниффинга MIME-типов браузерами, который может преобразовывать невыполняемые MIME-типы в выполняемые (атаки MIME Confusion).

    Рекомендация¶

    Правильно устанавливайте заголовок Content-Type на всём сайте.

    X-Content-Type-Options: nosniff

    Referrer-Policy¶

    HTTP-заголовок Referrer-Policy контролирует, сколько информации о реферере (отправляемой через заголовок Referer) должно включаться в запросы.

    Рекомендация¶

    Политика реферера поддерживается браузерами с 2014 года. Сегодня поведение по умолчанию в современных браузерах заключается в том, чтобы больше не отправлять всю информацию о реферере (источник, путь и строку запроса) на тот же сайт, а отправлять только источник на другие сайты. Однако, поскольку не все пользователи могут использовать последние версии браузеров, мы рекомендуем принудительно устанавливать это поведение, отправляя этот заголовок во всех ответах.

    Referrer-Policy: strict-origin-when-cross-origin

    • ПРИМЕЧАНИЕ: Подробнее о настройке этого заголовка см. в документации Mozilla Referrer-Policy.

    Content-Type¶

    Заголовок представления Content-Type используется для указания исходного медиатипа ресурса (до применения какого-либо кодирования содержимого для отправки). Если он не установлен корректно, ресурс (например, изображение) может интерпретироваться как HTML, что делает возможными уязвимости XSS.

    Хотя рекомендуется всегда правильно устанавливать заголовок Content-Type, это является уязвимостью только в случае, если содержимое предназначено для отображения клиентом и ресурс является ненадёжным (предоставлен или изменён пользователем).

    Рекомендация¶

    Content-Type: text/html; charset=UTF-8

    • ПРИМЕЧАНИЕ: атрибут charset необходим для предотвращения XSS в HTML-страницах
    • ПРИМЕЧАНИЕ: Content-Type может быть любым из возможных MIME-типов

    Set-Cookie¶

    HTTP-заголовок ответа Set-Cookie используется для отправки cookie с сервера пользовательскому агенту, чтобы пользовательский агент мог отправить его обратно на сервер позже. Для отправки нескольких cookie в одном ответе следует отправить несколько заголовков Set-Cookie.

    Сам по себе это не заголовок безопасности, но его атрибуты безопасности имеют решающее значение.

    Рекомендация¶

    • Подробное объяснение параметров конфигурации cookie см. в Шпаргалке по управлению сессиями.

    Strict-Transport-Security (HSTS)¶

    HTTP-заголовок ответа Strict-Transport-Security (часто сокращается как HSTS) предписывает браузерам обращаться к сайту только через HTTPS, даже если пользователь пытается подключиться через HTTP.

    Рекомендация¶

    Strict-Transport-Security: max-age=63072000; includeSubDomains; preload

    • ПРИМЕЧАНИЕ: Внимательно изучите, как работает этот заголовок, прежде чем его использовать. Если заголовок HSTS неправильно настроен или если возникла проблема с используемым SSL/TLS-сертификатом, легитимные пользователи могут не иметь доступа к сайту. Например, если заголовок HSTS установлен на очень длительный срок, а SSL/TLS-сертификат истекает или отзывается, легитимные пользователи могут не иметь доступа к сайту до истечения срока действия заголовка HSTS.

    Подробнее см. в Шпаргалке по HTTP Strict Transport Security.

    Expect-CT ❌¶

    Заголовок Expect-CT позволяет сайтам включить отчётность о требованиях Certificate Transparency (CT). Поскольку современные клиенты теперь требуют квалификации CT, единственной оставшейся ценностью является отчётность о таких случаях в указанное значение report-uri в заголовке. Теперь заголовок меньше связан с применением и больше с обнаружением/отчётностью.

    Рекомендация¶

    Не используйте его. Mozilla рекомендует избегать его и по возможности удалять из существующего кода.

    Content-Security-Policy (CSP)¶

    Content Security Policy (CSP) — функция безопасности, используемая для указания источника контента, который разрешено загружать на сайт или в веб-приложение. Это дополнительный уровень безопасности, помогающий обнаруживать и снижать риски определённых видов атак, включая межсайтовый скриптинг (XSS) и атаки инъекций данных. Эти атаки используются для всего — от кражи данных до порчи сайтов и распространения вредоносного ПО.

    • ПРИМЕЧАНИЕ: Этот заголовок актуален для страниц, которые могут загружать и интерпретировать скрипты и код, но может быть бессмысленным в ответе REST API, возвращающего содержимое, которое не будет отображаться.

    Рекомендация¶

    Content Security Policy сложна для настройки и обслуживания. Для объяснения параметров настройки прочитайте Шпаргалку по Content Security Policy.

    Access-Control-Allow-Origin¶

    Если вы не используете этот заголовок, ваш сайт по умолчанию защищён политикой одного источника (SOP). Этот заголовок ослабляет этот контроль при определённых обстоятельствах.

    Access-Control-Allow-Origin — заголовок CORS (совместного использования ресурсов между источниками). Этот заголовок указывает, может ли ответ, с которым он связан, совместно использоваться запрашивающим кодом из данного источника. Иными словами, если сайт A запрашивает ресурс с сайта B, сайт B должен указать в своём заголовке Access-Control-Allow-Origin, что сайту A разрешено получать этот ресурс; в противном случае доступ блокируется политикой одного источника (SOP).

    Рекомендация¶

    Если вы его используете, задавайте конкретные источники вместо *. Подробности см. в документации Access-Control-Allow-Origin.

    Access-Control-Allow-Origin: https://yoursite.com

    • ПРИМЕЧАНИЕ: Использование '*' может быть необходимым в зависимости от ваших потребностей. Например, для публичного API, который должен быть доступен с любого источника, может потребоваться разрешить '*'.

    Cross-Origin-Opener-Policy (COOP)¶

    HTTP-заголовок ответа Cross-Origin-Opener-Policy (COOP) позволяет гарантировать, что документ верхнего уровня не использует одну группу контекста просмотра с документами из других источников.

    Этот заголовок работает вместе с Cross-Origin-Embedder-Policy (COEP) и Cross-Origin-Resource-Policy (CORP), описанными ниже.

    Этот механизм защищает от атак, таких как Spectre, которые могут пересекать границу безопасности, установленную политикой одного источника (SOP) для ресурсов в одной группе контекста просмотра.

    Поскольку эти заголовки тесно связаны с браузерами, применять их к REST API или клиентам, не являющимся браузерами, может не иметь смысла.

    Рекомендация¶

    Изолирует контекст просмотра исключительно для документов того же источника.

    Cross-Origin-Opener-Policy: same-origin

    Cross-Origin-Embedder-Policy (COEP)¶

    HTTP-заголовок ответа Cross-Origin-Embedder-Policy (COEP) предотвращает загрузку документом каких-либо ресурсов из других источников, которые явно не предоставляют документу разрешение (с помощью CORP или CORS).

    • ПРИМЕЧАНИЕ: Включение этого параметра заблокирует загрузку ресурсов из других источников, настроенных неправильно.

    Рекомендация¶

    Документ может загружать только ресурсы из того же источника или ресурсы, явно помеченные как загружаемые из другого источника.

    Cross-Origin-Embedder-Policy: require-corp

    • ПРИМЕЧАНИЕ: вы можете обойти это для конкретных ресурсов, добавив атрибут crossorigin:
    • <img src="https://thirdparty.com/img.png" crossorigin>

    Cross-Origin-Resource-Policy (CORP)¶

    Заголовок Cross-Origin-Resource-Policy (CORP) позволяет управлять набором источников, которым разрешено включать ресурс. Это надёжная защита от атак, таких как Spectre, поскольку позволяет браузерам блокировать данный ответ до его попадания в процесс злоумышленника.

    Рекомендация¶

    Ограничить загрузку текущего ресурса только сайтом и поддоменами.

    Cross-Origin-Resource-Policy: same-site

    Permissions-Policy (ранее Feature-Policy)¶

    Permissions-Policy позволяет контролировать, какие источники могут использовать какие функции браузера, как на странице верхнего уровня, так и во встроенных фреймах. Для каждой функции, контролируемой политикой возможностей, функция включена в текущем документе или фрейме только в том случае, если его источник соответствует разрешённому списку источников. Это означает, что вы можете настроить свой сайт так, чтобы никогда не разрешать активацию камеры или микрофона. Это предотвращает включение злоумышленником, например XSS, камеры, микрофона или других функций браузера.

    Дополнительная информация: Permissions-Policy

    Рекомендация¶

    Установите и отключите все функции, которые ваш сайт не использует, или разрешите их только авторизованным доменам:

    Permissions-Policy: geolocation=(), camera=(), microphone=()

    • ПРИМЕЧАНИЕ: Этот пример отключает геолокацию, камеру и микрофон для всех доменов.

    FLoC (Federated Learning of Cohorts)¶

    FLoC — метод, предложенный Google в 2021 году для доставки рекламы на основе интересов группам пользователей («когортам»). Electronic Frontier Foundation, Mozilla и другие организации считают, что FLoC недостаточно защищает конфиденциальность пользователей.

    Рекомендация¶

    Сайт может объявить, что не хочет включаться в список сайтов пользователя для расчёта когорты, отправив этот HTTP-заголовок.

    Permissions-Policy: interest-cohort=()

    Server¶

    Заголовок Server описывает программное обеспечение, используемое исходным сервером, обработавшим запрос, то есть сервером, сгенерировавшим ответ.

    Сам по себе это не заголовок безопасности, но способ его использования важен для безопасности.

    Рекомендация¶

    Удалите этот заголовок или установите неинформативные значения.

    Server: webserver

    • ПРИМЕЧАНИЕ: Помните, что у злоумышленников есть и другие средства для определения технологии сервера.

    X-Powered-By¶

    Заголовок X-Powered-By описывает технологии, используемые веб-сервером. Эта информация раскрывает сервер злоумышленникам. Используя информацию в этом заголовке, злоумышленники могут легче находить уязвимости.

    Рекомендация¶

    Удалите все заголовки X-Powered-By.

    • ПРИМЕЧАНИЕ: Помните, что у злоумышленников есть и другие средства для определения вашего технологического стека.

    X-AspNet-Version¶

    Предоставляет информацию о версии .NET.

    Рекомендация¶

    Отключите отправку этого заголовка. Добавьте следующую строку в ваш файл web.config в секции <system.web>, чтобы удалить его.

    <httpRuntime enableVersionHeader="false" />
    • ПРИМЕЧАНИЕ: Помните, что у злоумышленников есть и другие средства для определения вашего технологического стека.

    X-AspNetMvc-Version¶

    Предоставляет информацию о версии .NET.

    Рекомендация¶

    Отключите отправку этого заголовка. Для удаления заголовка X-AspNetMvc-Version добавьте следующую строку в файл Global.asax.

    MvcHandler.DisableMvcResponseHeader = true;
    • ПРИМЕЧАНИЕ: Помните, что у злоумышленников есть и другие средства для определения вашего технологического стека.

    X-Robots-Tag¶

    HTTP-заголовок ответа X-Robots-Tag управляет тем, как поисковые системы и другие автоматизированные краулеры индексируют и отображают ресурсы, такие как PDF, изображения и другой нетекстовый HTML-контент. Он функционирует аналогично тегу <meta name="robots">, но применяется через HTTP-заголовок ответа, обеспечивая большую гибкость (например, для файлов, не являющихся HTML, или правил на уровне сервера).

    X-Robots-Tag: noindex, nofollow
    • Примечание: Только совместимые краулеры соблюдают эти директивы, и они всё равно должны делать HTTP-запрос для чтения заголовков перед принятием решения о том, как обрабатывать содержимое.

    Рекомендация¶

    Используйте заголовок X-Robots-Tag для управления поведением краулеров:

    • Для приватного или конфиденциального контента, который не нужно индексировать:

    X-Robots-Tag: noindex, nofollow Это запрещает совместимым поисковым системам индексировать ресурс или переходить по ссылкам в нём.

    • Для публичного контента, который нужно индексировать и делать доступным (например, документация, наборы данных):

    X-Robots-Tag: index, follow Это разрешает поисковым системам индексировать ресурс и переходить по его ссылкам.

    Можно также использовать другие директивы, такие как noarchive, nosnippet или noimageindex, в зависимости от ваших потребностей. Конфигурация сервера может применять этот заголовок избирательно — например, только для определённых типов файлов (например, PDF или изображений).

    X-DNS-Prefetch-Control¶

    HTTP-заголовок ответа X-DNS-Prefetch-Control управляет предварительным разрешением DNS — функцией, при которой браузеры упреждающе выполняют разрешение имён домена как для ссылок, по которым пользователь может перейти, так и для URL элементов, на которые ссылается документ, включая изображения, CSS, JavaScript и так далее.

    Рекомендация¶

    Поведение браузеров по умолчанию — кэшировать DNS, что хорошо для большинства сайтов. Если вы не контролируете ссылки на своём сайте, возможно, вы захотите установить значение off, чтобы отключить предварительное разрешение DNS и избежать утечки информации в эти домены.

    X-DNS-Prefetch-Control: off

    • ПРИМЕЧАНИЕ: Не полагайтесь на эту функциональность ни в каких производственно значимых случаях: она не является стандартной или полностью поддерживаемой, и реализация может различаться в зависимости от браузера.

    Public-Key-Pins (HPKP)¶

    HTTP-заголовок ответа Public-Key-Pins используется для связывания конкретного криптографического публичного ключа с определённым веб-сервером для снижения риска MITM-атак с поддельными сертификатами.

    Рекомендация¶

    Этот заголовок устарел и больше не должен использоваться.

    Добавление HTTP-заголовков в различных технологиях¶

    PHP¶

    Приведённый ниже пример кода устанавливает заголовок X-Frame-Options в PHP.

    header("X-Frame-Options: DENY");

    Apache¶

    Ниже приведён пример конфигурации .htaccess, устанавливающей заголовок X-Frame-Options в Apache.

    Как описано в документации Apache, Header set (по умолчанию onsuccess) и Header always set работают с отдельными внутренними таблицами заголовков.

    В некоторых случаях могут использоваться обе таблицы заголовков, что может привести к дублированию заголовков, если один и тот же заголовок настроен в обоих контекстах.

    Если заголовок нужно полностью удалить, его следует снять в обоих контекстах (onsuccess и always).

    Чтобы избежать дублирования и убедиться, что заголовок отправляется во всех ответах, сначала снимите его, а затем используйте always set:

    <IfModule mod_headers.c>
  Header unset X-Frame-Options
  Header always set X-Frame-Options "DENY"
</IfModule>

    IIS¶

    Добавьте следующие конфигурации в ваш файл Web.config в IIS для отправки заголовка X-Frame-Options.

    <system.webServer>
...
 <httpProtocol>
   <customHeaders>
     <add name="X-Frame-Options" value="DENY" />
   </customHeaders>
 </httpProtocol>
...
</system.webServer>

    HAProxy¶

    Добавьте следующую строку в конфигурации front-end, listen или backend для отправки заголовка X-Frame-Options.

    http-response set-header X-Frame-Options DENY

    Nginx¶

    Ниже приведён пример конфигурации, устанавливающей заголовок X-Frame-Options в Nginx. Обратите внимание, что без опции always заголовок будет отправляться только для определённых кодов состояния, как описано в документации nginx.

    add_header "X-Frame-Options" "DENY" always;

    Express¶

    Для настройки HTTP-заголовков в Express можно использовать helmet. Приведённый ниже код является примером добавления заголовка X-Frame-Options.

    const helmet = require('helmet');
const app = express();
// Устанавливает "X-Frame-Options: SAMEORIGIN"
app.use(
 helmet.frameguard({
   action: "sameorigin",
 })
);

    Тестирование правильной реализации заголовков безопасности¶

    Mozilla Observatory¶

    Mozilla Observatory — онлайн-инструмент, помогающий проверить статус заголовков вашего сайта.

    SmartScanner¶

    SmartScanner имеет специальный профиль тестирования для тестирования безопасности HTTP-заголовков. Онлайн-инструменты обычно тестируют главную страницу по указанному адресу. Но SmartScanner сканирует весь сайт. Таким образом, вы можете убедиться, что все ваши веб-страницы имеют правильные HTTP-заголовки.
