    Cross-Site Request Forgery Prevention Cheat Sheet¶

    Введение¶

    Атака Cross-Site Request Forgery (CSRF) происходит, когда вредоносный сайт, электронное письмо, блог, мгновенное сообщение или программа заставляет браузер аутентифицированного пользователя выполнить нежелательное действие на доверенном сайте. Если целевой пользователь аутентифицирован на сайте, незащищённые сайты не могут отличить легитимные авторизованные запросы от поддельных аутентифицированных запросов.

    Поскольку браузер автоматически включает в запросы все файлы cookie, включая сессионные, эта атака работает в отсутствие надлежащей авторизации — то есть когда механизм проверки подлинности на целевом сайте не верифицирует личность и полномочия запрашивающей стороны. По сути, CSRF-атаки заставляют целевую систему выполнять указанные злоумышленником функции через браузер жертвы без ведома жертвы (обычно до того момента, когда несанкционированные действия уже совершены).

    Вместе с тем успешные CSRF-атаки могут эксплуатировать только те возможности, которые предоставляет уязвимое приложение, и только в рамках привилегий пользователя. В зависимости от учётных данных пользователя злоумышленник может перевести средства, изменить пароль, совершить несанкционированную покупку, повысить привилегии целевой учётной записи или выполнить любое другое действие, разрешённое пользователю.

    Для защиты от CSRF необходимо придерживаться следующих принципов:

    ВАЖНО: Помните, что Cross-Site Scripting (XSS) может нейтрализовать все методы защиты от CSRF! Несмотря на то что XSS-уязвимости могут обходить CSRF-защиту, CSRF-токены по-прежнему необходимы для веб-приложений, использующих cookies для аутентификации. Учитывайте тип клиента и метод аутентификации при выборе подхода к CSRF-защите в вашем приложении.

    • См. XSS Prevention Cheat Sheet OWASP для подробного руководства по предотвращению XSS-уязвимостей.
    • Сначала проверьте, имеет ли ваш фреймворк встроенную CSRF-защиту и используйте её.
    • Если фреймворк не имеет встроенной CSRF-защиты, добавьте CSRF-токены ко всем запросам, изменяющим состояние (запросы, вызывающие действия на сайте), и проверяйте их на сервере.
    • Если ваше ПО ориентировано только на современные браузеры, вы можете использовать заголовки Fetch Metadata вместе с резервными вариантами, описанными ниже, для блокировки межсайтовых запросов, изменяющих состояние.
    • Программное обеспечение с состоянием должно использовать паттерн синхронизирующего токена
    • Программное обеспечение без состояния должно использовать двойную отправку cookie
    • Если сайт на базе API не может использовать теги <form>, рассмотрите использование пользовательских заголовков запросов
    • Реализуйте хотя бы одну защитную меру из раздела Эшелонированная оборона
    • Атрибут cookie SameSite можно использовать для сессионных cookie, но будьте осторожны и НЕ устанавливайте cookie специально для домена. Это создаёт уязвимость в системе безопасности, поскольку все поддомены этого домена будут иметь общий cookie — особенно это проблематично, если поддомен имеет CNAME на домены вне вашего контроля.
    • Рассмотрите реализацию защиты на основе взаимодействия с пользователем для особо чувствительных операций
    • Рассмотрите проверку источника с помощью стандартных заголовков
    • Не используйте GET-запросы для операций, изменяющих состояние.
    • Если по какой-либо причине вы это делаете, защитите эти ресурсы от CSRF

    Встроенные или существующие реализации CSRF-защиты¶

    Прежде чем создавать собственную реализацию токенов или Fetch-Metadata, проверьте, не предоставляет ли уже ваш фреймворк или платформа встроенную CSRF-защиту. Встроенные механизмы защиты, как правило, предпочтительнее, поскольку они поддерживаются авторами фреймворка и снижают риск незаметных ошибок реализации. Например:

    • .NET предлагает встроенную защиту для добавления токенов к уязвимым CSRF ресурсам. При использовании этой защиты .NET возлагает на вас ответственность за правильную конфигурацию (например, управление ключами и токенами).
    • Начиная с версии 1.25, разработчики Go могут использовать встроенный тип CrossOriginProtection. Он реализует CSRF-защиту на основе Fetch Metadata (включая проверку Sec-Fetch-Site и связанных заголовков) непосредственно в стандартной библиотеке.

    Защита на основе токенов¶

    Паттерн синхронизирующего токена является одним из наиболее популярных и рекомендуемых методов защиты от CSRF.

    Паттерн синхронизирующего токена¶

    CSRF-токены должны генерироваться на стороне сервера и создаваться только один раз за сессию пользователя или для каждого запроса. Поскольку временной промежуток, в течение которого злоумышленник может воспользоваться украденными токенами, минимален для токенов на каждый запрос, они более безопасны, чем токены на сессию. Однако использование токенов на каждый запрос может создавать неудобства с точки зрения удобства использования.

    Например, функциональность кнопки «Назад» в браузере может быть нарушена токеном на каждый запрос, поскольку предыдущая страница может содержать токен, срок действия которого уже истёк. В этом случае взаимодействие с предыдущей страницей приведёт к ложному срабатыванию CSRF на стороне сервера. При реализации с токенами на сессию после первоначальной генерации токена его значение сохраняется в сессии и используется для каждого последующего запроса до истечения срока действия сессии.

    Когда клиент отправляет запрос, серверный компонент должен проверить наличие и действительность токена в этом запросе и сравнить его с токеном, найденным в пользовательской сессии. Запрос должен быть отклонён, если токен не найден в запросе или предоставленное значение не совпадает со значением в пользовательской сессии. Следует также рассмотреть дополнительные действия, такие как регистрация события как потенциальной CSRF-атаки в процессе.

    CSRF-токены должны быть:

    • Уникальными для каждой пользовательской сессии.
    • Секретными.
    • Непредсказуемыми (большое случайное значение, сгенерированное безопасным методом).

    CSRF-токены предотвращают CSRF, потому что без CSRF-токена злоумышленник не может создать корректные запросы к серверу.

    Передача CSRF-токенов в синхронизированных паттернах¶

    CSRF-токен может быть передан клиенту как часть ответного содержимого, например HTML или JSON, а затем отправлен обратно на сервер как скрытое поле в форме или через AJAX-запрос в виде значения пользовательского заголовка или части JSON-данных. CSRF-токен не должен передаваться в cookie при использовании синхронизированных паттернов. CSRF-токен не должен утекать в логи сервера или в URL. GET-запросы потенциально могут привести к утечке CSRF-токенов в нескольких местах, например в истории браузера, лог-файлах, сетевых утилитах, которые записывают первую строку HTTP-запроса, и в заголовках Referer, если защищённый сайт содержит ссылки на внешний сайт.

    Например:

    <form action="/transfer.do" method="post">
<input type="hidden" name="CSRFToken" value="OWY4NmQwODE4ODRjN2Q2NTlhMmZlYWEwYzU1YWQwMTVhM2JmNGYxYjJiMGI4MjJjZDE1ZDZMGYwMGEwOA==">
[...]
</form>

    Поскольку запросы с пользовательскими заголовками автоматически подлежат политике одного источника, вставка CSRF-токена в пользовательский HTTP-заголовок через JavaScript более безопасна, чем добавление CSRF-токена в скрытое поле формы.

    АЛЬТЕРНАТИВА: Паттерн двойной отправки cookie¶

    Если поддержка состояния CSRF-токена на сервере затруднена, можно использовать альтернативный метод, известный как паттерн двойной отправки cookie. Этот метод прост в реализации и не требует хранения состояния. Существуют различные способы реализации этого метода, где наивный паттерн является наиболее распространённым вариантом.

    Подписанная двойная отправка cookie (РЕКОМЕНДУЕТСЯ)¶

    Наиболее безопасной реализацией паттерна двойной отправки cookie является Подписанная двойная отправка cookie, которая явно привязывает токены к аутентифицированной сессии пользователя (например, ID сессии). Простая подпись токенов без привязки к сессии обеспечивает минимальную защиту и остаётся уязвимой к атакам с подменой cookie. Всегда явно привязывайте CSRF-токен к данным, специфичным для сессии.

    Если токен содержит конфиденциальную информацию (например, идентификаторы сессий или claims), всегда используйте Hash-based Message Authentication (HMAC) с секретным ключом на стороне сервера. Это предотвращает подделку токенов, обеспечивая их целостность. HMAC предпочтительнее простого хеширования во всех случаях, поскольку защищает от различных криптографических атак. Для сценариев, требующих конфиденциальности содержимого токена, используйте аутентифицированное шифрование.

    Использование HMAC CSRF-токенов¶

    Для генерации HMAC CSRF-токенов (с зависящим от сессии значением пользователя) система должна иметь:

    • Зависящее от сессии значение, которое меняется при каждом входе в систему. Это значение должно быть действительным только в течение всей аутентифицированной сессии пользователя. Избегайте использования статических значений, таких как электронная почта или ID пользователя, поскольку они небезопасны (1 | 2 | 3). Стоит отметить, что слишком частое обновление CSRF-токена, например для каждого запроса, является заблуждением, предполагающим существенное повышение безопасности, тогда как на самом деле это ухудшает пользовательский опыт (1). Например, можно выбрать одно или комбинацию следующих зависящих от сессии значений:
      • ID серверной сессии (например, PHP или ASP.NET). Это значение никогда не должно покидать сервер или присутствовать в CSRF-токене в открытом виде.
      • Случайное значение (например, UUID) внутри JWT, которое меняется каждый раз при создании JWT.
    • Секретный криптографический ключ — не следует путать со случайным значением из наивной реализации. Это значение используется для генерации HMAC-хеша. В идеале храните этот ключ так, как описано на странице криптографического хранения.
    • Случайное значение для защиты от коллизий. Генерируйте случайное значение (предпочтительно криптографически случайное), чтобы последовательные вызовы в рамках одной секунды не производили одинаковый хеш (1).

    Следует ли включать временны́е метки в CSRF-токены для их истечения?

    Распространённым заблуждением является включение временны́х меток для указания времени истечения CSRF-токена. CSRF-токен — это не токен доступа. Они используются для проверки подлинности запросов в течение сессии с использованием информации о сессии. Новая сессия должна генерировать новый токен (1).

    Псевдокод для реализации HMAC CSRF-токенов¶

    Ниже приведён пример на псевдокоде, демонстрирующий описанные выше шаги реализации:

    // Получаем значения
secret = getSecretSecurely("CSRF_SECRET") // Секретный ключ HMAC
sessionID = session.sessionID // Текущая аутентифицированная сессия пользователя
randomValue = cryptographic.randomValue(64) // Криптографически случайное значение

// Создаём CSRF-токен
message = sessionID.length + "!" + sessionID + "!" + randomValue.length + "!" + randomValue.toHex() // Полезная нагрузка HMAC-сообщения
hmac = hmac("SHA256", secret, message) // Генерируем HMAC-хеш
// Добавляем `randomValue` к HMAC-хешу для создания итогового CSRF-токена.
// Избегайте использования `message`, поскольку он содержит sessionID в открытом виде,
// который сервер уже хранит отдельно.
csrfToken = hmac.toHex() + "." + randomValue.toHex()

// Сохраняем CSRF-токен в cookie
response.setCookie("csrf_token=" + csrfToken + "; Secure") // Устанавливаем cookie без флага HttpOnly

    Ниже приведён пример на псевдокоде, демонстрирующий проверку CSRF-токена после его отправки клиентом обратно:

    // Получаем CSRF-токен из запроса
csrfToken = request.getParameter("csrf_token") // Из заголовка или поля формы (НЕ из cookie)

// Разбиваем токен, чтобы получить randomValue
const tokenParts = csrfToken.split(".");
const hmacFromRequest = tokenParts[0];
const randomValue = tokenParts[1];

// Пересоздаём HMAC с текущей сессией и randomValue из запроса
secret = getSecretSecurely("CSRF_SECRET") // Секретный ключ HMAC
sessionID = session.sessionID // Текущая аутентифицированная сессия пользователя
message = sessionID.length + "!" + sessionID + "!" + randomValue.length + "!" + randomValue

// Генерируем ожидаемый HMAC
expectedHmac = hmac("SHA256", secret, message)

// Сравниваем HMAC из запроса с ожидаемым HMAC
if (!constantTimeEquals(hmacFromRequest, expectedHmac)) {
    // Проверка HMAC не пройдена, отклоняем запрос
    response.sendError(403, "Invalid CSRF token")
    logError("Invalid CSRF token", hmacFromRequest, expectedHmac)
    return
}

// Проверка CSRF пройдена, продолжаем обработку запроса
// ...

    Примечание: функция constantTimeEquals должна использоваться для сравнения HMAC-значений, чтобы предотвратить атаки по времени. Эта функция сравнивает две строки за постоянное время, независимо от количества совпадающих символов.

    Наивный паттерн двойной отправки cookie (НЕ РЕКОМЕНДУЕТСЯ)¶

    Метод наивной двойной отправки cookie — это масштабируемый и простой в реализации метод, который использует криптографически стойкое случайное значение одновременно как cookie и как параметр запроса (даже до аутентификации пользователя). Затем сервер проверяет совпадение значения cookie и значения запроса.

    Сайт должен требовать, чтобы каждый транзакционный запрос от пользователя включал это случайное значение только как пользовательский заголовок запроса или параметр формы. Проверка через cookie НЕБЕЗОПАСНА.

    Почему? Браузеры автоматически отправляют cookies при межсайтовых запросах. Злоумышленники могут инициировать это автоматически. Безопасность требует явной отправки клиентом (через заголовок/параметр), доказывающей намерение пользователя.

    Если значение совпадает на стороне сервера, сервер принимает его как легитимный запрос; в противном случае отклоняет запрос.

    Поскольку злоумышленник не может получить доступ к значению cookie при межсайтовом запросе, он не может включить совпадающее значение в скрытое поле формы или как параметр/заголовок запроса.

    Хотя метод наивной двойной отправки cookie прост и масштабируем, он остаётся уязвимым к атакам с подменой cookie, особенно когда злоумышленники контролируют поддомены или сетевые среды, позволяющие им подставлять или перезаписывать cookies. Например, подконтрольный злоумышленнику поддомен (например, через перехват DNS) может внедрить совпадающий cookie и тем самым подделать корректный токен запроса. Этот ресурс подробно описывает эти уязвимости. Поэтому всегда отдавайте предпочтение паттерну Подписанной двойной отправки cookie с HMAC-токенами, привязанными к сессии, для снижения этих угроз.

    Заголовки Fetch Metadata¶

    Заголовки запросов Fetch Metadata предоставляют дополнительную информацию о контексте, из которого был выполнен HTTP-запрос. Серверы могут использовать эти заголовки — прежде всего Sec-Fetch-Site — как лёгкий и надёжный метод блокировки очевидных межсайтовых запросов. Подробности см. в спецификации Fetch Metadata.

    Поскольку некоторые устаревшие браузеры не отправляют заголовки Sec-Fetch-*, резервный переход к проверке стандартного источника является обязательным требованием для любой реализации Fetch Metadata. Sec-Fetch-* поддерживается всеми основными браузерами начиная с марта 2023 года.

    Заголовки запросов Fetch Metadata:

    • Sec-Fetch-Site — основной сигнал для CSRF-защиты. Он указывает на соотношение между источником инициатора запроса и целевым источником: same-origin, same-site, cross-site или none.
    • Sec-Fetch-Mode, Sec-Fetch-Dest, Sec-Fetch-User — дополнительные заголовки, предоставляющие контекст о запросе (например, режим запроса, тип назначения или был ли он инициирован навигацией пользователя). Подробности см. в документации MDN.

    Если любой из указанных выше заголовков содержит значения, не перечисленные в спецификации, для поддержки прямой совместимости серверы должны игнорировать эти заголовки.

    Простота использования¶

    В отличие от синхронизирующих токенов или паттернов двойной отправки — которые требуют дополнительной координации между клиентом и сервером и сложны в правильной реализации — проверки Fetch Metadata значительно проще. Они обычно требуют лишь небольшого количества логики на стороне сервера (проверить Sec-Fetch-Site, при необходимости уточнить с помощью Sec-Fetch-Mode/Sec-Fetch-Dest) и не требуют изменений на стороне клиента. Такая простота снижает сложность, что делает этот подход привлекательным для многих приложений.

    Совместимость с браузерами¶

    Заголовки запросов Fetch Metadata поддерживаются во всех современных браузерах как на настольных компьютерах, так и на мобильных устройствах (Chrome, Edge, Firefox, Safari 16.4+, а также в webview на iOS и Android), с более чем 98% глобальным охватом. Подробности совместимости см. в таблице поддержки браузеров.

    В редких случаях устаревших или встроенных браузеров, не поддерживающих Sec-Fetch-*, резервный переход к проверке стандартного источника должен обеспечить необходимое покрытие. Если это приемлемо для вашего проекта, рассмотрите возможность предложить пользователям обновить браузеры, поскольку они используют устаревшие и потенциально небезопасные версии.

    Как обрабатывать заголовки Fetch Metadata на стороне сервера¶

    Sec-Fetch-Site — наиболее полезный заголовок Fetch Metadata для блокировки CSRF-подобных запросов из других источников и должен быть основным сигналом в политике на основе Fetch Metadata. Используйте другие заголовки Fetch Metadata (Sec-Fetch-Mode, Sec-Fetch-Dest, Sec-Fetch-User) для дальнейшего уточнения или настройки политик под нужды вашего приложения (например, разрешение запросов навигации верхнего уровня или определённых значений Dest для конечных точек ресурсов).

    Политика (высокий уровень)

    1. Если Sec-Fetch-Site присутствует

    1.1. Считать межсайтовые запросы ненадёжными для действий, изменяющих состояние. По умолчанию отклонять небезопасные методы (POST / PUT / PATCH / DELETE) при Sec-Fetch-Site: cross-site.

    const SAFE_METHODS = new Set(['GET','HEAD','OPTIONS']);
const site = req.get('Sec-Fetch-Site'); // например, 'cross-site','same-site','same-origin','none'

if (site === 'cross-site' && !SAFE_METHODS.has(req.method)) {
  return false; // запрещаем этот запрос
}

    1.2 Если ваше приложение использует безопасные HTTP-методы (GET, HEAD или OPTIONS) для действий, изменяющих состояние, следует явно отразить это в вашей политике — например, требуя проверки заголовка Fetch‑Metadata для запросов к этим конечным точкам. Это может быть закреплено правилом политики вида:

    const SAFE_METHODS = new Set(['GET','HEAD','OPTIONS']);
const SENSITIVE_ENDPOINTS = new Set([
  '/user/profile',
  '/account/details',
]);

const site = req.get('Sec-Fetch-Site');
const path = req.path;

// Блокировать, если cross-site + небезопасный метод ИЛИ cross-site + чувствительная конечная точка
if (site === 'cross-site' && (!SAFE_METHODS.has(req.method) || SENSITIVE_ENDPOINTS.has(path))) {
  return false; // запрещаем этот запрос
}

    1.3. Разрешить same-origin. Считать same-site разрешённым только в случае, если ваша модель угроз доверяет соседним поддоменам; в противном случае обрабатывать same-site консервативно (например, требовать дополнительной проверки).

    const trustSameSite = false; // установить true только если вы доверяете соседним поддоменам

if (site === 'same-origin') {
  return true;
} else if (site === 'same-site') {
  // обрабатывать same-site отдельно, чтобы подусловие было чётко привязано к same-site
  if (!trustSameSite && !SAFE_METHODS.has(req.method)) {
    return false; // считать same-site ненадёжным для методов, изменяющих состояние
  }
  return true;
}

    1.4. Разрешить none для навигации верхнего уровня, инициированной пользователем (закладки, введённые URL-адреса, явная отправка форм), где это уместно.

    1. Если заголовки Sec-Fetch-* отсутствуют: выберите резервный вариант на основе требований риска и совместимости: 2.1. Fail-safe (рекомендуется для чувствительных конечных точек): считать отсутствие заголовков неизвестным и блокировать запрос. 2.2. Fail-open (приоритет совместимости): резервный переход к (проверке стандартного источника, CSRF-токенам и/или требованию дополнительной проверки).

    2. Дополнительные опции

    3.1 Чтобы обеспечить возможность создания ссылок на ваш сайт с других сайтов, необходимо разрешить простую (HTTP GET) навигацию верхнего уровня.

    if (req.get('Sec-Fetch-Mode') === 'navigate' &&
    req.method === 'GET' &&
    req.get('Sec-Fetch-Dest') !== 'object' &&
    req.get('Sec-Fetch-Dest') !== 'embed') {
  return true; // разрешаем этот запрос
}

    3.2 Добавить конечные точки в явный список разрешений для межсайтовых запросов. Если определённые конечные точки намеренно принимают запросы из других источников (CORS JSON API, интеграции с третьими лицами, webhooks), явно исключите эти конечные точки из глобальной политики запрета Sec-Fetch и защитите их надлежащей конфигурацией CORS, аутентификацией и логированием.

    Требования¶

    • Ваше приложение должно обслуживаться по надёжным URL. Заголовки запросов Fetch Metadata отправляются только на потенциально надёжные URL. На практике это включает https, wss, file и localhost (включая 127.0.0.0/8 и ::1/128). Полные сведения см. в спецификации W3C Secure Contexts.
    • HTTPS должен быть обязательным для всего приложения. Это обеспечивает постоянное включение заголовков Fetch Metadata. Включение HTTP Strict Transport Security (HSTS) помогает достичь этого, автоматически переключая все HTTP-запросы на HTTPS.
    • Безопасные HTTP-методы не должны использоваться для запросов, изменяющих состояние.

    Предостережения¶

    • Предварительный рендеринг/предварительная загрузка и другие виды спекулятивной навигации могут отправлять значения Sec-Fetch-*, не соответствующие итоговой навигации, а инициированные браузером процессы (например, PaymentRequest) могут генерировать запросы без предсказуемых заголовков fetch-metadata. Эти особенности поведения ещё уточняются, поэтому распространение заголовков полностью стабильно не для всех типов навигации.
    • Промежуточные звенья (прокси, шлюзы, балансировщики нагрузки) могут удалять или изменять заголовки Origin и Sec-* — из-за фильтров конфиденциальности, оптимизации сети или простых ошибок конфигурации, — что может нарушить защиту на основе fetch-metadata. Такое удаление заголовков является проблематичным, но распространённым явлением.

    Рекомендации по развёртыванию и тестированию¶

    • Включите соответствующий заголовок Vary, чтобы кеши корректно обрабатывали ответ. Например, Vary: Sec-Fetch-Site, Origin. Подробнее см. в спецификации Fetch Metadata.
      • Обратите внимание, что заголовок Vary никак не влияет на CSRF-защиту. Это заголовок ответа, поэтому он применяется после того, как сервер уже принял решение разрешить/запретить на основе CSRF-защиты. Его назначение — операционное, а не защитное.
      • Если сервер отвечает по-разному в зависимости от HTTP-заголовков (например, Sec-Fetch-Site, Origin), кеши должны учитывать эти заголовки. Без этого CDN или прокси могут повторно использовать ответ, сгенерированный для другого контекста, что приводит к нарушению работы или способствует сценариям отравления кеша. Добавление соответствующего заголовка Vary гарантирует раздельное хранение таких ответов в кешах.
    • Начните в режиме «только логирование». Записывайте запросы, которые были бы заблокированы, и проверяйте на ложные срабатывания перед применением. Это самый безопасный способ обнаружить легитимные потоки, требующие добавления в список разрешений.
    • Отслеживайте охват UA. Контролируйте, какие пользовательские агенты включают Sec-Fetch-*, а какие — нет; убедитесь, что ваша резервная логика покрывает случаи отсутствия заголовков. Используйте метрики для принятия решений о применении более строгих политик.
    • Документируйте исключения. Ведите явный список конечных точек, добавленных в список разрешений для межсайтового доступа.

    Запрет простых запросов¶

    Когда тег <form> используется для отправки данных, он отправляет «простой» запрос, который браузеры не обозначают как «требующий предварительного запроса». Эти «простые» запросы создают риск CSRF, поскольку браузеры позволяют отправлять их на любой источник. Если ваше приложение использует теги <form> для отправки данных где-либо в клиенте, вам всё равно придётся защищать их с помощью альтернативных подходов, описанных в этом документе, таких как токены.

    Предостережение: Если ошибка браузера позволит использовать пользовательские HTTP-заголовки или не применять предварительный запрос для не-простых типов содержимого, это может скомпрометировать вашу безопасность. Хотя это маловероятно, при построении модели угроз это следует учитывать. Реализация CSRF-токенов добавляет дополнительный уровень защиты и даёт разработчикам больше контроля над безопасностью приложения.

    Запрет простых типов содержимого¶

    Чтобы запрос считался простым, он должен иметь один из следующих типов содержимого: application/x-www-form-urlencoded, multipart/form-data или text/plain. Многие современные веб-приложения используют JSON API, которые естественным образом требуют CORS, однако они могут принимать text/plain, что делает их уязвимыми к CSRF. Поэтому простой мерой защиты является запрет этих простых типов содержимого на стороне сервера или API.

    Использование пользовательских заголовков запросов для AJAX/API¶

    И синхронизирующий токен, и двойная отправка cookie используются для предотвращения подделки данных форм, но их сложно реализовать, и они снижают удобство использования. Многие современные веб-приложения не используют теги <form> для отправки данных. Удобная для пользователя защита, особенно хорошо подходящая для AJAX или API-конечных точек, — это использование пользовательского заголовка запроса. Для этого подхода токен не нужен.

    В этом паттерне клиент добавляет пользовательский заголовок к запросам, требующим CSRF-защиты. Заголовок может быть любой произвольной парой ключ-значение, если он не конфликтует с существующими заголовками.

    X-CSRF-Token: RANDOM-TOKEN-VALUE

    Многие популярные фреймворки используют стандартизированные имена заголовков для CSRF-защиты:

    • X-CSRF-Token — Ruby on Rails, Laravel, Django
    • X-XSRF-Token — AngularJS
    • CSRF-Token — Express.js (middleware csurf)
    • X-CSRFToken — Django

    Хотя подойдёт любое произвольное имя заголовка, использование одного из этих стандартных имён может улучшить совместимость с существующими инструментами и ожидания разработчиков.

    При обработке запроса API проверяет наличие этого заголовка. Если заголовок отсутствует, бэкенд отклоняет запрос как потенциальную подделку. У этого подхода есть несколько преимуществ:

    • Изменения UI не требуются.
    • Не вводится состояние на сервере для отслеживания токенов.

    Эта защита основана на механизме предварительного запроса CORS, который отправляет запрос OPTIONS для проверки соответствия CORS на целевом сервере. Все современные браузеры обозначают запросы с пользовательскими заголовками как «требующие предварительного запроса». Когда API проверяет наличие пользовательского заголовка, становится известно, что запрос должен был пройти предварительную проверку, если он пришёл из браузера.

    Пользовательские заголовки и CORS¶

    По умолчанию cookies не устанавливаются при запросах из других источников (CORS). Чтобы включить cookies для API, нужно установить Access-Control-Allow-Credentials=true. Браузер отклонит любой ответ, содержащий Access-Control-Allow-Origin=*, если разрешены учётные данные. Чтобы разрешить CORS-запросы, но защитить от CSRF, нужно убедиться, что сервер разрешает только несколько избранных источников, которые вы действительно контролируете, через заголовок Access-Control-Allow-Origin. Любой межсайтовый запрос из разрешённого домена сможет устанавливать пользовательские заголовки.

    В качестве примера можно настроить бэкенд для разрешения CORS с cookies с http://www.yoursite.com и http://mobile.yoursite.com, так что единственными возможными ответами на предварительный запрос будут:

    Access-Control-Allow-Origin=http://mobile.yoursite.com
Access-Control-Allow-Credentials=true

    или

    Access-Control-Allow-Origin=http://www.yoursite.com
Access-Control-Allow-Credentials=true

    Менее безопасная конфигурация — настроить серверный сервер для разрешения CORS со всех поддоменов вашего сайта с использованием регулярного выражения. Если злоумышленник сможет захватить поддомен (что не редкость с облачными сервисами), ваша конфигурация CORS позволит ему обойти политику одного источника и подделать запрос с вашим пользовательским заголовком.

    Борьба с клиентскими CSRF-атаками (ВАЖНО)¶

    Клиентский CSRF — это новый вариант CSRF-атак, при котором злоумышленник обманывает клиентский JavaScript-код, заставляя его отправить поддельный HTTP-запрос на уязвимый целевой сайт путём манипуляции входными параметрами программы. Клиентский CSRF возникает, когда JavaScript-программа использует контролируемые злоумышленником входные данные, такие как URL, для генерации асинхронных HTTP-запросов.

    Примечание: Эти варианты CSRF особенно важны, поскольку они могут обходить некоторые распространённые меры защиты от CSRF, такие как защита на основе токенов и SameSite cookies. Например, при использовании синхронизирующих токенов или пользовательских HTTP-заголовков запросов JavaScript-программа будет включать их в асинхронные запросы. Кроме того, веб-браузеры включают cookies в контексты запросов с того же сайта, инициированных JavaScript-программами, обходя политики SameSite cookie.

    Клиентский CSRF против классического CSRF: В классической модели CSRF серверная программа является наиболее уязвимым компонентом, поскольку не может определить, было ли входящее аутентифицированное действие выполнено намеренно — это также известно как проблема растерянного заместителя. В модели клиентского CSRF наиболее уязвимым компонентом является клиентская JavaScript-программа, потому что злоумышленник может использовать её для генерации произвольных асинхронных запросов путём манипуляции конечной точкой запроса и/или её параметрами. Клиентский CSRF является следствием проблемы валидации входных данных, и он заново вводит уязвимость растерянного заместителя: сервер снова не сможет определить, было ли действие выполнено намеренно.

    Для получения дополнительной информации о клиентских CSRF-уязвимостях см. разделы 2 и 5 данной статьи, главу CSRF SameSite wiki и эту публикацию от Meta Bug Bounty Program.

    Пример клиентского CSRF¶

    Следующий фрагмент кода демонстрирует простой пример клиентской CSRF-уязвимости.

    <script type="text/javascript">
    const csrf_token = document.querySelector("meta[name='csrf-token']").getAttribute("content");

    const ajaxLoad = () => {
        // обрабатываем фрагмент хеша URL
        const hashFragment = window.location.hash.slice(1);

        // фрагмент хеша должен иметь формат: /^(get|post);(.*)$/
        // например, https://site.com/index/#post;/profile
        if (hashFragment.length > 0 && hashFragment.includes(';')) {
            const params = hashFragment.match(/^(get|post);(.*)$/);

            if (params && params.length) {
                const requestMethod = params[1];
                const requestEndpoint = params[3];

                fetch(requestEndpoint, {
                    method: requestMethod,
                    headers: {
                        'X-CSRF-Token': csrf_token,
                        // [...]
                    },
                    // [...]
                })
                .then(response => { /* [...] */ })
                .catch(error => console.error('Request failed:', error));
            }
        }
    };

    // инициировать асинхронный запрос при загрузке страницы - лучшей практикой является использование слушателей событий
    window.addEventListener('DOMContentLoaded', ajaxLoad);
</script>

    Уязвимость: В этом фрагменте программа вызывает функцию ajaxLoad() при загрузке страницы, которая отвечает за загрузку различных элементов веб-страницы. Функция считывает значение фрагмента хеша URL (строка 4) и извлекает из него две части информации (метод запроса и конечную точку) для генерации асинхронного HTTP-запроса (строки 11-13). Уязвимость возникает в строках 15-22, когда JavaScript-программа использует фрагменты URL для получения конечной точки на стороне сервера для асинхронного HTTP-запроса (строка 15) и метода запроса. Однако оба входных параметра могут контролироваться веб-злоумышленниками, которые могут выбирать любое значение и создавать вредоносный URL, содержащий атакующую нагрузку.

    Атака: Как правило, злоумышленники делятся вредоносным URL с жертвой (например, через целевые фишинговые письма), и поскольку вредоносный URL выглядит как принадлежащий честному, авторитетному (но уязвимому) сайту, пользователь часто нажимает на него. В качестве альтернативы злоумышленники могут создать страницу атаки для злоупотребления браузерными API (например, API window.open()) и обманом заставить уязвимый JavaScript целевой страницы отправить HTTP-запрос, что очень напоминает модель атаки классического CSRF.

    Дополнительные примеры клиентского CSRF см. в этой публикации от Meta Bug Bounty Program и в этой статье USENIX Security.

    Методы защиты от клиентского CSRF¶

    Независимые запросы: Клиентский CSRF можно предотвратить, когда асинхронные запросы не могут генерироваться через контролируемые злоумышленником входные данные, такие как URL, имя окна, документный реферер и postMessages, чтобы назвать лишь несколько примеров.

    Валидация входных данных: Достижение полной изоляции между входными данными и параметрами запроса не всегда возможно в зависимости от контекста и функциональности. В таких случаях необходимо реализовать проверки валидации входных данных. Эти проверки должны строго оценивать формат и выбор значений параметров запроса и решать, можно ли их использовать только в операциях, не изменяющих состояние (например, разрешать только GET-запросы и конечные точки, начинающиеся с заданного префикса).

    Предопределённые данные запроса: Ещё один метод защиты — хранить в JavaScript-коде список предопределённых, безопасных данных запроса (например, комбинаций конечных точек, методов запроса и других параметров, которые безопасно воспроизводить). Программа может затем использовать параметр-переключатель в фрагменте URL, чтобы решить, какую запись списка должна использовать каждая JavaScript-функция.

    Техники эшелонированной обороны¶

    SameSite (атрибут cookie)¶

    SameSite — это атрибут cookie (аналогичный HTTPOnly, Secure и др.), цель которого — снизить риск CSRF-атак. Он определён в RFC6265bis. Этот атрибут помогает браузеру решить, следует ли отправлять cookies вместе с межсайтовыми запросами. Возможные значения этого атрибута: Lax, Strict или None.

    Значение Strict предотвращает отправку cookie браузером на целевой сайт в любом межсайтовом контексте просмотра, даже при переходе по обычной ссылке. Например, если сайт по типу GitHub использует значение Strict, вошедший в систему пользователь GitHub, пытающийся перейти по ссылке на приватный проект GitHub, опубликованной на корпоративном форуме или в электронном письме, не сможет получить доступ к проекту, поскольку GitHub не получит сессионный cookie. Поскольку банковский сайт не позволяет ссылаться ни на одну транзакционную страницу с внешних сайтов, флаг Strict наиболее подходит для банков.

    Если сайт хочет поддерживать авторизованную сессию пользователя после перехода с внешней ссылки, значение Lax по умолчанию в SameSite обеспечивает разумный баланс между безопасностью и удобством использования. Если в описанном выше сценарии GitHub используется значение Lax, сессионный cookie будет разрешён при переходе по обычной ссылке с внешнего сайта, но заблокирован для подверженных CSRF методов запроса, таких как POST. Только межсайтовые запросы, разрешённые в режиме Lax, — это навигация верхнего уровня, использующая безопасные HTTP-методы.

    Дополнительные сведения о значениях SameSite см. в следующем разделе RFC.

    Пример cookies с этим атрибутом:

    Set-Cookie: JSESSIONID=xxxxx; SameSite=Strict
Set-Cookie: JSESSIONID=xxxxx; SameSite=Lax

    Все современные настольные и мобильные браузеры поддерживают атрибут SameSite. Основными исключениями являются устаревшие браузеры, включая Opera Mini (все версии), UC Browser для Android и более старые мобильные браузеры (iOS Safari < 13.2, Android Browser < 97). Для отслеживания браузеров, реализующих его, и понимания того, как используется атрибут, обратитесь к следующему сервису. Chrome реализовал SameSite=Lax как поведение по умолчанию в 2020 году, Firefox и Edge последовали его примеру. Кроме того, флаг Secure обязателен для cookies, помеченных как SameSite=None.

    Важно отметить, что этот атрибут должен быть реализован как дополнительный уровень концепции эшелонированной обороны. Этот атрибут защищает пользователя через поддерживающие его браузеры, и он содержит 2 способа обхода, упомянутых в следующем разделе. Этот атрибут не должен заменять CSRF-токен. Вместо этого он должен сосуществовать с токеном, чтобы более надёжно защищать пользователя.

    Использование стандартных заголовков для проверки источника¶

    В этом методе защиты есть два шага, оба из которых изучают значение заголовка HTTP-запроса:

    1. Определение источника запроса (исходный источник). Это можно сделать через заголовки Origin или Referer.
    2. Определение источника назначения запроса (целевой источник).

    На стороне сервера проверяется их совпадение. Если они совпадают, запрос принимается как легитимный (то есть это запрос с одного источника); если нет — запрос отклоняется (запрос пришёл из другого домена). Надёжность этих заголовков обусловлена тем, что они не могут быть изменены программно, поскольку входят в список запрещённых заголовков, то есть только браузер может их устанавливать.

    Определение исходного источника (через заголовок Origin/Referer)¶

    Проверка заголовка Origin¶

    Если заголовок Origin присутствует, убедитесь, что его значение совпадает с целевым источником. В отличие от Referer, заголовок Origin будет присутствовать в HTTP-запросах, исходящих из HTTPS URL.

    Проверка заголовка Referer при отсутствии заголовка Origin¶

    Если заголовок Origin отсутствует, убедитесь, что имя хоста в заголовке Referer совпадает с целевым источником. Этот метод защиты от CSRF также широко используется при неаутентифицированных запросах, например при запросах до установления состояния сессии, необходимого для отслеживания токена синхронизации.

    В обоих случаях убедитесь, что проверка целевого источника надёжна. Например, если ваш сайт — example.org, убедитесь, что example.org.attacker.com не проходит проверку источника (то есть выполняйте сопоставление с завершающим символом / после источника, чтобы убедиться в сопоставлении всего источника).

    Если ни один из этих заголовков не присутствует, вы можете либо принять, либо заблокировать запрос. Мы рекомендуем блокировать. В качестве альтернативы можно регистрировать все подобные случаи, отслеживать их варианты использования/поведение, а затем начинать блокировать запросы только после получения достаточной уверенности.

    Определение целевого источника¶

    Как правило, определить целевой источник не всегда просто. Не всегда удаётся просто взять целевой источник (то есть имя хоста и порт #) из URL в запросе, поскольку сервер приложений часто находится за одним или несколькими прокси. Это означает, что исходный URL может отличаться от URL, фактически полученного сервером приложений. Однако если к серверу приложений пользователи обращаются напрямую, то использование источника из URL вполне допустимо.

    Если вы находитесь за прокси, есть ряд вариантов.

    • Настройте приложение на знание своего целевого источника: Поскольку это ваше приложение, вы можете найти его целевой источник и задать это значение в какой-либо записи конфигурации сервера. Это будет наиболее безопасным подходом, поскольку он определён на стороне сервера, то есть является доверенным значением. Однако это может быть затруднительно при развёртывании приложения во многих местах, например в средах dev, test, QA, production и, возможно, в нескольких продакшн-инстанциях. Установка правильного значения для каждой из этих ситуаций может быть сложной, но если вы можете сделать это через централизованную конфигурацию и предоставить вашим инстанциям возможность получать значение из неё — это отличное решение! (Примечание: Убедитесь, что централизованное хранилище конфигурации надёжно защищено, поскольку значительная часть вашей CSRF-защиты зависит от него.)
    • Используйте значение заголовка Host: Если вы хотите, чтобы приложение самостоятельно определяло свой целевой источник без необходимости настройки для каждой развёрнутой инстанции, рекомендуется использовать семейство заголовков Host. Заголовок Host предназначен для содержания целевого источника запроса. Но если ваш сервер приложений находится за прокси, значение заголовка Host, скорее всего, изменено прокси на целевой источник URL за прокси, который отличается от исходного URL. Этот изменённый целевой источник заголовка Host не будет совпадать с исходным источником в исходных заголовках Origin или Referer.
    • Используйте значение заголовка X-Forwarded-Host: Чтобы избежать возможности изменения прокси заголовка host, можно использовать другой заголовок под названием X-Forwarded-Host, содержащий исходное значение заголовка Host, полученное прокси. Большинство прокси передают исходное значение заголовка Host в заголовке X-Forwarded-Host. Таким образом, значение в X-Forwarded-Host, вероятно, является целевым значением источника, которое нужно сравнить с исходным источником в заголовке Origin или Referer.

    Использование этого значения заголовка для защиты будет работать корректно, когда заголовки origin или referrer присутствуют в запросах. Хотя эти заголовки включаются большую часть времени, есть несколько случаев использования, когда они не включаются (большинство из них — по уважительным причинам для защиты конфиденциальности пользователей/адаптации к экосистеме браузеров).

    Случаи использования, когда X-Forward-Host не применяется:

    • При перенаправлении 302 на другой источник, заголовок Origin не включается в перенаправленный запрос, поскольку это может считаться конфиденциальной информацией, которую не следует отправлять другому источнику.
    • Существуют некоторые контексты конфиденциальности, где Origin устанавливается в значение «null». Например, см. следующий пример.
    • Заголовок Origin включается для всех запросов из других источников, но для запросов с того же источника в большинстве браузеров он включается только для POST/DELETE/PUT. Примечание: Хотя это не идеально, многие разработчики используют GET-запросы для операций, изменяющих состояние.
    • Заголовок Referer — не исключение. Существует множество случаев использования, при которых заголовок referrer также опускается (1, 2, 3, 4 и 5). Балансировщики нагрузки, прокси и встроенные сетевые устройства также хорошо известны тем, что удаляют заголовок referrer по соображениям конфиденциальности при его записи в логах.

    Обычно небольшой процент трафика попадает в указанные выше категории (1-2%), и ни одна компания не хочет терять этот трафик. Одним из популярных методов, используемых в интернете для повышения удобства применения этого метода, является принятие запроса, если Origin/referrer совпадает с настроенным списком доменов «ИЛИ» имеет значение null (примеры здесь. Значение null покрывает граничные случаи, упомянутые выше, когда эти заголовки не отправляются). Обратите внимание, что злоумышленники могут использовать это, но люди предпочитают применять этот метод как меру эшелонированной обороны из-за минимальных усилий, необходимых для его развёртывания.

    Использование cookies с префиксами хоста для определения источников¶

    Пока атрибуты SameSite и Secure, упомянутые ранее, ограничивают отправку уже установленных cookies, а HttpOnly ограничивает чтение установленного cookie, злоумышленник всё равно может попытаться внедрить или перезаписать иначе защищённые cookies (ср. атаки фиксации сессии). Использование Cookie Prefixes для cookies с CSRF-токенами расширяет защиту от такого рода атак. Если cookies имеют префиксы __Host-, например Set-Cookie: __Host-token=RANDOM; path=/; Secure, то каждый cookie:

    • Не может быть (пере)записан с другого поддомена.
    • Не может иметь атрибут Domain.
    • Должен иметь путь /.
    • Должен быть помечен как Secure (то есть не может отправляться через незашифрованный HTTP).

    В дополнение к префиксу __Host-, более слабый префикс __Secure- также поддерживается производителями браузеров. Он ослабляет ограничения на перезапись домена, то есть они:

    • Могут иметь атрибуты Domain.
    • Могут быть перезаписаны поддоменами.
    • Могут иметь путь Path, отличный от /.

    Этот ослабленный вариант может использоваться как альтернатива «привязанному к домену» префиксу __Host-, если аутентифицированным пользователям необходимо посещать разные (под-)домены. Во всех остальных случаях рекомендуется использовать префикс __Host- в дополнение к атрибуту SameSite.

    Префиксы cookie поддерживаются всеми основными браузерами.

    Дополнительную информацию о префиксах cookie см. в Mozilla Developer Network и IETF Draft.

    CSRF-защита на основе взаимодействия с пользователем¶

    Хотя все методы, упомянутые здесь, не требуют никакого взаимодействия с пользователем, иногда проще или уместнее привлечь пользователя к транзакции, чтобы предотвратить несанкционированные операции (поддельные через CSRF или иным образом). Ниже приведены некоторые примеры методов, которые при правильной реализации могут служить надёжной CSRF-защитой:

    • Механизмы повторной аутентификации.
    • Одноразовые токены.

    НЕ используйте CAPTCHA, поскольку она специально разработана для защиты от ботов. В некоторых реализациях CAPTCHA возможно получить доказательство взаимодействия человека/присутствия из другой пользовательской сессии. Хотя это усложняет эксплойт CSRF, это не защищает от него.

    Хотя это очень надёжные средства защиты от CSRF, они могут существенно влиять на пользовательский опыт. Поэтому они обычно используются только для критически важных с точки зрения безопасности операций (таких как изменение пароля, денежные переводы и т. д.) в сочетании с другими средствами защиты, описанными в этом cheat sheet.

    Возможные CSRF-уязвимости в формах входа¶

    Большинство разработчиков склонны игнорировать CSRF-уязвимости в формах входа, предполагая, что CSRF неприменим к формам входа, поскольку пользователь не аутентифицирован на этом этапе. Однако это предположение не всегда верно. CSRF-уязвимости всё ещё могут возникать в формах входа, где пользователь не аутентифицирован, но воздействие и риск отличаются.

    Например, если злоумышленник использует CSRF, чтобы взять на себя аутентифицированную личность целевой жертвы на сайте интернет-магазина с использованием учётной записи злоумышленника, а жертва затем вводит данные своей кредитной карты, злоумышленник потенциально сможет совершать покупки, используя сохранённые данные карты жертвы. Для получения дополнительной информации о CSRF при входе и других рисках см. раздел 3 этой статьи.

    CSRF при входе можно снизить путём создания пред-сессий (сессий до аутентификации пользователя) и включения токенов в форму входа. Для генерации токенов можно использовать любой из описанных выше методов. Помните, что пред-сессии нельзя переводить в реальные сессии после аутентификации пользователя — сессия должна быть уничтожена и создана новая, чтобы избежать атак фиксации сессии. Этот метод описан в Robust Defenses for Cross-Site Request Forgery, раздел 4.1. CSRF при входе также можно снизить, включив пользовательский заголовок запроса в AJAX-запрос, как описано выше.

    JavaScript: Автоматическое включение CSRF-токенов в качестве заголовка AJAX-запроса¶

    Следующее руководство для JavaScript по умолчанию считает методы GET, HEAD и OPTIONS безопасными операциями. Поэтому AJAX-вызовы методом GET, HEAD и OPTIONS не нуждаются в добавлении заголовка с CSRF-токеном. Однако если эти методы используются для выполнения операций, изменяющих состояние, они также потребуют заголовка с CSRF-токеном (хотя это плохая практика, которой следует избегать).

    Методы POST, PUT, PATCH и DELETE, как методы, изменяющие состояние, должны иметь CSRF-токен, прикреплённый к запросу. Следующее руководство продемонстрирует, как создавать переопределения в JavaScript-библиотеках, чтобы CSRF-токены автоматически включались в каждый AJAX-запрос для методов, изменяющих состояние, упомянутых выше.

    Хранение значения CSRF-токена в DOM¶

    CSRF-токен может быть включён в тег <meta>, как показано ниже. Все последующие вызовы на странице могут извлекать CSRF-токен из этого тега <meta>. Он также может быть сохранён в JavaScript-переменной или в любом другом месте DOM. Однако не рекомендуется хранить CSRF-токен в cookies или в локальном хранилище браузера.

    Следующий фрагмент кода можно использовать для включения CSRF-токена в качестве тега <meta>:

    <meta name="csrf-token" content="{{ csrf_token() }}">

    Точный синтаксис заполнения атрибута content будет зависеть от языка программирования бэкенда вашего веб-приложения.

    Переопределение настроек по умолчанию для установки пользовательского заголовка¶

    Несколько JavaScript-библиотек позволяют переопределять настройки по умолчанию, чтобы заголовок автоматически добавлялся ко всем AJAX-запросам.

    XMLHttpRequest (нативный JavaScript)¶

    Метод open() XMLHttpRequest можно переопределить, чтобы устанавливать заголовок X-CSRF-Token при каждом вызове метода open(). Функция csrfSafeMethod(), определённая ниже, будет фильтровать безопасные HTTP-методы и добавлять заголовок только к небезопасным HTTP-методам.

    Это можно сделать, как показано в следующем фрагменте кода:

    <script type="text/javascript">
    const csrf_token = document.querySelector("meta[name='csrf-token']").getAttribute("content");

    const csrfSafeMethod = (method) => {
        // эти HTTP-методы не требуют CSRF-защиты
        return /^(GET|HEAD|OPTIONS)$/.test(method);
    };

    const originalOpen = XMLHttpRequest.prototype.open;
    XMLHttpRequest.prototype.open = function(...args) {
        const result = originalOpen.apply(this, args);

        if (!csrfSafeMethod(args[0])) {
            this.setRequestHeader('X-CSRF-Token', csrf_token);
        }

        return result;
    };
</script>

    CSRF-защита в современных фреймворках¶

    Современные Single Page Application (SPA) фреймворки, такие как Angular, React и Vue, как правило, используют паттерн cookie-to-header для снижения риска атак Cross-Site Request Forgery (CSRF). Этот подход использует тот факт, что браузеры автоматически прикрепляют cookies к межсайтовым запросам, но только JavaScript, запущенный в том же источнике, может читать значения и устанавливать пользовательские заголовки — что позволяет обнаруживать и блокировать поддельные запросы. Паттерн cookie-to-header работает следующим образом:

    1. Сервер генерирует CSRF-токен: когда пользователь аутентифицируется или загружает приложение, сервер устанавливает CSRF-токен в cookie (например, XSRF-TOKEN). Этот cookie доступен через JavaScript (то есть не HttpOnly) и обычно имеет SameSite=Lax или Strict.
    2. Клиент считывает токен: SPA (часто используя библиотеку, такую как Angular's HttpClient или axios в React/Vue) считывает CSRF-токен из cookie.
    3. Клиент прикрепляет токен к пользовательскому заголовку: для каждого запроса, изменяющего состояние (POST, PUT, DELETE и т. д.), клиент устанавливает токен как пользовательский HTTP-заголовок (обычно X-XSRF-TOKEN или X-CSRF-TOKEN).
    4. Сервер проверяет токен: сервер проверяет, совпадает ли токен из заголовка с токеном из cookie. Если они совпадают, запрос принимается; если нет — отклоняется как потенциально поддельный.

    Angular предоставляет этот паттерн «из коробки», автоматически обрабатывая шаги 2 и 3 через свой HttpClient. В отличие от этого, фреймворки, такие как React и Vue, требуют от разработчиков реализации этой логики вручную или с помощью вспомогательных библиотек, таких как перехватчики axios. Этот паттерн гарантирует, что даже если браузер включает cookies в поддельный запрос, злоумышленник не может установить совпадающий пользовательский заголовок из другого источника.

    Angular¶

    HttpClient Angular поддерживает паттерн Cookie-to-Header, используемый для предотвращения XSRF-атак. При выполнении HTTP-запросов перехватчик считывает токен из cookie (по умолчанию XSRF-TOKEN) и устанавливает его как HTTP-заголовок X-XSRF-TOKEN. Дополнительную документацию можно найти в документации Angular по безопасности HttpClient XSRF/CSRF.

Функция csrfSafeMethod(), определённая ниже, будет фильтровать безопасные HTTP-методы и добавлять заголовок только к небезопасным HTTP-методам.

    Вы можете настроить jQuery для автоматического добавления токена во все заголовки запросов, приняв следующий фрагмент кода. Это обеспечивает простую и удобную CSRF-защиту для ваших приложений на основе AJAX:

    <script type="text/javascript">

    Утилиты TypeScript для CSRF-защиты¶

    TypeScript позволяет создавать строго типизированные утилиты для CSRF-защиты. Ниже представлен повторно используемый модуль утилит для управления CSRF-токенами:

    // csrf-protection.ts

/**
 * Параметры конфигурации для CSRF-защиты
 */
interface CSRFOptions {
  /** Имя cookie, в котором хранится CSRF-токен */
  cookieName: string;
  /** Имя HTTP-заголовка для отправки токена */
  headerName: string;
  /** HTTP-методы, требующие CSRF-защиты */
  unsafeMethods: string[];
}

/**
 * Конфигурация по умолчанию для CSRF-защиты
 */
const DEFAULT_CSRF_OPTIONS: CSRFOptions = {
  cookieName: 'XSRF-TOKEN',
  headerName: 'X-CSRF-Token',
  unsafeMethods: ['POST', 'PUT', 'PATCH', 'DELETE']
};

/**
 * Класс утилиты CSRF-защиты
 */
export class CSRFProtection {
  private options: CSRFOptions;

  constructor(options: Partial<CSRFOptions> = {}) {
    this.options = { ...DEFAULT_CSRF_OPTIONS, ...options };
  }

  /**
   * Извлечь CSRF-токен из cookies
   * @returns CSRF-токен или пустую строку, если не найден
   */
  public getToken(): string {
    const cookieValue = document.cookie
      .split('; ')
      .find(cookie => cookie.startsWith(`${this.options.cookieName}=`));

    return cookieValue ? cookieValue.split('=')[1] : '';
  }

  /**
   * Проверить, требует ли указанный HTTP-метод CSRF-защиты
   */
  public requiresProtection(method: string): boolean {
    return this.options.unsafeMethods.includes(method.toUpperCase());
  }

  /**
   * Добавить CSRF-токен к предоставленному объекту заголовков, если необходимо
   */
  public addTokenToHeaders(method: string, headers: Record<string, string>): Record<string, string> {
    if (this.requiresProtection(method)) {
      const token = this.getToken();
      if (token) {
        headers[this.options.headerName] = token;
      }
    }
    return headers;
  }
}

    Для пользовательского HTTP-перехватчика, обрабатывающего CSRF-токены:

    // csrf.interceptor.ts
import { Injectable } from '@angular/core';
import {
  HttpRequest,
  HttpHandler,
  HttpEvent,
  HttpInterceptor
} from '@angular/common/http';
import { Observable } from 'rxjs';

@Injectable()
export class CsrfInterceptor implements HttpInterceptor {
  private readonly TOKEN_HEADER_NAME = 'X-CSRF-Token';
  private readonly SAFE_METHODS = ['GET', 'HEAD', 'OPTIONS'];

  constructor() {}

  intercept(request: HttpRequest<unknown>, next: HttpHandler): Observable<HttpEvent<unknown>> {
    // Пропускаем CSRF-защиту для безопасных методов
    if (this.SAFE_METHODS.includes(request.method)) {
      return next.handle(request);
    }

    // Получаем токен из cookie
    const token = this.getTokenFromCookie();

    if (token) {
      // Клонируем запрос и добавляем заголовок с CSRF-токеном
      const modifiedRequest = request.clone({
        headers: request.headers.set(this.TOKEN_HEADER_NAME, token)
      });
      return next.handle(modifiedRequest);
    }

    return next.handle(request);
  }

  private getTokenFromCookie(): string {
    const tokenCookie = document.cookie
      .split('; ')
      .find(cookie => cookie.startsWith('XSRF-TOKEN='));

    return tokenCookie ? tokenCookie.split('=')[1] : '';
  }
}

    React с TypeScript¶

    Реализация TypeScript для React-приложений с использованием axios:

    // csrf-axios.ts
import axios, { AxiosInstance, AxiosRequestConfig } from 'axios';

/**
 * Создать экземпляр axios с CSRF-защитой
 */
export function createCSRFProtectedAxios(
  options: {
    baseURL?: string;
    csrfHeaderName?: string;
    csrfCookieName?: string;
  } = {}
): AxiosInstance {
  const {
    baseURL = '',
    csrfHeaderName = 'X-CSRF-Token',
    csrfCookieName = 'XSRF-TOKEN'
  } = options;

  // Создаём экземпляр axios
  const instance = axios.create({ baseURL });

  // Добавляем перехватчик CSRF-токена
  instance.interceptors.request.use((config: AxiosRequestConfig) => {
    // Добавлять только для не-GET запросов
    if (config.method && !['get', 'head', 'options'].includes(config.method.toLowerCase())) {
      const token = getCsrfToken(csrfCookieName);

      if (token && config.headers) {
        config.headers[csrfHeaderName] = token;
      }
    }
    return config;
  });

  return instance;
}

/**
 * Интерфейс параметров CSRF-защиты
 */
interface CSRFFetchOptions {
  csrfHeaderName: string;
  csrfCookieName: string;
  baseUrl: string;
}

/**
 * Обёртка вокруг fetch API с CSRF-защитой
 */
export class CSRFProtectedFetch {
  private options: CSRFFetchOptions;

  constructor(options: Partial<CSRFFetchOptions> = {}) {
    this.options = {
      csrfHeaderName: 'X-CSRF-Token',
      csrfCookieName: 'XSRF-TOKEN',
      baseUrl: '',
      ...options
    };
  }

  /**
   * Выполняет fetch-запрос с CSRF-защитой
   */
  public async fetch<T>(
    url: string,
    options: RequestInit = {}
  ): Promise<T> {
    const { method = 'GET' } = options;
    const fullUrl = `${this.options.baseUrl}${url}`;

    // Создаём заголовки с CSRF-токеном для небезопасных методов
    const headers = new Headers(options.headers);

    if (!['GET', 'HEAD', 'OPTIONS'].includes(method.toUpperCase())) {
      const token = this.getCsrfToken();
      if (token) {
        headers.append(this.options.csrfHeaderName, token);
      }
    }

    // Выполняем запрос
    const response = await fetch(fullUrl, {
      ...options,
      headers
    });

    if (!response.ok) {
      throw new Error(`Request failed with status ${response.status}`);
    }

    return response.json();
  }

  /**
   * Сокращение для POST-запросов
   */
  public async post<T>(url: string, data: any, options: RequestInit = {}): Promise<T> {
    return this.fetch<T>(url, {
      ...options,
      method: 'POST',
      body: JSON.stringify(data),
      headers: {
        ...options.headers,
        'Content-Type': 'application/json'
      }
    });
  }

  /**
   * Извлечь CSRF-токен из cookies
   */
  private getCsrfToken(): string {
    const tokenCookie = document.cookie
      .split('; ')
      .find(cookie => cookie.startsWith(`${this.options.csrfCookieName}=`));

    return tokenCookie ? tokenCookie.split('=')[1] : '';
  }
}
