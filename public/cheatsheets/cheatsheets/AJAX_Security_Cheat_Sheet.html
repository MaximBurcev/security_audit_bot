    Шпаргалка по безопасности AJAX¶

    Введение¶

    Данный документ является отправной точкой для изучения безопасности AJAX и, как ожидается, будет регулярно обновляться и дополняться более подробной информацией о конкретных фреймворках и технологиях.

    Прежде чем применять какие-либо конкретные меры защиты, разработчики должны усвоить базовый принцип безопасности: Все данные следует считать ненадёжными, если они явно не прошли проверку и не обрабатываются безопасным образом. Это относится к:

    • Входным данным на стороне клиента
    • Ответам API
    • Сторонним интеграциям
    • Внутренним сервисам и микросервисам
    • Кэшированным ответам
    • Хранилищу браузера (localStorage, sessionStorage)
    • Скрытым полям форм

    Клиентская сторона (JavaScript)¶

    Используйте innerHTML с крайней осторожностью¶

    Манипуляция Document Object Model (DOM) широко распространена в веб-приложениях — как в монолитных приложениях с серверным рендерингом (например, PHP, ASP.NET), так и в AJAX-приложениях. Хотя innerHTML кажется удобным способом вставки HTML-содержимого, его использование с ненадёжными данными сопряжено с серьёзными рисками безопасности, в особенности с уязвимостями cross-site scripting (XSS).

    Что такое innerHTML?¶

    Свойство innerHTML устанавливает или получает HTML-содержимое элемента, включая теги, которые браузер разбирает и отображает как часть DOM. Например, установка innerHTML = "<p>Hello</p>" создаёт элемент-абзац.

    Почему innerHTML требует крайней осторожности?¶

    Использование innerHTML с ненадёжными данными (например, из ответов API в AJAX) может позволить выполнение вредоносного JavaScript в браузере пользователя, что приводит к уязвимостям XSS. Возможные риски включают:

    • Кражу куки сессии пользователя.
    • Порчу сайта.
    • Перенаправление пользователей на вредоносные сайты.
    • Выполнение несанкционированных действий (например, вызовов API от имени пользователя).
    • Кейлоггинг вводимых данных.
    Уязвимый пример¶
        document.getElementById('content').innerHTML = data;
    // ОПАСНО! Сервер мог вернуть нагрузку, выполняющую скрипты, например: <img src=abc onerror=alert('xss!')>.
    Когда innerHTML допустим?¶

    Основное правило безопасности — никогда не использовать innerHTML с ненадёжными данными. Однако в ограниченных случаях, например в устаревших монолитных приложениях без жизнеспособных альтернатив, innerHTML может использоваться с осторожностью:

    • Статический, жёстко закодированный HTML: Для небольших, фиксированных HTML-фрагментов, являющихся частью исходного кода приложения и не содержащих пользовательских данных:
    document.getElementById('footer').innerHTML = '<p>© 2025 My Company. All rights reserved.</p>';
    • Санированный HTML: Для HTML, созданного пользователем (например, в редакторах форматированного текста), выполняйте санацию с помощью библиотеки, например DOMPurify, перед использованием innerHTML:
    import DOMPurify from 'dompurify';
const userInput = '<img src=abc onerror=alert("xss")>';
document.getElementById('content').innerHTML = DOMPurify.sanitize(userInput); // Безопасно, удаляет вредоносный код
    Альтернативы¶
    • Используйте шаблонизаторы (с автоэкранированием) для повторно используемых структурированных HTML-фрагментов.
    • Используйте современные фреймворки (React, Vue, Angular, Svelte) для сложных приложений. Они стандартизируют манипуляцию DOM, обеспечивают реактивность и по умолчанию выполняют санацию динамических данных. Однако разработчики должны избегать небезопасных API (например, dangerouslySetInnerHTML в React, [innerHTML] в Angular) для предотвращения уязвимостей XSS.

    Использование textContent или innerText для обновления DOM (только для текстового содержимого)¶

    В AJAX-приложениях и монолитных приложениях с серверным рендерингом (например, PHP, ASP.NET) динамические обновления Document Object Model (DOM) широко используются для отображения текстового содержимого из API или пользовательских данных.

    Что такое textContent?¶

    Свойство textContent устанавливает или получает простое текстовое содержимое элемента. Вставленные HTML-теги обрабатываются как буквальный текст и не разбираются. Идеально подходит для большинства обновлений с текстовым содержимым, например для отображения комментариев пользователей и т.д.

    const userInput = '<script>alert("OWASP")</script>';
document.getElementById('content').textContent = userInput; // Отображается как обычный текст
    Что такое innerText?¶

    Свойство innerText устанавливает или получает видимое текстовое содержимое элемента с учётом стилей CSS (например, игнорируя текст в элементах с display: none). Также отражает форматирование отображаемого текста — переносы строк и отступы.

    const userInput = 'OWASP';
document.getElementById('content').innerText = userInput;
    Когда использовать textContent и innerText¶
    • Используйте textContent: В монолитных приложениях для безопасной вставки простого текста, возвращаемого API.
    • Используйте innerText: Только когда требуется учёт CSS-видимости или форматирования отображаемого текста (например, игнорирование текста в элементах с display: none).

    Примечание: textContent немного быстрее и более предсказуем; используйте его, если только не нужно учитывать форматирование отображаемого текста (innerText).

    Примечание¶
    • Хотя textContent и innerText безопасны для вставки обычного текста в DOM, они не защищают от XSS в других контекстах, таких как HTML-атрибуты, обработчики событий JavaScript или URL. Всегда проверяйте и санируйте ненадёжные входные данные.
    • Современные фреймворки, такие как React, Vue, Angular или Svelte, автоматически обновляют текстовое содержимое, поэтому нет необходимости вручную использовать textContent или innerText.

    Не используйте eval(), new Function() и другие инструменты выполнения кода¶

    Функция eval() опасна, никогда её не используйте. Потребность в eval() обычно указывает на проблему в проектировании.

    Примечание: Использование eval() или new Function() открывает двери для удалённого выполнения кода и XSS. Избегайте их полностью.

    Кодируйте данные перед использованием в контексте вывода¶

    При использовании данных для построения HTML, скрипта, CSS, XML, JSON и т.д. обязательно учитывайте, как эти данные должны быть представлены в буквальном смысле для сохранения логического значения.

    Данные должны быть правильно закодированы перед использованием таким образом, чтобы предотвратить уязвимости типа инъекций и обеспечить сохранение логического смысла.

    Ознакомьтесь с проектом OWASP Java Encoder.

    Не полагайтесь на клиентскую логику для обеспечения безопасности¶

    Не забывайте, что пользователь контролирует клиентскую логику. Существует множество плагинов для браузера, позволяющих устанавливать точки останова, пропускать код, изменять значения и т.д. Никогда не полагайтесь на клиентскую логику для обеспечения безопасности.

    Не полагайтесь на клиентскую бизнес-логику¶

    Как и в случае с логикой безопасности, убедитесь, что все важные бизнес-правила дублируются на стороне сервера, чтобы пользователь не мог их обойти, что могло бы привести к неожиданному или дорогостоящему поведению.

    Избегайте написания кода сериализации¶

    Это сложная задача, и даже небольшая ошибка может повлечь серьёзные проблемы безопасности. Уже существует множество фреймворков, предоставляющих эту функциональность.

    Подробнее см. на странице JSON.

    Избегайте динамического построения XML или JSON¶

    Как и при построении HTML или SQL, вы можете создать уязвимости XML-инъекций, поэтому избегайте этого или, как минимум, используйте библиотеку кодирования или безопасную библиотеку JSON/XML для защиты атрибутов и данных элементов.

    • Предотвращение XSS (Cross Site Scripting)
    • Предотвращение SQL Injection

    Никогда не передавайте секреты клиенту¶

    Всё, что отправляется клиенту, может быть прочитано или изменено пользователем, поэтому храните все секретные данные на сервере.

    Не выполняйте шифрование на стороне клиента¶

    Используйте TLS/SSL и шифруйте на стороне сервера!

    Не выполняйте на стороне клиента логику, влияющую на безопасность¶

    Этот принцип является защитной мерой последнего рубежа: если принятие решения в области безопасности неоднозначно, принимайте его на стороне сервера.

    Защита от перехвата JSON для старых браузеров¶

    Изучите механизм защиты AngularJS от перехвата JSON¶

    См. раздел JSON Vulnerability Protection в документации AngularJS.

    Всегда возвращайте JSON с объектом на внешнем уровне¶

    Всегда используйте объект в качестве внешнего примитива для строк JSON:

    Уязвимо:

    [{"object": "inside an array"}]

    Не уязвимо:

    {"object": "not inside an array"}

    Также не уязвимо:

    {"result": [{"object": "inside an array"}]}

    Избегайте написания кода сериализации на стороне сервера¶

    Помните о разнице между ссылочными и значимыми типами; используйте проверенную библиотеку.

    Сервисы могут вызываться напрямую пользователями¶

    Несмотря на то, что вы ожидаете вызовов к этим сервисам только со стороны вашего AJAX-клиентского кода, злоумышленник также может вызывать их напрямую.

    Проверяйте входные данные и обращайтесь с ними как с данными, находящимися под контролем пользователя.

    Избегайте ручного построения XML или JSON — используйте фреймворк¶

    Используйте фреймворк для сериализации данных; ручное построение нагрузки может создавать проблемы безопасности.

    Используйте JSON и XML schema для веб-сервисов¶

    Используйте сторонние библиотеки для проверки входных данных веб-сервисов.
