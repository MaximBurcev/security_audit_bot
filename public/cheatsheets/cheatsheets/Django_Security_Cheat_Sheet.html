    Django Security Cheat Sheet¶

    Введение¶

    Django — мощный веб-фреймворк на Python со встроенными механизмами безопасности, которые можно применять «из коробки» для защиты от распространённых веб-уязвимостей. В этом чит-листе перечислены действия и советы по безопасности, которые помогут разработчикам создавать защищённые приложения на Django. Документ охватывает наиболее частые уязвимости и способы повышения уровня безопасности Django-приложения. Каждый пункт содержит краткое пояснение и соответствующие примеры кода, характерные для среды Django.

    Django предоставляет ряд встроенных функций безопасности, изначально ориентированных на безопасность по умолчанию. Эти функции также достаточно гибки, чтобы разработчики могли повторно использовать компоненты в сложных сценариях. Это открывает возможность для ситуаций, когда разработчики, незнакомые с внутренним устройством компонентов, могут настроить их небезопасным образом. Данный чит-лист призван рассмотреть некоторые из таких случаев.

    Общие рекомендации¶

    • Всегда обновляйте Django и зависимости вашего приложения, чтобы не упустить исправления уязвимостей безопасности.
    • Убедитесь, что приложение никогда не работает в режиме DEBUG в производственной среде. Никогда не используйте DEBUG = True в продакшене.
    • Используйте пакеты вроде django_ratelimit или django-axes для защиты от атак перебора паролей.

    Аутентификация¶

    • Используйте приложение django.contrib.auth для представлений и форм, связанных с аутентификацией пользователей: вход, выход, смена пароля и т. д. Включите модуль и его зависимости django.contrib.contenttypes и django.contrib.sessions в настройку INSTALLED_APPS файла settings.py.
    INSTALLED_APPS = [
    # ...
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    # ...
]
    • Используйте декоратор @login_required, чтобы гарантировать доступ к представлению только для аутентифицированных пользователей. Пример использования @login_required:
    from django.contrib.auth.decorators import login_required

# Пользователь перенаправляется на страницу входа по умолчанию, если не аутентифицирован.
@login_required
def my_view(request):
  # Логика вашего представления

# Пользователь перенаправляется на '/login-page/', если не аутентифицирован.
@login_required(login_url='/login-page/')
def my_view(request):
  # Логика вашего представления
    • Используйте валидаторы паролей для соблюдения политики паролей. Добавьте или обновите настройку AUTH_PASSWORD_VALIDATORS в settings.py, включив валидаторы, необходимые вашему приложению.
    AUTH_PASSWORD_VALIDATORS = [
  {
    # Проверяет сходство пароля с набором атрибутов пользователя.
    'NAME': 'django.contrib.auth.password_validation.UserAttributeSimilarityValidator',
    'OPTIONS': {
      'user_attributes': ('username', 'email', 'first_name', 'last_name'),
      'max_similarity': 0.7,
    }
  },
  {
    # Проверяет, соответствует ли пароль минимальной длине.
    'NAME': 'django.contrib.auth.password_validation.MinimumLengthValidator',
    'OPTIONS': {
      'min_length': 8,
    }
  },
  {
    # Проверяет, не входит ли пароль в список распространённых паролей.
    'NAME': 'django.contrib.auth.password_validation.CommonPasswordValidator',
  },
  {
    # Проверяет, что пароль не состоит полностью из цифр.
    'NAME': 'django.contrib.auth.password_validation.NumericPasswordValidator',
  }
]
    • Храните пароли с помощью утилиты make_password для хэширования пароля в открытом виде.
    from django.contrib.auth.hashers import make_password
#...
hashed_pwd = make_password('plaintext_password')
    • Для проверки пароля в открытом виде против хэшированного используйте утилиту check_password.
    from django.contrib.auth.hashers import check_password
#...
plain_pwd = 'plaintext_password'
hashed_pwd = 'hashed_password_from_database'

if check_password(plain_pwd, hashed_pwd):
  print("Пароль верный.")
else:
  print("Пароль неверный.")

    Управление ключами¶

    Параметр SECRET_KEY в settings.py используется для криптографической подписи и должен храниться в тайне. Учитывайте следующие рекомендации:

    • Генерируйте ключ длиной не менее 50 символов, содержащий смесь букв, цифр и символов.
    • Убедитесь, что SECRET_KEY генерируется с помощью надёжного генератора случайных чисел, например функции get_random_secret_key() в Django.
    • Избегайте жёсткого прописывания значения SECRET_KEY в settings.py или любом другом месте. Рассмотрите возможность хранения ключа в переменных окружения или менеджерах секретов.
    import os
SECRET_KEY = os.environ.get('DJANGO_SECRET_KEY')
    • Регулярно ротируйте ключ, учитывая, что это действие может аннулировать сессии, токены сброса пароля и т. д. Немедленно смените ключ, если он был скомпрометирован.

    Заголовки¶

    Включите модуль django.middleware.security.SecurityMiddleware в настройку MIDDLEWARE в settings.py проекта для добавления заголовков безопасности к ответам. Этот модуль используется для установки следующих параметров:

    • SECURE_CONTENT_TYPE_NOSNIFF: установите в True. Защищает от атак подмены MIME-типа, включая заголовок X-Content-Type-Options: nosniff.
    • SECURE_HSTS_SECONDS: гарантирует, что сайт доступен только через HTTPS.

    Включите модуль django.middleware.clickjacking.XFrameOptionsMiddleware в настройку MIDDLEWARE в settings.py проекта (этот модуль должен располагаться после django.middleware.security.SecurityMiddleware, поскольку порядок важен). Этот модуль используется для установки следующих параметров:

    • X_FRAME_OPTIONS: установите значение 'DENY' или 'SAMEORIGIN'. Этот параметр добавляет заголовок X-Frame-Options ко всем HTTP-ответам и защищает от атак кликджекинга.

    Cookies¶

    • SESSION_COOKIE_SECURE: установите в True в settings.py. Это обеспечит передачу сессионного cookie только через защищённые соединения (HTTPS).
    • CSRF_COOKIE_SECURE: установите в True в settings.py. Это обеспечит передачу CSRF-cookie только через защищённые соединения.
    • При установке пользовательского cookie в представлении с помощью метода HttpResponse.set_cookie() обязательно устанавливайте параметр secure в True.
    response = HttpResponse("Some response")
response.set_cookie('my_cookie', 'cookie_value', secure=True)

    Межсайтовая подделка запроса (CSRF)¶

    • Включите модуль django.middleware.csrf.CsrfViewMiddleware в настройку MIDDLEWARE в settings.py проекта для добавления CSRF-заголовков к ответам.
    • В формах используйте тег шаблона {% csrf_token %} для включения CSRF-токена. Пример:
    <form method="post">
    {% csrf_token %}
    <!-- Поля формы -->
</form>
    • Для AJAX-вызовов CSRF-токен запроса необходимо извлечь перед использованием в AJAX-вызове.
    • Дополнительные рекомендации и средства защиты можно найти в документации Django по защите от межсайтовой подделки запроса.

    Межсайтовый скриптинг (XSS)¶

    Рекомендации в этом разделе дополняют ранее упомянутые рекомендации по XSS.

    • Используйте встроенную систему шаблонов для рендеринга шаблонов в Django. Подробнее см. документацию Django по автоматическому экранированию HTML.
    • Старайтесь избегать использования фильтра safe (или функции mark_safe) для отключения автоматического экранирования шаблонов Django. Если вам всё же нужно его использовать, убедитесь, что входные данные поступают из доверенного источника. При работе с данными, контролируемыми пользователем, требуется особая осторожность.
    • Используйте фильтр шаблонов json_script для передачи данных в JavaScript внутри шаблонов Django.
    • Подробнее см. документацию Django по защите от межсайтового скриптинга (XSS).

    HTTPS¶

    • Включите модуль django.middleware.security.SecurityMiddleware в настройку MIDDLEWARE в settings.py проекта, если он ещё не добавлен.
    • Установите SECURE_SSL_REDIRECT = True в settings.py, чтобы гарантировать, что всё взаимодействие происходит по HTTPS. Это автоматически перенаправит любые HTTP-запросы на HTTPS. Это также постоянный редирект (301), поэтому браузер запомнит его для последующих запросов.
    • Если ваше Django-приложение работает за прокси или балансировщиком нагрузки, установите настройку SECURE_PROXY_SSL_HEADER, чтобы Django мог определить протокол исходного запроса. Подробнее см. документацию SECURE_PROXY_SSL_HEADER.

    URL панели администратора¶

    Рекомендуется изменить URL по умолчанию, ведущий к панели администратора (example.com/admin/), чтобы немного усложнить автоматизированные атаки. Как это сделать:

    В папке приложения по умолчанию внутри вашего проекта найдите файл urls.py, управляющий URL верхнего уровня. В этом файле измените переменную urlpatterns (список) так, чтобы URL, ведущий к admin.site.urls, отличался от "admin/". Такой подход добавляет дополнительный уровень безопасности, скрывая стандартный endpoint административного доступа.

    Встроенная команда Django check --deploy¶

    Django имеет встроенную команду check --deploy для проверки безопасности. Пример:

    $ ./manage.py check --deploy
System check identified some issues:

WARNINGS:
?: (security.W004) You have not set a value for the SECURE_HSTS_SECONDS setting. If your entire site is served only over SSL, you may want to consider setting a value and enabling HTTP Strict Transport Security. Be sure to read the documentation first; enabling HSTS carelessly can cause serious, irreversible problems.
?: (security.W008) Your SECURE_SSL_REDIRECT setting is not set to True. Unless your site should be available over both SSL and non-SSL connections, you may want to either set this setting True or configure a load balancer or reverse-proxy server to redirect all connections to HTTPS.
?: (security.W009) Your SECRET_KEY has less than 50 characters, less than 5 unique characters, or it's prefixed with 'django-insecure-' indicating that it was generated automatically by Django. Please generate a long and random value, otherwise many of Django's security-critical features will be vulnerable to attack.
?: (security.W012) SESSION_COOKIE_SECURE is not set to True. Using a secure-only session cookie makes it more difficult for network traffic sniffers to hijack user sessions.
?: (security.W016) You have 'django.middleware.csrf.CsrfViewMiddleware' in your MIDDLEWARE, but you have not set CSRF_COOKIE_SECURE to True. Using a secure-only CSRF cookie makes it more difficult for network traffic sniffers to steal the CSRF token.
?: (security.W018) You should not have DEBUG set to True in deployment.
?: (security.W020) ALLOWED_HOSTS must not be empty in deployment.

System check identified 7 issues (0 silenced).

    Вы можете усилить защиту вашего Django-проекта, устранив предупреждения, выдаваемые этой командой.
