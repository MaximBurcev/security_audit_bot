    SQL Injection Prevention Cheat Sheet¶

    Введение¶

    Данный cheat sheet поможет вам предотвратить уязвимости SQL injection в ваших приложениях. Здесь объясняется, что такое SQL injection, где возникают эти уязвимости, и описаны четыре способа защиты от атак SQL injection. Атаки SQL Injection распространены по двум причинам:

    1. Уязвимости SQL Injection встречаются очень часто, и
    2. База данных приложения является частой целью злоумышленников, поскольку обычно содержит интересные/критически важные данные.

    Что такое атака SQL Injection?¶

    Злоумышленники могут использовать SQL injection в приложении, если оно содержит динамические запросы к базе данных, использующие конкатенацию строк и пользовательский ввод. Чтобы избежать уязвимостей SQL injection, разработчики должны:

    1. Прекратить писать динамические запросы с конкатенацией строк, или
    2. Предотвратить включение вредоносного SQL-ввода в выполняемые запросы.

    Существуют простые техники предотвращения уязвимостей SQL injection, которые можно использовать практически с любым языком программирования и любым типом базы данных. Хотя XML-базы данных могут иметь аналогичные проблемы (например, XPath и XQuery injection), эти техники также могут применяться для их защиты.

    Анатомия типичной уязвимости SQL Injection¶

    Ниже показана распространённая уязвимость SQL injection в Java. Поскольку непроверенный параметр "customerName" просто добавляется к запросу, злоумышленник может ввести SQL-код в этот запрос, и приложение выполнит этот код в базе данных.

    String query = "SELECT account_balance FROM user_data WHERE user_name = "
             + request.getParameter("customerName");
try {
    Statement statement = connection.createStatement( ... );
    ResultSet results = statement.executeQuery( query );
}

    Основные способы защиты¶

    • Вариант 1: Использование подготовленных выражений (с параметризованными запросами)
    • Вариант 2: Использование правильно написанных хранимых процедур
    • Вариант 3: Валидация ввода по белому списку
    • Вариант 4: НАСТОЯТЕЛЬНО НЕ РЕКОМЕНДУЕТСЯ: Экранирование всего пользовательского ввода

    Вариант защиты 1: Подготовленные выражения (с параметризованными запросами)¶

    Когда разработчиков обучают написанию запросов к базе данных, им следует рекомендовать использовать подготовленные выражения с привязкой переменных (так называемые параметризованные запросы). Подготовленные выражения просты в написании и понятнее динамических запросов, а параметризованные запросы заставляют разработчика сначала определить весь SQL-код, а затем передавать каждый параметр в запрос.

    Если запросы к базе данных используют такой стиль написания кода, база данных всегда будет различать код и данные, независимо от того, какой пользовательский ввод предоставлен. Кроме того, подготовленные выражения гарантируют, что злоумышленник не сможет изменить намерение запроса, даже если SQL-команды будут вставлены злоумышленником.

    Безопасный пример подготовленного выражения на Java¶

    В безопасном примере на Java ниже, если злоумышленник введёт userID как tom' or '1'='1, параметризованный запрос будет искать имя пользователя, которое буквально совпадает со всей строкой tom' or '1'='1. Таким образом, база данных будет защищена от внедрения вредоносного SQL-кода.

    Следующий пример кода использует PreparedStatement — реализацию параметризованного запроса в Java — для выполнения того же запроса к базе данных.

    // Это тоже ДЕЙСТВИТЕЛЬНО нужно валидировать
String custname = request.getParameter("customerName");
// Выполнение валидации ввода для обнаружения атак
String query = "SELECT account_balance FROM user_data WHERE user_name = ? ";
PreparedStatement pstmt = connection.prepareStatement( query );
pstmt.setString( 1, custname);
ResultSet results = pstmt.executeQuery( );

    Безопасный пример подготовленного выражения на C# .NET¶

    В .NET создание и выполнение запроса не меняется. Просто передайте параметры в запрос с помощью вызова Parameters.Add(), как показано ниже.

    String query = "SELECT account_balance FROM user_data WHERE user_name = ?";
try {
  OleDbCommand command = new OleDbCommand(query, connection);
  command.Parameters.Add(new OleDbParameter("customerName", CustomerName Name.Text));
  OleDbDataReader reader = command.ExecuteReader();
  // …
} catch (OleDbException se) {
  // обработка ошибок
}

    Хотя мы показали примеры на Java и .NET, практически все другие языки (включая Cold Fusion и Classic ASP) поддерживают интерфейсы параметризованных запросов. Даже уровни абстракции SQL, такие как Hibernate Query Language (HQL) с теми же типами проблем внедрения (называемых HQL Injection), поддерживают параметризованные запросы:

    Пример подготовленного выражения Hibernate Query Language (HQL) (именованные параметры)¶

    // Это небезопасный HQL-запрос
Query unsafeHQLQuery = session.createQuery("from Inventory where productID='"+userSuppliedParameter+"'");
// Вот безопасная версия того же запроса с использованием именованных параметров
Query safeHQLQuery = session.createQuery("from Inventory where productID=:productid");
safeHQLQuery.setParameter("productid", userSuppliedParameter);

    Другие примеры безопасных подготовленных выражений¶

    Если вам нужны примеры параметризованных запросов/языков, включая Ruby, PHP, Cold Fusion, Perl и Rust, см. Query Parameterization Cheat Sheet или этот сайт.

    Как правило, разработчики предпочитают подготовленные выражения, поскольку весь SQL-код остаётся внутри приложения, что делает приложения относительно независимыми от базы данных.

    Вариант защиты 2: Хранимые процедуры¶

    Хотя хранимые процедуры не всегда защищены от SQL injection, разработчики могут использовать определённые стандартные конструкции программирования хранимых процедур. Этот подход имеет тот же эффект, что и использование параметризованных запросов, при условии, что хранимые процедуры реализованы безопасно (что является нормой для большинства языков хранимых процедур).

    Безопасный подход к хранимым процедурам¶

    Если необходимо использовать хранимые процедуры, наиболее безопасный подход требует, чтобы разработчик строил SQL-выражения с параметрами, которые автоматически параметризуются, если только разработчик не делает что-то нестандартное. Разница между подготовленными выражениями и хранимыми процедурами заключается в том, что SQL-код хранимой процедуры определяется и хранится в самой базе данных, а затем вызывается из приложения. Поскольку подготовленные выражения и безопасные хранимые процедуры одинаково эффективны в предотвращении SQL injection, ваша организация должна выбрать подход, наиболее подходящий для вас.

    Когда хранимые процедуры могут увеличить риск¶

    Иногда хранимые процедуры могут увеличить риск при атаке на систему. Например, в MS SQL Server есть три основные роли по умолчанию: db_datareader, db_datawriter и db_owner. До появления хранимых процедур DBA предоставляли права db_datareader или db_datawriter пользователю веб-сервиса в зависимости от требований.

    Однако хранимые процедуры требуют прав на выполнение — роли, недоступной по умолчанию. В некоторых конфигурациях, где управление пользователями централизовано, но ограничено этими 3 ролями, веб-приложениям приходится работать как db_owner, чтобы хранимые процедуры работали. Это означает, что в случае взлома сервера злоумышленник получает полные права на базу данных, тогда как ранее мог иметь только права на чтение.

    Безопасный пример хранимой процедуры на Java¶

    Следующий пример кода использует реализацию интерфейса хранимой процедуры в Java (CallableStatement) для выполнения того же запроса к базе данных. Хранимая процедура sp_getAccountBalance должна быть предварительно определена в базе данных и реализовывать ту же функциональность, что и запрос выше.

    // Это ДЕЙСТВИТЕЛЬНО нужно валидировать
String custname = request.getParameter("customerName");
try {
  CallableStatement cs = connection.prepareCall("{call sp_getAccountBalance(?)}");
  cs.setString(1, custname);
  ResultSet results = cs.executeQuery();
  // … обработка результирующего набора
} catch (SQLException se) {
  // … логирование и обработка ошибок
}

    Следующий пример кода использует SqlCommand — реализацию интерфейса хранимой процедуры в .NET — для выполнения того же запроса к базе данных. Хранимая процедура sp_getAccountBalance должна быть предварительно определена в базе данных и реализовывать ту же функциональность, что и запрос выше.

     Try

   command.CommandType = CommandType.StoredProcedure
   command.Parameters.Add(new SqlParameter("@CustomerName", CustomerName.Text))
   Dim reader As SqlDataReader = command.ExecuteReader()
   '...
 Catch se As SqlException
   'обработка ошибок
 End Try

    Вариант защиты 3: Валидация ввода по белому списку¶

    Если вы столкнулись с частями SQL-запросов, в которых нельзя использовать привязку переменных, например, именами таблиц, именами столбцов или индикаторами порядка сортировки (ASC или DESC), наиболее подходящей защитой является валидация ввода или переработка запроса. Когда требуются имена таблиц или столбцов, эти значения в идеале должны поступать из кода, а не из параметров пользователя.

    Пример безопасной валидации имён таблиц¶

    ВНИМАНИЕ: Использование значений параметров пользователя для адресации имён таблиц или столбцов является симптомом плохого дизайна, и при наличии времени следует рассмотреть полную переработку. Если это невозможно, разработчики должны сопоставлять значения параметров с разрешёнными/ожидаемыми именами таблиц или столбцов, чтобы непроверенный пользовательский ввод не попадал в запрос.

    В примере ниже, поскольку tableName идентифицирован как одно из допустимых и ожидаемых значений имени таблицы в этом запросе, его можно непосредственно добавить к SQL-запросу. Имейте в виду, что общие функции валидации таблиц могут привести к потере данных, если имена таблиц используются в запросах, где они не ожидаются.

    String tableName;
switch(PARAM):
  case "Value1": tableName = "fooTable";
                 break;
  case "Value2": tableName = "barTable";
                 break;
  ...
  default      : throw new InputValidationException("неожиданное значение для"
                                                  + " имени таблицы");

    Наиболее безопасное использование динамической генерации SQL (НЕ РЕКОМЕНДУЕТСЯ)¶

    Когда мы говорим, что хранимая процедура "реализована безопасно", это означает, что она не включает небезопасную динамическую генерацию SQL. Разработчики обычно не генерируют динамический SQL внутри хранимых процедур. Однако это возможно, но следует избегать этого.

    Если избежать этого невозможно, хранимая процедура должна использовать валидацию ввода или надлежащее экранирование, описанное в этой статье, чтобы гарантировать, что весь пользовательский ввод в хранимую процедуру не может быть использован для внедрения SQL-кода в динамически генерируемый запрос. Аудиторы всегда должны искать использование sp_execute, execute или exec внутри хранимых процедур SQL Server. Аналогичные руководства по аудиту необходимы для похожих функций других поставщиков.

    Пример более безопасной динамической генерации запросов (НЕ РЕКОМЕНДУЕТСЯ)¶

    Для чего-то простого, как порядок сортировки, лучше всего преобразовать пользовательский ввод в логическое значение, а затем использовать это логическое значение для выбора безопасного значения для добавления к запросу. Это очень распространённая потребность при создании динамических запросов.

    Например:

    public String someMethod(boolean sortOrder) {
 String SQLquery = "some SQL ... order by Salary " + (sortOrder ? "ASC" : "DESC");`
 ...

    Каждый раз, когда пользовательский ввод может быть преобразован в не-строковый тип, например дату, число, логическое значение, перечисление и т. д., перед добавлением к запросу или использованием для выбора значения для добавления к запросу, это обеспечивает безопасность такой операции.

    Валидация ввода также рекомендуется как вторичная защита во ВСЕХ случаях, даже при использовании привязки переменных, как обсуждалось ранее в этой статье. Дополнительные техники реализации надёжной валидации ввода описаны в Input Validation Cheat Sheet.

    Вариант защиты 4: НАСТОЯТЕЛЬНО НЕ РЕКОМЕНДУЕТСЯ: Экранирование всего пользовательского ввода¶

    В этом подходе разработчик экранирует весь пользовательский ввод перед помещением его в запрос. Реализация этого подхода очень специфична для конкретной базы данных. Этот метод менее надёжен по сравнению с другими способами защиты, и мы НЕ МОЖЕМ гарантировать, что данный вариант предотвратит все SQL injections во всех ситуациях.

    Если приложение строится с нуля или требует низкой терпимости к риску, оно должно быть построено или переписано с использованием параметризованных запросов, хранимых процедур или какого-либо объектно-реляционного маппера (ORM), который строит запросы за вас.

    Дополнительные меры защиты¶

    Помимо принятия одного из четырёх основных способов защиты, мы также рекомендуем принять все эти дополнительные меры защиты для обеспечения глубокоэшелонированной защиты. Эти дополнительные меры защиты:

    • Принцип наименьших привилегий
    • Валидация ввода по белому списку

    Принцип наименьших привилегий¶

    Чтобы минимизировать потенциальный ущерб от успешной атаки SQL injection, следует минимизировать привилегии, назначенные каждой учётной записи базы данных в вашей среде. Начните с определения необходимых прав доступа для учётных записей приложения снизу вверх, а не пытайтесь выяснить, какие права нужно отозвать.

    Убедитесь, что учётным записям, которым нужен только доступ для чтения, предоставлен только доступ для чтения к таблицам, к которым им нужен доступ. НЕ НАЗНАЧАЙТЕ ДОСТУП УРОВНЯ DBA ИЛИ АДМИНИСТРАТОРА УЧЁТНЫМ ЗАПИСЯМ ПРИЛОЖЕНИЯ. Мы понимаем, что это легко, и всё просто "работает" при таком подходе, но это очень опасно.

    Минимизация привилегий приложения и операционной системы¶

    SQL injection — не единственная угроза для данных вашей базы данных. Злоумышленники могут просто изменить значения параметров с одного из допустимых значений, которые им предоставляются, на значение, которое не авторизовано для них, но само приложение может быть авторизовано для доступа к нему. Таким образом, минимизация привилегий, предоставленных вашему приложению, снизит вероятность таких попыток несанкционированного доступа, даже когда злоумышленник не пытается использовать SQL injection в рамках своей эксплойтации.

    При этом следует минимизировать привилегии учётной записи операционной системы, под которой работает СУБД. Не запускайте СУБД от имени root или system! Большинство СУБД работают с очень мощной системной учётной записью по умолчанию. Например, MySQL по умолчанию работает как system в Windows! Измените учётную запись ОС СУБД на что-то более подходящее с ограниченными привилегиями.

    Детали принципа наименьших привилегий при разработке¶

    Если учётной записи нужен доступ только к части таблицы, рассмотрите создание представления (view), ограничивающего доступ к этой части данных, и назначьте учётной записи доступ к представлению вместо базовой таблицы. Редко, если вообще когда-либо, предоставляйте учётным записям базы данных права на создание или удаление.

    Если вы применяете политику использования хранимых процедур везде и не разрешаете учётным записям приложения напрямую выполнять свои запросы, ограничьте эти учётные записи возможностью выполнять только те хранимые процедуры, которые им нужны. Не предоставляйте им никаких прав напрямую к таблицам в базе данных.

    Наименьшие административные привилегии для нескольких БД¶

    Разработчики веб-приложений должны избегать использования одной и той же учётной записи владельца/администратора в веб-приложениях для подключения к базе данных. Для разных веб-приложений следует использовать разных пользователей БД.

    В общем случае каждое отдельное веб-приложение, которому требуется доступ к базе данных, должно иметь назначенную учётную запись пользователя базы данных, которую приложение будет использовать для подключения к БД. Таким образом, разработчик приложения сможет обеспечить хорошую детализацию в управлении доступом, максимально сокращая привилегии. Каждый пользователь БД будет иметь доступ для выборки только к тому, что ему нужно, и доступ для записи по мере необходимости.

    Например, страница входа требует доступа для чтения к полям имени пользователя и пароля таблицы, но не требует доступа для записи какого-либо вида (без вставки, обновления или удаления). Однако страница регистрации определённо требует привилегии вставки в эту таблицу; это ограничение может быть применено только в том случае, если эти веб-приложения используют разных пользователей БД для подключения к базе данных.

    Расширение принципа наименьших привилегий с помощью SQL Views¶

    Вы можете использовать SQL views для дальнейшего увеличения детализации доступа, ограничивая доступ для чтения конкретными полями таблицы или объединениями таблиц. Это может иметь дополнительные преимущества.

    Например, если система обязана (возможно, из-за определённых правовых требований) хранить пароли пользователей вместо хэшированных паролей с солью, разработчик мог бы использовать views для компенсации этого ограничения. Они могли бы отозвать весь доступ к таблице (у всех пользователей БД, кроме владельца/администратора) и создать view, которое выводит хэш поля пароля, а не само поле.

    Любая атака SQL injection, которая успешно похищает информацию БД, будет ограничена кражей хэшей паролей (это может быть даже хэш с ключом), поскольку ни один пользователь БД ни одного из веб-приложений не имеет доступа к самой таблице.

    Валидация ввода по белому списку¶

    Помимо того, что валидация ввода является основной защитой, когда другие варианты невозможны (например, когда привязка переменной недопустима), она также может быть вторичной защитой для обнаружения несанкционированного ввода перед его передачей в SQL-запрос. Для получения дополнительной информации см. Input Validation Cheat Sheet. Будьте осторожны. Проверенные данные не обязательно безопасны для вставки в SQL-запросы через построение строк.
