    Памятка по восстановлению пароля¶

    Введение¶

    Для реализации надлежащей системы управления пользователями системы интегрируют сервис восстановления пароля, который позволяет пользователю запросить сброс пароля.

    Несмотря на то что эта функциональность выглядит простой и лёгкой в реализации, она является распространённым источником уязвимостей, таких как известная атака на перечисление пользователей.

    Следующие краткие рекомендации можно использовать в качестве быстрого справочника для защиты сервиса восстановления пароля:

    • Возвращать одинаковое сообщение как для существующих, так и для несуществующих аккаунтов.
    • Обеспечить одинаковое время ответа для всех запросов.
    • Использовать сторонний канал для передачи метода сброса пароля.
    • Использовать URL-токены как наиболее простую и быструю реализацию.
    • Обеспечить, чтобы генерируемые токены или коды были:
      • Случайными, сгенерированными с использованием криптографически безопасного алгоритма.
      • Достаточно длинными для защиты от атак грубой силы.
      • Надёжно хранились.
      • Одноразовыми и истекали через соответствующий период времени.
    • Не вносить изменений в аккаунт до предъявления действительного токена, например не блокировать аккаунт.

    Эта памятка сосредоточена на сбросе пользовательских паролей. Для руководства по сбросу многофакторной аутентификации (MFA) см. соответствующий раздел в Памятке по многофакторной аутентификации.

    Сервис восстановления пароля¶

    Процесс сброса пароля можно разбить на два основных этапа, описанных в следующих разделах.

    Запрос на восстановление пароля¶

    Когда пользователь использует сервис восстановления пароля и вводит своё имя пользователя или email, для реализации безопасного процесса необходимо следовать приведённым ниже рекомендациям:

    • Возвращать одинаковое сообщение как для существующих, так и для несуществующих аккаунтов.
    • Обеспечить, чтобы ответы возвращались за одинаковое время, чтобы предотвратить перечисление существующих аккаунтов злоумышленником. Этого можно достичь с помощью асинхронных вызовов или путём обеспечения одинаковой логики обработки, вместо использования метода быстрого выхода.
    • Реализовать защиту от чрезмерных автоматизированных запросов, например ограничение числа запросов на уровне аккаунта, требование CAPTCHA или другие средства контроля. В противном случае злоумышленник может делать тысячи запросов на сброс пароля в час для заданного аккаунта, засоряя систему ввода пользователя (например, почтовый ящик или SMS) бесполезными запросами.
    • Применять обычные меры безопасности, такие как методы предотвращения SQL-инъекций и валидация входных данных.

    Сброс пароля пользователем¶

    После того как пользователь подтвердил свою личность, предоставив токен (отправленный по email) или код (отправленный по SMS или другими механизмами), он должен сбросить пароль на новый безопасный. Для обеспечения безопасности этого этапа следует принять следующие меры:

    • Пользователь должен подтвердить установленный пароль, введя его дважды.
    • Убедиться, что действует надёжная политика паролей, соответствующая остальным частям приложения.
    • Обновить и сохранить пароль в соответствии с безопасными практиками.
    • Отправить пользователю email с уведомлением о том, что его пароль был сброшен (не отправляйте пароль в email!).
    • После установки нового пароля пользователь должен войти через обычный механизм. Не выполнять автоматический вход, поскольку это привносит дополнительную сложность в код аутентификации и управления сессиями и увеличивает вероятность появления уязвимостей.
    • Спросить пользователя, хочет ли он аннулировать все существующие сессии, или автоматически аннулировать сессии.

    Методы¶

    Для того чтобы пользователь мог запросить сброс пароля, необходим какой-либо способ идентификации пользователя или средство связи с ним через сторонний канал.

    Это можно сделать любым из следующих методов:

    • URL-токены.
    • PIN-коды
    • Офлайн-методы
    • Контрольные вопросы.

    Эти методы можно использовать вместе для обеспечения большей степени уверенности в том, что пользователь является тем, за кого себя выдаёт. В любом случае необходимо убедиться, что у пользователя всегда есть способ восстановить доступ к аккаунту, даже если это предполагает обращение в службу поддержки и подтверждение личности сотрудникам.

    Общие практики безопасности¶

    Крайне важно применять надёжные практики безопасности для идентификаторов сброса (токенов, кодов, PIN-кодов и т.д.). Некоторые пункты не применяются к офлайн-методам, например ограничение срока действия. Все токены и коды должны быть:

    • Сгенерированы с использованием криптографически безопасного генератора случайных чисел.
      • Также возможно использовать JSON Web Tokens (JWT) вместо случайных токенов, хотя это может привести к дополнительным уязвимостям, таким как те, что рассматриваются в Памятке по JSON Web Token.
    • Достаточно длинными для защиты от атак грубой силы.
    • Привязанными к отдельному пользователю в базе данных.
    • Аннулированными после использования.
    • Надёжно хранящимися, как обсуждается в Памятке по хранению паролей.

    URL-токены¶

    URL-токены передаются в строке запроса URL и обычно отправляются пользователю по email. Общая схема процесса выглядит следующим образом:

    1. Сгенерировать токен для пользователя и прикрепить его в строке запроса URL.
    2. Отправить этот токен пользователю по email. - Не использовать заголовок Host при создании URL для сброса, чтобы избежать атак Host Header Injection. URL должен быть жёстко задан или проверяться по списку доверенных доменов. - Убедиться, что URL использует HTTPS.
    3. Пользователь получает email и переходит по URL с прикреплённым токеном. - Убедиться, что страница сброса пароля добавляет тег Referrer Policy со значением noreferrer, чтобы избежать утечки реферера. - Реализовать соответствующую защиту для предотвращения перебора токенов в URL, например ограничение числа запросов.
    4. При необходимости выполнить дополнительные шаги проверки, например потребовать от пользователя ответить на контрольные вопросы.
    5. Позволить пользователю создать новый пароль и подтвердить его. Убедиться, что применяется та же политика паролей, что и в остальных частях приложения.

    Примечание: URL-токены могут следовать той же логике, что и PIN-коды, создавая ограниченную сессию из токена. Решение следует принимать исходя из потребностей и опыта разработчика.

    PIN-коды¶

    PIN-коды — это числа (от 6 до 12 цифр), отправляемые пользователю через сторонний канал, например SMS.

    1. Сгенерировать PIN-код.
    2. Отправить его пользователю по SMS или другим механизмом. - Разделение PIN-кода пробелами облегчает пользователю его чтение и ввод.
    3. Затем пользователь вводит PIN-код вместе со своим именем пользователя на странице сброса пароля.
    4. Создать ограниченную сессию из этого PIN-кода, которая позволяет пользователю только сбросить пароль.
    5. Позволить пользователю создать новый пароль и подтвердить его. Убедиться, что применяется та же политика паролей, что и в остальных частях приложения.

    Офлайн-методы¶

    Офлайн-методы отличаются от других методов тем, что позволяют пользователю сбросить пароль без запроса специального идентификатора (например, токена или PIN-кода) с бэкенда. Однако аутентификация всё равно должна выполняться бэкендом для подтверждения легитимности запроса. Офлайн-методы предоставляют определённый идентификатор либо при регистрации, либо когда пользователь захочет его настроить.

    Эти идентификаторы должны храниться офлайн и безопасным образом (например, в менеджерах паролей), а бэкенд должен надлежащим образом следовать общим практикам безопасности. Некоторые реализации построены на аппаратных OTP-токенах, сертификатах или любой другой реализации, которая может использоваться внутри предприятия. Это выходит за рамки данной памятки.

    Если аккаунт имеет включённую MFA и вы ищете восстановление MFA, различные методы можно найти в соответствующей Памятке по многофакторной аутентификации.

    Контрольные вопросы¶

    Контрольные вопросы не следует использовать в качестве единственного механизма сброса паролей, поскольку ответы на них часто легко угадать или получить злоумышленникам. Однако они могут обеспечить дополнительный уровень безопасности в сочетании с другими методами, рассматриваемыми в этой памятке. Если они используются, убедитесь, что выбраны безопасные вопросы, как обсуждается в Памятке по контрольным вопросам.

    Блокировка аккаунта¶

    Аккаунты не должны блокироваться в ответ на атаку с забытым паролем, поскольку это может быть использовано для отказа в доступе пользователям с известными именами. Более подробную информацию о блокировках аккаунтов см. в Памятке по аутентификации.
