    Mobile Application Security Cheat Sheet¶

    Разработка мобильных приложений сопряжена с определёнными проблемами безопасности, уникальными по сравнению с веб-приложениями и другими видами программного обеспечения. Данная шпаргалка содержит рекомендации по вопросам безопасности при разработке мобильных приложений. Это не исчерпывающее руководство, а лишь отправная точка для разработчиков, желающих уделять внимание безопасности в процессе создания мобильных приложений.

    Архитектура и проектирование¶

    1. Проектирование с учётом безопасности¶

    • Выбирайте безопасный подход к проектированию с самого начала разработки, а не в качестве запоздалой меры.
    • Помните о принципах безопасности: наименьших привилегий, эшелонированной защиты и разделения ответственности.
    • Следуйте отраслевым стандартам и лучшим практикам, например:
      • National Institute of Standards and Technology (NIST)
      • Internet Engineering Task Force (IETF)

    Дополнительную информацию см. в Secure Product Design Cheat Sheet.

    2. Безопасные API¶

    • Убедитесь, что мобильное приложение безопасно взаимодействует с серверными службами.
    • Используйте OAuth2, JWT или аналогичные механизмы для защищённой аутентификации.
    • Регулярно обновляйте и ротируйте используемые API-ключи и токены.

    3. Принцип наименьших привилегий¶

    • Запрашивайте только те разрешения, которые действительно необходимы вашему приложению.
    • Это касается не только разрешений устройства, предоставляемых пользователем, но и разрешений, выдаваемых приложению серверными службами.
    • Избегайте хранения файлов приложения с избыточными правами доступа.
    • Безопасность по умолчанию: приложения должны иметь наиболее защищённые настройки по умолчанию.

    4. Цепочка поставок¶

    Разработка с использованием сторонних библиотек и компонентов создаёт возможность появления неизвестных уязвимостей безопасности.

    • Обеспечьте подпись приложения.
    • Используйте только проверенные и надёжные сторонние библиотеки и компоненты.
    • Установите средства контроля безопасности для обновлений, патчей и выпусков приложения.
    • Отслеживайте и выявляйте инциденты безопасности в используемых сторонних продуктах.

    Рекомендации по управлению сторонними зависимостями при обнаружении уязвимостей см. в Vulnerable Dependency Management Cheat Sheet.

    Аутентификация и авторизация¶

    Аутентификация — сложная тема, в которой легко допустить ошибку. Логика аутентификации должна разрабатываться и тестироваться с исключительной тщательностью. Приведённые советы — лишь отправная точка, едва затрагивающая поверхность проблемы. Дополнительную информацию см. в Authentication Cheat Sheet и M1: Insecure Authentication/Authorization из OWASP Mobile Top 10.

    1. Не доверяйте клиенту¶

    • Выполняйте аутентификацию/авторизацию на стороне сервера и загружайте данные на устройство только после успешной аутентификации.
    • При локальном хранении данных шифруйте их с использованием ключа, производного от учётных данных пользователя.
    • Не храните пароли пользователей на устройстве; используйте специфичные для устройства токены, которые можно отозвать.
    • Избегайте использования поддельных значений, таких как идентификаторы устройств, для аутентификации.
    • Исходите из того, что любые клиентские проверки могут быть обойдены, и дублируйте их на стороне сервера.
    • Включите в клиентский код механизм обнаружения подмены кода и бинарных файлов.

    2. Обработка учётных данных¶

    • Не встраивайте учётные данные в код мобильного приложения.
    • Шифруйте учётные данные при передаче.
    • Не храните учётные данные пользователей на устройстве. Рассмотрите использование защищённых, отзываемых токенов доступа.

    3. Политика паролей и PIN-кодов¶

    • Требуйте соответствия пароля определённой сложности.
    • Не допускайте использования коротких PIN-кодов, например из 4 цифр.
    • Используйте платформенные механизмы безопасного хранения, такие как Keychain (iOS) или Keystore (Android).

    4. Биометрическая аутентификация¶

    • Используйте поддерживаемые платформой методы биометрической аутентификации.
    • Всегда предоставляйте резервный вариант, например PIN-код.

    5. Управление сессиями¶

    • Сессии должны завершаться по истечении периода неактивности.
    • Предусмотрите функцию удалённого завершения сессии.
    • Используйте случайно сгенерированные токены сессий.
    • Обеспечьте защиту данных сессии как на стороне клиента, так и на стороне сервера.

    6. Хранение токенов¶

    • Храните токены аутентификации в защищённом месте.
    • Корректно обрабатывайте истечение срока действия токенов.

    7. Чувствительные операции¶

    • Требуйте повторной аутентификации пользователя для чувствительных операций, таких как смена пароля или обновление платёжных данных.
    • Рассмотрите также требование повторной аутентификации перед отображением особо чувствительной информации.
    • Требуйте проверок авторизации для любой серверной функциональности.

    Хранение данных и конфиденциальность¶

    1. Шифрование данных¶

    • Шифруйте чувствительные данные как в состоянии покоя, так и при передаче.
    • Храните приватные данные во внутреннем хранилище устройства.
    • Используйте платформенные API для шифрования. Не пытайтесь реализовывать собственные алгоритмы шифрования.
    • По возможности используйте аппаратные функции безопасности (например, Secure Enclave на iOS, Strongbox на Android) для хранения ключей и криптографических операций.

    2. Утечка данных¶

    • Остерегайтесь кэширования, журналирования и создания снимков при сворачивании приложения. Убедитесь, что чувствительные данные не утекают через эти механизмы.

    Примеры данных, которые не следует записывать в журнал, см. в Logging Cheat Sheet.

    3. Используйте HTTPS¶

    • Всегда используйте HTTPS для сетевых коммуникаций.

    4. Сторонние библиотеки¶

    • Убедитесь, что все сторонние библиотеки защищены и актуальны.

    5. Персональные данные (PII)¶

    • Сводите объём персональных данных к минимуму, необходимому для работы.
    • По возможности заменяйте персональные данные менее критичной информацией.
    • Сокращайте объём персональных данных, например за счёт более редкого обновления геолокации.
    • Реализуйте автоматическое истечение срока хранения и удаление персональных данных для минимизации периода их хранения.
    • Запрашивайте согласие пользователя перед сбором или использованием персональных данных.

    Сетевое взаимодействие¶

    1. Не доверяйте сети¶

    • Исходите из того, что все сетевые коммуникации небезопасны и могут быть перехвачены.

    2. Используйте защищённые протоколы¶

    • Используйте HTTPS для всех сетевых коммуникаций.
    • Не отключайте проверку SSL-сертификатов для разрешения самоподписанных или недействительных сертификатов.
    • Избегайте смешанных версий SSL-сессий.
    • Шифруйте данные даже при передаче по SSL — на случай будущих уязвимостей SSL.
    • Используйте надёжные, отраслевые наборы шифров с соответствующей длиной ключей.
    • Используйте сертификаты, подписанные доверенным удостоверяющим центром (CA).
    • Избегайте передачи чувствительных данных по SMS.

    3. Certificate Pinning¶

    • Рассмотрите использование certificate pinning. Плюсы и минусы этого подхода см. в Pinning Cheat Sheet.

    Пользовательский интерфейс¶

    1. Маскирование данных в UI¶

    • Маскируйте чувствительную информацию в полях UI для защиты от подглядывания через плечо.

    2. Уведомления пользователя¶

    • Информируйте пользователя о событиях, связанных с безопасностью, например о входе с нового устройства.

    3. Валидация ввода¶

    • Валидируйте и обезвреживайте пользовательский ввод. Дополнительную информацию см. в Input Validation Cheat Sheet.

    4. Валидация вывода¶

    • Валидируйте и обезвреживайте выводимые данные для предотвращения атак типа инъекций и выполнения кода.

    Качество кода¶

    1. Статический анализ¶

    • Используйте инструменты статического анализа для выявления уязвимостей.

    2. Код-ревью¶

    • Уделяйте особое внимание безопасности в процессе код-ревью.

    3. Обновление библиотек¶

    • Поддерживайте все библиотеки в актуальном состоянии для устранения известных уязвимостей.

    Целостность приложения¶

    • Отключите режим отладки.
    • Включите в код проверку целостности кода приложения.
    • Обфусцируйте бинарный файл приложения.
    • Реализуйте средства защиты от модификации во время выполнения:
      • Проверяйте признаки отладки, перехвата вызовов или инъекции кода.
      • Определяйте, запущено ли приложение в эмуляторе или на устройстве с root/jailbreak.
      • Проверяйте подпись приложения во время выполнения.
      • Применяйте соответствующие меры при обнаружении модификации (например, ограничение функциональности).

    Тестирование¶

    1. Пентест¶

    • Проводите этичный взлом для выявления уязвимостей.
    • Примеры тестов:
      • Оценка криптографических уязвимостей.
      • Попытка анонимного вызова серверной функциональности путём удаления токенов сессии из POST/GET-запросов.

    2. Автоматизированные тесты¶

    • Используйте автоматизированные тесты для проверки работоспособности функций безопасности и соблюдения контроля доступа.

    3. Тестирование удобства использования¶

    • Убедитесь, что меры безопасности не ухудшают удобство использования, что может привести к их обходу пользователями.

    После развёртывания¶

    1. Реагирование на инциденты¶

    • Разработайте чёткий план реагирования на инциденты.

    2. Обновления¶

    • Планируйте регулярные обновления и патчи. В случае мобильных приложений это особенно важно из-за задержки между выпуском патча и его фактическим получением пользователями, обусловленной процедурой проверки в магазинах приложений и временем, необходимым пользователям для обновления.

    • Используйте механизм принудительного обновления приложения до требуемой версии при необходимости.

    3. Мониторинг и аналитика¶

    • Используйте мониторинг в реальном времени для обнаружения угроз и реагирования на них.

    Руководство для конкретных платформ¶

    Android¶

    • Используйте Android ProGuard для обфускации кода.
    • Избегайте хранения чувствительных данных в SharedPreferences. Подробнее см. в документации Android о безопасной работе с данными.

    • Отключите режим резервного копирования, чтобы предотвратить попадание чувствительных данных в резервные копии.

    • Используйте Android Keystore с аппаратной поддержкой (TEE или StrongBox) для безопасного хранения криптографических ключей.

      • Как: Генерируйте ключи с аппаратной поддержкой, указывая .setIsStrongBoxBacked(true) в KeyGenParameterSpec.Builder при наличии поддержки (Android 9+).
      • Проверяйте наличие аппаратного хранилища через KeyInfo.isInsideSecureHardware().
      • Используйте обычное аппаратное хранилище ключей, если Strongbox недоступен.
      • Настраивайте ограничения использования ключей с помощью .setUserAuthenticationRequired(true) для чувствительных операций.
      • См. документацию Hardware-backed Keystore.

    • Реализуйте Play Integrity API от Google для проверки целостности устройства и приложения.

      • Как: Получите вердикт целостности от устройства, проверьте его на стороне сервера и примите меры в случае неудачной проверки.
      • SafetyNet Attestation API был полностью отключён в январе 2025 года. Все разработчики должны перейти на Play Integrity API.
      • См. документацию Play Integrity API.

    iOS и iPadOS¶

    Разрешения для Shortcuts¶

    • iOS/iPadOS Shortcuts позволяют автоматизировать функции приложения, что может давать доступ к чувствительным действиям даже при заблокированном устройстве.

    • Существует несколько сценариев, при которых пользователь может выполнить Shortcut при заблокированном устройстве:

    1. Если Shortcut добавлен как виджет в Today View, к нему можно получить доступ и запустить его при заблокированном устройстве.
    2. Если Shortcut назначен кнопке Action Button (на моделях iPhone 15 Pro и iPhone 16 Pro), его можно запустить нажатием кнопки при заблокированном устройстве.
    3. Если Shortcut добавлен в Control Center (в iOS/iPadOS 18+), его можно запустить, открыв Control Center и нажав кнопку Shortcut при заблокированном устройстве.
    4. Shortcut можно запустить через Siri при заблокированном устройстве.
    5. Если Shortcut добавлен на домашний экран пользователя (в iOS/iPadOS 18+), его можно напрямую запустить, нажав кнопку Shortcut на экране блокировки при заблокированном устройстве.
    6. Если Shortcut настроен на запуск через определённые интервалы или в определённое время, он может выполняться даже при заблокированном устройстве.

    • Чувствительные функции приложения, запускаемые через Shortcuts, должны всегда требовать разблокировки устройства перед выполнением.

    • Как: Храните защищённые токены в Keychain, которые приложение проверяет перед выполнением чувствительных shortcuts. Реализуйте проверки с помощью UIApplication.shared.isProtectedDataAvailable для ограничения выполнения чувствительных действий при заблокированном устройстве.

    Разрешения для Siri¶

    • Siri может получать доступ к функциям приложения через голосовые команды или Type to Siri команды, которые по умолчанию доступны даже при заблокированном устройстве, что потенциально позволяет выполнять несанкционированные действия.
    • Как: Установите requiresUserAuthentication в true для интентов, предоставляющих доступ к чувствительной информации или функциональности. Дополнительно установите INIntent.userConfirmationRequired = true для операций, требующих явного подтверждения пользователя. Эти настройки обеспечивают надлежащую аутентификацию (например, Face ID или PIN) и явное подтверждение перед выполнением Siri чувствительных команд. (Дополнительную информацию см. в документации Apple Developer SiriKit.)

    Безопасность Deep Links¶

    • Deep links обеспечивают прямой доступ к конкретным экранам приложения, что может потенциально обходить аутентификацию при отсутствии защиты, открывая несанкционированным пользователям доступ к защищённым разделам приложения.
    • Пример подобной уязвимости в Microsoft Authenticator для iOS (устранённой в июле 2024 года) позволял пользователям обойти блокировку приложения простым переходом по адресу msauth://microsoft.aad.brokerplugin/?, что открывало Authenticator и убирало запрос Face ID/Touch ID/пароля.
    • Как: Реализуйте проверки аутентификации для всех контроллеров представлений или конечных точек, доступных через deep links. Настройте и проверьте Universal Links с помощью файлов apple-app-site-association для безопасной обработки deep links. Обезвреживайте и валидируйте все параметры, получаемые через deep links, для предотвращения атак типа инъекций. Убедитесь, что несанкционированные пользователи перенаправляются на экран входа, исключая прямой доступ к чувствительным разделам приложения без надлежащей аутентификации. (Дополнительную информацию см. в документации Apple Developer Supporting universal links in your app.)

    Безопасность WidgetKit¶

    • Виджеты на экране блокировки могут отображать чувствительные данные, потенциально раскрывая их без разблокировки устройства.
    • Как: Для iOS/iPadOS версии 17 и выше используйте WidgetInfo.isLocked для определения состояния экрана блокировки. Для более ранних версий iOS реализуйте пользовательскую логику на основе доступных состояний виджетов, поскольку widgetFamily сам по себе не предоставляет информацию об экране блокировки. Применяйте условную логику для маскирования или ограничения отображения чувствительного содержимого виджетов при несоблюдении необходимых условий безопасности. (Дополнительную информацию см. в документации Apple WidgetKit security.)

    Дополнительные соображения по безопасности¶

    • Настройте соответствующие политики фонового обновления для предотвращения обновления чувствительных данных при заблокированном устройстве.
    • Реализуйте надлежащие конфигурации, связанные с конфиденциальностью, в Info.plist для функций, требующих разрешений пользователя.
    • Используйте App Groups с соответствующими настройками безопасности при совместном использовании данных между приложением и виджетами.
    • Используйте ATS (App Transport Security) для применения строгих политик безопасности в сетевых коммуникациях.

    • Не храните чувствительные данные в файлах plist.

    • Используйте Apple Secure Enclave для безопасного хранения криптографических ключей и выполнения чувствительных операций.

      • Как: Создавайте ключи с помощью SecKeyCreateRandomKey с kSecAttrTokenID, установленным в kSecAttrTokenIDSecureEnclave.
      • Ключи, созданные в Secure Enclave, никогда не покидают защищённое аппаратное обеспечение — только операции с использованием этих ключей выполняются там.
      • Для биометрических операций используйте LAContext с evaluatePolicy для выполнения аутентификации напрямую через Secure Enclave без передачи биометрических данных вашему приложению.
      • Рассмотрите параметры контроля доступа, такие как kSecAccessControlBiometryAny или kSecAccessControlUserPresence, для требования аутентификации пользователя перед использованием ключа.
      • См. документацию Secure Enclave.

    • Используйте App Attest API от Apple (iOS 14+) для проверки целостности приложения.

      • Как: Генерируйте ключи аттестации и утверждения с помощью DCAppAttestService и проверяйте утверждения на стороне сервера.
      • Дополняйте DeviceCheck API от Apple для отслеживания постоянного состояния устройства.
      • См. документацию App Attest.

    Расширенная аппаратная безопасность и мониторинг¶

    • Современные устройства, как правило, предоставляют Trusted Execution Environment (TEE) или защищённые аппаратные модули. Используйте их через стандартные API операционной системы.
    • Рассмотрите дополнительные меры безопасности во время выполнения (обнаружение поведенческих аномалий, мониторинг во время выполнения) для дополнения встроенных средств защиты ОС в сценариях с повышенным уровнем риска.

    Для дальнейшего изучения посетите OWASP Mobile Top 10 Project. Более подробную методологию обеспечения безопасности мобильных приложений см. в OWASP Mobile Application Security Project.
