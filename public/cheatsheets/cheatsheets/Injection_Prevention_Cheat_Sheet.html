    Шпаргалка по предотвращению инъекций¶

    Введение¶

    Эта статья посвящена предоставлению чётких, простых и практических рекомендаций по предотвращению всей категории уязвимостей типа «инъекция» в ваших приложениях. Атаки типа «инъекция», особенно SQL Injection, к сожалению, очень распространены.

    Доступность исходного кода приложения является важным фактором в защите от уязвимостей типа «инъекция» и их предотвращении. Лишь меньшинство всех приложений в компании или на предприятии разрабатывается внутри самой организации, тогда как большинство приложений поступает из внешних источников. Приложения с открытым исходным кодом предоставляют хотя бы возможность исправить проблемы, тогда как к приложениям с закрытым исходным кодом требуется иной подход.

    Уязвимости типа «инъекция» возникают, когда приложение передаёт недоверенные данные интерпретатору. Они широко распространены, особенно в устаревшем коде, и часто встречаются в SQL-запросах, LDAP-запросах, XPath-запросах, командах ОС, аргументах программ и т. д. Уязвимости типа «инъекция» легко обнаружить при анализе кода, но сложнее — при тестировании. Сканеры и фаззеры могут помочь злоумышленникам их найти.

    В зависимости от доступности исходного кода необходимо предпринимать различные меры для их устранения. Лучшим способом всегда остаётся исправление проблемы непосредственно в исходном коде или даже перепроектирование отдельных частей приложений. Однако если исходный код недоступен или исправление устаревшего программного обеспечения экономически нецелесообразно, единственным вариантом является виртуальное исправление.

    Типы приложений¶

    В компании, как правило, можно выделить три класса приложений. Эти три типа необходимы для определения действий, которые необходимо предпринять для предотвращения или устранения уязвимостей типа «инъекция».

    A1: Новое приложение¶

    Новое веб-приложение на стадии проектирования или на раннем этапе разработки.

    A2: Продуктивное приложение с открытым исходным кодом¶

    Уже работающее приложение, которое легко адаптировать. Приложение типа Model-View-Controller (MVC) — лишь один из примеров легкодоступной архитектуры приложения.

    A3: Продуктивное приложение с закрытым исходным кодом¶

    Работающее приложение, которое невозможно или крайне сложно изменить.

    Формы инъекций¶

    Существует несколько форм инъекций, направленных на различные технологии: SQL-запросы, LDAP-запросы, XPath-запросы и команды ОС.

    Языки запросов¶

    Наиболее известной формой инъекции является SQL Injection, при которой злоумышленник может изменять существующие запросы к базе данных. Подробнее см. Шпаргалку по предотвращению SQL Injection.

    Однако и запросы на основе LDAP, SOAP, XPath и REST могут быть подвержены атакам типа «инъекция», что позволяет злоумышленникам извлекать данные или обходить средства управления доступом.

    SQL Injection¶

    Атака типа SQL Injection заключается во вставке или «инъекции» частичного или полного SQL-запроса через входные данные, передаваемые от клиента (браузера) к веб-приложению.

    Успешная атака SQL Injection позволяет читать конфиденциальные данные из базы данных, изменять данные в базе данных (вставка/обновление/удаление), выполнять административные операции с базой данных (например, остановить СУБД), восстанавливать содержимое файла в файловой системе СУБД или записывать в неё файлы, а в некоторых случаях — выполнять команды на уровне операционной системы. Атаки SQL Injection — это разновидность инъекционных атак, при которых SQL-команды внедряются в поля ввода данных с целью повлиять на выполнение заранее определённых SQL-команд.

    Атаки SQL Injection можно разделить на следующие три класса:

    • Inband (канальная): данные извлекаются по тому же каналу, который используется для внедрения SQL-кода. Это наиболее прямолинейный вид атаки, при котором извлечённые данные отображаются непосредственно на веб-странице приложения.
    • Out-of-band (внеполосная): данные извлекаются по другому каналу (например, создаётся электронное письмо с результатами запроса, которое отправляется тестировщику).
    • Inferential или Blind (слепая): фактической передачи данных не происходит, однако тестировщик может восстановить информацию, отправляя определённые запросы и наблюдая за поведением сервера баз данных.
    Как проверить наличие проблемы¶
    В ходе анализа кода¶

    Проверьте, не выполняются ли какие-либо запросы к базе данных без использования подготовленных выражений.

    Если используются динамические выражения, проверьте, выполняется ли очистка данных перед их включением в запрос.

    Аудиторы всегда должны обращать внимание на использование sp_execute, execute или exec в хранимых процедурах SQL Server. Аналогичные рекомендации по аудиту применимы к схожим функциям других производителей.

    Автоматизированная эксплуатация¶

    Большинство ситуаций и техник, описанных ниже, можно реализовать в автоматизированном режиме с помощью специальных инструментов. В этой статье тестировщик может найти информацию о том, как выполнять автоматизированный аудит с помощью SQLMap.

    Правила анализа потоков данных в инструментах статического анализа кода также позволяют обнаруживать, может ли неочищенные входные данные, контролируемые пользователем, изменить SQL-запрос.

    Внедрение в хранимые процедуры¶

    При использовании динамического SQL внутри хранимой процедуры приложение должно надлежащим образом очищать пользовательский ввод, чтобы исключить риск внедрения кода. Если очистка не выполняется, пользователь может ввести вредоносный SQL-код, который будет выполнен внутри хранимой процедуры.

    Техника эксплуатации с задержкой по времени¶

    Техника эксплуатации с задержкой по времени весьма полезна, когда тестировщик сталкивается с ситуацией слепой SQL-инъекции, при которой ничего не известно о результате операции. Техника состоит в отправке инъецированного запроса: если условие истинно, тестировщик может отслеживать время, которое сервер тратит на ответ. Наличие задержки позволяет предположить, что результат условного запроса истинен. Данная техника эксплуатации может различаться в зависимости от СУБД (см. раздел по конкретной СУБД).

    http://www.example.com/product.php?id=10 AND IF(version() like '5%', sleep(10), 'false'))--

    В этом примере тестировщик проверяет, является ли версия MySql 5.x или нет, заставляя сервер задержать ответ на 10 секунд. Тестировщик может увеличить время задержки и наблюдать за ответами. Кроме того, тестировщику не обязательно ждать ответа — иногда можно задать очень большое значение (например, 100) и отменить запрос через несколько секунд.

    Техника внеполосной эксплуатации¶

    Эта техника весьма полезна, когда тестировщик сталкивается с ситуацией слепой SQL-инъекции, при которой ничего не известно о результате операции. Техника заключается в использовании функций СУБД для установления внеполосного соединения и передачи результатов внедрённого запроса в запросе на сервер тестировщика. Как и техники на основе ошибок, каждая СУБД имеет собственные функции. Обратитесь к разделу по конкретной СУБД.

    Устранение¶
    Вариант защиты 1: Подготовленные выражения (с параметризованными запросами)¶

    Подготовленные выражения гарантируют, что злоумышленник не сможет изменить намерение запроса, даже если SQL-команды были вставлены злоумышленником. В приведённом ниже безопасном примере, если злоумышленник введёт в качестве userID строку tom' or '1'='1, параметризованный запрос не будет уязвим и вместо этого выполнит поиск имени пользователя, буквально совпадающего со всей строкой tom' or '1'='1.

    Вариант защиты 2: Хранимые процедуры¶

    Разница между подготовленными выражениями и хранимыми процедурами состоит в том, что SQL-код хранимой процедуры определяется и хранится в самой базе данных, а затем вызывается из приложения.

    Обе техники одинаково эффективны для предотвращения SQL Injection, поэтому организация должна выбрать подход, который наиболее ей подходит. Хранимые процедуры не всегда защищены от SQL Injection. Однако определённые стандартные конструкции программирования хранимых процедур оказывают тот же эффект, что и параметризованные запросы, если они реализованы безопасно* — что является нормой для большинства языков хранимых процедур.

    Примечание: «Реализованы безопасно» означает, что хранимая процедура не содержит небезопасной генерации динамического SQL.

    Вариант защиты 3: Валидация входных данных на основе списка допустимых значений¶

    Различные части SQL-запросов не допускают использования переменных привязки, например имена таблиц или столбцов и индикаторы порядка сортировки (ASC или DESC). В таких случаях наиболее подходящей защитой является валидация входных данных или перепроектирование запроса. В идеале имена таблиц и столбцов должны поступать из кода, а не из пользовательских параметров.

    Однако если значения пользовательских параметров используются для задания имён таблиц и столбцов, эти значения следует сопоставлять с допустимыми или ожидаемыми именами таблиц или столбцов, чтобы неvalidированные пользовательские данные не попадали в запрос. Обратите внимание: это является признаком неудачного проектирования, и при наличии времени следует рассмотреть возможность полной переработки.

    Вариант защиты 4: Экранирование всех данных, поставляемых пользователем¶

    Эту технику следует использовать только в крайнем случае, когда ни один из перечисленных выше вариантов неосуществим. Валидация входных данных, вероятно, является лучшим выбором, поскольку данная методология ненадёжна по сравнению с другими методами защиты и не гарантирует предотвращение всех SQL-инъекций во всех ситуациях.

    Техника заключается в экранировании пользовательских данных перед их включением в запрос. Как правило, она рекомендуется только для доработки устаревшего кода в случаях, когда внедрение валидации входных данных экономически нецелесообразно.

    Примеры кода — Java¶
    Пример безопасного подготовленного выражения на Java¶

    В следующем примере кода используется PreparedStatement — реализация параметризованного запроса в Java — для выполнения того же запроса к базе данных.

    // Это значение ДЕЙСТВИТЕЛЬНО нужно валидировать
String custname = request.getParameter("customerName");
// Выполнить валидацию входных данных для обнаружения атак
String query = "SELECT account_balance FROM user_data WHERE user_name = ?";
PreparedStatement pstmt = connection.prepareStatement(query);
pstmt.setString(1, custname);
ResultSet results = pstmt.executeQuery();

    Примеры приведены на Java, однако практически все другие языки, включая Cold Fusion и Classic ASP, также поддерживают интерфейсы параметризованных запросов.

    Пример безопасной хранимой процедуры на Java¶

    В следующем примере кода используется CallableStatement — реализация интерфейса хранимой процедуры в Java — для выполнения того же запроса к базе данных. Хранимая процедура sp_getAccountBalance должна быть заранее определена в базе данных и реализовывать ту же функциональность, что и запрос, описанный выше.

    // Это значение ДЕЙСТВИТЕЛЬНО нужно валидировать
String custname = request.getParameter("customerName");
try {
 CallableStatement cs = connection.prepareCall("{call sp_getAccountBalance(?)}");
 cs.setString(1, custname);
 ResultSet results = cs.executeQuery();
 // Обработка результирующего набора...
} catch (SQLException se) {
 // Журналирование и обработка ошибок...
}

    LDAP Injection¶

    LDAP Injection — это атака, используемая для эксплуатации веб-приложений, которые формируют LDAP-выражения на основе пользовательского ввода. Когда приложение не выполняет надлежащую очистку пользовательского ввода, становится возможным изменение LDAP-выражений с помощью техник, схожих с SQL Injection. Атаки LDAP Injection могут приводить к предоставлению разрешений на несанкционированные запросы и изменению содержимого в дереве LDAP. Подробнее об атаках LDAP Injection см. LDAP injection.

    Атаки LDAP injection широко распространены по двум причинам:

    1. Отсутствие более безопасных, параметризованных интерфейсов LDAP-запросов.
    2. Широкое использование LDAP для аутентификации пользователей в системах.
    Как проверить наличие проблемы¶
    В ходе анализа кода¶

    Проверьте, выполняется ли экранирование специальных символов во всех запросах к LDAP — подробнее см. здесь.

    Автоматизированная эксплуатация¶

    Модуль сканера в таких инструментах, как OWASP ZAP, имеет модуль для обнаружения проблем LDAP injection.

    Устранение¶
    Экранирование всех переменных с использованием корректной функции LDAP-кодирования¶

    Основной способ хранения имён в LDAP основан на DN (distinguished name — отличительное имя). Его можно рассматривать как уникальный идентификатор. Они иногда используются для доступа к ресурсам, например в качестве имени пользователя.

    DN может выглядеть следующим образом:

    cn=Richard Feynman, ou=Physics Department, dc=Caltech, dc=edu

    или

    uid=inewton, ou=Mathematics Department, dc=Cambridge, dc=com

    В DN существуют определённые символы, которые считаются специальными. Исчерпывающий список: \ # + < > , ; " = и пробелы в начале или в конце строки.

    Каждый DN указывает ровно на 1 запись, которую можно считать аналогом строки в реляционной СУБД. Для каждой записи существует 1 или более атрибутов, аналогичных столбцам реляционной СУБД. Если вас интересует поиск в LDAP пользователей с определёнными атрибутами, для этого можно использовать поисковые фильтры. В поисковом фильтре можно применять стандартную булеву логику для получения списка пользователей, соответствующих произвольным условиям. Поисковые фильтры записываются в польской нотации, также известной как префиксная нотация.

    Пример:

    (&(ou=Physics)(| (manager=cn=Freeman Dyson,ou=Physics,dc=Caltech,dc=edu)
(manager=cn=Albert Einstein,ou=Physics,dc=Princeton,dc=edu) ))

    При формировании LDAP-запросов в коде приложения НЕОБХОДИМО экранировать любые недоверенные данные, добавляемые в любой LDAP-запрос. Существует две формы экранирования в LDAP: кодирование для поискового фильтра LDAP и кодирование для LDAP DN (distinguished name). Выбор корректного экранирования зависит от того, выполняется ли очистка входных данных для поискового фильтра или DN используется в качестве учётных данных (аналога имени пользователя) для доступа к некоему ресурсу.

    Примеры кода — Java¶
    Пример безопасного экранирования LDAP на Java¶
    public String escapeDN (String name) {
 //Из RFC 2253 и символ / для JNDI
 final char[] META_CHARS = {'+', '"', '<', '>', ';', '/'};
 String escapedStr = new String(name);
 //Обратный слеш является символом экранирования и в Java, и в LDAP,
 //поэтому экранируем его первым
 escapedStr = escapedStr.replaceAll("\\\\\\\\","\\\\\\\\");
 //Позиционные символы — см. RFC 2253
 escapedStr = escapedStr.replaceAll("\^#","\\\\\\\\#");
 escapedStr = escapedStr.replaceAll("\^ | $","\\\\\\\\ ");
 for (int i=0 ; i < META_CHARS.length ; i++) {
        escapedStr = escapedStr.replaceAll("\\\\" +
                     META_CHARS[i],"\\\\\\\\" + META_CHARS[i]);
 }
 return escapedStr;
}

    Обратите внимание, что символ обратного слеша является символом экранирования как в строковых литералах Java, так и в регулярных выражениях.

    public String escapeSearchFilter (String filter) {
 //Из RFC 2254
 String escapedStr = new String(filter);
 escapedStr = escapedStr.replaceAll("\\\\\\\\","\\\\\\\\5c");
 escapedStr = escapedStr.replaceAll("\\\\\*","\\\\\\\\2a");
 escapedStr = escapedStr.replaceAll("\\\\(","\\\\\\\\28");
 escapedStr = escapedStr.replaceAll("\\\\)","\\\\\\\\29");
 escapedStr = escapedStr.replaceAll("\\\\" +
               Character.toString('\\u0000'), "\\\\\\\\00");
 return escapedStr;
}

    Скриптовые языки¶

    Все скриптовые языки, используемые в веб-приложениях, имеют некую форму вызова eval, который получает код во время выполнения и исполняет его. Если код формируется с использованием непроверенного и неэкранированного пользовательского ввода, возможна инъекция кода, что позволяет злоумышленнику подменить логику приложения и в конечном итоге получить локальный доступ.

    Каждый раз, когда используется скриптовый язык, фактическая реализация «высокоуровневого» скриптового языка выполняется на «низкоуровневом» языке, таком как C. Если в скриптовом языке имеется уязвимость в коде обработки данных, могут применяться векторы атак «Null Byte Injection» для получения доступа к другим областям памяти, что приводит к успешной атаке.

    Команды операционной системы¶

    OS command injection — это техника, применяемая через веб-интерфейс для выполнения команд ОС на веб-сервере. Пользователь вводит команды операционной системы через веб-интерфейс с целью их выполнения.

    Любой веб-интерфейс, не выполняющий надлежащую очистку данных, подвержен этой уязвимости. Имея возможность выполнять команды ОС, пользователь может загружать вредоносные программы или даже получать пароли. OS command injection можно предотвратить, если уделять должное внимание безопасности при проектировании и разработке приложений.

    Как проверить наличие проблемы¶

    В ходе анализа кода¶

    Проверьте, вызываются ли какие-либо методы выполнения команд с неvalидированными пользовательскими данными в качестве входных данных для этих команд.

    Помимо этого, добавление точки с запятой в конец параметра URL-запроса с последующей командой операционной системы выполнит эту команду. %3B — это URL-кодированное значение, соответствующее точке с запятой. Это происходит потому, что символ ; интерпретируется как разделитель команд.

    Пример: http://sensitive/something.php?dir=%3Bcat%20/etc/passwd

    Если приложение возвращает содержимое файла /etc/passwd, атака была успешной. Для тестирования данной атаки можно использовать множество сканеров веб-приложений — они внедряют различные варианты command injection и анализируют ответы.

    Инструменты статического анализа кода также отслеживают поток недоверенных пользовательских данных в веб-приложение и проверяют, передаются ли эти данные в опасные методы, исполняющие пользовательский ввод в качестве команды.

    Устранение¶

    Если вызов системной команды с пользовательскими данными всё же неизбежен, в программном обеспечении следует использовать следующие два уровня защиты для предотвращения атак:

    1. Параметризация — если возможно, используйте структурированные механизмы, которые автоматически обеспечивают разделение данных и команды. Эти механизмы могут помочь с необходимым экранированием и кодированием.
    2. Валидация входных данных — команды и соответствующие аргументы должны проходить валидацию. Существуют различные уровни валидации для самой команды и её аргументов:
      • В отношении используемых команд — они должны проверяться по списку допустимых команд.
      • В отношении используемых аргументов для этих команд — их следует валидировать с помощью следующих подходов:
        • Позитивная валидация по списку допустимых значений — явное определение разрешённых аргументов.
        • Регулярное выражение на основе списка допустимых значений — явное определение списка допустимых символов и максимальной длины строки. Убедитесь, что метасимволы & | ; $ > < \ ` \ ! и пробелы не входят в регулярное выражение. Например, следующее регулярное выражение допускает только строчные буквы и цифры, не содержит метасимволов, а длина ограничена 3–10 символами:

    ^[a-z0-9]{3,10}$

    Некорректное использование¶
    ProcessBuilder b = new ProcessBuilder("C:\DoStuff.exe -arg1 -arg2");

    В этом примере команда вместе с аргументами передаётся единой строкой, что облегчает манипуляцию этим выражением и внедрение вредоносных строк.

    Корректное использование¶

    Ниже приведён пример запуска процесса с изменённым рабочим каталогом. Команда и каждый из аргументов передаются раздельно. Это позволяет легко проверить каждый элемент и снижает риск внедрения вредоносных строк.

    ProcessBuilder pb = new ProcessBuilder("TrustedCmd", "TrustedArg1", "TrustedArg2");
Map<String, String> env = pb.environment();
pb.directory(new File("TrustedDir"));
Process p = pb.start();

    Сетевые протоколы¶

    Веб-приложения часто взаимодействуют с сетевыми демонами (такими как SMTP, IMAP, FTP), при этом пользовательский ввод становится частью потока взаимодействия. Здесь возможно внедрение последовательностей команд для злоупотребления установленным сеансом.

    Правила предотвращения инъекций¶

    Правило #1 (Выполняйте надлежащую валидацию входных данных)¶

    Выполняйте надлежащую валидацию входных данных. Рекомендуется также позитивная валидация по списку допустимых значений с соответствующей канонизацией, однако это не является полноценной защитой, поскольку многие приложения требуют наличия специальных символов во входных данных.

    Правило #2 (Используйте безопасный API)¶

    Предпочтительным вариантом является использование безопасного API, который полностью исключает использование интерпретатора или предоставляет параметризованный интерфейс. Будьте осторожны с API, такими как хранимые процедуры, которые являются параметризованными, но всё же могут допускать инъекции на нижнем уровне.

    Правило #3 (Контекстно-зависимое экранирование пользовательских данных)¶

    Если параметризованный API недоступен, следует тщательно экранировать специальные символы, используя синтаксис экранирования, специфичный для конкретного интерпретатора.
