    Шпаргалка по безопасности баз данных¶

    Введение¶

    Эта шпаргалка содержит рекомендации по безопасной настройке SQL-баз данных, таких как MySQL, PostgreSQL, MariaDB и Microsoft SQL Server. Она предназначена прежде всего для разработчиков приложений и системных администраторов, ответственных за управление реляционными базами данных или работу с ними.

    Для защиты от инъекций на уровне приложения см. Шпаргалку по предотвращению SQL-инъекций. Для нереляционных систем (например, MongoDB, Redis, Cassandra, DynamoDB) см. Шпаргалку по безопасности NoSQL.

    Защита серверной базы данных¶

    Серверная база данных приложения должна быть изолирована от других серверов и подключаться к как можно меньшему числу хостов. Эта задача зависит от архитектуры системы и сети. Рекомендуется:

    • Отключить сетевой доступ (TCP) и потребовать, чтобы все подключения выполнялись через локальный файл сокета или именованный канал.
    • Настроить базу данных так, чтобы она работала только на localhost.
    • Ограничить доступ к сетевому порту для конкретных хостов с помощью правил брандмауэра.
    • Разместить сервер базы данных в отдельной DMZ, изолированной от сервера приложений.
    • Защитить любые веб-инструменты управления (например, phpMyAdmin, pgAdmin) аутентификацией, HTTPS и сетевыми ограничениями.

    Когда приложение работает в недоверенной системе (например, в толстом клиенте), оно всегда должно подключаться к серверной части через API, обеспечивающий надлежащий контроль доступа и ограничения. Прямые подключения от толстого клиента к серверной базе данных категорически запрещены.

    Реализация защиты транспортного уровня¶

    В большинстве конфигураций баз данных по умолчанию используются незашифрованные сетевые соединения, хотя некоторые шифруют начальную аутентификацию (например, Microsoft SQL Server). Даже если начальная аутентификация зашифрована, остальной трафик будет передаваться в открытом виде, и по сети будет передаваться вся конфиденциальная информация. Для предотвращения незашифрованного трафика необходимо предпринять следующие меры:

    • Настроить базу данных так, чтобы она принимала только зашифрованные соединения.
    • Установить доверенный цифровой сертификат на сервере.
    • Настроить клиентское приложение для подключения с использованием TLSv1.2+ с современными шифрами (например, AES-GCM или ChaCha20).
    • Настроить клиентское приложение для проверки корректности цифрового сертификата.

    Шпаргалка по безопасности транспортного уровня содержит подробные рекомендации по безопасной настройке TLS.

    Настройка безопасной аутентификации¶

    База данных всегда должна требовать аутентификацию, включая подключения с локального сервера. Учётные записи базы данных должны:

    • Быть защищены надёжными и уникальными паролями.
    • Использоваться одним приложением или сервисом.
    • Иметь минимально необходимые права доступа, как обсуждается в разделе о правах доступа ниже.

    Как и в любой системе с собственными учётными записями пользователей, должны соблюдаться стандартные процессы управления учётными записями, включая:

    • Регулярные проверки учётных записей для подтверждения их необходимости.
    • Регулярные проверки прав доступа.
    • Удаление учётных записей пользователей при выводе приложения из эксплуатации.
    • Смену паролей при увольнении сотрудников или при наличии оснований полагать, что они могли быть скомпрометированы.

    Для Microsoft SQL Server рассмотрите использование Windows или интегрированной аутентификации, которая использует существующие учётные записи Windows вместо учётных записей SQL Server. Это также устраняет необходимость хранения учётных данных в приложении, поскольку оно будет подключаться с использованием учётных данных пользователя Windows, под которым работает. Плагины нативной аутентификации Windows обеспечивают аналогичную функциональность для MySQL.

    Безопасное хранение учётных данных базы данных¶

    Учётные данные базы данных никогда не должны храниться в исходном коде приложения, особенно если они не зашифрованы. Вместо этого они должны храниться в файле конфигурации, который:

    • Находится за пределами веб-корня.
    • Имеет соответствующие права доступа, так что его могут читать только необходимые пользователи.
    • Не включён в репозитории исходного кода.

    По возможности эти учётные данные также должны быть зашифрованы или защищены иным образом с использованием встроенных функций, например шифрования web.config в ASP.NET.

    Создание безопасных прав доступа¶

    При назначении прав доступа учётным записям пользователей базы данных разработчики должны применять принцип минимальных привилегий (то есть учётные записи должны иметь лишь минимальный набор прав, необходимых для работы приложения). Этот принцип может применяться на нескольких всё более детальных уровнях в зависимости от функциональности, доступной в базе данных. В любой среде возможно следующее:

    • Не использовать встроенные учётные записи root, sa или SYS.
    • Не предоставлять учётной записи права администратора экземпляра базы данных.
    • Убедиться, что учётная запись может подключаться только с разрешённых хостов. Как правило, это localhost или адрес сервера приложений.
    • Учётная запись должна иметь доступ только к конкретным необходимым базам данных. Среды разработки, UAT и продуктивная среда должны использовать отдельные базы данных и учётные записи.
    • Предоставлять только необходимые права на базы данных. Большинству приложений потребуются лишь права SELECT, UPDATE и DELETE. Учётная запись не должна быть владельцем базы данных, поскольку это может привести к уязвимостям повышения привилегий.
    • Избегать использования ссылок на базы данных или связанных серверов. Если они необходимы, используйте учётную запись с доступом только к минимально необходимым базам данных, таблицам и системным привилегиям.

    В большинстве критически важных с точки зрения безопасности приложений права доступа предоставляются на более детальных уровнях, включая:

    • Права на уровне таблиц.
    • Права на уровне столбцов.
    • Права на уровне строк.
    • Блокировка доступа к базовым таблицам с требованием осуществлять весь доступ через ограниченные представления.

    Конфигурация и усиление защиты базы данных¶

    Операционная система сервера базы данных должна быть усилена с использованием безопасных базовых конфигураций, таких как CIS Benchmarks или Microsoft Security Baselines.

    Приложение базы данных также должно быть правильно настроено и усилено. Следующие принципы должны применяться к любому приложению и платформе базы данных:

    • Устанавливать необходимые обновления и патчи безопасности.
    • Настраивать службы базы данных для работы под учётной записью с минимальными привилегиями.
    • Удалить все учётные записи и базы данных по умолчанию.
    • Хранить журналы транзакций на отдельном диске от основных файлов базы данных.
    • Настроить регулярное резервное копирование базы данных. Убедитесь, что резервные копии защищены соответствующими правами доступа и в идеале зашифрованы.

    Следующие разделы содержат дополнительные рекомендации для конкретного программного обеспечения баз данных в дополнение к более общим рекомендациям, приведённым выше.

    Усиление защиты Microsoft SQL Server¶

    • Отключить xp_cmdshell, xp_dirtree и другие хранимые процедуры, которые не нужны.
    • Отключить выполнение Common Language Runtime (CLR).
    • Отключить службу SQL Browser.
    • Отключить смешанный режим аутентификации, если он не требуется.
    • Убедиться, что примеры баз данных Northwind и AdventureWorks удалены.
    • См. статьи Microsoft о защите SQL Server.

    Усиление защиты MySQL или MariaDB¶

    • Запустить скрипт mysql_secure_installation для удаления баз данных и учётных записей по умолчанию.
    • Отключить привилегию FILE для всех пользователей, чтобы предотвратить чтение или запись файлов.
    • См. руководства по усилению защиты Oracle MySQL и MariaDB.
