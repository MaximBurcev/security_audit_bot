    Node.js Docker Cheat Sheet¶

    Следующая шпаргалка содержит рекомендации производственного уровня по созданию оптимизированных и безопасных Node.js Docker образов. Она будет полезна независимо от того, какое Node.js приложение вы собираетесь собирать. Эта статья будет для вас актуальна если:

    • вы хотите создать фронтенд приложение, используя возможности серверного рендеринга (SSR) Node.js для React.
    • вы ищете советы по правильной сборке Docker образа Node.js для ваших микросервисов на базе Fastify, NestJS или других фреймворков.

    1) Используйте явные и детерминированные теги базового Docker образа¶

    Может показаться очевидным решением строить образ на основе Docker образа node, но что именно вы получаете при сборке? На Docker образы всегда ссылаются по тегам, и если тег не указан, используется тег по умолчанию — :latest.

    Таким образом, указав в Dockerfile следующее, вы каждый раз будете собирать последнюю версию Docker образа, опубликованную рабочей группой Node.js Docker:

    FROM node¶

    Недостатки сборки на основе образа node по умолчанию следующие:

    1. Сборки Docker образов непоследовательны. Так же, как мы используем lockfiles для детерминированного поведения npm ci при каждой установке npm пакетов, мы хотели бы получать детерминированные сборки Docker образов. Если мы строим образ от node — что фактически означает тег node:latest — то каждая сборка будет подтягивать заново собранный Docker образ node. Мы не хотим допускать такого недетерминированного поведения.
    2. Docker образ node основан на полноценной операционной системе, насыщенной библиотеками и инструментами, которые могут и не потребоваться для работы вашего Node.js веб-приложения. Это имеет два недостатка. Во-первых, больший образ означает больший размер загрузки, что помимо увеличения требований к хранилищу, приводит к большему времени загрузки и пересборки образа. Во-вторых, это означает потенциальное добавление в образ уязвимостей безопасности, которые могут присутствовать во всех этих библиотеках и инструментах.

    Фактически, Docker образ node довольно большой и содержит сотни уязвимостей безопасности различных типов и степеней критичности. Если вы его используете, то по умолчанию ваша отправная точка — это 642 уязвимости безопасности и сотни мегабайт данных образа, загружаемых при каждом pull и build.

    Рекомендации по сборке лучших Docker образов:

    1. Используйте небольшие Docker образы — это уменьшит программный след в Docker образе, сокращая потенциальные векторы уязвимостей, а также ускорит процесс сборки образа благодаря меньшему размеру.
    2. Используйте digest Docker образа — статический SHA256 хеш образа. Это гарантирует детерминированные сборки Docker образа от базового образа.

    Исходя из этого, убедимся, что мы используем версию Node.js с долгосрочной поддержкой (LTS) и минимальный тип образа alpine для наименьшего размера и программного следа:

    FROM node:lts-alpine¶

    Тем не менее, эта директива базового образа по-прежнему будет подтягивать новые сборки этого тега. Мы можем найти хеш SHA256 на Docker Hub для этого тега Node.js, либо выполнив следующую команду после локального скачивания образа и найдя поле Digest в выводе:

    $ docker pull node:lts-alpine
lts-alpine: Pulling from library/node
0a6724ff3fcd: Already exists
9383f33fa9f3: Already exists
b6ae88d676fe: Already exists
565e01e00588: Already exists
Digest: sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
Status: Downloaded newer image for node:lts-alpine
docker.io/library/node:lts-alpine

    Другой способ найти хеш SHA256 — выполнить следующую команду:

    $ docker images --digests
REPOSITORY                     TAG              DIGEST                                                                    IMAGE ID       CREATED             SIZE
node                           lts-alpine       sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a   51d926a5599d   2 weeks ago         116MB

    Теперь можно обновить Dockerfile для этого Node.js Docker образа следующим образом:

    FROM node@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
WORKDIR /usr/src/app
COPY . /usr/src/app
RUN npm ci
CMD "npm" "start"

    Однако приведённый выше Dockerfile содержит только имя Docker образа Node.js без тега образа, что создаёт неоднозначность относительно того, какой именно тег используется — это нечитаемо, сложно в обслуживании и не способствует хорошему опыту разработчика.

    Исправим это, обновив Dockerfile и указав полный тег базового образа для версии Node.js, соответствующей этому хешу SHA256:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
WORKDIR /usr/src/app
COPY . /usr/src/app
RUN npm ci
CMD "npm" "start"

    2) Устанавливайте только production зависимости в Node.js Docker образе¶

    Следующая директива Dockerfile устанавливает все зависимости в контейнер, включая devDependencies, которые не нужны для работы приложения. Это добавляет ненужный риск безопасности от пакетов, используемых как зависимости разработки, а также неоправданно увеличивает размер образа.

    RUN npm ci

    Обеспечьте детерминированные сборки с помощью npm ci. Это предотвращает неожиданности в процессе непрерывной интеграции (CI), так как команда прерывается при любых отклонениях от lockfile.

    При сборке Docker образа для production мы хотим убедиться, что устанавливаем только production зависимости детерминированным образом, что приводит нас к следующей рекомендации по установке npm зависимостей в образе контейнера:

    RUN npm ci --omit=dev

    Обновлённое содержимое Dockerfile на этом этапе выглядит следующим образом:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
WORKDIR /usr/src/app
COPY . /usr/src/app
RUN npm ci --omit=dev
CMD "npm" "start"

    3) Оптимизируйте инструментарий Node.js для production¶

    При сборке Docker образа Node.js для production необходимо убедиться, что все фреймворки и библиотеки используют оптимальные настройки производительности и безопасности.

    Это приводит нас к добавлению следующей директивы Dockerfile:

    ENV NODE_ENV production

    На первый взгляд это выглядит избыточным, так как мы уже указали только production зависимости на этапе npm ci — так зачем это нужно?

    Разработчики в основном связывают переменную окружения NODE_ENV=production с установкой зависимостей, связанных с production, однако эта настройка имеет и другие эффекты, о которых нам нужно знать.

    Некоторые фреймворки и библиотеки могут включать оптимизированную конфигурацию для production только в том случае, если переменная окружения NODE_ENV установлена в production. Независимо от нашего мнения о том, является ли это хорошей или плохой практикой для фреймворков, важно об этом знать.

    Например, документация Express подчёркивает важность установки этой переменной окружения для включения оптимизаций производительности и безопасности:

    Влияние переменной NODE_ENV на производительность может быть очень значительным.

    Многие другие библиотеки, на которые вы полагаетесь, также могут ожидать, что эта переменная установлена, поэтому мы должны задать её в нашем Dockerfile.

    Обновлённый Dockerfile теперь должен выглядеть следующим образом со встроенной настройкой переменной окружения NODE_ENV:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
ENV NODE_ENV production
WORKDIR /usr/src/app
COPY . /usr/src/app
RUN npm ci --omit=dev
CMD "npm" "start"

    4) Не запускайте контейнеры от имени root¶

    Принцип наименьших привилегий — давно существующий контроль безопасности со времён ранних версий Unix, и мы всегда должны следовать ему при запуске контейнеризованных Node.js веб-приложений.

    Оценка угроз довольно проста — если злоумышленник сможет скомпрометировать веб-приложение способом, позволяющим внедрение команд или обход пути к директории, то они будут выполнены от имени пользователя, которому принадлежит процесс приложения. Если этим процессом окажется root, злоумышленник сможет делать практически всё в контейнере, включая [попытку побега из контейнера или эскалацию привилегий. Зачем нам рисковать? Правильно, незачем.

    Повторяйте за мной: "хорошие друзья не позволяют запускать контейнеры от имени root!"

    Официальный Docker образ node, а также его варианты, такие как alpine, включают непривилегированного пользователя с таким же именем: node. Однако недостаточно просто запустить процесс от имени node. Например, следующего может быть недостаточно для нормальной работы приложения:

    USER node
CMD "npm" "start"

    Причина в том, что директива USER в Dockerfile лишь гарантирует, что процесс принадлежит пользователю node. Но как насчёт всех файлов, скопированных ранее инструкцией COPY? Они принадлежат root. Именно так Docker работает по умолчанию.

    Полный и правильный способ снижения привилегий выглядит следующим образом, с учётом всех актуальных практик Dockerfile на данный момент:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
ENV NODE_ENV production
WORKDIR /usr/src/app
COPY --chown=node:node . /usr/src/app
RUN npm ci --omit=dev
USER node
CMD "npm" "start"

    5) Правильно обрабатывайте события для безопасного завершения Node.js Docker веб-приложения¶

    Одна из наиболее распространённых ошибок, которую я вижу в статьях о контейнеризации Node.js приложений в Docker, — это способ запуска процесса. Все следующие варианты и их производные являются плохими паттернами, которых следует избегать:

    • CMD "npm" "start"
    • CMD ["yarn", "start"]
    • CMD "node" "server.js"
    • CMD "start-app.sh"

    Давайте разберёмся! Я расскажу вам о различиях между ними и объясню, почему все они являются паттернами, которых следует избегать.

    Следующие соображения являются ключевыми для понимания контекста правильного запуска и завершения Node.js Docker приложений:

    1. Оркестровый движок, например Docker Swarm, Kubernetes или даже сам Docker engine, должен иметь возможность отправлять сигналы процессу в контейнере. В основном это сигналы завершения приложения, такие как SIGTERM и SIGKILL.
    2. Процесс может запускаться косвенно, и в этом случае не всегда гарантировано, что он получит эти сигналы.
    3. Ядро Linux обрабатывает процессы, запущенные с идентификатором процесса 1 (PID), иначе, чем любые другие идентификаторы процессов.

    Вооружившись этими знаниями, давайте начнём исследовать способы запуска процесса для контейнера, начав с примера из собираемого нами Dockerfile:

    CMD "npm" "start"

    Здесь есть два подводных камня. Во-первых, мы косвенно запускаем node приложение, напрямую вызывая npm клиент. Кто может гарантировать, что npm CLI перенаправляет все события в node runtime? На самом деле нет, и мы можем легко это проверить.

    Убедитесь, что в вашем Node.js приложении установлен обработчик события для сигнала SIGHUP, который выводит в консоль сообщение каждый раз при получении события. Простой пример кода выглядит так:

    function handle(signal) {
   console.log(`*^!@4=> Received event: ${signal}`)
}
process.on('SIGHUP', handle)

    Затем запустите контейнер, и когда он поднимется, отправьте ему сигнал SIGHUP через docker CLI со специальным флагом командной строки --signal:

    $ docker kill --signal=SIGHUP elastic_archimedes

    Ничего не произошло, верно? Это потому, что npm клиент не пересылает никакие сигналы порождённому им node процессу.

    Второй подводный камень связан с различными способами указания директивы CMD в Dockerfile. Существует два способа, и они не равнозначны:

    1. shellform нотация, при которой контейнер порождает интерпретатор shell, который оборачивает процесс. В таких случаях shell может не пересылать сигналы должным образом вашему процессу.
    2. execform нотация, при которой процесс запускается напрямую без оборачивания в shell. Она задаётся с использованием нотации JSON массива, например: CMD ["npm", "start"]. Все сигналы, отправленные контейнеру, напрямую передаются процессу.

    Исходя из этих знаний, мы хотим улучшить директиву выполнения процесса в нашем Dockerfile следующим образом:

    CMD ["node", "server.js"]

    Теперь мы запускаем node процесс напрямую, гарантируя, что он получает все отправленные ему сигналы, не будучи обёрнут в интерпретатор shell.

    Однако это вводит ещё один подводный камень.

    Когда процессы запускаются с PID 1, они фактически берут на себя часть обязанностей системы инициализации (init), которая обычно отвечает за инициализацию операционной системы и процессов. Ядро обрабатывает PID 1 иначе, чем другие идентификаторы процессов. Это особое обращение со стороны ядра означает, что обработка сигнала SIGTERM для запущенного процесса не вызовет запасное поведение по умолчанию в виде завершения процесса, если обработчик для него не установлен явно.

    Процитируем рекомендацию рабочей группы Node.js Docker по этому поводу: "Node.js не был разработан для запуска с PID 1, что приводит к неожиданному поведению внутри Docker. Например, процесс Node.js, запущенный с PID 1, не будет реагировать на SIGINT (CTRL-C) и аналогичные сигналы".

    Таким образом, следует использовать инструмент, который будет действовать как процесс init: запускаться с PID 1, затем порождать наше Node.js приложение как отдельный процесс, гарантируя при этом проксирование всех сигналов этому Node.js процессу. По возможности мы хотим использовать минимальный инструментарий для этого, чтобы не добавлять уязвимостей безопасности в наш образ контейнера.

    Одним из таких инструментов является dumb-init, который статически слинкован и имеет небольшой размер. Вот как его настроить:

    RUN apk add dumb-init
CMD ["dumb-init", "node", "server.js"]

    Это приводит нас к следующему актуальному Dockerfile. Обратите внимание, что мы разместили установку пакета dumb-init сразу после объявления образа, чтобы воспользоваться кешированием слоёв Docker:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
RUN apk add dumb-init
ENV NODE_ENV production
WORKDIR /usr/src/app
COPY --chown=node:node . .
RUN npm ci --omit=dev
USER node
CMD ["dumb-init", "node", "server.js"]

    Полезно знать: команды docker kill и docker stop отправляют сигналы только процессу контейнера с PID 1. Если вы используете shell скрипт для запуска вашего Node.js приложения, учтите, что экземпляр shell — например, /bin/sh — не пересылает сигналы дочерним процессам, то есть ваше приложение никогда не получит SIGTERM.

    6) Graceful завершение для ваших Node.js веб-приложений¶

    Раз мы уже обсуждаем сигналы процессов для завершения приложений, убедимся, что мы завершаем их правильно и корректно, не нарушая работу пользователей.

    Когда Node.js приложение получает сигнал прерывания, известный как SIGINT, или CTRL+C, это вызывает резкое завершение процесса — если, конечно, не установлены обработчики событий для иного поведения. Это означает, что клиенты, подключённые к веб-приложению, будут немедленно отключены. Представьте теперь сотни контейнеров Node.js, оркестрируемых Kubernetes, которые поднимаются и опускаются по мере необходимости для масштабирования или обработки ошибок. Не самый лучший пользовательский опыт.

    Вы можете легко смоделировать эту проблему. Вот пример стандартного Fastify веб-приложения со встроенной задержкой ответа в 60 секунд для одного из эндпоинтов:

    fastify.get('/delayed', async (request, reply) => {
 const SECONDS_DELAY = 60000
 await new Promise(resolve => {
     setTimeout(() => resolve(), SECONDS_DELAY)
 })
 return { hello: 'delayed world' }
})

const start = async () => {
 try {
   await fastify.listen(PORT, HOST)
   console.log(`*^!@4=> Process id: ${process.pid}`)
 } catch (err) {
   fastify.log.error(err)
   process.exit(1)
 }
}

start()

    Запустите это приложение и после его старта отправьте простой HTTP запрос к этому эндпоинту:

    $ time curl https://localhost:3000/delayed

    Нажмите CTRL+C в консоли запущенного Node.js и вы увидите, что curl запрос завершился резко. Это моделирует тот же опыт, который получат ваши пользователи при остановке контейнеров.

    Для обеспечения лучшего опыта мы можем сделать следующее:

    1. Установить обработчик событий для различных сигналов завершения, таких как SIGINT и SIGTERM.
    2. Обработчик ожидает завершения операций очистки, таких как соединения с базой данных, текущие HTTP запросы и другое.
    3. Затем обработчик завершает Node.js процесс.

    Конкретно в Fastify мы можем заставить наш обработчик вызвать fastify.close(), который возвращает промис, который мы будем ожидать, а Fastify также позаботится об ответе на каждое новое соединение кодом HTTP статуса 503, сигнализируя о том, что приложение недоступно.

    Добавим наш обработчик событий:

    async function closeGracefully(signal) {
   console.log(`*^!@4=> Received signal to terminate: ${signal}`)

   await fastify.close()
   // await db.close() if we have a db connection in this app
   // await other things we should cleanup nicely
   process.exit()
}
process.on('SIGINT', closeGracefully)
process.on('SIGTERM', closeGracefully)

    Признаём, что это больше относится к общим вопросам веб-приложений, чем к Dockerfile, однако в оркестрированных средах это ещё более важно.

    8) Используйте многоэтапные сборки¶

    Многоэтапные сборки — отличный способ перейти от простого, но потенциально ненадёжного Dockerfile к разделённым этапам сборки Docker образа, что позволяет избежать утечки конфиденциальной информации. Кроме того, мы можем использовать больший базовый Docker образ для установки зависимостей, компиляции нативных npm модулей при необходимости, а затем скопировать все эти артефакты в небольшой production базовый образ, как в нашем примере с alpine.

    Предотвращение утечки конфиденциальной информации¶

    Сценарий утечки конфиденциальной информации здесь встречается чаще, чем вы думаете.

    Если вы собираете Docker образы в рабочих проектах, велика вероятность, что вы также поддерживаете приватные npm пакеты. В таком случае вам, вероятно, нужно было найти способ передать секретный NPM_TOKEN в npm install.

    Вот пример того, о чём я говорю:

    FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
RUN apk add dumb-init
ENV NODE_ENV production
ENV NPM_TOKEN 1234
WORKDIR /usr/src/app
COPY --chown=node:node . .
#RUN npm ci --omit=dev
RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && \
   npm ci --omit=dev
USER node
CMD ["dumb-init", "node", "server.js"]

    Однако при таком подходе файл .npmrc с секретным npm токеном остаётся внутри Docker образа. Можно попытаться улучшить это, удалив его впоследствии, например так:

    RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && \
   npm ci --omit=dev
RUN rm -rf .npmrc

    Однако теперь файл .npmrc доступен в другом слое Docker образа. Если этот Docker образ публичен или кто-то получит к нему доступ, ваш токен будет скомпрометирован. Лучшим вариантом улучшения будет следующее:

    RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && \
   npm ci --omit=dev; \
   rm -rf .npmrc

    Проблема теперь в том, что сам Dockerfile должен рассматриваться как секретный актив, поскольку он содержит внутри секретный npm токен.

    К счастью, Docker поддерживает возможность передачи аргументов в процесс сборки:

    ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && \
   npm ci --omit=dev; \
   rm -rf .npmrc

    Затем собираем его следующим образом:

    $ docker build . -t nodejs-tutorial --build-arg NPM_TOKEN=1234

    Знаю, вы думали, что на этом всё готово, но, к сожалению, нет 🙂

    Вот как бывает с безопасностью — иногда очевидные вещи оказываются очередным подводным камнем.

    В чём же проблема теперь? Аргументы сборки, переданные таким образом в Docker, сохраняются в журнале истории. Убедимся сами. Выполним команду:

    $ docker history nodejs-tutorial

    которая выводит следующее:

    IMAGE          CREATED              CREATED BY                                      SIZE      COMMENT

<missing>      About a minute ago   USER node                                       0B        buildkit.dockerfile.v0
<missing>      About a minute ago   RUN |1 NPM_TOKEN=1234 /bin/sh -c echo "//reg…   5.71MB    buildkit.dockerfile.v0
<missing>      About a minute ago   ARG NPM_TOKEN                                   0B        buildkit.dockerfile.v0

<missing>      About a minute ago   WORKDIR /usr/src/app                            0B        buildkit.dockerfile.v0

    Видите секретный npm токен там? Вот о чём я и говорю.

    Есть отличный способ управления секретами для образа контейнера, но сейчас самое время представить многоэтапные сборки как способ решения этой проблемы, а также показать, как мы можем создавать минимальные образы.

    Введение в многоэтапные сборки для Node.js Docker образов¶

    Следуя принципу разделения ответственностей из разработки программного обеспечения, мы применим те же идеи для сборки наших Node.js Docker образов. У нас будет один образ, используемый для сборки всего необходимого для запуска Node.js приложения — в мире Node.js это означает установку npm пакетов и компиляцию нативных npm модулей при необходимости. Это будет наш первый этап.

    Второй Docker образ, представляющий второй этап сборки Docker, будет production Docker образом. Этот второй и последний этап — образ, который мы фактически оптимизируем и публикуем в реестр, если он у нас есть. Первый образ, который мы будем называть образом build, отбрасывается и остаётся как висячий (dangling) образ на Docker хосте, выполнившем сборку, до его очистки.

    Вот обновление нашего Dockerfile с учётом прогресса на данный момент, разделённое на два этапа:

    # --------------> The build image
FROM node:latest AS build
ARG NPM_TOKEN
WORKDIR /usr/src/app
COPY package*.json /usr/src/app/
RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && \
   npm ci --omit=dev && \
   rm -f .npmrc

# --------------> The production image
FROM node:lts-alpine@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
RUN apk add dumb-init
ENV NODE_ENV production
USER node
WORKDIR /usr/src/app
COPY --chown=node:node --from=build /usr/src/app/node_modules /usr/src/app/node_modules
COPY --chown=node:node . /usr/src/app
CMD ["dumb-init", "node", "server.js"]

    Как видите, я выбрал больший образ для этапа build, так как мне может понадобиться инструментарий, такой как gcc (GNU Compiler Collection), для компиляции нативных npm пакетов или других нужд.

    На втором этапе есть специальная нотация для директивы COPY, которая копирует папку node_modules/ из сборочного Docker образа в этот новый production базовый образ.

    Кроме того, обратите внимание: видите ли вы NPM_TOKEN, переданный как аргумент сборки в промежуточный Docker образ build? Его больше нет в выводе команды docker history nodejs-tutorial, потому что он не существует в нашем production docker образе.

    9) Исключайте ненужные файлы из ваших Node.js Docker образов¶

    У вас есть файл .gitignore, чтобы не засорять git репозиторий ненужными и потенциально конфиденциальными файлами, верно? То же самое применимо к Docker образам.

    Docker имеет .dockerignore, который гарантирует, что файлы, соответствующие glob паттернам внутри него, не будут отправлены Docker daemon. Вот список файлов, чтобы дать вам представление о том, что вы, возможно, помещаете в свой Docker образ и что нам желательно исключить:

    .dockerignore
node_modules
npm-debug.log
Dockerfile
.git
.gitignore

    Как видите, исключение node_modules/ действительно важно, поскольку в противном случае упрощённая версия Dockerfile, с которой мы начали, привела бы к копированию локальной папки node_modules/ в контейнер как есть.

    FROM node@sha256:b2da3316acdc2bec442190a1fe10dc094e7ba4121d029cb32075ff59bb27390a
WORKDIR /usr/src/app
COPY . /usr/src/app
RUN npm ci
CMD "npm" "start"

    На самом деле, наличие файла .dockerignore ещё более важно при использовании многоэтапных сборок Docker. Для освежения памяти, вот как выглядит 2-й этап сборки Docker:

    # --------------> The production image
FROM node:lts-alpine
RUN apk add dumb-init
ENV NODE_ENV production
USER node
WORKDIR /usr/src/app
COPY --chown=node:node --from=build /usr/src/app/node_modules /usr/src/app/node_modules
COPY --chown=node:node . /usr/src/app
CMD ["dumb-init", "node", "server.js"]

    Важность наличия .dockerignore заключается в том, что при выполнении COPY . /usr/src/app на 2-м этапе Dockerfile мы также копируем в Docker образ локальную папку node_modules/. Это категорически недопустимо, так как мы можем скопировать изменённый исходный код внутри node_modules/.

    Помимо этого, используя подстановку COPY ., мы также можем копировать в Docker образ конфиденциальные файлы, содержащие учётные данные или локальную конфигурацию.

    Ключевые выводы относительно файла .dockerignore:

    • Исключает потенциально изменённые копии node_modules/ в Docker образе.
    • Защищает от раскрытия секретов, например содержимого файлов .env или aws.json с учётными данными, которые могут попасть в Node.js Docker образ.
    • Ускоряет сборки Docker, игнорируя файлы, которые иначе привели бы к инвалидации кеша. Например, изменение лог-файла или локального файла конфигурации среды — всё это привело бы к инвалидации кеша Docker образа на том слое, где происходит копирование локальной директории.

    10) Монтирование секретов в Docker образ при сборке¶

    Важно отметить, что файл .dockerignore работает по принципу "всё или ничего" и не может быть включён или выключен для отдельных этапов сборки в многоэтапной сборке Docker.

    Почему это важно? В идеале нам нужен файл .npmrc на этапе сборки, поскольку он может включать секретный npm токен для доступа к приватным npm пакетам. Возможно, в нём также задана конкретная конфигурация прокси или реестра для скачивания пакетов.

    Это означает, что имеет смысл делать файл .npmrc доступным на этапе build — однако на втором этапе для production образа он нам не нужен совсем, и мы также не хотим его там видеть, так как он может содержать конфиденциальную информацию, например секретный npm токен.

    Один из способов обойти это ограничение .dockerignore — монтировать локальную файловую систему, которая будет доступна на этапе сборки, однако есть способ получше.

    Docker поддерживает относительно новую возможность, называемую Docker secrets, которая идеально подходит для нашего случая с .npmrc. Вот как это работает:

    • При запуске команды docker build мы укажем аргументы командной строки, определяющие новый идентификатор секрета и ссылающиеся на файл как источник секрета.
    • В Dockerfile мы добавим флаги к директиве RUN для установки production npm, которая монтирует файл, на который ссылается идентификатор секрета, в целевое расположение — локальный файл .npmrc, где он нам нужен.
    • Файл .npmrc монтируется как секрет и никогда не копируется в Docker образ.
    • Наконец, не забудем добавить файл .npmrc в содержимое файла .dockerignore, чтобы он не попал в образ ни на этапе сборки, ни на production этапе.

    Посмотрим, как всё это работает вместе. Сначала обновлённый файл .dockerignore:

    .dockerignore
node_modules
npm-debug.log
Dockerfile
.git
.gitignore
.npmrc

    Затем полный Dockerfile с обновлённой директивой RUN для установки npm пакетов с указанием точки монтирования .npmrc:

    # --------------> The build image
FROM node:latest AS build
WORKDIR /usr/src/app
COPY package*.json /usr/src/app/
RUN --mount=type=secret,mode=0644,id=npmrc,target=/usr/src/app/.npmrc npm ci --omit=dev

# --------------> The production image
FROM node:lts-alpine
RUN apk add dumb-init
ENV NODE_ENV production
USER node
WORKDIR /usr/src/app
COPY --chown=node:node --from=build /usr/src/app/node_modules /usr/src/app/node_modules
COPY --chown=node:node . /usr/src/app
CMD ["dumb-init", "node", "server.js"]

    И наконец, команда для сборки Node.js Docker образа:

    docker build . -t nodejs-tutorial --secret id=npmrc,src=.npmrc

    Примечание: Secrets — это новая функция Docker, и если вы используете более старую версию, вам может потребоваться включить Buildkit следующим образом:

    DOCKER_BUILDKIT=1 docker build . -t nodejs-tutorial --build-arg NPM_TOKEN=1234 --secret id=npmrc,src=.npmrc
