    Ruby on Rails Cheat Sheet¶

    Введение¶

    Данная Шпаргалка предназначена для предоставления разработчикам основных советов по безопасности Ruby on Rails. Она дополняет и развивает положения, изложенные в руководстве по безопасности Rails от основной команды Rails.

    Фреймворк Rails избавляет разработчиков от значительного объёма рутинной работы и предоставляет средства для быстрого и удобного решения сложных задач. Начинающим разработчикам, незнакомым с внутренним устройством Rails, скорее всего необходим базовый набор рекомендаций для защиты фундаментальных аспектов их приложений. Именно этой цели служит данный документ.

    Разделы¶

    Внедрение команд¶

    Ruby предоставляет функцию "eval", которая динамически формирует новый код Ruby из строк. Также существует ряд способов вызова системных команд.

    eval("ruby code here")
system("os command here")
`ls -al /` # (обратные кавычки содержат команду ОС)
exec("os command here")
spawn("os command here")
open("| os command here")
Process.exec("os command here")
Process.spawn("os command here")
IO.binread("| os command here")
IO.binwrite("| os command here", "foo")
IO.foreach("| os command here") {}
IO.popen("os command here")
IO.read("| os command here")
IO.readlines("| os command here")
IO.write("| os command here", "foo")

    Несмотря на всю полезность этих команд, при их использовании в Rails-приложениях необходимо проявлять крайнюю осторожность. Как правило, это просто плохая практика. В случае необходимости следует использовать список разрешённых значений и максимально тщательно валидировать любые входные данные.

    Руководства Rails и OWASP содержат дополнительную информацию о внедрении команд.

    SQL-инъекция¶

    Ruby on Rails часто используется с ORM под названием ActiveRecord, хотя фреймворк достаточно гибок и может работать с другими источниками данных. Как правило, в простых Rails-приложениях для запроса данных используются методы моделей Rails. Во многих случаях защита от SQL-инъекций работает «из коробки». Тем не менее возможно написание кода, допускающего SQL-инъекции.

    name = params[:name]
@projects = Project.where("name like '" + name + "'");

    Данное выражение уязвимо для инъекций, поскольку параметр name не экранируется.

    Вот правильный способ построения подобного запроса:

    @projects = Project.where("name like ?", "%#{ActiveRecord::Base.sanitize_sql_like(params[:name])}%")

    Следует избегать построения SQL-запросов на основе пользовательских данных. Более реалистичные и подробные примеры можно найти здесь: rails-sqli.org. OWASP содержит обширную информацию о SQL-инъекциях.

    Межсайтовый скриптинг (XSS)¶

    По умолчанию защита от XSS является поведением по умолчанию. При отображении строковых данных в представлениях они экранируются перед отправкой в браузер. Это существенная защита, однако нередко разработчики её обходят — например, для реализации форматированного ввода текста. Если требуется передать переменные во фронтенд с сохранением HTML-тегов, может возникнуть соблазн сделать следующее в файле .erb (разметка Ruby):

    # Неправильно! Не делайте этого!
<%= raw @product.name %>

# Неправильно! Не делайте этого!
<%== @product.name %>

# Неправильно! Не делайте этого!
<%= @product.name.html_safe %>

    К сожалению, любое поле, использующее raw, html_safe или аналогичные методы, является потенциальной целью XSS-атаки. Следует отметить, что существуют и широко распространённые заблуждения относительно html_safe().

    Эта статья подробно описывает лежащий в основе механизм SafeBuffer. Другие теги, изменяющие способ подготовки строк к выводу, могут порождать аналогичные проблемы.

    Метод html_safe класса String носит несколько вводящее в заблуждение название. Он означает, что мы достоверно знаем: содержимое строки безопасно для включения в HTML без экранирования. Сам по себе этот метод небезопасен!

    Если необходимо принимать HTML-контент от пользователей, рассмотрите использование языка разметки для форматированного текста в приложении (например: Markdown и textile) и запретите HTML-теги. Это помогает гарантировать, что принимаемые входные данные не содержат потенциально вредоносного HTML.

    Если ограничить пользователей от ввода HTML невозможно, рассмотрите внедрение политики безопасности контента (Content Security Policy) для запрета выполнения JavaScript. Наконец, рассмотрите использование метода #sanitize, позволяющего перечислить допустимые теги. Будьте осторожны: этот метод неоднократно оказывался уязвимым и никогда не станет исчерпывающим решением.

    Часто упускаемый из виду вектор XSS-атаки в старых версиях Rails — значение атрибута href ссылки:

    <%= link_to "Personal Website", @user.website %>

    Если @user.website содержит ссылку, начинающуюся с javascript:, содержимое выполнится при клике пользователя на сгенерированную ссылку:

    <a href="javascript:alert('Haxored')">Personal Website</a>

    В новых версиях Rails подобные ссылки экранируются более надёжно.

    link_to "Personal Website", 'javascript:alert(1);'.html_safe()
# Сгенерирует:
# "<a href="javascript:alert(1);">Personal Website</a>"

    Использование Content Security Policy — ещё одна мера безопасности для запрета выполнения ссылок, начинающихся с javascript:.

    Сканер Brakeman помогает обнаруживать XSS-проблемы в Rails-приложениях.

    OWASP предоставляет более общую информацию о XSS на странице верхнего уровня: Cross-site Scripting (XSS).

    Сессии¶

    По умолчанию Ruby on Rails использует хранилище сессий на основе Cookie. Это означает, что если ничего не изменить, сессия не будет истекать на сервере. Следовательно, некоторые стандартные приложения могут быть уязвимы для атак воспроизведения. Это также означает, что конфиденциальная информация не должна никогда помещаться в сессию.

    Лучшей практикой является использование хранилища сессий на основе базы данных, что в Rails реализуется очень просто:

    Project::Application.config.session_store :active_record_store

    Существует Шпаргалка по управлению сессиями.

    Аутентификация¶

    Как и в случае с любыми чувствительными данными, начните защиту аутентификации с включения TLS в конфигурации:

    # config/environments/production.rb
# Принудительный HTTPS для всего приложения, Strict-Transport-Security,
# и безопасные куки
config.force_ssl = true

    Раскомментируйте строку 3, как показано выше, в вашей конфигурации.

    В целом Rails не предоставляет встроенной аутентификации. Однако большинство разработчиков, работающих с Rails, используют такие библиотеки, как Devise или AuthLogic.

    Для включения аутентификации можно использовать gem Devise.

    Установите его:

    gem 'devise'

    Затем установите его для модели пользователя:

    rails generate devise:install

    Далее укажите в маршрутах, какие ресурсы (маршруты) требуют аутентифицированного доступа:

    Rails.application.routes.draw do
  authenticate :user do
    resources :something do  # эти ресурсы требуют аутентификации
      ...
    end
  end

  devise_for :users # маршруты регистрации/входа/выхода

  root to: 'static#home' # аутентификация не требуется
end

    Для обеспечения сложности паролей можно использовать zxcvbn gem. Настройте модель пользователя с его использованием:

    class User < ApplicationRecord
  devise :database_authenticatable,
    # другие функции devise, затем
    :zxcvbnable
end

    И настройте требуемую сложность пароля:

    # в config/initializers/devise.rb
Devise.setup do |config|
  # оценка zxcvbn для devise
  config.min_password_score = 4 # оценка сложности здесь.
  ...

    Вы можете попробовать этот PoC для более подробного изучения.

    Далее, omniauth gem позволяет использовать множество стратегий аутентификации. С его помощью можно настроить безопасную аутентификацию через Facebook, LDAP и многих других провайдеров. Подробнее читайте здесь.

    Аутентификация по токену¶

    Devise обычно использует Cookies для аутентификации.

    В случае если желательна аутентификация по токену, её можно реализовать с помощью gem devise_token_auth.

    Он поддерживает множество технологий фронтенда, например angular2-token.

    Этот gem настраивается аналогично самому gem Devise. Он также требует omniauth в качестве зависимости.

    # аутентификация на основе токенов
gem 'devise_token_auth'
gem 'omniauth'

    Затем определяется маршрут:

    mount_devise_token_auth_for 'User', at: 'auth'

    И модель User изменяется соответствующим образом.

    Эти действия можно выполнить одной командой:

    rails g devise_token_auth:install [USER_CLASS] [MOUNT_PATH]

    В зависимости от вашего случая использования может потребоваться отредактировать сгенерированную миграцию, чтобы исключить ненужные поля и/или дублирование полей.

    Примечание: при использовании только аутентификации по токену в контроллерах больше нет необходимости в защите от CSRF. Если на некоторых путях используется аутентификация на основе Cookie, на них по-прежнему необходима защита от подделки!

    Существует Шпаргалка по аутентификации.

    Небезопасные прямые ссылки на объекты или принудительный просмотр¶

    По умолчанию Rails-приложения используют RESTful структуру URI. Это означает, что пути зачастую интуитивно понятны и предсказуемы. Для защиты от попыток пользователя получить доступ к данным другого пользователя или изменить их важно явно контролировать действия. В стандартном Rails-приложении такая защита отсутствует «из коробки». Её можно реализовать вручную на уровне контроллера.

    Также возможно, и, вероятно, рекомендуется, рассмотреть библиотеки управления доступом на основе ресурсов, такие как cancancan (замена cancan) или pundit. Это гарантирует, что все операции с объектами базы данных авторизованы бизнес-логикой приложения.

    Более общая информация об этом классе уязвимостей находится на странице OWASP Top 10.

    CSRF (Межсайтовая подделка запросов)¶

    Ruby on Rails имеет специальную встроенную поддержку CSRF-токенов. Для её включения или проверки того, что она включена, найдите базовый ApplicationController и найдите директиву следующего вида:

    class ApplicationController < ActionController::Base
  protect_from_forgery

    Обратите внимание, что синтаксис этого типа управления включает способ добавления исключений. Исключения могут быть полезны для API или по другим причинам — но должны быть проверены и намеренно включены. В приведённом ниже примере Rails ProjectController не будет обеспечивать защиту от CSRF для метода show.

    class ProjectController < ApplicationController
  protect_from_forgery except: :show

    Также следует отметить, что по умолчанию Rails не обеспечивает защиту от CSRF для HTTP-запросов GET.

    Примечание: если вы используете только аутентификацию по токену, в контроллерах нет необходимости защищаться от CSRF подобным образом. Если аутентификация на основе Cookie используется на некоторых путях, то защита по-прежнему обязательна для них.

    На OWASP есть страница верхнего уровня для Cross-Site Request Forgery (CSRF).

    Перенаправления и переходы¶

    Веб-приложениям нередко требуется возможность динамически перенаправлять пользователей на основе данных, предоставленных клиентом. Динамическое перенаправление обычно предполагает, что клиент включает URL в параметр запроса к приложению. Получив запрос, приложение перенаправляет пользователя на URL, указанный в запросе.

    Например:

    http://www.example.com/redirect?url=http://www.example_commerce_site.com/checkout

    Приведённый запрос перенаправит пользователя на http://www.example.com/checkout. Угроза безопасности, связанная с этой функциональностью, заключается в использовании доверенного бренда организации для фишинга пользователей и перенаправления их на вредоносный сайт, в нашем примере — badhacker.com.

    Пример:

    http://www.example.com/redirect?url=http://badhacker.com

    Самой базовой, но ограничительной защитой является использование опции :only_path. При установке значения true она по существу удаляет любую информацию о хосте. Однако опция :only_path должна быть частью первого аргумента. Если первый аргумент не является хэш-таблицей, передать эту опцию невозможно. При отсутствии пользовательского хелпера или списка разрешённых значений один из возможных подходов выглядит следующим образом:

    begin
  if path = URI.parse(params[:url]).path
    redirect_to path
  end
rescue URI::InvalidURIError
  redirect_to '/'
end

    Если необходимо сопоставлять пользовательский ввод со списком одобренных сайтов или TLD с помощью регулярных выражений, имеет смысл использовать библиотеку, например URI.parse(), для получения хоста, а затем сопоставлять значение хоста с шаблонами регулярных выражений. Эти регулярные выражения должны, как минимум, содержать якоря, иначе вероятность обхода злоумышленником процедуры валидации возрастает.

    Пример:

    require 'uri'
host = URI.parse("#{params[:url]}").host
# это может быть уязвимо для javascript://trusted.com/%0Aalert(0)
# поэтому проверяйте также .scheme и .port
validation_routine(host) if host
def validation_routine(host)
  # Процедура валидации, где используются \A и \z в качестве якорей, *не* ^ и $
  # можно также сопоставить значение хоста со списком разрешённых значений
end

    Также слепое перенаправление на параметр пользовательского ввода может привести к XSS.

    Пример кода:

    redirect_to params[:to]

    Даст следующий URL:

    http://example.com/redirect?to[status]=200&to[protocol]=javascript:alert(0)//

    Очевидным способом устранения данного типа уязвимости является ограничение до конкретных доменов верхнего уровня (TLD), статическое определение конкретных сайтов или сопоставление ключа с его значением.

    Пример кода:

    ACCEPTABLE_URLS = {
  'our_app_1' => "https://www.example_commerce_site.com/checkout",
  'our_app_2' => "https://www.example_user_site.com/change_settings"
}

    Даст следующий URL:

    http://www.example.com/redirect?url=our_app_1

    Код обработки перенаправления:

    def redirect
  url = ACCEPTABLE_URLS["#{params[:url]}"]
  redirect_to url if url
end

    Существует более общий ресурс OWASP о невалидированных перенаправлениях и переходах.

    Динамические пути рендеринга¶

    В Rails действия контроллера и представления могут динамически определять, какое представление или частичный шаблон отрисовать, вызывая метод render. Если пользовательские данные используются в имени шаблона или для его определения, злоумышленник может заставить приложение отрисовать произвольное представление, например административную страницу.

    Следует проявлять осторожность при использовании пользовательского ввода для определения отрисовываемого представления. По возможности избегайте использования пользовательского ввода в имени или пути к представлению.

    Совместное использование ресурсов из разных источников (CORS)¶

    Иногда возникает необходимость совместного использования ресурсов с другим доменом. Например, функция загрузки файлов, отправляющая данные через AJAX-запрос на другой домен. В таких случаях должны соблюдаться правила одного источника, которым следуют веб-браузеры. Современные браузеры, соответствующие стандартам HTML5, допускают это, но для этого необходимо принять ряд мер предосторожности.

    При использовании нестандартных HTTP-конструкций, например нетипичного заголовка Content-Type, применяется следующее:

    Принимающий сайт должен перечислять только те домены, которым разрешено делать подобные запросы, а также устанавливать заголовок Access-Control-Allow-Origin как в ответе на запрос OPTIONS, так и в ответе на запрос POST. Это связано с тем, что сначала отправляется запрос OPTIONS для определения того, допускает ли удалённый или принимающий сайт запрашивающий домен. Затем отправляется второй запрос — POST. И снова заголовок должен быть установлен, чтобы транзакция считалась успешной.

    При использовании стандартных HTTP-конструкций:

    Запрос отправляется, и браузер при получении ответа проверяет заголовки ответа для определения того, может ли и должен ли ответ быть обработан.

    Список разрешённых значений в Rails:

    Gemfile:

    gem 'rack-cors', :require => 'rack/cors'

    config/application.rb:

    module Sample
  class Application < Rails::Application
    config.middleware.use Rack::Cors do
      allow do
        origins 'someserver.example.com'
        resource %r{/users/\d+.json},
        :headers => ['Origin', 'Accept', 'Content-Type'],
        :methods => [:post, :get]
      end
    end
  end
end

    Заголовки, связанные с безопасностью¶

    Для установки значения заголовка просто обратитесь к объекту response.headers как к хэшу внутри вашего контроллера (часто в before/after_filter).

    response.headers['X-header-name'] = 'value'

    Rails предоставляет функциональность default_headers, которая будет автоматически применять указанные значения. Это работает для большинства заголовков практически во всех случаях.

    ActionDispatch::Response.default_headers = {
  'X-Frame-Options' => 'SAMEORIGIN',
  'X-Content-Type-Options' => 'nosniff',
  'X-XSS-Protection' => '0'
}

    Strict transport security — особый случай, он устанавливается в файле среды (например, production.rb)

    config.force_ssl = true

    Для тех, кто не использует последние версии, существует библиотека (secure_headers) с аналогичным поведением и предоставляемой абстракцией политики безопасности контента. Она автоматически применяет логику на основе user agent для формирования краткого набора заголовков.

    Ошибки бизнес-логики¶

    Любое приложение на любой технологии может содержать ошибки бизнес-логики, приводящие к уязвимостям безопасности. Ошибки бизнес-логики сложно или невозможно обнаружить с помощью автоматизированных инструментов. Лучшими способами предотвращения ошибок безопасности в бизнес-логике являются проверка кода, парное программирование и написание юнит-тестов.

    Поверхность атаки¶

    В целом Rails избегает уязвимостей типа открытого перенаправления и обхода путей благодаря файлу /config/routes.rb, который определяет, какие URL должны быть доступны и какими контроллерами обрабатываться. Файл маршрутов — отличное место для оценки масштабов поверхности атаки.

    Пример может выглядеть следующим образом:

    # это пример того, чего НЕ нужно делать
match ':controller(/:action(/:id(.:format)))'

    В данном случае этот маршрут позволяет вызывать любой публичный метод любого контроллера как действие. Как разработчик, вы должны убедиться, что пользователи могут достигать только предусмотренных методов контроллера и именно предусмотренным способом.

    Чувствительные файлы¶

    Многие Rails-приложения являются открытым исходным кодом и размещены в публично доступных репозиториях. Независимо от того, так ли это или код хранится в корпоративной системе контроля версий, существуют определённые файлы, которые должны быть либо исключены, либо тщательно управляемы.

    /config/database.yml                 -  Может содержать учётные данные для production.
/config/initializers/secret_token.rb -  Содержит секрет для хэширования куки сессии.
/db/seeds.rb                         -  Может содержать начальные данные, включая начального администратора.
/db/development.sqlite3              -  Может содержать реальные данные.

    Шифрование¶

    Rails использует шифрование ОС. В целом, всегда плохая идея — писать собственное шифрование.

    Devise по умолчанию использует bcrypt для хэширования паролей, что является подходящим решением.

    Как правило, следующая конфигурация задаёт 10 итераций для production: /config/initializers/devise.rb

    config.stretches = Rails.env.test? ? 1 : 10

    Обновление Rails и процесс обновления зависимостей¶

    В начале 2013 года в фреймворке Rails был выявлен ряд критических уязвимостей. Организации, отставшие от актуальных версий, испытывали больше трудностей с обновлением и сталкивались с более сложными решениями, включая необходимость патчить исходный код самого фреймворка.

    Дополнительная проблема Ruby-приложений в целом заключается в том, что большинство библиотек (gems) не подписаны их авторами. Построить Rails-проект с библиотеками из доверенных источников буквально невозможно. Хорошей практикой может быть аудит используемых gems.

    В целом важно иметь процесс обновления зависимостей. Примерный процесс может определять три механизма инициирования обновления:

    • Каждый месяц/квартал зависимости обновляются в целом.
    • Каждую неделю учитываются важные уязвимости безопасности, что потенциально инициирует обновление.
    • В ИСКЛЮЧИТЕЛЬНЫХ случаях могут потребоваться экстренные обновления.

    Инструменты¶

    Используйте brakeman — инструмент анализа кода с открытым исходным кодом для Rails-приложений — для выявления многих потенциальных проблем. Он не обязательно даст исчерпывающие результаты проверки безопасности, но поможет найти легко обнаруживаемые проблемы. Отличный способ увидеть потенциальные проблемы в Rails — изучить документацию brakeman по типам предупреждений.

    Более новой альтернативой является bearer — инструмент анализа безопасности и конфиденциальности кода с открытым исходным кодом для Ruby и JavaScript/TypeScript, позволяющий выявлять широкий спектр потенциальных проблем из OWASP Top 10. Он предоставляет множество параметров конфигурации и легко интегрируется в CI/CD-конвейер.

    Существуют появляющиеся инструменты для отслеживания проблем безопасности в наборах зависимостей, например автоматическое сканирование от GitHub и GitLab.

    Ещё одной областью инструментария является инструмент тестирования безопасности Gauntlt, построенный на cucumber и использующий синтаксис gherkin для определения файлов атак.

    Запущенный в мае 2013 года и очень схожий со сканером brakeman, dawnscanner — rubygem-статический анализатор проблем безопасности для веб-приложений Rails, Sinatra и Padrino. Версия 1.6.6 содержит более 235 проверок безопасности CVE, специфичных для Ruby.
