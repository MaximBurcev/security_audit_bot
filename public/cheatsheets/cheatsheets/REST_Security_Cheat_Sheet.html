    REST Security Cheat Sheet¶

    Введение¶

    REST (или REpresentational State Transfer) — это архитектурный стиль, впервые описанный в докторской диссертации Роя Филдинга «Архитектурные стили и проектирование сетевых программных архитектур».

    Этот стиль развивался по мере того, как Филдинг работал над спецификациями HTTP/1.1 и URI, и доказал свою пригодность для разработки распределённых гипермедийных приложений. Хотя REST применим в более широком контексте, чаще всего он используется для взаимодействия со службами по протоколу HTTP.

    Ключевой абстракцией информации в REST является ресурс. Ресурс REST API идентифицируется URI, как правило — HTTP URL. Компоненты REST используют коннекторы для выполнения действий над ресурсом: представление фиксирует текущее или желаемое состояние ресурса, после чего это представление передаётся по сети.

    Основные типы коннекторов — клиент и сервер; вспомогательные — кэш, резолвер и туннель.

    REST API являются безсостоятельными (stateless). Сервисы с сохранением состояния (stateful) не соответствуют архитектурному стилю REST. Слово «State» в аббревиатуре REST относится к состоянию ресурса, к которому обращается API, а не к состоянию сессии, в рамках которой вызывается API. Хотя для построения stateful API могут существовать веские причины, важно понимать, что управление сессиями — задача сложная и трудно реализуемая безопасным образом.

    Stateful-сервисы выходят за рамки данного Cheat Sheet: передача состояния от клиента к бэкенду, формально делающая сервис stateless, является антипаттерном, которого также следует избегать, поскольку это создаёт уязвимости для атак с повторным использованием (replay) и имперсонации.

    Для реализации рабочих процессов с REST API ресурсы, как правило, создаются, читаются, обновляются и удаляются. Например, сайт электронной коммерции может предоставлять методы для создания пустой корзины, добавления товаров и оформления заказа. Каждый из этих REST-вызовов является stateless, и эндпоинт должен проверять, авторизован ли вызывающий на выполнение запрошенной операции.

    Ещё одна ключевая особенность REST-приложений — использование стандартных HTTP-методов и кодов ошибок, что позволяет устранить излишние различия между разными сервисами.

    Ещё одна ключевая особенность REST-приложений — использование HATEOAS (Hypermedia As The Engine of Application State). Это делает REST-приложения самодокументируемыми и облегчает разработчикам взаимодействие с REST-сервисом без предварительных знаний о нём.

    HTTPS¶

    Защищённые REST-сервисы должны предоставлять только HTTPS-эндпоинты. Это защищает учётные данные аутентификации при передаче — например, пароли, API-ключи или JSON Web Tokens. Кроме того, это позволяет клиентам аутентифицировать сервис и гарантирует целостность передаваемых данных.

    Дополнительную информацию см. в Transport Layer Security Cheat Sheet.

    Рассмотрите возможность использования взаимной аутентификации на основе клиентских сертификатов для дополнительной защиты высокопривилегированных веб-сервисов.

    Управление доступом¶

    Непубличные REST-сервисы должны выполнять контроль доступа на каждом эндпоинте API. В монолитных приложениях веб-сервисы реализуют это с помощью аутентификации пользователей, логики авторизации и управления сессиями. Для современных архитектур, построенных из нескольких микросервисов в стиле RESTful, такой подход имеет ряд недостатков.

    • Чтобы минимизировать задержку и снизить связанность сервисов, решение о контроле доступа должно приниматься локально на REST-эндпоинтах.
    • Аутентификация пользователей должна быть централизована в Identity Provider (IdP), который выдаёт токены доступа.

    JWT¶

    Наблюдается тенденция к использованию JSON Web Tokens (JWT) в качестве формата токенов безопасности. JWT — это структуры данных JSON, содержащие набор утверждений (claims), которые могут использоваться для принятия решений об управлении доступом. Криптографическая подпись или код аутентификации сообщения (MAC) могут использоваться для защиты целостности JWT.

    • Убедитесь, что целостность JWT защищена либо подписью, либо MAC. Не допускайте использования незащищённых JWT: {"alg":"none"}.
      • См. здесь
    • В общем случае предпочтительнее использовать подписи, а не MAC для защиты целостности JWT.

    Если для защиты целостности используются MAC, любой сервис, способный проверять JWT, также может создавать новые JWT с использованием того же ключа. Это означает, что все сервисы, использующие один и тот же ключ, должны взаимно доверять друг другу. Следствием этого является то, что компрометация любого сервиса компрометирует и все остальные сервисы, разделяющие тот же ключ. Дополнительную информацию см. здесь.

    Проверяющая сторона (relying party) или потребитель токена проверяет JWT, верифицируя его целостность и содержащиеся в нём утверждения.

    • Проверяющая сторона должна верифицировать целостность JWT на основе собственной конфигурации или жёстко заданной логики. Нельзя полагаться на информацию заголовка JWT при выборе алгоритма верификации. См. здесь и здесь

    Ряд утверждений стандартизирован и должен присутствовать в JWT, используемых для контроля доступа. Необходимо проверять как минимум следующие стандартные утверждения:

    • iss (issuer) — является ли это доверенным издателем? Является ли он ожидаемым владельцем ключа подписи?
    • aud (audience) — входит ли проверяющая сторона в целевую аудиторию данного JWT?
    • exp (expiration time) — является ли текущее время более ранним, чем окончание периода действия токена?
    • nbf (not before time) — является ли текущее время более поздним, чем начало периода действия токена?

    Поскольку JWT содержат данные аутентифицированной сущности (пользователя и т.д.), может возникнуть рассинхронизация между JWT и текущим состоянием сессии пользователя — например, если сессия завершена раньше времени истечения срока действия токена вследствие явного выхода или тайм-аута бездействия. При наступлении события явного завершения сессии дайджест или хэш связанных JWT должен быть передан в список запрещённых (denylist) на API, что аннулирует данный JWT для всех запросов вплоть до истечения срока действия токена. Подробнее см. в JSON_Web_Token_for_Java_Cheat_Sheet.

    API Keys¶

    Публичные REST-сервисы без контроля доступа рискуют стать объектом массированного использования (farming), что может привести к чрезмерным расходам на полосу пропускания или вычислительные ресурсы. API-ключи могут снизить этот риск. Они также часто используются организациями для монетизации API: вместо блокировки высокочастотных вызовов клиентам предоставляется доступ в соответствии с приобретённым тарифным планом.

    API-ключи могут снизить воздействие атак типа «отказ в обслуживании» (DoS). Однако при выдаче сторонним клиентам их относительно легко скомпрометировать.

    • Требуйте API-ключи для каждого запроса к защищённому эндпоинту.
    • Возвращайте HTTP-код ответа 429 Too Many Requests, если запросы поступают слишком быстро.
    • Отзывайте API-ключ, если клиент нарушает соглашение об использовании.
    • Не полагайтесь исключительно на API-ключи для защиты чувствительных, критически важных или высокоценных ресурсов.

    Ограничение HTTP-методов¶

    • Применяйте allowlist допустимых HTTP-методов, например GET, POST, PUT.
    • Отклоняйте все запросы, не соответствующие allowlist, с HTTP-кодом ответа 405 Method not allowed.
    • Убедитесь, что вызывающая сторона авторизована на использование входящего HTTP-метода для данной коллекции ресурсов, действия и записи.

    В Java EE, в частности, это может быть сложно реализовать корректно. См. Bypassing Web Authentication and Authorization with HTTP Verb Tampering для объяснения этой распространённой ошибки конфигурации.

    Предотвращение выполнения API-вызовов не в том порядке¶

    Современные REST API часто реализуют бизнес-процессы через последовательность эндпоинтов (например, создать → проверить → одобрить → завершить). Если бэкенд явно не проверяет переходы состояний рабочего процесса, злоумышленники могут вызывать эндпоинты не в том порядке, обходя предусмотренные механизмы контроля.

    Проблема¶

    Выполнение API-вызовов не в том порядке происходит, когда злоумышленник:

    • Пропускает обязательные шаги рабочего процесса, напрямую обращаясь к эндпоинтам последующих этапов.
    • Воспроизводит или повторно использует токены в разных точках рабочего процесса.
    • Эксплуатирует допущение о том, что фронтенд обеспечивает корректный порядок выполнения.

    Поскольку каждый эндпоинт может быть индивидуально аутентифицирован и авторизован, традиционные проверки контроля доступа часто не выявляют подобные проблемы.

    Пример¶

    Рабочий процесс оформления заказа предполагает следующую последовательность:

    POST /checkout/create
POST /checkout/pay
POST /checkout/confirm

    Если бэкенд не проверяет переходы состояний рабочего процесса, злоумышленник может напрямую вызвать:

    POST /checkout/confirm

    не завершив оплату.

    Рекомендации по защите¶

    • Выполняйте валидацию состояния рабочего процесса на стороне сервера для каждого запроса.
    • Явно моделируйте рабочие процессы с использованием конечных состояний или машин состояний.
    • Привязывайте токены или идентификаторы к конкретным этапам рабочего процесса.
    • Не полагайтесь на логику фронтенда для обеспечения корректного порядка вызовов.
    • Отклоняйте недопустимые или неупорядоченные переходы с понятными сообщениями об ошибках.

    Контрольный список для тестирования¶

    • Можно ли вызывать эндпоинты не в том порядке?
    • Проверяет ли каждый эндпоинт текущее состояние рабочего процесса?
    • Можно ли повторно использовать токены на разных шагах рабочего процесса?
    • Последовательно ли отклоняются недопустимые переходы состояний?

    Валидация входных данных¶

    • Не доверяйте входным параметрам/объектам.
    • Проверяйте входные данные: длину / диапазон / формат и тип.
    • Добивайтесь неявной валидации входных данных, используя строгие типы — числа, булевы значения, даты, время или фиксированные диапазоны данных в параметрах API.
    • Ограничивайте строковые входные данные с помощью регулярных выражений.
    • Отклоняйте неожиданное/недопустимое содержимое.
    • Используйте библиотеки или фреймворки для валидации/санитизации, доступные для вашего языка программирования.
    • Определите подходящий лимит размера запроса и отклоняйте запросы, превышающие его, с HTTP-статусом 413 Request Entity Too Large.
    • Рассмотрите возможность журналирования ошибок валидации входных данных. Следует предполагать злой умысел у того, кто совершает сотни неудачных попыток валидации входных данных в секунду.
    • Ознакомьтесь с cheat sheet по валидации входных данных для исчерпывающего объяснения.
    • Используйте безопасный парсер для разбора входящих сообщений. При использовании XML убедитесь, что применяется парсер, не уязвимый к атакам XXE и подобным.

    Валидация типов содержимого¶

    Тело REST-запроса или ответа должно соответствовать предполагаемому типу содержимого, указанному в заголовке. В противном случае это может привести к неверной интерпретации на стороне потребителя/производителя и к внедрению/выполнению кода.

    • Документируйте все поддерживаемые типы содержимого в вашем API.

    Валидация типов содержимого запросов¶

    • Отклоняйте запросы с неожиданными или отсутствующими заголовками Content-Type с HTTP-статусом 406 Unacceptable или 415 Unsupported Media Type. Однако для запросов с Content-Length: 0 заголовок Content-type является необязательным.
    • Для XML-типов содержимого обеспечьте соответствующее усиление защиты XML-парсера, см. XXE cheat sheet.
    • Избегайте случайного раскрытия нежелательных типов содержимого, явно объявляя их — например, в Jersey (Java): @consumes("application/json"); @produces("application/json"). Это позволяет, в частности, избежать векторов XXE-атак.

    Отправка безопасных типов содержимого ответов¶

    REST-сервисы нередко поддерживают несколько типов ответов (например, application/xml или application/json), а клиент указывает предпочтительный порядок типов ответов через заголовок Accept в запросе.

    • НЕ копируйте заголовок Accept в заголовок Content-type ответа напрямую.
    • Отклоняйте запрос (предпочтительно с ответом 406 Not Acceptable), если заголовок Accept не содержит явно ни одного из допустимых типов.

    Сервисы, включающие в ответы код скриптов (например, JavaScript), должны уделять особое внимание защите от атак с внедрением заголовков.

    • Убедитесь, что в ответе отправляются правильные заголовки Content-Type, соответствующие содержимому тела — например, application/json, а не application/javascript.

    Эндпоинты управления¶

    • Избегайте открытого доступа к эндпоинтам управления через Интернет.
    • Если эндпоинты управления должны быть доступны через Интернет, убедитесь, что пользователи обязаны использовать надёжный механизм аутентификации, например многофакторный.
    • Размещайте эндпоинты управления на других HTTP-портах или хостах, предпочтительно на отдельном сетевом интерфейсе (NIC) и в ограниченной подсети.
    • Ограничивайте доступ к этим эндпоинтам с помощью правил межсетевого экрана или списков контроля доступа (ACL).

    Обработка ошибок¶

    • Возвращайте общие сообщения об ошибках — избегайте излишнего раскрытия деталей сбоя.
    • Не передавайте клиенту технические подробности (например, трассировки стека вызовов или другие внутренние подсказки).

    Журналы аудита¶

    • Записывайте журналы аудита до и после событий, связанных с безопасностью.
    • Рассмотрите возможность журналирования ошибок валидации токенов для обнаружения атак.
    • Защищайтесь от атак с внедрением данных в журналы, предварительно санитизируя данные журналов.

    Заголовки безопасности¶

    Существует ряд заголовков, связанных с безопасностью, которые можно возвращать в HTTP-ответах, чтобы браузеры действовали определённым образом. Однако некоторые из этих заголовков предназначены для использования с HTML-ответами и поэтому могут обеспечивать незначительную пользу или вовсе не приносить её в API, не возвращающем HTML.

    Следующие заголовки должны быть включены во все ответы API:

    Заголовок Обоснование
    Cache-Control: no-store Заголовок, управляющий кэшированием в браузерах. Значение no-store указывает, что любые кэши (приватные или общие) не должны сохранять ответ, содержащий этот заголовок. Браузер обязан делать новый запрос при каждом обращении к API для получения актуального ответа. Этот заголовок со значением no-store предотвращает кэширование или сохранение чувствительной информации.
    Content-Security-Policy: frame-ancestors 'none' Заголовок, определяющий, может ли ответ быть встроен во фрейм через элементы <frame>, <iframe>, <embed> или <object>. Для ответа API нет необходимости во встраивании в какой-либо из этих элементов. Значение frame-ancestors 'none' запрещает любому домену обрамлять ответ, возвращаемый API. Этот заголовок защищает от кликджекинг-атак методом перетаскивания.
    Content-Type Заголовок для указания типа содержимого ответа. Должен быть задан в соответствии с типом содержимого, возвращаемого API. Если не указан или указан некорректно, браузер может попытаться угадать тип содержимого, что может привести к атакам типа MIME sniffing. Одним из распространённых значений является application/json, если ответ API представлен в формате JSON.
    Strict-Transport-Security Заголовок, предписывающий браузеру обращаться к домену только по HTTPS, а любые последующие попытки доступа по HTTP автоматически преобразовывать в HTTPS. Этот заголовок гарантирует, что API-вызовы выполняются по HTTPS, и защищает от подменённых сертификатов.
    X-Content-Type-Options: nosniff Заголовок, предписывающий браузеру всегда использовать MIME-тип, объявленный в заголовке Content-Type, а не пытаться определить его по содержимому файла. Значение nosniff предотвращает выполнение браузером MIME sniffing и некорректную интерпретацию ответов как HTML.
    X-Frame-Options: DENY Заголовок, определяющий, может ли ответ быть встроен во фрейм через элементы <frame>, <iframe>, <embed> или <object>. Для ответа API нет необходимости во встраивании в какой-либо из этих элементов. Значение DENY запрещает любому домену обрамлять ответ, возвращаемый API. Этот заголовок со значением DENY защищает от кликджекинг-атак методом перетаскивания.

    Приведённые ниже заголовки предназначены для обеспечения дополнительной безопасности только в случае, когда ответы отображаются как HTML. Таким образом, если API никогда не возвращает HTML в ответах, эти заголовки могут не потребоваться. Однако при любой неопределённости относительно функций заголовков или типов информации, возвращаемой API (или которую он может возвращать в будущем), рекомендуется включить их в рамках подхода «глубокой защиты» (defence-in-depth).

    Заголовок Пример Обоснование
    Content-Security-Policy Content-Security-Policy: default-src 'none' Большинство функций CSP влияют только на страницы, отображаемые как HTML.
    Permissions-Policy Permissions-Policy: accelerometer=(), ambient-light-sensor=(), autoplay=(), battery=(), camera=(), cross-origin-isolated=(), display-capture=(), document-domain=(), encrypted-media=(), execution-while-not-rendered=(), execution-while-out-of-viewport=(), fullscreen=(), geolocation=(), gyroscope=(), keyboard-map=(), magnetometer=(), microphone=(), midi=(), navigation-override=(), payment=(), picture-in-picture=(), publickey-credentials-get=(), screen-wake-lock=(), sync-xhr=(), usb=(), web-share=(), xr-spatial-tracking=() Ранее этот заголовок назывался Feature-Policy. Когда браузеры следуют этому заголовку, он используется для управления функциями браузера с помощью директив. Пример отключает функции с пустым allowlist для ряда разрешённых имён директив. При применении этого заголовка убедитесь, что директивы актуальны и соответствуют вашим потребностям. Подробное объяснение управления функциями браузера см. в этой статье.
    Referrer-Policy Referrer-Policy: no-referrer Не-HTML-ответы не должны инициировать дополнительные запросы.

    CORS¶

    Cross-Origin Resource Sharing (CORS) — это стандарт W3C для гибкого определения допустимых межсайтовых запросов. Возвращая соответствующие CORS-заголовки, ваш REST API сообщает браузеру, каким доменам (они же origins) разрешено выполнять JavaScript-вызовы к REST-сервису.

    • Отключайте CORS-заголовки, если межсайтовые вызовы не поддерживаются или не предполагаются.
    • При задании разрешённых origins для межсайтовых вызовов будьте максимально конкретны и лишь настолько общи, насколько это необходимо.

    Чувствительная информация в HTTP-запросах¶

    RESTful веб-сервисы должны внимательно следить за тем, чтобы не допускать утечки учётных данных. Пароли, токены безопасности и API-ключи не должны присутствовать в URL, так как это может быть зафиксировано в журналах веб-сервера, что делает их ценной мишенью.

    • В запросах POST/PUT чувствительные данные следует передавать в теле запроса или в заголовках запроса.
    • В запросах GET чувствительные данные следует передавать в HTTP-заголовке.

    Правильно:

    https://example.com/resourceCollection/[ID]/action

    https://twitter.com/vanderaj/lists

    Неправильно:

    https://example.com/controller/123/action?apiKey=a53f435643de32 — потому что apiKey содержится в URL.

    HTTP-коды ответа¶

    HTTP определяет коды статуса. При проектировании REST API не используйте только 200 для успеха или 404 для ошибки. Всегда применяйте семантически подходящий код статуса для ответа.

    Ниже приведена неполная подборка кодов статуса REST API, связанных с безопасностью. Используйте её для проверки корректности возвращаемых кодов.

    Код Сообщение Описание
    200 OK Ответ на успешное действие REST API. HTTP-метод может быть GET, POST, PUT, PATCH или DELETE.
    201 Created Запрос выполнен и ресурс создан. URI созданного ресурса возвращается в заголовке Location.
    202 Accepted Запрос принят в обработку, но обработка ещё не завершена.
    301 Moved Permanently Постоянное перенаправление.
    304 Not Modified Ответ, связанный с кэшированием: возвращается, когда у клиента есть такая же копия ресурса, что и на сервере.
    307 Temporary Redirect Временное перенаправление ресурса.
    400 Bad Request Запрос сформирован некорректно, например ошибка формата тела сообщения.
    401 Unauthorized Предоставлены неверные или отсутствуют идентификатор/пароль аутентификации.
    403 Forbidden Используется, когда аутентификация прошла успешно, но аутентифицированный пользователь не имеет прав доступа к запрошенному ресурсу.
    404 Not Found Запрошен несуществующий ресурс.
    405 Method Not Acceptable Ошибка при использовании неожиданного HTTP-метода. Например, REST API ожидает HTTP GET, но был использован HTTP PUT.
    406 Unacceptable Клиент указал в заголовке Accept тип содержимого, который не поддерживается API сервера.
    413 Payload too large Используется для сигнализации о том, что размер запроса превышает установленный лимит, например при загрузке файлов.
    415 Unsupported Media Type Запрошенный тип содержимого не поддерживается REST-сервисом.
    429 Too Many Requests Ошибка используется при обнаружении возможной DoS-атаки или при отклонении запроса из-за ограничения скорости (rate limiting).
    500 Internal Server Error Непредвиденное условие не позволило серверу выполнить запрос. Обратите внимание, что ответ не должен раскрывать внутреннюю информацию, которая может помочь злоумышленнику, — например, подробные сообщения об ошибках или трассировки стека.
    501 Not Implemented REST-сервис ещё не реализовал запрошенную операцию.
    503 Service Unavailable REST-сервис временно не может обработать запрос. Используется для информирования клиента о необходимости повторить попытку позже.
