    Шпаргалка по защите от Clickjacking¶

    Введение¶

    Эта шпаргалка предназначена для разработчиков и содержит рекомендации по защите от атак Clickjacking (известных также как атаки подмены UI).

    Существуют три основных механизма защиты от подобных атак:

    • Запрет браузеру загружать страницу во фрейме с помощью HTTP-заголовков X-Frame-Options или Content Security Policy (frame-ancestors).
    • Запрет включения сессионных cookies при загрузке страницы во фрейме с помощью атрибута cookie SameSite.
    • Внедрение JavaScript-кода на страницу для предотвращения её загрузки во фрейме (так называемый «frame-buster»).

    Обратите внимание, что все эти механизмы независимы друг от друга, и там, где это возможно, следует реализовывать более одного из них для обеспечения эшелонированной защиты.

    Защита с помощью директивы frame-ancestors CSP¶

    Директива frame-ancestors может использоваться в HTTP-заголовке ответа Content-Security-Policy, чтобы указать браузеру, разрешено ли отображать страницу в элементах <frame> или <iframe>. Сайты могут использовать это для защиты от атак Clickjacking, гарантируя, что их контент не встраивается в другие сайты.

    frame-ancestors позволяет сайту авторизовать несколько доменов, используя стандартный синтаксис Content Security Policy.

    Примеры Content-Security-Policy: frame-ancestors¶

    Распространённые варианты использования CSP frame-ancestors:

    • Content-Security-Policy: frame-ancestors 'none';
      • Запрещает любому домену встраивать контент во фрейм. Этот параметр рекомендуется, если не выявлена конкретная необходимость во фреймировании.
    • Content-Security-Policy: frame-ancestors 'self';
      • Разрешает встраивать контент во фрейм только текущему сайту.
    • Content-Security-Policy: frame-ancestors 'self' *.somesite.com https://myfriend.site.com;
      • Разрешает встраивание текущим сайтом, а также любой страницей на somesite.com (по любому протоколу) и только страницей myfriend.site.com исключительно через HTTPS на стандартном порту (443).

    Обратите внимание, что одинарные кавычки обязательны вокруг self и none, но не используются вокруг других выражений источников.

    Дополнительные сведения и более сложные примеры см. в следующей документации:

    • https://w3c.github.io/webappsec-csp/#directive-frame-ancestors
    • https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/frame-ancestors

    Ограничения¶

    Приоритет X-Frame-Options: Раздел «Relation to X-Frame-Options» спецификации CSP гласит: «Если ресурс доставляется с политикой, включающей директиву frame-ancestors с режимом применения «enforce», заголовок X-Frame-Options ДОЛЖЕН игнорироваться», однако старые версии браузеров (например, Chrome 40 и Firefox 35) игнорировали это требование и следовали заголовку X-Frame-Options.

    Поддержка браузерами¶

    Следующие браузеры поддерживают CSP frame-ancestors.

    Защита с помощью заголовка ответа X-Frame-Options¶

    HTTP-заголовок ответа X-Frame-Options может использоваться для указания браузеру, разрешено ли отображать страницу в элементах <frame> или <iframe>. Сайты могут применять этот заголовок для защиты от атак Clickjacking, гарантируя, что их контент не встраивается в другие сайты. Устанавливайте заголовок X-Frame-Options для всех ответов, содержащих HTML-контент. Возможные значения: «DENY», «SAMEORIGIN» или «ALLOW-FROM uri».

    Типы заголовка X-Frame-Options¶

    Существуют три возможных значения заголовка X-Frame-Options:

    • DENY — запрещает любому домену встраивать контент во фрейм. Параметр «DENY» рекомендуется, если не выявлена конкретная необходимость во фреймировании.
    • SAMEORIGIN — разрешает встраивать контент во фрейм только текущему сайту.
    • ALLOW-FROM uri — разрешает указанному «uri» встраивать данную страницу во фрейм (например, ALLOW-FROM http://www.example.com).
      • Эта директива устарела и больше не поддерживается в современных браузерах.
      • Ознакомьтесь с ограничениями ниже, поскольку при отсутствии поддержки браузером это может привести к открытому сбою (fail open).
      • Другие браузеры поддерживают новую директиву CSP frame-ancestors. Некоторые поддерживают оба варианта.

    Поддержка браузерами¶

    Следующие браузеры поддерживают заголовок X-Frame-Options.

    Ссылки:

    • Mozilla Developer Network
    • IETF Draft
    • X-Frame-Options Compatibility Test — проверьте здесь актуальную информацию о поддержке браузерами заголовка X-Frame-Options

    Реализация¶

    Для внедрения этой защиты необходимо добавить HTTP-заголовок ответа X-Frame-Options на каждую страницу, которую требуется защитить от встраивания. Один из способов — добавить HTTP-заголовок ответа вручную на каждую страницу. Более простой способ — реализовать фильтр, автоматически добавляющий заголовок на каждую страницу, или настроить его на уровне Web Application Firewall или веб-/прикладного сервера.

    Распространённые ошибки защиты¶

    Meta-теги, пытающиеся применить директиву X-Frame-Options, НЕ РАБОТАЮТ. Например, <meta http-equiv="X-Frame-Options" content="deny"> не будет работать. Директива X-FRAME-OPTIONS должна применяться в виде HTTP-заголовка ответа, как описано выше. Это же правило распространяется на директиву CSP frame-ancestors, которая также должна быть настроена как HTTP-заголовок ответа, а не в теге <meta>.

    Ограничения¶

    • Указание политики для каждой страницы: политика должна быть указана для каждой страницы, что может усложнить развёртывание. Возможность применять её для всего сайта, например во время входа в систему, упростила бы внедрение.
    • Проблемы с многодоменными сайтами: текущая реализация не позволяет администратору сайта указывать список доменов, которым разрешено встраивать страницу. Хотя перечисление разрешённых доменов может быть опасным, в некоторых случаях у администратора сайта нет иного выбора, кроме как использовать несколько имён хостов.
    • Поддержка ALLOW-FROM браузерами: опция ALLOW-FROM устарела и больше не работает в современных браузерах. БУДЬТЕ ОСТОРОЖНЫ, ПОЛАГАЯСЬ НА ALLOW-FROM. Если вы её применяете, а браузер её не поддерживает, у вас не будет НИКАКОЙ защиты от Clickjacking.
    • Несколько значений не поддерживаются: нет способа разрешить текущему сайту и стороннему сайту одновременно встраивать один и тот же ответ. Браузеры обрабатывают только один заголовок X-Frame-Options с одним значением.
    • Вложенные фреймы не работают с SAMEORIGIN и ALLOW-FROM: в следующей ситуации фрейм http://framed.invalid/child не загрузится, поскольку ALLOW-FROM применяется к контексту просмотра верхнего уровня, а не непосредственного родителя. Решение — использовать ALLOW-FROM в обоих фреймах (родительском и дочернем), однако это не позволит дочернему фрейму загрузиться, если страница //framed.invalid/parent открыта как документ верхнего уровня.

    • Устаревание X-Frame-Options: несмотря на то что заголовок X-Frame-Options поддерживается основными браузерами, он объявлен устаревшим в пользу директивы frame-ancestors из спецификации CSP Level 2.
    • Прокси-серверы: веб-прокси-серверы печально известны добавлением и удалением заголовков. Если веб-прокси удаляет заголовок X-Frame-Options, сайт лишается защиты от встраивания во фреймы.

    Защита с помощью атрибута SameSite для cookies¶

    Атрибут cookie SameSite, определённый в RFC 6265bis, предназначен прежде всего для защиты от межсайтовой подделки запросов (CSRF), однако также может обеспечивать защиту от атак Clickjacking.

    Cookies с атрибутом SameSite со значением strict или lax не будут включаться в запросы, сделанные к странице внутри <iframe>. Это означает, что если сессионные cookies помечены как SameSite, любая атака Clickjacking, требующая аутентификации жертвы, не сработает, поскольку cookie не будет отправлен. В статье на блоге Netsparker подробно описано, при каких типах запросов cookies отправляются при различных политиках SameSite.

    Этот подход обсуждается на сайте JavaScript.info.

    Ограничения¶

    Если атака Clickjacking не требует аутентификации пользователя, данный атрибут не обеспечит никакой защиты.

    Кроме того, несмотря на то что атрибут SameSite поддерживается большинством современных браузеров, часть пользователей (около 6% по состоянию на ноябрь 2020 года) использует браузеры без его поддержки.

    Применение этого атрибута следует рассматривать как элемент эшелонированной защиты, и не стоит полагаться на него как на единственную меру защиты от Clickjacking.

    Современный скрипт блокировки фреймов для устаревших браузеров¶

    Один из способов защиты от Clickjacking — включить на каждую страницу, которую не следует встраивать во фрейм, скрипт-«frame-breaker». Следующий метод позволит предотвратить встраивание веб-страницы во фрейм даже в устаревших браузерах, не поддерживающих заголовок X-Frame-Options.

    В элемент HEAD документа добавьте следующее:

    Сначала присвойте ID элементу style:

    <style id="antiClickjack">
    body{display:none !important;}
</style>

    Затем сразу после удалите этот style по его ID с помощью скрипта:

    <script type="text/javascript">
    if (self === top) {
        var antiClickjack = document.getElementById("antiClickjack");
        antiClickjack.parentNode.removeChild(antiClickjack);
    } else {
        top.location = self.location;
    }
</script>

    Таким образом, всё можно разместить в HEAD документа, и потребуется лишь один метод/тегlib в вашем API.

    Защита с помощью window.confirm()¶

    Использование X-Frame-Options или скрипта-«frame-breaker» является более надёжным методом защиты от Clickjacking. Однако в сценариях, где контент должен поддерживать встраивание во фреймы, можно использовать window.confirm() для снижения риска Clickjacking, информируя пользователя о действии, которое он собирается выполнить.

    Вызов window.confirm() отображает всплывающее окно, которое нельзя встроить во фрейм. Если window.confirm() вызывается из iframe с доменом, отличным от родительского, в диалоговом окне будет показано, из какого домена был вызван window.confirm(). В этом сценарии браузер отображает источник диалогового окна для снижения риска атак Clickjacking. Например:

    <script type="text/javascript">
    var action_confirm = window.confirm("Are you sure you want to delete your youtube account?")
    if (action_confirm) {
        //... Выполнить действие
    } else {
        //... Пользователь не хочет выполнять запрошенное действие.
    }
</script>

    Небезопасные нерабочие скрипты — НЕ ИСПОЛЬЗОВАТЬ¶

    Рассмотрим следующий фрагмент, который НЕ рекомендуется для защиты от Clickjacking:

    <script>if (top!=self) top.location.href=self.location.href</script>

    Этот простой скрипт блокировки фреймов пытается предотвратить встраивание страницы во фрейм или iframe, принудительно загружая URL текущего фрейма в родительском окне. К сожалению, стало известно несколько способов обхода подобных скриптов. Ниже приведены некоторые из них.

    Двойное фреймирование¶

    Некоторые техники блокировки фреймов осуществляют переход на правильную страницу путём присвоения значения parent.location. Это работает, если страница-жертва встроена в единственный фрейм. Однако если злоумышленник заключит жертву в один фрейм внутри другого (двойное фреймирование), обращение к parent.location становится нарушением безопасности во всех популярных браузерах из-за политики навигации дочернего фрейма. Это нарушение безопасности отключает контрмеру навигации.

    Код блокировки фрейма на стороне жертвы:

    if(top.location != self.location) {
    parent.location = self.location;
}

    Верхний фрейм злоумышленника:

    <iframe src="attacker2.html">

    Вложенный фрейм злоумышленника:

    <iframe src="http://www.victim.com">

    Событие onBeforeUnload¶

    Пользователь может вручную отменить любой запрос навигации, отправленный встроенной страницей. Чтобы воспользоваться этим, фреймирующая страница регистрирует обработчик onBeforeUnload, который вызывается каждый раз, когда фреймирующая страница должна быть выгружена из-за навигации. Функция обработчика возвращает строку, которая отображается пользователю в виде подсказки.

    Предположим, злоумышленник хочет встроить PayPal во фрейм. Он регистрирует функцию обработчика выгрузки, возвращающую строку «Do you want to exit PayPal?». Когда эта строка отображается пользователю, он, скорее всего, отменит навигацию, срывая тем самым попытку PayPal заблокировать фреймирование.

    Злоумышленник осуществляет эту атаку, регистрируя событие выгрузки на верхней странице с помощью следующего кода:

    <script>
    window.onbeforeunload = function(){
        return "Asking the user nicely";
    }
</script>

<iframe src="http://www.paypal.com">

    Код блокировки фреймов PayPal сгенерирует событие BeforeUnload, активирующее нашу функцию и предлагающее пользователю отменить событие навигации.

    Сброс без содержимого¶

    Хотя предыдущая атака требует взаимодействия с пользователем, та же атака может быть осуществлена без его участия. Современные браузеры позволяют злоумышленнику автоматически отменять входящий запрос навигации в обработчике события onBeforeUnload, многократно отправляя запрос навигации на сайт, отвечающий с кодом «204 - No Content».

    Навигация на сайт с ответом No Content фактически является пустой операцией, но сбрасывает очередь запросов, тем самым отменяя исходный запрос навигации. Вот пример кода для этого:

    var preventbust = 0
window.onbeforeunload = function() { killbust++ }
setInterval( function() {
    if(killbust > 0){
    killbust = 2;
    window.top.location = 'http://nocontent204.com'
    }
}, 1);

    <iframe src="http://www.victim.com">

    Ограниченные зоны¶

    Большинство методов блокировки фреймов основаны на JavaScript во встроенной странице для обнаружения фреймирования и выхода из него. Если JavaScript отключён в контексте вложенного фрейма, код блокировки не выполнится. К сожалению, существует несколько способов ограничить JavaScript в подфрейме:

    В Chrome:

    <iframe src="http://www.victim.com" sandbox></iframe>

    Firefox:

    Активируйте designMode на родительской странице. Хотя designMode по-прежнему поддерживается в современных браузерах, его эффективность как вектора атаки Clickjacking может варьироваться в актуальных версиях браузеров.

    document.designMode = "on";
