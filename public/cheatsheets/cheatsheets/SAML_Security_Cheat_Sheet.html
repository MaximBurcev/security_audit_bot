    Шпаргалка по безопасности SAML¶

    Введение¶

    Security Assertion Markup Language (SAML) — открытый стандарт для обмена информацией об авторизации и аутентификации. Профиль SAML/SSO для веб-браузера с привязками Redirect/POST является одной из наиболее распространённых реализаций SSO. Данная шпаргалка сосредоточена преимущественно на этом профиле.

    Проверка конфиденциальности и целостности сообщений¶

    TLS 1.2 — наиболее распространённое решение для обеспечения конфиденциальности и целостности сообщений на транспортном уровне. Обратитесь к SAML Security (раздел 4.2.1) для получения дополнительной информации. Этот шаг поможет противодействовать следующим атакам:

    • Перехват (Eavesdropping) 7.1.1.1
    • Кража информации аутентификации пользователя 7.1.1.2
    • Кража Bearer-токена 7.1.1.3
    • Удаление сообщений 7.1.1.6
    • Модификация сообщений 7.1.1.7
    • Атака «человек посередине» 7.1.1.8

    Сообщение с цифровой подписью и сертифицированным ключом — наиболее распространённое решение для обеспечения целостности и аутентификации сообщений. Обратитесь к SAML Security (раздел 4.3) для получения дополнительной информации. Этот шаг поможет противодействовать следующим атакам:

    • Атака «человек посередине» 6.4.2
    • Поддельное утверждение (Forged Assertion) 6.4.3
    • Модификация сообщений 7.1.1.7

    Утверждения могут быть зашифрованы через XMLEnc для предотвращения раскрытия конфиденциальных атрибутов после передачи. Обратитесь к SAML Security (раздел 4.2.2) для получения дополнительной информации. Этот шаг поможет противодействовать следующим атакам:

    • Кража информации аутентификации пользователя 7.1.1.2

    Проверка использования протокола¶

    Это распространённая область для пробелов в безопасности — см. уязвимость Google SSO как реальный пример. Их SSO-профиль был уязвим к атаке «человек посередине» со стороны вредоносного SP (Service Provider).

    Профиль SSO для веб-браузера наиболее уязвим к атакам со стороны доверенных партнёров. Эта конкретная уязвимость была обнаружена потому, что SAML Response не содержал всех необходимых элементов данных для безопасного обмена сообщениями. Соблюдение требований использования SAML Profile для AuthnRequest (4.1.4.1) и Response (4.1.4.2) поможет противодействовать этой атаке.

    Команда AVANTSSAR предложила следующие обязательные элементы данных:

    • AuthnRequest(ID, SP): AuthnRequest должен содержать ID и SP. Где ID — строка, однозначно идентифицирующая запрос, а SP идентифицирует Service Provider, инициировавший запрос. Кроме того, атрибут ID запроса должен быть возвращён в ответе (InResponseTo="<requestId>"). InResponseTo помогает гарантировать подлинность ответа от доверенного IdP. Это был один из отсутствующих атрибутов, из-за которого SSO Google оказался уязвимым.
    • Response(ID, SP, IdP, {AA} K -1/IdP): Response должен содержать все эти элементы. Где ID — строка, однозначно идентифицирующая ответ. SP идентифицирует получателя ответа. IdP идентифицирует поставщика удостоверений, авторизующего ответ. {AA} K -1/IdP — утверждение с цифровой подписью, подписанное закрытым ключом IdP.
    • AuthAssert(ID, C, IdP, SP): В Response должно существовать утверждение аутентификации. Оно должно содержать ID, клиента (C), поставщика удостоверений (IdP) и идентификатор поставщика услуг (SP).

    Проверка подписей¶

    Уязвимости в реализациях SAML, связанные с атаками XML Signature Wrapping, были описаны в 2012 году в работе On Breaking SAML: Be Whoever You Want to Be.

    В ответ были предложены следующие рекомендации (Secure SAML validation to prevent XML signature wrapping attacks):

    • Без исключений всегда выполняйте валидацию схемы XML-документа перед его использованием в целях безопасности:
      • Всегда используйте локальные, доверенные копии схем для валидации.
      • Никогда не разрешайте автоматическую загрузку схем из сторонних источников.
      • По возможности проверяйте схемы и выполняйте их ужесточение, отключая возможные выражения с подстановочными типами или упрощённой обработкой.
    • Надёжно проверяйте цифровую подпись:
      • Если ожидается только один ключ подписи, используйте StaticKeySelector. Получите ключ непосредственно от поставщика удостоверений, сохраните его в локальном файле и игнорируйте любые элементы KeyInfo в документе.
      • Если ожидается более одного ключа подписи, используйте X509KeySelector (вариант JKS). Получите эти ключи непосредственно от поставщиков удостоверений, сохраните их в локальном JKS и игнорируйте любые элементы KeyInfo в документе.
    • Избегайте атак подмены подписи (signature-wrapping).
      • Никогда не используйте getElementsByTagName для выбора элементов безопасности в XML-документе без предварительной валидации.
      • Всегда используйте абсолютные XPath-выражения для выбора элементов, если не применяется ужесточённая схема для валидации.

    Проверка правил обработки протокола¶

    Это ещё одна распространённая область пробелов в безопасности, просто из-за огромного количества шагов, которые необходимо проверить.

    Обработка SAML response — дорогостоящая операция, но все шаги должны быть проверены:

    • Проверьте правила обработки AuthnRequest. Обратитесь к SAML Core (3.4.1.4) для получения всех правил обработки AuthnRequest. Этот шаг поможет противодействовать следующим атакам:
      • Атака «человек посередине» (6.4.2)
    • Проверьте правила обработки Response. Обратитесь к SAML Profiles (4.1.4.3) для получения всех правил обработки Response. Этот шаг поможет противодействовать следующим атакам:
      • Украденное утверждение (Stolen Assertion) (6.4.1)
      • Атака «человек посередине» (6.4.2)
      • Поддельное утверждение (Forged Assertion) (6.4.3)
      • Раскрытие состояния браузера (Browser State Exposure) (6.4.4)

    Проверка реализации привязки¶

    • Для HTTP Redirect Binding обратитесь к SAML Binding (3.4). Для просмотра примера кодирования можно обратиться к RequestUtil.java из эталонной реализации Google.
    • Для HTTP POST Binding обратитесь к SAML Binding (3.5). Соображения о кешировании также очень важны. Если SAML-сообщение протокола будет закешировано, оно впоследствии может быть использовано в атаках «Украденное утверждение» (Stolen Assertion) (6.4.1) или «Повторное воспроизведение» (Replay) (6.4.5).

    Проверка мер безопасности¶

    Пересмотрите каждую угрозу безопасности из документа SAML Security и убедитесь, что вы применили соответствующие контрмеры для угроз, которые могут существовать в вашей конкретной реализации.

    Дополнительные рассматриваемые меры должны включать:

    • При необходимости предпочтительна фильтрация по IP. Например, эта мера могла бы предотвратить первоначальную уязвимость безопасности Google, если бы Google предоставил каждому доверенному партнёру отдельный endpoint и настроил IP-фильтр для каждого endpoint. Этот шаг поможет противодействовать следующим атакам:
      • Украденное утверждение (Stolen Assertion) (6.4.1)
      • Атака «человек посередине» (6.4.2)
    • Предпочтительно короткое время жизни SAML Response. Этот шаг поможет противодействовать следующим атакам:
      • Украденное утверждение (Stolen Assertion) (6.4.1)
      • Раскрытие состояния браузера (Browser State Exposure) (6.4.4)
    • Предпочтительно использование OneTimeUse в SAML Response. Этот шаг поможет противодействовать следующим атакам:
      • Раскрытие состояния браузера (Browser State Exposure) (6.4.4)
      • Повторное воспроизведение (Replay) (6.4.5)

    Нужна архитектурная диаграмма? Технический обзор SAML содержит наиболее полные диаграммы. Для профиля SSO для веб-браузера с привязками Redirect/POST обратитесь к разделу 4.1.3. В целом, из всей документации SAML технический обзор является наиболее ценным с высокоуровневой точки зрения.

    Соображения по незапрошенным ответам (IdP Initiated SSO) для Service Provider¶

    Незапрошенный ответ (Unsolicited Response) по своей конструкции менее безопасен из-за отсутствия защиты от login CSRF. Это ограничение возникает потому, что Service Provider (SP) не имеет возможности создать сессию до входа или проверить, что запрос аутентификации был намеренно инициирован пользователем.

    Хотя эта конструкция не делает IdP-инициированный SSO уникально уязвимым к атакам «человек посередине» (MITM) — эти риски в равной мере применимы к SP-инициированным потокам при компрометации безопасности транспорта — она устраняет важный уровень проверки намерений при входе.

    Несмотря на эти опасения, IdP-инициированный SSO остаётся поддерживаемым для обратной совместимости (особенно с SAML 1.1). Если его необходимо включить, следующие шаги (в дополнение к упомянутым выше) должны помочь защитить этот поток:

    • Следуйте процессу валидации, описанному в SAML Profiles (раздел 4.1.5). Этот шаг поможет противодействовать следующим атакам:
      • Повторное воспроизведение (Replay) (6.1.2)
      • Вставка сообщений (Message Insertion) (6.1.3)
    • Если значение параметра RelayState является URL, убедитесь, что URL проверяется и явно включён в список разрешённых. Этот шаг поможет противодействовать следующей атаке:
      • Открытое перенаправление (Open Redirect)
    • Реализуйте надлежащее обнаружение повторного воспроизведения на уровне ответа или утверждения. Это поможет противодействовать следующей атаке:
      • Повторное воспроизведение (Replay) (6.1.2)

    Соображения для Identity Provider и Service Provider¶

    Протокол SAML редко является предпочтительным вектором атаки, хотя важно иметь шпаргалки, чтобы убедиться в его надёжности. Различные endpoints подвергаются атакам чаще, поэтому способ генерации SAML-токена и его потребления одинаково важны на практике.

    Соображения по сертификатам X.509¶

    Как правило, ассоциация безопасности между Identity Provider (IdP) и Service Provider (SP) создаётся, когда SP явно выбирает доверие подписывающему сертификату X.509 IdP. Способ, которым это происходит, может оказать сильное влияние на общую безопасность. Способ генерации сертификата, содержимое сертификата и защита соответствующего закрытого ключа сертификата — всё это оказывает сильное влияние на безопасность. Например, если злоумышленник имеет доступ к ключу подписи IdP, он может создавать SAML-ответы с любыми желаемыми утверждениями.

    Во многих случаях метод ручной установки ассоциации аналогичен Certificate Pinning, что не является идеальным решением. В зависимости от программного обеспечения IdP и SP или различных конструктивных соображений, это может быть неизбежным.

    Имейте в виду, что тип подписи сертификата может отличаться от типа подписи XML-документа. Соответствующий закрытый ключ сертификата — единственный ключ, который может использоваться для подписи XML-документа, но алгоритм подписи выбирается по усмотрению IdP. Наиболее широко поддерживаемый алгоритм подписи — rsa-sha256.

    Стороны SAML и организации¶

    Наиболее распространённые случаи использования SAML — это бизнес-взаимодействие (B2B). Это означает, что у двух сторон разные политики безопасности, практики и допустимые уровни риска. Это руководство сосредоточено главным образом на случае использования B2B. Однако федерация или SSO на основе SAML широко используются внутри организации. В этом случае термин «сторонний CA» не применяется. Вероятно, CA был создан и управляется в соответствии со стандартами компании и несёт не больший и не меньший риск для систем SAML. Термин «сторонний CA» означает частный CA, управляемый третьей стороной.

    Случаи использования сертификатов¶

    В системе SAML есть 5 отдельных случаев использования сертификатов. Хотя этот документ в основном говорит о подписывающем сертификате SAML IdP, соображения безопасности применимы ко всем четырём сертификатам, связанным с SAML. Пятый сертификат — TLS-сертификат сервера IdP — ничем не отличается от любого другого серверного сертификата.

    Подписание SAML IdP¶

    Это сертификат, который SP использует для проверки SAML-ответа IdP. IdP подписывает этот ответ соответствующим закрытым ключом сертификата. Это часто наиболее важный сертификат и закрытый ключ, поскольку они защищают утверждения об идентификации, отправляемые SP.

    Шифрование SAML IdP¶

    Это менее распространённый случай, так как он используется, когда SP хочет защитить SAML-запрос, отправляемый IdP, не только от подделки, но и от раскрытия информации. В SAML-запросе не должно быть конфиденциальной информации, поэтому он используется реже. При использовании сертификат и закрытый ключ должны отличаться от подписывающего сертификата SAML.

    Подписание SP¶

    Хотя это и не обязательно, рекомендуется, чтобы SP и IdP не разрешали IdP Initiated SSO. Это означает, что вызывающая сторона начинает поток SAML на стороне SP, который создаёт подписанный SAML-запрос, предназначенный для IdP.

    Шифрование SP¶

    Рекомендуется избегать размещения конфиденциальных данных в SAML-ответе IdP, но иногда это неизбежно. Это могут быть имена пользователей или другие персональные данные (PII). Когда раскрытие информации является соображением, SP будет иметь сертификат шифрования SAML. IdP будет использовать его и встроенный публичный ключ для шифрования SAML-ответа. SP должен использовать отдельную пару сертификата и ключа для подписания и шифрования SAML.

    Содержимое сертификата¶

    В контексте подписания и шифрования SAML сертификаты X.509 чаще всего рассматриваются просто как обёртка для хранения публичного ключа, используемого для проверки подписи или обёртывания симметричного ключа для шифрования SAML. Тем не менее сертификат может содержать атрибуты, которые могут быть использованы для дополнительного повышения безопасности.

    OWASP рекомендует IdP и SP принять EKU, KU и сроки жизни ключей, упомянутые ниже. Они законным образом повышают безопасность и позволяют проверяющей стороне дополнительно защитить себя. Они также помогают продемонстрировать соответствие нормам PKI.

    Ключи и алгоритмы подписи¶

    Размер и тип пары ключей и выбор алгоритма подписи оказывают сильное влияние на безопасность и совместимость. Не все программные пакеты или библиотеки IdP и SP поддерживают все комбинации параметров. Поскольку один IdP часто связан со многими SP, единственный вариант — выбрать наименее защищённый вариант, который всё ещё считается безопасным. Наиболее поддерживаемая и в настоящее время безопасная комбинация — использование ключей RSA 2048 бит и хеширования/подписания SHA-256. Это относится к алгоритму подписи сертификата, а не к подписанию XML SAML.

    По мере того как постквантовые алгоритмы становятся более распространёнными и в конечном счёте обязательными, это становится ещё более сложным. Разработчики программного обеспечения SAML SP и IdP должны начать изучать варианты поддержки большего количества ключей и алгоритмов подписи.

    Ключи¶

    Ключи ECC могут быть значительно меньше при обеспечении большей безопасности, чем ключи RSA, а математические операции выполняются быстрее. Они предпочтительны, когда все стороны могут их использовать. Ключи ECC могут быть всего 256 бит и при этом оставаться безопасными. Ключи RSA более совместимы. Минимальный размер ключа RSA должен составлять 2048 бит. По крайней мере один крупный поставщик Microsoft Entra не поддерживает ключи ECC.

    Алгоритмы подписи¶

    При использовании криптографии с публичным ключом для подписи данных данные сначала хешируются выбранным алгоритмом, а затем хеш подписывается закрытым ключом.

    Ни один IdP не должен использовать SHA-1 в качестве хеша подписи сертификата. SHA-256 — минимальный порог. Тем не менее, если возможно, переход на более крупные алгоритмы хеширования, такие как SHA-384 или SHA-512, означает лучшее обеспечение будущей совместимости службы. В данном контексте речь идёт об алгоритме подписи сертификата, а не о том, который используется для подписания XML SAML-ответа.

    Срок жизни сертификата¶

    Сертификаты содержат атрибуты NotBefore и NotOnorAfter. Большинство IdP игнорируют их в пользу гарантии доступности, если смена сертификата не происходит вовремя. Срок жизни SAML-сертификата должен управляться достаточно хорошо, чтобы игнорирование этих атрибутов не было необходимым. Игнорирование периода действия сертификата — принципиально плохая идея. Хотя NIST SP 800-57 (Часть 1, Версия 5) позволяет ключам RSA 2048 бит служить 3 года, максимальный срок жизни подписывающего сертификата SAML должен составлять два года. Если закрытый ключ не защищён должным образом, например в Hardware Security Module (HSM), этого может быть слишком долго для безопасности.

    Extended Key Usage (EKU) и Key Usage (KU)¶

    EKU описывает конкретный случай использования, для которого предназначен сертификат. Это такие случаи использования, как аутентификация сервера, аутентификация клиента и подписание кода, которые не подходят для подписания SAML. Не существует широко принятого EKU для подписания SAML, но RFC 9336 определяет один, который идеально подходит: id-kp-documentSigning (1.3.6.1.5.5.7.3.36). IdP и SP могут рассмотреть возможность стандартизации на этом EKU.

    KU описывает базовые криптографические операции, для которых предназначен закрытый ключ. Это такие вещи, как digitalSignature, nonRepudiation, keyEncipherment и т.д. IdP и SP могут рассмотреть требование digitalSignature и, кроме того, запрет сертификатов, которые имеют другие KU, поскольку сертификаты должны использоваться только для одного случая применения. Например, TLS-сертификат сервера IdP никогда не должен быть подписывающим сертификатом SAML.

    Точка распределения списка отзыва сертификатов (CRL Distribution Point, CDP)¶

    Точки распределения CRL (Certificate Revocation List) — это список сертификатов, которым CA отзывает доверие. Они чаще всего доставляются по HTTP, а URL-адреса CRL обычно встроены в каждый сертификат, выданный CA. CRL подписан CA, поэтому атака «человек посередине» против HTTP не может нарушить целостность списка, кроме как подделать его, тем самым делая его недействительным. То есть злоумышленник не может его изменить. Только сертификаты, подписанные CA, могут иметь CRL. Если в SAML-сертификате указан CRL, он должен быть доступен проверяющей стороне, и эта сторона должна проверить его.

    Учитывая уровень риска при компрометации закрытого ключа и меньший масштаб отношений IdP-SP, стороны в системе SAML должны разработать план со списками контактов для уведомления и быстрой смены сертификатов в случае инцидента. Многие продукты и библиотеки SAML не поддерживают проверку отзыва, и простой отзыв сертификата без скоординированной замены означает простой.

    Протокол статуса онлайн-сертификата (OCSP)¶

    OCSP — ещё один способ проверки отзыва сертификата. URL-адрес OCSP встроен в сертификат, как и CRL, и должен быть доступен по HTTP. Ответ подписан, поэтому атаки MITM не являются угрозой целостности. OCSP становится менее популярным, поскольку обмен создаёт проблемы конфиденциальности. IP-адрес вызывающей стороны виден, и раскрывается сертификат, который используется. Это менее актуально для SAML, поскольку не раскрывается целевой веб-сайт, а общее использование снизилось. Если URL-адрес OCSP присутствует в каком-либо сертификате в цепочке, его следует использовать для проверки отзыва сертификата.

    Иерархия сертификатов¶

    Подписывающий сертификат SAML может быть подписан одним из трёх способов. Сертификат может быть самоподписанным, подписанным публичным CA или подписанным частным CA. У каждого есть свои плюсы и минусы, однако, учитывая текущее состояние WebPKI (публичного) и частного PKI, использование самоподписанных SAML-сертификатов является явным победителем при соблюдении надлежащих мер предосторожности при обмене сертификатами.

    Издатель сертификата¶

    Все сертификаты X.509 подписываются с использованием закрытого ключа органом, известным как Издатель (Issuer). Это может быть CA или в случае самоподписанного сертификата — соответствующий закрытый ключ сертификата. В случае сертификата, подписанного CA, подписывающая сторона также может иметь сертификат, у которого есть Издатель, и так далее. Это называется цепочкой или путём, и она должна завершаться корневым CA (который по определению является самоподписанным). Издатель должен быть проверен. Если издателем является CA, его атрибуты, такие как EKU, KU и CRL, также могут быть проверены. Это должно происходить для каждого сертификата в пути вплоть до корневого.

    Публичный центр сертификации (CA)¶

    При использовании этого типа сертификата публичный CA выдаёт сертификат в соответствии со своими правилами и правилами CA Browser Forum (CABF). Эти публичные корневые CA включаются в хранилища доверия, поддерживаемые крупными производителями браузеров. Большинство вещей в Интернете доверяют им, потому что кто-то следит за тем, чтобы хранилища доверия были там, где они должны быть.

    Когда IdP меняет свой подписывающий сертификат SAML, каждый SP должен одновременно обновить явное доверие к этому сертификату. Это может быть сложным при небольшом количестве SP. При большом их количестве это почти невозможно. Эта трудность привела к использованию подписывающих сертификатов SAML с максимально длительными сроками жизни. Раньше это было два года с публичными CA, затем 398 дней. Основное внимание стандартов WebPKI и CABF уделяется серверным сертификатам для TLS. Недавние и продолжающиеся изменения в сроках жизни сертификатов делают сертификаты, выданные публичным CA, менее привлекательными. Это связано с тем, что у CABF есть путь к тому, чтобы сертификаты, выданные публичным CA, служили только 47 дней. Поскольку IdP должен получить сертификат, объявить об изменении в разумные сроки, а затем выполнить это изменение, IdP и SP будут находиться в постоянном состоянии обновления сертификатов.

    Стоит отметить, что у CABF нет нормативного регулирования использования или получения сертификатов SAML; сертификаты от их членов CA — это то, что широко считается публичными CA. То есть им широко доверяют браузеры, операционные системы и различные фреймворки разработки.

    Использование сертификатов, подписанных публичным CA, позволяет проверять отзыв, что может повысить безопасность, но если обмен сертификатами не защищён, это может создать ложное чувство безопасности.

    Частный центр сертификации (CA)¶

    Поскольку большинство IdP и SP рассматривают сертификаты X.509 как явное доверие, частные CA и PKI могут использоваться. Способ разработки, создания и управления частными CA сильно варьируется, и в конечном счёте грамотное управление CA обходится очень дорого. Чтобы доверять CA третьей стороны, необходимо чётко понимать жизненный цикл CA. Существуют два типа аудита, которые охватывают это, оба из которых очень дороги в дополнение к созданию и управлению CA. Если вы полагаетесь на сторонние CA, они должны быть проверены по WebTrust, ETSI или SOC 2 Type II.

    Доверие сторонним CA при ненадлежащем подходе может привести к нежелательному чрезмерному доверию для таких вещей, как TLS и подписание кода. Если вы решите доверять сторонним CA, убедитесь, что им доверяют только для процесса проверки подписи IdP.

    Если используются сторонние CA, они по-прежнему не должны выдавать подписывающие сертификаты SAML, у которых срок жизни сертификата превышает срок жизни базовой пары ключей, исходя из руководства стандартных организаций, таких как NIST, NSA и т.д.. При использовании наиболее надёжных типов закрытых ключей это устанавливает верхний предел в два года.

    Самоподписанный сертификат¶

    Благодаря явному характеру большинства ассоциаций безопасности SAML самоподписанные сертификаты идеально подходят для данного случая использования. Содержимое сертификата и срок жизни не ограничены политикой или процессом выдающего CA, будь то публичный или частный. Поскольку смена SAML-сертификатов может быть болезненной и трудоёмкой, установка срока жизни сертификата на максимально безопасно возможный срок является ключевым фактором. Немногие CA допускают достаточно длительные сроки жизни из-за их ориентации на модель угроз TLS.

    Создание самоподписанного SAML-сертификата¶

    Если вы используете Hardware Security Module (HSM), следуйте инструкциям поставщика. В этом процессе используется openssl. В примере используется слишком обобщённое различающееся имя. Ваше Common Name (CN) должно быть значимым и конкретным.

    1. Генерация закрытого ключа: openssl genrsa -out private.key 2048 или openssl ecparam -genkey -name prime256v1 -out private.pem

    2. Создание файла конфигурации (например, cert.cnf):

    [req] distinguished_name = req_distinguished_name x509_extensions = v3_ca prompt = no

    [req_distinguished_name] C = US ST = California L = San Francisco O = MyOrganization OU = MyUnit CN = SAML Signing

    [v3_ca] basicConstraints = CA:FALSE keyUsage = digitalSignature extendedKeyUsage = 1.3.6.1.5.5.7.3.36

    1. Генерация самоподписанного сертификата: openssl req -x509 -new -nodes -key private.key -sha256 -days 365 -out certificate.crt -config cert.cnf -extensions v3_ca

    URL-адреса метаданных сертификата¶

    Многие IdP публикуют URL-адрес метаданных, содержащий базовую информацию о конфигурации, включая подписывающий сертификат SAML. Многие SP могут получать данные от IdP, обновляя информацию подписывающего сертификата практически в реальном времени. Использование этих параметров является идеальным. Эта модель точно соответствует намерению Certificate and Public Key Pinning при необходимости использования pinning.

    URL-адрес метаданных должен быть защищён с использованием TLS, где серверный сертификат поступает от WebPKI CA, которому широко доверяют и который соответствует руководству в Transport Layer Security Cheat Sheet.

    Идеальное состояние отношений IdP и SP — использование URL-адресов метаданных, независимо от того, какой тип сертификата используется. Если URL-адреса метаданных не используются, необходимо проявлять особую осторожность, чтобы злоумышленник не убедил SP доверять неправильному сертификату. Избегайте отправки сертификатов по электронной почте. Вместо этого, как и с URL-адресами метаданных, представляйте их через надлежащим образом настроенный TLS.

    Защита ключа подписи¶

    Ключи подписи SAML — это важнейший актив безопасности и цель злоумышленников. При создании ключей и при необходимости копировании их на узлы кластера IdP необходимо проявлять особую осторожность. Ключи на основе файлов тривиально извлечь злоумышленнику, имеющему доступ. Операторы IdP должны настоятельно рассмотреть возможность защиты закрытых ключей с помощью Hardware Security Module (HSM). HSM позволяют приложению использовать ключ без возможности его экспорта или копирования. Они имеют механизмы для безопасной репликации ключей в резервный HSM без какого-либо раскрытия ключей за пределами HSM. Качественные HSM имеют рейтинг FIPS 140-2 или FIPS 140-3.

    Соображения для Identity Provider (IdP)¶

    • Проверьте сертификат X.509 на совместимость алгоритмов, стойкость шифрования, ограничения экспорта и содержимое выше
    • Проверьте варианты строгой аутентификации для генерации SAML-токена
    • Валидация IDP (какой IDP создаёт токен)
    • Синхронизация с общим интернет-источником времени
    • Определите уровни надёжности для верификации личности
    • Предпочитайте асимметричные идентификаторы для утверждений идентификации вместо персональных данных (например, SSN и т.д.)
    • Подписывайте каждое отдельное утверждение или весь элемент Response

    Соображения для Service Provider (SP)¶

    • Проверка состояния сессии пользователя
    • Уровень детализации при установке контекста авторизации при потреблении SAML-токена (используете ли вы группы, роли, атрибуты)
    • Убедитесь, что каждое утверждение или весь элемент Response подписан
    • Проверка подписей
    • Проверка подписи авторизованным IdP
    • Проверка сертификатов IDP на отзыв по CRL/OCSP при их наличии
    • Проверка NotBefore и NotOnorAfter
    • Проверка атрибута Recipient
    • Определение критериев для выхода из системы SAML
    • Обмен утверждениями только по защищённым транспортным протоколам, таким как TLS
    • Определение критериев для управления сессиями
    • По возможности проверяйте идентификаторы пользователей, полученные из утверждений SAML-токена.

    Валидация входных данных¶

    Тот факт, что SAML является протоколом безопасности, не означает, что валидация входных данных отходит на второй план.

    • Убедитесь, что все поставщики/потребители SAML выполняют надлежащую валидацию входных данных.

    Криптография¶

    Решения, основанные на криптографических алгоритмах, должны следить за последними разработками в области криптоанализа.

    • Убедитесь, что все элементы SAML в цепочке используют надёжное шифрование
    • Рассмотрите возможность отказа от поддержки небезопасных алгоритмов XMLEnc
