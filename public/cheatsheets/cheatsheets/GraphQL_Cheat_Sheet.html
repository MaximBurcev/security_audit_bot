    Памятка по GraphQL¶

    Введение¶

    GraphQL — это язык запросов с открытым исходным кодом, изначально разработанный Facebook, который может использоваться для построения API в качестве альтернативы REST и SOAP. Он набрал популярность с момента своего появления в 2012 году благодаря встроенной гибкости, которую он предлагает как создателям, так и потребителям API. Существуют серверы и клиенты GraphQL, реализованные на различных языках. Многие компании используют GraphQL, включая GitHub, Credit Karma, Intuit и PayPal.

    Эта памятка содержит рекомендации по различным аспектам, которые необходимо учитывать при работе с GraphQL:

    • Применять надлежащие проверки валидации входных данных для всех входящих данных.
    • Затратные запросы приведут к отказу в обслуживании (DoS), поэтому следует добавлять проверки для ограничения или предотвращения слишком дорогих запросов.
    • Убедиться, что API имеет надлежащие проверки контроля доступа.
    • Отключить небезопасные конфигурации по умолчанию (например, избыточные ошибки, интроспекцию, GraphiQL и т.д.).

    Распространённые атаки¶

    • Инъекции — обычно включают, но не ограничиваются следующим:
      • SQL и NoSQL инъекции
      • Инъекции OS-команд
      • SSRF и CRLF инъекции/Request Smuggling
    • DoS (Отказ в обслуживании)
    • Злоупотребление нарушенной авторизацией: как ненадлежащий, так и избыточный доступ, включая IDOR
    • Атаки пакетной обработки (Batching Attacks) — специфический для GraphQL метод атаки грубой силы
    • Злоупотребление небезопасными конфигурациями по умолчанию

    Лучшие практики и рекомендации¶

    Валидация входных данных¶

    Добавление строгой валидации входных данных может помочь предотвратить инъекции и DoS. Основной принцип проектирования GraphQL состоит в том, что пользователь предоставляет один или несколько идентификаторов, а бэкенд имеет ряд инструментов для получения данных, выполняющих HTTP, DB или другие вызовы с использованием этих идентификаторов. Это означает, что пользовательский ввод будет включён в HTTP-запросы, DB-запросы или другие запросы/вызовы, что создаёт возможность для инъекций, которые могут привести к различным атакам или DoS.

    См. памятки OWASP по валидации входных данных и общему предотвращению инъекций для получения полных сведений о наилучшем выполнении валидации входных данных и предотвращении инъекций.

    Общие практики¶

    Проверяйте все входящие данные, допуская только допустимые значения (то есть список разрешённых).

    • Использовать специфические типы данных GraphQL, такие как скаляры или перечисления. Писать пользовательские валидаторы GraphQL для более сложных проверок. Пользовательские скаляры также могут быть полезны.
    • Определять схемы для входных данных мутаций.
    • Перечислять допустимые символы — не использовать список запрещённых
      • Чем строже список допустимых символов, тем лучше. Хорошей отправной точкой часто является разрешение только буквенно-цифровых не-unicode символов, поскольку это заблокирует многие атаки.
    • Для корректной обработки unicode-ввода использовать единую внутреннюю кодировку символов
    • Корректно отклонять недопустимые входные данные, избегая раскрытия избыточной информации о том, как работает API и его валидация.

    Предотвращение инъекций¶

    При обработке входных данных, предназначенных для передачи другому интерпретатору (например, SQL/NoSQL/ORM, OS, LDAP, XML):

    • Всегда выбирать библиотеки/модули/пакеты, предлагающие безопасные API, такие как параметризованные запросы.
      • Убедиться, что документация используется надлежащим образом для правильного применения инструмента
      • Использование ORM и ODM является хорошим вариантом, но они должны использоваться правильно, чтобы избежать ошибок, таких как ORM-инъекции.
    • Если такие инструменты недоступны, всегда экранировать/кодировать входные данные в соответствии с лучшими практиками целевого интерпретатора
      • Выбирать хорошо задокументированную и активно поддерживаемую библиотеку для экранирования/кодирования. Во многих языках и фреймворках эта функциональность встроена.

    Дополнительную информацию можно найти на следующих страницах:

    • Предотвращение SQL-инъекций
    • Предотвращение NoSQL-инъекций
    • Предотвращение LDAP-инъекций
    • Предотвращение инъекций OS-команд
    • Безопасность XML и Предотвращение XXE-инъекций

    Валидация процессов¶

    При использовании пользовательского ввода, даже если он санируется и/или валидируется, его не следует использовать в определённых целях, которые дадут пользователю контроль над потоком данных. Например, не следует делать HTTP/ресурсный запрос к хосту, предоставленному пользователем (если только нет абсолютной бизнес-необходимости).

    Предотвращение DoS¶

    DoS — это атака на доступность и стабильность API, которая может сделать его медленным, неотзывчивым или полностью недоступным. В этой памятке описываются несколько методов ограничения возможности DoS-атаки на уровне приложения и других уровнях технологического стека. Также существует отдельная памятка, посвящённая теме DoS.

    Вот рекомендации, специфичные для GraphQL, по ограничению потенциала для DoS:

    • Добавить ограничение глубины для входящих запросов
    • Добавить ограничение количества для входящих запросов
    • Добавить пагинацию для ограничения объёма данных, которые могут быть возвращены в одном ответе
    • Добавить разумные таймауты на уровне приложения, уровне инфраструктуры или на обоих уровнях
    • Рассмотреть возможность анализа стоимости запросов и установить максимально допустимую стоимость на запрос
    • Применять ограничение числа запросов для входящих запросов по IP или пользователю (или обоим), чтобы предотвратить базовые DoS-атаки
    • Реализовать технику пакетирования и кэширования на стороне сервера (для этого можно использовать DataLoader от Facebook)

    Ограничение запросов (глубина и количество)¶

    В GraphQL каждый запрос имеет глубину (например, вложенные объекты) и для каждого запрошенного объекта может быть указано количество (например, 99999999 экземпляров объекта). По умолчанию оба параметра могут быть неограниченными, что может привести к DoS. Следует устанавливать ограничения на глубину и количество для предотвращения DoS, но это обычно требует небольшой пользовательской реализации, поскольку не поддерживается GraphQL нативно. См. эту и эту страницы для получения дополнительной информации об этих атаках и о том, как добавить ограничения глубины и количества. Добавление пагинации также может помочь с производительностью.

    API, использующие graphql-java, могут использовать встроенный MaxQueryDepthInstrumentation для ограничения глубины. API, использующие JavaScript, могут использовать graphql-depth-limit для реализации ограничения глубины и graphql-input-number для реализации ограничения количества.

    Вот пример запроса GraphQL с глубиной N:

    query evil {            // Глубина: 0
  album(id: 42) {       // Глубина: 1
    songs {             // Глубина: 2
      album {           // Глубина: 3
        ...             // Глубина: ...
        album {id: N}   // Глубина: N
      }
    }
  }
}

    Вот пример запроса GraphQL, запрашивающего 99999999 экземпляров объекта:

    query {
  author(id: "abc") {
    posts(first: 99999999) {
      title
    }
  }
}

    Таймауты¶

    Добавление таймаутов может быть простым способом ограничения ресурсов, потребляемых одним запросом. Однако таймауты не всегда эффективны, поскольку они могут не сработать до того, как вредоносный запрос уже потребил избыточные ресурсы. Требования к таймаутам будут различаться в зависимости от API и механизма получения данных; не существует единого значения таймаута, подходящего для всех случаев.

    На уровне приложения таймауты могут быть добавлены для запросов и функций разрешителей. Этот вариант обычно более эффективен, поскольку выполнение запроса/разрешения можно остановить по достижении таймаута. GraphQL не поддерживает таймауты запросов нативно, поэтому требуется пользовательский код. Подробнее об использовании таймаутов с GraphQL см. в этой статье блога или в двух примерах ниже.

    Пример таймаута на JavaScript

    Фрагмент кода из этого ответа на SO:

    request.incrementResolverCount =  function () {
    var runTime = Date.now() - startTime;
    if (runTime > 10000) {  // таймаут 10 секунд
      if (request.logTimeoutError) {
        logger('ERROR', `Request ${request.uuid} query execution timeout`);
      }
      request.logTimeoutError = false;
      throw 'Query execution has timeout. Field resolution aborted';
    }
    this.resolverCount++;
  };

    Пример таймаута на Java с использованием Instrumentation

    public class TimeoutInstrumentation extends SimpleInstrumentation {
    @Override
    public DataFetcher<?> instrumentDataFetcher(
            DataFetcher<?> dataFetcher, InstrumentationFieldFetchParameters parameters
    ) {
        return environment ->
            Observable.fromCallable(() -> dataFetcher.get(environment))
                .subscribeOn(Schedulers.computation())
                .timeout(10, TimeUnit.SECONDS)  // таймаут 10 секунд
                .blockingFirst();
    }
}

    Таймаут на уровне инфраструктуры

    Другой вариант добавления таймаута, который обычно проще реализовать, — добавить таймаут на HTTP-сервере (Apache/httpd, nginx), обратном прокси или балансировщике нагрузки. Однако таймауты на уровне инфраструктуры часто неточны и могут быть обойдены легче, чем таймауты на уровне приложения.

    Анализ стоимости запросов¶

    Анализ стоимости запросов включает присвоение стоимости разрешению полей или типов во входящих запросах, чтобы сервер мог отклонять слишком дорогие для выполнения или потребляющие слишком много ресурсов запросы. Это непросто реализовать и может не всегда быть необходимым, но это наиболее тщательный подход к предотвращению DoS. Дополнительные сведения о реализации этого элемента управления см. в разделе «Query Cost Analysis» в этой статье блога.

    Apollo рекомендует:

    Прежде чем тратить много времени на реализацию анализа стоимости запросов, убедитесь, что он вам нужен. Попробуйте «завалить» или замедлить ваш staging API с помощью вредоносного запроса и посмотрите, насколько это удастся — возможно, у вашего API нет таких вложенных отношений, или он способен без проблем обрабатывать тысячи записей за раз и не нуждается в анализе стоимости запросов!

    API, использующие graphql-java, могут использовать встроенный MaxQueryComplexityInstrumentation для применения максимальной сложности запроса. API, использующие JavaScript, могут использовать graphql-cost-analysis или graphql-validation-complexity для применения максимальной стоимости запроса.

    Ограничение числа запросов¶

    Применение ограничения числа запросов по IP или пользователю (для анонимного и неавторизованного доступа) может помочь ограничить способность одного пользователя засыпать сервис запросами и влиять на производительность. В идеале это можно сделать с помощью WAF, API-шлюза или веб-сервера (Nginx, Apache/HTTPD), чтобы снизить усилия по добавлению ограничений.

    Или можно сделать более сложное управление трафиком и реализовать его в коде (нетривиально). Подробнее о специфичном для GraphQL ограничении числа запросов см. «Throttling» здесь.

    Пакетирование и кэширование на стороне сервера¶

    Для повышения эффективности GraphQL API и снижения потребления ресурсов можно использовать технику пакетирования и кэширования, чтобы предотвратить дублирование запросов данных в течение короткого промежутка времени. Одним из способов реализации этого является инструмент DataLoader от Facebook.

    Управление системными ресурсами¶

    Отсутствие надлежащего ограничения объёма ресурсов, потребляемых API (например, CPU или памяти), может нарушить его отзывчивость и доступность, делая его уязвимым для DoS-атак. Некоторые ограничения можно настроить на уровне операционной системы.

    В Linux можно использовать комбинацию Control Groups (cgroups), User Limits (ulimits) и Linux Containers (LXC).

    Однако платформы контейнеризации имеют тенденцию значительно упрощать эту задачу. Информацию о том, как предотвратить DoS при использовании контейнеров, см. в разделе ограничения ресурсов в Памятке по безопасности Docker.

    Контроль доступа¶

    Для обеспечения надлежащего контроля доступа в GraphQL API выполните следующее:

    • Всегда проверять, что запрашивающий авторизован для просмотра или изменения запрашиваемых данных. Это можно сделать с помощью RBAC или других механизмов контроля доступа.
      • Это предотвратит проблемы IDOR, включая BOLA и BFLA.
    • Применять проверки авторизации как для рёбер, так и для узлов (см. пример отчёта об ошибке, где узлы не имели проверок авторизации, а рёбра имели).
    • Использовать Interfaces и Unions для создания структурированных, иерархических типов данных, которые можно использовать для возврата большего или меньшего количества свойств объекта в зависимости от разрешений запрашивающего.
    • Разрешители запросов и мутаций можно использовать для выполнения проверки контроля доступа, возможно с использованием промежуточного ПО RBAC.
    • Отключить интроспекционные запросы на системном уровне в любых рабочих или общедоступных средах.
    • Отключить GraphiQL и другие аналогичные инструменты исследования схем в рабочих или общедоступных средах.

    Общий доступ к данным¶

    В GraphQL-запросах обычно используются один или несколько прямых ID объектов для их получения или изменения. Например, запрос определённого изображения может включать ID, который фактически является первичным ключом в базе данных для этого изображения. Как и при любом запросе, сервер должен проверять, что вызывающий имеет доступ к запрашиваемому объекту. Однако иногда разработчики допускают ошибку, предполагая, что владение ID объекта означает, что у вызывающего должен быть доступ. Неспособность проверить доступ запрашивающего в этом случае называется Нарушенной аутентификацией на уровне объекта (Broken Object Level Authentication), также известной как IDOR.

    GraphQL API может поддерживать доступ к объектам по их ID, даже если это не предусмотрено. Иногда в объекте запроса есть поля node или nodes или оба, и их можно использовать для прямого доступа к объектам по ID. Проверить, есть ли в вашей схеме эти поля, можно, выполнив в командной строке (при условии, что schema.json содержит вашу GraphQL-схему): cat schema.json | jq ".data.__schema.types[] | select(.name==\"Query\") | .fields[] | .name" | grep node. Удаление этих полей из схемы должно отключить функциональность, но всегда следует применять надлежащие проверки авторизации для верификации того, что вызывающий имеет доступ к запрашиваемому объекту.

    Доступ к запросам (получение данных)¶

    В рамках GraphQL API существуют различные поля данных, которые можно вернуть. Одно из соображений — нужны ли разные уровни доступа к этим полям. Например, может потребоваться, чтобы только определённые потребители могли получать определённые поля данных, а не чтобы все потребители могли получать все доступные поля. Это можно сделать, добавив в код проверку, чтобы убедиться, что запрашивающий имеет право читать поле, которое он пытается получить.

    Доступ к мутациям (манипуляция данными)¶

    GraphQL поддерживает мутации, или манипуляцию данными, в дополнение к наиболее распространённому варианту использования — получению данных. Если API реализует/допускает мутации, может потребоваться введение средств контроля доступа для ограничения того, какие потребители, если таковые имеются, могут изменять данные через API. Настройки, требующие контроля доступа к мутациям, включают API, где для запрашивающих предназначен только доступ на чтение, или где только определённые стороны должны иметь возможность изменять определённые поля.

    Атаки пакетной обработки¶

    GraphQL поддерживает пакетную обработку запросов, также известную как батчинг запросов. Это позволяет вызывающим либо группировать несколько запросов, либо группировать запросы для нескольких экземпляров объектов в одном сетевом вызове, что приводит к так называемой атаке пакетной обработки. Это форма атаки грубой силы, специфичная для GraphQL, которая обычно обеспечивает более быстрые и менее обнаруживаемые эксплойты. Вот наиболее распространённый способ выполнения батчинга запросов:

    [
  {
    query: < запрос 0 >,
    variables: < переменные для запроса 0 >,
  },
  {
    query: < запрос 1 >,
    variables: < переменные для запроса 1 >,
  },
  {
    query: < запрос n >
    variables: < переменные для запроса n >,
  }
]

    А вот пример одного батч-запроса GraphQL, запрашивающего несколько различных экземпляров объекта droid:

    query {
  droid(id: "2000") {
    name
  }
  second:droid(id: "2001") {
    name
  }
  third:droid(id: "2002") {
    name
  }
}

    В этом случае его можно использовать для перечисления всех возможных объектов droid, хранящихся на сервере, за очень небольшое количество сетевых запросов, в отличие от стандартного REST API, где запрашивающему пришлось бы отправлять разные сетевые запросы для каждого ID droid. Этот тип атаки может привести к следующим проблемам:

    • DoS-атаки на уровне приложения — большое количество запросов или запросов объектов в одном сетевом вызове может вызвать зависание базы данных или истощение других доступных ресурсов (например, памяти, CPU, нижестоящих сервисов).
    • Перечисление объектов на сервере, таких как пользователи, email-адреса и ID пользователей.
    • Перебор паролей, кодов двухфакторной аутентификации (OTP), токенов сессий или других чувствительных значений.
    • WAF, RASP, IDS/IPS, SIEM или другие инструменты безопасности, скорее всего, не обнаружат эти атаки, поскольку они выглядят как одиночный запрос, а не как огромный объём сетевого трафика.
    • Эта атака, вероятно, обойдёт существующие ограничения числа запросов в таких инструментах, как Nginx или другие прокси/шлюзы, поскольку они ориентируются на сырое количество запросов.

    Смягчение атак пакетной обработки¶

    Для смягчения этого типа атаки следует устанавливать ограничения на входящие запросы на уровне кода, чтобы они применялись для каждого запроса. Существует 3 основных варианта:

    • Добавить ограничение числа объектных запросов в коде
    • Предотвратить пакетирование для чувствительных объектов
    • Ограничить количество запросов, которые могут выполняться одновременно

    Один из вариантов — создать ограничение на уровне кода на количество объектов, которые вызывающие могут запрашивать. Это означает, что бэкенд будет отслеживать, сколько различных экземпляров объектов запросил вызывающий, чтобы он был заблокирован после запроса слишком большого количества объектов, даже если он группирует запросы объектов в одном сетевом вызове. Это воспроизводит ограничение на уровне сети, которое делает WAF или другой инструмент.

    Другой вариант — предотвратить пакетирование для чувствительных объектов, которые вы не хотите подвергать перебору грубой силой, таких как имена пользователей, email-адреса, пароли, OTP, токены сессий и т.д. Таким образом злоумышленник вынужден атаковать API как REST API и делать разные сетевые вызовы для каждого экземпляра объекта. Это не поддерживается нативно, поэтому потребует пользовательского решения. Однако после введения этого элемента управления другие стандартные элементы управления будут функционировать нормально, помогая предотвратить любой перебор грубой силой.

    Ограничение количества операций, которые могут быть объединены в пакет и выполнены одновременно, — ещё один вариант смягчения атак пакетной обработки GraphQL, приводящих к DoS. Однако это не панацея и должно использоваться в сочетании с другими методами.

    Безопасные конфигурации¶

    По умолчанию большинство реализаций GraphQL имеют некоторые небезопасные конфигурации по умолчанию, которые следует изменить:

    • Не возвращать избыточные сообщения об ошибках (например, отключить трассировки стека и режим отладки).
    • Отключить или ограничить интроспекцию и GraphiQL в зависимости от ваших нужд.
    • Предложение похожих полей при опечатке, если интроспекция отключена

    Интроспекция + GraphiQL¶

    GraphQL часто поставляется по умолчанию с включёнными интроспекцией и/или GraphiQL без требования аутентификации. Это позволяет потребителю вашего API узнать всё о вашем API, схемах, мутациях, устаревших полях и иногда нежелательных «приватных полях».

    Это может быть намеренной конфигурацией, если ваш API предназначен для внешних клиентов, но также может быть проблемой, если API был предназначен только для внутреннего использования. Хотя безопасность через неизвестность не рекомендуется, может быть хорошей идеей рассмотреть отключение интроспекции, чтобы избежать любых утечек. Если ваш API доступен публично, возможно, стоит рассмотреть его отключение для неаутентифицированных или неавторизованных пользователей.

    Для внутреннего API самый простой подход — просто отключить интроспекцию на системном уровне. Обратитесь к этой странице или документации вашей реализации GraphQL, чтобы узнать, как полностью отключить интроспекцию. Если ваша реализация не поддерживает отключение интроспекции нативно или вы хотите разрешить некоторым потребителям/ролям иметь этот доступ, вы можете создать в своём сервисе фильтр, позволяющий только одобренным потребителям получать доступ к системе интроспекции.

    Имейте в виду, что даже если интроспекция отключена, злоумышленники всё равно могут угадывать поля путём перебора грубой силой. Кроме того, GraphQL имеет встроенную функцию возврата подсказки, когда имя поля, предоставленное запрашивающим, похоже (но не совпадает) на существующее поле (например, запрос содержит usr и ответ спросит Did you mean "user?"). Следует рассмотреть отключение этой функции, если вы отключили интроспекцию, чтобы снизить раскрытие информации, хотя не все реализации GraphQL поддерживают это. Shapeshifter — один из инструментов, который должен справляться с этим.

    Отключение интроспекции — Java

    GraphQLSchema schema = GraphQLSchema.newSchema()
    .query(StarWarsSchema.queryType)
    .fieldVisibility( NoIntrospectionGraphqlFieldVisibility.NO_INTROSPECTION_FIELD_VISIBILITY )
    .build();

    Отключение интроспекции и GraphiQL — JavaScript

    app.use('/graphql', graphqlHTTP({
  schema: MySessionAwareGraphQLSchema,
+ validationRules: [NoIntrospection]
  graphiql: process.env.NODE_ENV === 'development',
}));

    Не возвращать избыточные ошибки¶

    GraphQL API в рабочей среде не должны возвращать трассировки стека или работать в режиме отладки. Реализация этого зависит от конкретного инструмента, но использование промежуточного ПО — один из популярных способов лучше контролировать ошибки, возвращаемые сервером. Для отключения избыточных ошибок с Apollo Server передайте debug: false в конструктор Apollo Server или установите переменную окружения NODE_ENV в значение 'production' или 'test'. Однако, если вы хотите логировать трассировку стека внутренне, не возвращая её пользователю, см. здесь, как маскировать и логировать ошибки, чтобы они были доступны разработчикам, но не вызывающим API.
