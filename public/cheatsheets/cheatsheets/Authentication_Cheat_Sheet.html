    Шпаргалка по аутентификации¶

    Введение¶

    Аутентификация (AuthN) — это процесс проверки того, что человек, организация или веб-сайт являются теми, за кого себя выдают, путём проверки одного или нескольких аутентификаторов (таких как пароли, отпечатки пальцев или токены безопасности), которые подтверждают данное утверждение.

    Цифровая идентичность — уникальное представление субъекта, участвующего в онлайн-транзакции. Цифровая идентичность всегда уникальна в контексте цифрового сервиса, однако не обязательно должна быть отслеживаемой до конкретного реального лица.

    Подтверждение личности устанавливает, что субъект действительно является тем, за кого себя выдаёт. Данная концепция связана с KYC-концепциями и направлена на связывание цифровой идентичности с реальным человеком.

    Управление сессиями — это процесс, посредством которого сервер поддерживает состояние взаимодействующего с ним субъекта. Это необходимо для того, чтобы сервер помнил, как реагировать на последующие запросы в ходе транзакции. Сессии поддерживаются на сервере с помощью идентификатора сессии, который может передаваться туда и обратно между клиентом и сервером при отправке и получении запросов. Сессии должны быть уникальными для каждого пользователя и крайне сложными для предсказания. Шпаргалка по управлению сессиями содержит дополнительные рекомендации по лучшим практикам в этой области.

    Общие рекомендации по аутентификации¶

    Идентификаторы пользователей¶

    Основная функция идентификатора пользователя (User ID) — уникально идентифицировать пользователя в системе. В идеале User ID должны генерироваться случайным образом, чтобы предотвратить создание предсказуемых или последовательных идентификаторов, что может представлять угрозу безопасности, особенно в системах, где User ID могут быть раскрыты или выведены из внешних источников.

    Имена пользователей¶

    Имена пользователей (username) — это легко запоминаемые идентификаторы, выбираемые пользователем для идентификации себя при входе в систему или сервис. Термины User ID и username могут использоваться взаимозаменяемо, если выбранное пользователем имя также служит его уникальным идентификатором в системе.

    Пользователям следует разрешить использовать адрес электронной почты в качестве имени пользователя при условии, что адрес верифицирован в процессе регистрации. Кроме того, им должна быть предоставлена возможность выбрать имя пользователя, отличное от адреса электронной почты. Для получения информации о валидации адресов электронной почты см. обсуждение адресов электронной почты в шпаргалке по валидации входных данных.

    Решение для аутентификации и привилегированные учётные записи¶

    • НЕ разрешайте вход с привилегированными учётными записями (т.е. учётными записями, которые могут использоваться внутри системы, например для доступа к бэкенду / промежуточному ПО / базе данных) через пользовательские интерфейсы фронтенда
    • НЕ используйте одно и то же решение для аутентификации (например, IDP / AD), применяемое внутри компании, для незащищённого доступа (например, публичного доступа / DMZ)

    Реализация надлежащих требований к надёжности пароля¶

    Ключевой проблемой при использовании паролей для аутентификации является их надёжность. Политика «надёжного» пароля делает угадывание пароля вручную или автоматическими средствами трудным или практически невозможным. Надёжный пароль характеризуется следующими свойствами:

    • Длина пароля
      • Минимальная длина паролей должна быть принудительно применяться приложением.
        • Если включена MFA, пароли короче 8 символов считаются слабыми (NIST SP800-63B).
        • Если MFA не включена, пароли короче 15 символов считаются слабыми (NIST SP800-63B).
      • Максимальная длина пароля должна составлять не менее 64 символов, чтобы разрешить использование парольных фраз (NIST SP800-63B). Обратите внимание, что некоторые реализации алгоритмов хеширования могут вызывать отказ в обслуживании при длинных паролях.
    • Не обрезайте пароли без уведомления. Шпаргалка по хранению паролей содержит дополнительные рекомендации по обработке паролей длиннее максимальной.
    • Разрешайте использование всех символов, включая юникод и пробелы. Не должно быть правил составления пароля, ограничивающих типы допустимых символов. Не должно быть требований к наличию заглавных или строчных букв, цифр или специальных символов.
    • Обеспечивайте ротацию учётных данных при утечке пароля, в момент выявления компрометации или при смене технологии аутентификатора. Избегайте требований периодической смены пароля; вместо этого рекомендуйте пользователям выбирать надёжные пароли и включать многофакторную аутентификацию (MFA). Согласно рекомендациям NIST, верификаторы не должны требовать произвольных смен пароля (например, периодических).
    • Включите индикатор надёжности пароля, чтобы помочь пользователям создавать более сложные пароли
      • Для этой цели можно использовать библиотеку zxcvbn-ts.
      • Другие реализации zxcvbn на различных языках перечислены здесь; однако перед использованием проверяйте возраст и зрелость каждого примера.
    • Блокируйте распространённые и ранее скомпрометированные пароли
      • Pwned Passwords — сервис, позволяющий проверять пароли по базе ранее скомпрометированных. Подробности об API здесь.
      • Также можно скачать базу данных Pwned Passwords с помощью этого механизма для самостоятельного размещения.
      • Доступны и другие топ-списки паролей, однако нет гарантий их актуальности:
        • Различные списки паролей от SecLists Дэниела Миcлера.
        • Статическая копия топ-100 000 паролей из «Have I Been Pwned», размещённая NCSC в форматах text и JSON.

    Реализация безопасного механизма восстановления пароля¶

    В приложениях обычно предусмотрен механизм, позволяющий пользователю получить доступ к своей учётной записи в случае, если он забыл пароль. Подробности об этой функции см. в шпаргалке по восстановлению пароля.

    Хранение паролей в безопасном виде¶

    Крайне важно, чтобы приложение хранило пароль с использованием правильного криптографического метода. Подробности об этой функции см. в шпаргалке по хранению паролей.

    Сравнение хешей паролей с использованием безопасных функций¶

    Там, где это возможно, введённый пользователем пароль следует сравнивать с хранимым хешем пароля с помощью безопасной функции сравнения паролей, предоставляемой языком или фреймворком, например функции password_verify() в PHP. Там, где это невозможно, убедитесь, что функция сравнения:

    • Имеет максимальную длину входных данных для защиты от атак типа «отказ в обслуживании» с очень длинными входными данными.
    • Явно задаёт тип обеих переменных для защиты от атак на основе путаницы типов, таких как Magic Hashes в PHP.
    • Возвращает результат за постоянное время для защиты от атак по времени.

    Функция смены пароля¶

    При разработке функции смены пароля убедитесь в наличии:

    • Аутентифицированного пользователя с активной сессией.
    • Проверки текущего пароля. Это необходимо для того, чтобы убедиться, что пароль меняет законный пользователь. Рассмотрим сценарий злоупотребления: пользователь входит на публичном компьютере и забывает выйти из системы. Другой человек может воспользоваться этой активной сессией. Если мы не проверяем текущий пароль, этот другой человек может сменить пароль.

    Передача паролей только через TLS или другой надёжный транспорт¶

    См.: Шпаргалка по безопасности транспортного уровня

    Страница входа и все последующие аутентифицированные страницы должны быть доступны исключительно через TLS или другой надёжный транспорт. Несоблюдение TLS или другого надёжного транспорта для страницы входа позволяет злоумышленнику изменить действие формы входа, вызвав отправку учётных данных пользователя в произвольное место. Несоблюдение TLS или другого надёжного транспорта для аутентифицированных страниц после входа позволяет злоумышленнику просматривать незашифрованный идентификатор сессии и компрометировать аутентифицированную сессию пользователя.

    Требование повторной аутентификации для чувствительных функций¶

    В целях снижения риска CSRF и перехвата сессии важно требовать текущие учётные данные учётной записи перед обновлением чувствительной информации учётной записи, такой как пароль или адрес электронной почты пользователя, — или перед выполнением чувствительных транзакций, например при отправке покупки на новый адрес. Без этой защитной меры злоумышленник может выполнить чувствительные транзакции посредством CSRF- или XSS-атаки, не зная текущих учётных данных пользователя. Кроме того, злоумышленник может временно получить физический доступ к браузеру пользователя или похитить его идентификатор сессии для захвата сессии.

    Повторная аутентификация после событий риска¶

    Обзор: Повторная аутентификация критически важна, когда учётная запись подверглась высокорисковой активности, такой как восстановление учётной записи, сброс пароля или подозрительные паттерны поведения. В этом разделе описывается, когда и как инициировать повторную аутентификацию для защиты пользователей и предотвращения несанкционированного доступа. Дополнительные сведения см. в разделе Требование повторной аутентификации для чувствительных функций.

    Когда инициировать повторную аутентификацию¶

    • Подозрительная активность учётной записи При возникновении необычных паттернов входа, смене IP-адреса или регистрации новых устройств
    • Восстановление учётной записи После сброса пользователем пароля или изменения чувствительных данных учётной записи
    • Критические действия Для высокорисковых действий, таких как изменение платёжных реквизитов или добавление новых доверенных устройств

    Механизмы повторной аутентификации¶

    • Адаптивная аутентификация Использование моделей аутентификации на основе рисков, адаптирующихся к поведению и контексту пользователя
    • Многофакторная аутентификация (MFA) Требование дополнительного уровня верификации для чувствительных действий или событий
    • Верификация с вызовом Запрос у пользователей подтверждения личности с помощью контрольного вопроса или вторичного метода

    Рекомендации по реализации¶

    • Минимизация трений для пользователя Убедитесь, что повторная аутентификация не нарушает пользовательский опыт без необходимости
    • Контекстно-зависимые решения Принимайте решения о повторной аутентификации на основе контекста (например, геолокация, тип устройства, предыдущие паттерны)
    • Безопасное управление сессиями Инвалидируйте сессии после повторной аутентификации и ротируйте токены — см. Шпаргалку OWASP по управлению сессиями

    Рассмотрение строгой аутентификации транзакций¶

    Некоторые приложения должны использовать второй фактор для проверки возможности пользователя выполнять чувствительные операции. Дополнительные сведения см. в шпаргалке по авторизации транзакций.

    TLS-аутентификация клиента¶

    TLS-аутентификация клиента, также известная как двусторонняя TLS-аутентификация, предполагает, что и браузер, и сервер отправляют свои соответствующие TLS-сертификаты в процессе TLS-рукопожатия. Так же, как вы можете подтвердить подлинность сервера, используя сертификат и обращаясь к проверяемому Центру Сертификации (CA), сервер может аутентифицировать пользователя, получив сертификат от клиента и проверив его у стороннего CA или собственного CA. Для этого сервер должен предоставить пользователю сертификат, сгенерированный специально для него, назначив значения субъекту, чтобы они могли использоваться для определения того, какой пользователь должен быть подтверждён сертификатом. Пользователь устанавливает сертификат в браузере и теперь использует его для веб-сайта.

    Этот подход уместен, когда:

    • Допустимо (или даже предпочтительно), что пользователь имеет доступ к веб-сайту только с одного компьютера/браузера.
    • Пользователь не пугается процедуры установки TLS-сертификатов в браузере, или найдётся кто-то, вероятно из ИТ-поддержки, кто сделает это за пользователя.
    • Веб-сайт требует дополнительного уровня безопасности.
    • Это также хорошо, когда веб-сайт предназначен для интранета компании или организации.

    Как правило, не рекомендуется использовать этот метод для широко и публично доступных веб-сайтов с обычными пользователями. Например, не стоит реализовывать это для такого веб-сайта, как Facebook. Хотя этот метод может предотвратить необходимость ввода пользователем пароля (тем самым защищая от среднестатистического кейлоггера), всё же считается хорошей идеей использовать как пароль, так и TLS-аутентификацию клиента вместе.

    Кроме того, если клиент находится за корпоративным прокси-сервером, выполняющим расшифровку SSL/TLS, это нарушит аутентификацию по сертификату, если сайт не разрешён на прокси.

    Дополнительные сведения см.: TLS-рукопожатие с аутентификацией клиента

    Аутентификация и сообщения об ошибках¶

    Неправильно реализованные сообщения об ошибках при аутентификации могут использоваться для перечисления идентификаторов пользователей и паролей. Приложение должно отвечать (как по HTTP, так и в HTML) в обобщённой манере.

    Ответы при аутентификации¶

    При использовании любого из механизмов аутентификации (вход, сброс пароля или восстановление пароля) приложение должно возвращать обобщённое сообщение об ошибке независимо от того:

    • Неверен ли идентификатор пользователя или пароль.
    • Не существует ли учётная запись.
    • Заблокирована ли или отключена учётная запись.

    Функция регистрации учётной записи также должна приниматься во внимание, и тот же подход с обобщённым сообщением об ошибке может применяться в случае, когда пользователь уже существует.

    Цель — предотвратить создание фактора несоответствия, позволяющего злоумышленнику выполнять перечисление пользователей в приложении.

    Интересно отметить, что сама бизнес-логика может привносить фактор несоответствия, связанный со временем обработки. В зависимости от реализации время обработки может существенно различаться в зависимости от случая (успех против неудачи), что позволяет злоумышленнику проводить атаку по времени (дельта в несколько секунд, например).

    Пример на псевдокоде для функции входа:

    • Первая реализация с подходом «быстрый выход»
    IF USER_EXISTS(username) THEN
    password_hash=HASH(password)
    IS_VALID=LOOKUP_CREDENTIALS_IN_STORE(username, password_hash)
    IF NOT IS_VALID THEN
        RETURN Error("Invalid Username or Password!")
    ENDIF
ELSE
   RETURN Error("Invalid Username or Password!")
ENDIF

    Ясно видно, что если пользователь не существует, приложение немедленно выдаёт ошибку. Иначе, когда пользователь существует, а пароль неверен, очевидно, что перед ошибкой будет больше обработки. В результате время ответа будет разным для одной и той же ошибки, что позволяет злоумышленнику различать неверное имя пользователя и неверный пароль.

    • Вторая реализация без использования подхода «быстрый выход»:
    password_hash=HASH(password)
IS_VALID=LOOKUP_CREDENTIALS_IN_STORE(username, password_hash)
IF NOT IS_VALID THEN
   RETURN Error("Invalid Username or Password!")
ENDIF

    Этот код проходит одинаковый процесс независимо от пользователя или пароля, что позволяет приложению возвращать ответ приблизительно за одинаковое время.

    Проблема возврата обобщённого сообщения об ошибке пользователю является вопросом пользовательского опыта (UX). Законный пользователь может чувствовать замешательство от обобщённых сообщений, что делает использование приложения трудным, и может после нескольких попыток покинуть приложение из-за его сложности. Решение о возврате обобщённого сообщения об ошибке может приниматься исходя из критичности приложения и его данных. Например, для критических приложений команда может решить, что при сценарии сбоя пользователь всегда будет перенаправляться на страницу поддержки и будет возвращаться обобщённое сообщение об ошибке.

    Что касается перечисления пользователей, защита от атак перебором также эффективна, поскольку она предотвращает проведение злоумышленником перечисления в масштабе. Использование CAPTCHA может применяться для функции, для которой нельзя возвращать обобщённое сообщение об ошибке, поскольку необходимо сохранить пользовательский опыт.

    Примеры неверных и правильных ответов¶
    Вход¶

    Примеры неверных ответов:

    • "Login for User foo: invalid password."
    • "Login failed, invalid user ID."
    • "Login failed; account disabled."
    • "Login failed; this user is not active."

    Пример правильного ответа:

    • "Login failed; Invalid user ID or password."
    Восстановление пароля¶

    Примеры неверных ответов:

    • "We just sent you a password reset link."
    • "This email address doesn't exist in our database."

    Пример правильного ответа:

    • "If that email address is in our database, we will send you an email to reset your password."
    Создание учётной записи¶

    Примеры неверных ответов:

    • "This user ID is already in use."
    • "Welcome! You have signed up successfully."

    Пример правильного ответа:

    • "A link to activate your account has been emailed to the address provided."
    Коды ошибок и URL¶

    Приложение может возвращать различный HTTP-код ошибки в зависимости от результата попытки аутентификации. Оно может отвечать 200 при положительном результате и 403 при отрицательном. Хотя пользователю отображается обобщённая страница ошибки, HTTP-код ответа может отличаться, что может раскрывать информацию о том, существует ли учётная запись.

    Раскрытие ошибки также может использоваться как фактор несоответствия, обратитесь к шпаргалке по обработке ошибок относительно глобальной обработки различных ошибок в приложении.

    Защита от автоматических атак¶

    Существует ряд различных типов автоматических атак, которые злоумышленники могут использовать для компрометации учётных записей пользователей. Наиболее распространённые типы перечислены ниже:

    Тип атаки Описание
    Перебор (Brute Force) Тестирование нескольких паролей из словаря или другого источника против одной учётной записи.
    Подстановка учётных данных (Credential Stuffing) Тестирование пар имя пользователя/пароль, полученных в результате взлома другого сайта.
    Распыление паролей (Password Spraying) Тестирование одного слабого пароля против большого количества различных учётных записей.

    Для защиты от этих атак могут быть реализованы различные защитные механизмы. Во многих случаях эти защитные меры не обеспечивают полную защиту, однако при реализации ряда из них в рамках глубокоэшелонированной защиты можно достичь разумного уровня безопасности.

    Следующие разделы сосредоточены в первую очередь на предотвращении атак перебором, хотя эти средства контроля также могут быть эффективны против других типов атак. Дополнительные рекомендации по защите от подстановки учётных данных и распыления паролей см. в шпаргалке по предотвращению подстановки учётных данных.

    Многофакторная аутентификация¶

    Многофакторная аутентификация (MFA) является наилучшей защитой от большинства атак, связанных с паролями, включая атаки перебором: по данным анализа Microsoft, она позволила бы предотвратить 99,9% компрометаций учётных записей. Поэтому её следует внедрять везде, где это возможно; однако, в зависимости от аудитории приложения, принудительное использование MFA может быть непрактичным или нецелесообразным.

    Шпаргалка по многофакторной аутентификации содержит дополнительные рекомендации по реализации MFA.

    Ограничение частоты входа¶

    Ограничение частоты входа (Login Throttling) — это протокол, используемый для предотвращения чрезмерного числа попыток злоумышленника угадать пароль с помощью обычных интерактивных средств, он включает следующие меры контроля:

    • Максимальное количество попыток.
    Блокировка учётной записи¶

    Наиболее распространённая защита от этих атак — реализация блокировки учётной записи, которая предотвращает дальнейшие попытки входа на определённый период после определённого числа неудачных входов.

    Счётчик неудачных входов должен быть связан с самой учётной записью, а не с IP-адресом источника, чтобы предотвратить попытки входа злоумышленника с большого числа различных IP-адресов. Существует ряд различных факторов, которые следует учитывать при реализации политики блокировки учётной записи для нахождения баланса между безопасностью и удобством использования:

    • Количество неудачных попыток до блокировки учётной записи (порог блокировки).
    • Временной период, в течение которого должны произойти эти попытки (окно наблюдения).
    • Продолжительность блокировки учётной записи (длительность блокировки).

    Вместо реализации фиксированной длительности блокировки (например, десять минут) некоторые приложения используют экспоненциальную блокировку, при которой длительность блокировки начинается с очень короткого периода (например, одна секунда), но удваивается после каждой неудачной попытки входа.

    • Время задержки после каждой блокировки учётной записи (максимум 2-3, после чего постоянная блокировка учётной записи).

    При разработке системы блокировки учётных записей необходимо принять меры, чтобы предотвратить её использование для атак типа «отказ в обслуживании» путём блокировки учётных записей других пользователей. Один из способов — разрешить использование функции «забытого пароля» для входа в систему, даже если учётная запись заблокирована.

    CAPTCHA¶

    Использование эффективной CAPTCHA может помочь предотвратить автоматические попытки входа в учётные записи. Однако многие реализации CAPTCHA имеют уязвимости, позволяющие их решать с помощью автоматических методов или передавать на аутсорс сервисам, способным их решать. Поэтому использование CAPTCHA следует рассматривать как элемент глубокоэшелонированной защиты, делающий атаки перебором более трудоёмкими и дорогостоящими, а не как превентивную меру.

    Более удобным для пользователя может быть требование решить CAPTCHA только после небольшого числа неудачных попыток входа, а не с самого первого входа.

    Контрольные вопросы и памятные слова¶

    Добавление контрольного вопроса или памятного слова также может помочь защититься от автоматических атак, особенно когда пользователю предлагается ввести несколько случайно выбранных символов из слова. Следует отметить, что это не является многофакторной аутентификацией, поскольку оба фактора являются одинаковыми (то, что вы знаете). Кроме того, контрольные вопросы часто слабые и имеют предсказуемые ответы, поэтому их необходимо тщательно выбирать. Шпаргалка по выбору и использованию контрольных вопросов содержит дополнительные рекомендации по этой теме.

    Журналирование и мониторинг¶

    Включите журналирование и мониторинг функций аутентификации для обнаружения атак/сбоев в режиме реального времени

    • Убедитесь, что все сбои регистрируются в журнале и проверяются
    • Убедитесь, что все сбои паролей регистрируются в журнале и проверяются
    • Убедитесь, что все блокировки учётных записей регистрируются в журнале и проверяются

    Использование протоколов аутентификации без пароля¶

    Хотя аутентификация с помощью комбинации имени пользователя, пароля и многофакторной аутентификации считается в целом безопасной, существуют случаи использования, когда это не считается лучшим вариантом или даже безопасным. Примерами являются сторонние приложения, желающие подключиться к веб-приложению — с мобильного устройства, другого веб-сайта, рабочего стола или в иных ситуациях. В таких случаях НЕ считается безопасным позволять стороннему приложению хранить комбинацию пользователь/пароль, поскольку это расширяет поверхность атаки в их руки, что находится вне вашего контроля. Для этого и других случаев использования существует несколько протоколов аутентификации, способных защитить вас от раскрытия данных пользователей злоумышленникам.

    OAuth 2.0 и 2.1¶

    OAuth — это фреймворк авторизации для делегированного доступа к API. См. также: Шпаргалка по OAuth 2.0.

    Примечание: OAuth 2.1 — это черновой вариант рабочей группы IETF, объединяющий OAuth 2.0 и широко принятые лучшие практики, и предназначен для замены RFC 6749/6750; рекомендации в данной шпаргалке применимы как к OAuth 2.0, так и к OAuth 2.1. Ссылки: draft-ietf-oauth-v2-1-13, oauth.net/2.1

    OpenID Connect (OIDC)¶

    OpenID Connect 1.0 (OIDC) — это идентификационный уровень поверх OAuth. Он определяет, как клиент (полагающаяся сторона) верифицирует идентичность конечного пользователя с использованием ID Token (подписанного JWT) и как получать пользовательские claims совместимым способом. Используйте OIDC для аутентификации/SSO; используйте OAuth для авторизации к API.

    Рекомендации по реализации OIDC¶

    • Проверяйте ID Token на стороне полагающейся стороны: издатель (iss), аудитория (aud), подпись (по JWKs провайдера), срок действия (exp).
    • Предпочитайте хорошо поддерживаемые библиотеки/SDK и конечные точки обнаружения провайдера/JWKS.
    • Используйте конечную точку UserInfo, когда требуются дополнительные claims помимо ID Token.

    Избегайте путаницы: OpenID 2.0 ("OpenID") был отдельным, устаревшим протоколом аутентификации, который заменён OpenID Connect и считается устаревшим. Новые системы не должны реализовывать OpenID 2.0. Ссылки: OpenID Foundation — устаревшие библиотеки OpenID 2.0, миграция с OpenID 2.0 на OIDC

    SAML¶

    Security Assertion Markup Language (SAML) часто рассматривается как конкурент OpenID. Наиболее рекомендуемой версией является 2.0, поскольку она очень функционально полна и обеспечивает высокий уровень безопасности. Как и OpenID, SAML использует провайдеры идентичности, но, в отличие от OpenID, он основан на XML и обеспечивает большую гибкость. SAML основан на перенаправлениях браузера, которые передают XML-данные. Кроме того, SAML инициируется не только поставщиком сервиса; он также может быть инициирован провайдером идентичности. Это позволяет пользователю перемещаться по различным порталам, оставаясь при этом аутентифицированным без необходимости что-либо делать, делая процесс прозрачным.

    Хотя OpenID занял большую часть потребительского рынка, SAML часто является выбором для корпоративных приложений, поскольку существует мало провайдеров идентичности OpenID, которые считаются корпоративного класса (то есть способ, которым они проверяют идентичность пользователя, не соответствует высоким стандартам, требуемым для корпоративной идентичности). Чаще всего SAML используется внутри сайтов интранета, иногда даже с использованием сервера из интранета в качестве провайдера идентичности.

    В последние годы такие приложения, как SAP ERP и SharePoint (SharePoint с использованием Active Directory Federation Services 2.0), решили использовать аутентификацию SAML 2.0 в качестве часто предпочтительного метода для реализаций единого входа (SSO) при необходимости корпоративной федерации для веб-сервисов и веб-приложений.

    См. также: Шпаргалка по безопасности SAML

    FIDO¶

    Альянс Fast Identity Online (FIDO) создал два протокола для упрощения онлайн-аутентификации: протокол Universal Authentication Framework (UAF) и протокол Universal Second Factor (U2F). В то время как UAF фокусируется на аутентификации без пароля, U2F позволяет добавить второй фактор к существующей аутентификации на основе пароля. Оба протокола основаны на модели запрос-ответ с криптографией с открытым ключом.

    UAF использует существующие технологии безопасности, присутствующие на устройствах для аутентификации, включая датчики отпечатков пальцев, камеры (биометрия лица), микрофоны (голосовая биометрия), доверенные среды выполнения (TEE), защищённые элементы (SE) и другие. Протокол разработан для подключения этих возможностей устройства к общей системе аутентификации. UAF работает как с нативными приложениями, так и с веб-приложениями.

    U2F дополняет аутентификацию на основе пароля с использованием аппаратного токена (обычно USB), который хранит криптографические ключи аутентификации и использует их для подписи. Пользователь может использовать один и тот же токен в качестве второго фактора для нескольких приложений. U2F работает с веб-приложениями. Он обеспечивает защиту от фишинга, используя URL веб-сайта для поиска хранимого ключа аутентификации.

    FIDO2: FIDO2 и WebAuthn, охватывающие предыдущие стандарты (UAF/U2F), являются основой современной технологии Passkeys. Passkeys позволяют пользователям безопасно входить в систему, используя локальную верификацию пользователя (например, биометрию или PIN-коды устройства) с поддержкой облачной синхронизации между устройствами. Эта технология широко поддерживается основными платформами. (Windows Hello/Mac Touch ID)

    Менеджеры паролей¶

    Менеджеры паролей — это программы, плагины для браузера или веб-сервисы, автоматизирующие управление большим количеством различных учётных данных. Большинство менеджеров паролей имеют функциональность, позволяющую пользователям легко использовать их на веб-сайтах: (a) путём вставки паролей в форму входа -- или -- (b) путём имитации ввода пользователем.

    Веб-приложения не должны усложнять работу менеджеров паролей больше, чем необходимо, соблюдая следующие рекомендации:

    • Используйте стандартные HTML-формы для ввода имени пользователя и пароля с соответствующими атрибутами type.
    • Избегайте страниц входа на основе плагинов (таких как Flash или Silverlight).
    • Реализуйте разумную максимальную длину пароля — не менее 64 символов, как обсуждается в разделе о реализации требований к надёжности пароля.
    • Разрешите использование любых печатаемых символов в паролях.
    • Разрешите пользователям вставлять данные в поля имени пользователя, пароля и MFA.
    • Разрешите пользователям переключаться между полями имени пользователя и пароля с помощью одного нажатия клавиши Tab.

    Смена зарегистрированного адреса электронной почты пользователя¶

    Адреса электронной почты пользователей часто меняются. Для обработки таких ситуаций в системе рекомендуется следующий процесс:

    Примечание: Процесс менее строгий при наличии многофакторной аутентификации, поскольку доказательство личности более надёжно, чем опора исключительно на пароль.

    Рекомендуемый процесс, если у пользователя ВКЛЮЧЕНА многофакторная аутентификация¶

    1. Подтвердите действительность куки/токена аутентификации пользователя. Если недействителен — отобразите экран входа.
    2. Опишите пользователю процесс смены зарегистрированного адреса электронной почты.
    3. Попросите пользователя отправить предлагаемый новый адрес электронной почты, убедившись, что он соответствует правилам системы.
    4. Запросите использование многофакторной аутентификации для верификации личности.
    5. Сохраните предлагаемый новый адрес электронной почты как ожидающее изменение.
    6. Создайте и сохраните два ограниченных по времени одноразовых кода для (a) уведомления системных администраторов и (b) подтверждения пользователем.

    7. Отправьте два сообщения электронной почты со ссылками, включающими эти коды:

      • Информационное сообщение на текущий адрес, предупреждающее пользователя о предстоящей смене и предоставляющее ссылку для сообщения о неожиданной активности.

      • Сообщение, требующее подтверждения, на предлагаемый новый адрес, предлагающее пользователю подтвердить смену и предоставляющее ссылку для неожиданных ситуаций.

    8. Обработайте ответы по ссылкам соответствующим образом.

    Рекомендуемый процесс, если у пользователя НЕ ВКЛЮЧЕНА многофакторная аутентификация¶

    1. Подтвердите действительность куки/токена аутентификации пользователя. Если недействителен — отобразите экран входа.
    2. Опишите пользователю процесс смены зарегистрированного адреса электронной почты.
    3. Попросите пользователя отправить предлагаемый новый адрес электронной почты, убедившись, что он соответствует правилам системы.
    4. Запросите текущий пароль пользователя для верификации личности.
    5. Сохраните предлагаемый новый адрес электронной почты как ожидающее изменение.
    6. Создайте и сохраните три ограниченных по времени одноразовых кода для уведомления системных администраторов, подтверждения пользователем и дополнительного шага для использования пароля.

    7. Отправьте два сообщения электронной почты со ссылками на эти коды:

      • Сообщение, требующее подтверждения, на текущий адрес, предлагающее пользователю подтвердить смену и предоставляющее ссылку для неожиданных ситуаций.

      • Отдельное сообщение, требующее подтверждения, на предлагаемый новый адрес, предлагающее пользователю подтвердить смену и предоставляющее ссылку для неожиданных ситуаций.

    8. Обработайте ответы по ссылкам соответствующим образом.

    Примечания к вышеуказанным процессам¶

    • Стоит отметить, что Google применяет другой подход для учётных записей, защищённых только паролем — где текущий адрес электронной почты получает только информационное сообщение. Этот метод несёт риски и требует бдительности пользователя.

    • Регулярное обучение по социальной инженерии крайне важно. Системные администраторы и сотрудники службы поддержки должны быть обучены следовать предписанному процессу и распознавать атаки социальной инженерии и реагировать на них. Обратитесь к руководству CISA "Avoiding Social Engineering and Phishing Attacks".

    Адаптивная аутентификация или аутентификация на основе рисков¶

    Одной из функций более продвинутых приложений является возможность требовать различные этапы аутентификации в зависимости от различных атрибутов среды и контекста (включая, помимо прочего, чувствительность данных, к которым запрашивается доступ, время суток, местоположение пользователя, IP-адрес или цифровой отпечаток устройства).

    Например, приложение может требовать MFA при первом входе с определённого устройства, но не при последующих входах с этого устройства. Альтернативно, решение для единого входа может аутентифицировать пользователя и позволить ему оставаться в системе в течение дня, но требовать повторной аутентификации при попытке доступа к странице профиля.

    Другой вариант — противоположный подход, при котором приложение разрешает низкорисковый доступ только с тем, что идентифицирует устройство (например, цифровой отпечаток конкретного мобильного устройства, постоянный куки и цифровой отпечаток браузера и т.д. с предыдущего IP-адреса), а затем постепенно требует более строгой аутентификации для более чувствительных операций. Например, разрешить кому-то активировать что-то для просмотра текущего баланса банковского счёта, но не номера счёта или чего-либо ещё. Если им нужно просмотреть транзакции, приложение проводит их через базовый уровень аутентификации, а если они хотят совершить движение денег, требуется MFA.

    Вопросы, которые следует рассмотреть при реализации подобного механизма:

    • Соответствуют ли внедряемые политики корпоративным политикам и особенно любым нормативным требованиям?
    • Какие атрибуты пользователя или устройства (IP, геолокация, цифровой отпечаток устройства, время суток, поведенческая биометрия и т.д.) будут отслеживаться в начале сессии?
    • Какие из этих сигналов необходимо обновлять в течение активной сессии и с какой периодичностью?
    • Как будет обеспечиваться точность каждого сигнала и обрабатываться отсутствующие или низкоуверенные данные?
    • Какая модель оценки рисков (веса, пороги, ML, на основе правил, гибридная) будет преобразовывать исходные сигналы в уровень риска?
    • Где будет работать модель (на периферии, в API-шлюзе, централизованном сервисе) и каков допустимый уровень задержки?
    • Какое действие соответствует каждому уровню риска (разрешить, CAPTCHA, MFA с подтверждением, заблокировать, отозвать сессию)?
    • Какие сообщения для пользователей и коды ошибок будут сопровождать каждое действие?
    • На каких именно уровнях кода или платформы будет вызываться движок оценки рисков (контроллер входа, промежуточное ПО, API-шлюз, сервисная сеть)?
    • Как решения будут распространяться согласованно между веб-, мобильными и API-клиентами?
    • Как изменять, расширять или отзывать токены/куки при эскалации проверки рисков в середине сессии?
    • Как синхронизировать состояние между несколькими одновременно работающими устройствами или вкладками браузера?
    • Какой мониторинг и оповещения будут реализованы для потенциально подозрительной активности, включая уведомление пользователя.
