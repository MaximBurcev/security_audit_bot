    Шпаргалка по безопасности Docker¶

    Введение¶

    Docker — наиболее популярная технология контейнеризации. При правильном использовании она может повысить уровень безопасности по сравнению с запуском приложений непосредственно на хост-системе. Однако некоторые неправильные конфигурации могут снизить уровень безопасности или привести к появлению новых уязвимостей.

    Цель этой шпаргалки — предоставить простой список типичных ошибок безопасности и лучших практик для защиты контейнеров Docker.

    Правила¶

    ПРАВИЛО #0 - Поддерживайте хост и Docker в актуальном состоянии¶

    Для защиты от известных уязвимостей выхода из контейнера, таких как Leaky Vessels, которые обычно позволяют злоумышленнику получить root-доступ к хосту, крайне важно поддерживать хост и Docker в актуальном состоянии. Это включает регулярное обновление ядра хоста, а также Docker Engine.

    Это связано с тем, что контейнеры совместно используют ядро хоста. Если ядро хоста уязвимо, контейнеры также уязвимы. Например, эксплойт повышения привилегий ядра Dirty COW, выполненный внутри хорошо изолированного контейнера, всё равно приведёт к получению root-доступа на уязвимом хосте.

    ПРАВИЛО #1 - Не открывайте доступ к сокету демона Docker (даже для контейнеров)¶

    Сокет Docker /var/run/docker.sock — это UNIX-сокет, который прослушивает Docker. Это основная точка входа для Docker API. Владельцем этого сокета является root. Предоставление кому-либо доступа к нему равносильно предоставлению неограниченного root-доступа к хосту.

    Не включайте TCP-сокет демона Docker. Если вы запускаете демон Docker с флагом -H tcp://0.0.0.0:XXX или аналогичным, вы открываете незашифрованный и неаутентифицированный прямой доступ к демону Docker. Если хост подключён к интернету, это означает, что демон Docker на вашем компьютере может использовать любой пользователь из интернета. Если вам действительно очень нужно это сделать, необходимо защитить его. Проверьте, как это сделать, в официальной документации Docker.

    Не открывайте доступ к /var/run/docker.sock для других контейнеров. Если вы запускаете docker-образ с флагом -v /var/run/docker.sock://var/run/docker.sock или аналогичным, вам следует изменить это. Помните, что монтирование сокета в режиме только для чтения — не решение, а лишь усложнение эксплуатации. Эквивалент в файле docker compose выглядит следующим образом:

    volumes:
  - "/var/run/docker.sock:/var/run/docker.sock"

    ПРАВИЛО #2 - Задайте пользователя¶

    Настройка контейнера для работы под непривилегированным пользователем — лучший способ предотвратить атаки повышения привилегий. Это можно сделать тремя способами:

    1. Во время выполнения с помощью опции -u команды docker run, например:
    docker run -u 4000 alpine
    1. Во время сборки. Просто добавьте пользователя в Dockerfile и используйте его. Например:
    FROM alpine
RUN groupadd -r myuser && useradd -r -g myuser myuser
#    <ЗДЕСЬ ВЫПОЛНИТЕ ВСЁ НЕОБХОДИМОЕ ОТ ИМЕНИ ROOT, НАПРИМЕР УСТАНОВКУ ПАКЕТОВ>
USER myuser
    1. Включите поддержку пространств имён пользователей (--userns-remap=default) в демоне Docker

    Дополнительную информацию по этой теме можно найти в официальной документации Docker. Для дополнительной безопасности можно также запустить в безкорневом режиме, который обсуждается в Правиле #11.

    В Kubernetes это можно настроить в Security Context с помощью поля runAsUser с идентификатором пользователя, например:

    apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: example
      image: gcr.io/google-samples/node-hello:1.0
      securityContext:
        runAsUser: 4000 # <-- Идентификатор пользователя пода

    Как администратор кластера Kubernetes, вы можете настроить усиленные параметры по умолчанию с помощью уровня Restricted со встроенным контроллером допуска Pod Security. Если требуется большая настраиваемость, рассмотрите использование Admission Webhooks или сторонней альтернативы.

    ПРАВИЛО #3 - Ограничивайте возможности (предоставляйте только конкретные возможности, необходимые контейнеру)¶

    Возможности ядра Linux — набор привилегий, которые могут использоваться привилегированными процессами. По умолчанию Docker работает только с частью этих возможностей. Вы можете изменить это: убрать некоторые возможности (с помощью --cap-drop) для усиления защиты контейнеров или добавить некоторые возможности (с помощью --cap-add), если это необходимо. Не запускайте контейнеры с флагом --privileged — он добавит ВСЕ возможности ядра Linux в контейнер.

    Наиболее безопасная настройка — убрать все возможности с помощью --cap-drop all, а затем добавить только необходимые. Например:

    docker run --cap-drop all --cap-add CHOWN alpine

    И помните: не запускайте контейнеры с флагом --privileged!!!

    В Kubernetes это можно настроить в Security Context с помощью поля capabilities, например:

    apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: example
      image: gcr.io/google-samples/node-hello:1.0
      securityContext:
        capabilities:
          drop:
            - ALL
          add: ["CHOWN"]

    Как администратор кластера Kubernetes, вы можете настроить усиленные параметры по умолчанию с помощью уровня Restricted со встроенным контроллером допуска Pod Security. Если требуется большая настраиваемость, рассмотрите использование Admission Webhooks или сторонней альтернативы.

    ПРАВИЛО #4 - Предотвращайте повышение привилегий внутри контейнера¶

    Всегда запускайте docker-образы с флагом --security-opt=no-new-privileges для предотвращения повышения привилегий. Это не позволит контейнеру получать новые привилегии через бинарные файлы setuid или setgid.

    В Kubernetes это можно настроить в Security Context с помощью поля allowPrivilegeEscalation, например:

    apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: example
      image: gcr.io/google-samples/node-hello:1.0
      securityContext:
        allowPrivilegeEscalation: false

    Как администратор кластера Kubernetes, вы можете настроить усиленные параметры по умолчанию с помощью уровня Restricted со встроенным контроллером допуска Pod Security. Если требуется большая настраиваемость, рассмотрите использование Admission Webhooks или сторонней альтернативы.

    ПРАВИЛО #5 - Учитывайте взаимодействие между контейнерами¶

    Межконтейнерное взаимодействие (icc) включено по умолчанию, что позволяет всем контейнерам общаться друг с другом через мостовую сеть docker0. Вместо использования флага --icc=false для демона Docker, который полностью отключает межконтейнерное взаимодействие, рассмотрите определение конкретных конфигураций сети. Это можно сделать путём создания пользовательских сетей Docker и указания, какие контейнеры должны быть к ним подключены. Такой подход обеспечивает более детальный контроль над взаимодействием контейнеров.

    Подробное руководство по настройке сетей Docker для взаимодействия контейнеров см. в документации Docker.

    В средах Kubernetes Network Policies можно использовать для определения правил, регулирующих взаимодействие подов в кластере. Эти политики предоставляют надёжную основу для контроля того, как поды взаимодействуют друг с другом и с другими сетевыми конечными точками. Кроме того, Network Policy Editor упрощает создание и управление сетевыми политиками, делая более доступным определение сложных правил сети через удобный интерфейс.

    ПРАВИЛО #6 - Используйте модули безопасности Linux (seccomp, AppArmor или SELinux) для безопасности во время выполнения¶

    Прежде всего, не отключайте профиль безопасности по умолчанию! Всегда начинайте с профиля Docker или вашего хоста по умолчанию в качестве базы.

    Рекомендации по профилям безопасности:

    • Seccomp: Ограничьте системные вызовы до минимально необходимых для вашего контейнера. Используйте профиль seccomp Docker по умолчанию в качестве отправной точки и настраивайте его для каждой рабочей нагрузки. Docker Seccomp

    • AppArmor: Применяйте профили AppArmor для каждого контейнера для обеспечения обязательного контроля доступа. Docker AppArmor

    • SELinux: Включите SELinux на хосте и убедитесь, что контейнеры правильно помечены. Применяйте политики SELinux для предотвращения несанкционированного доступа к ресурсам хоста. Руководство SELinux для Docker

    Улучшения безопасности во время выполнения:

    • Поведенческий мониторинг: Используйте инструменты, такие как Falco, Tetragon или Cilium eBPF, для обнаружения неожиданной или вредоносной активности контейнеров. Примеры: неожиданные вызовы exec, попытки повышения привилегий, необычные сетевые соединения.

    • Обнаружение аномалий: Непрерывно отслеживайте процессы контейнеров, изменения файловой системы и сетевую активность для выявления аномальных паттернов в режиме реального времени.

    • Контекст безопасности Kubernetes: Настройте поды или контейнеры с профилями seccomp и AppArmor в Kubernetes. Настройка Security Context для пода или контейнера

    ПРАВИЛО #7 - Ограничивайте ресурсы (память, CPU, файловые дескрипторы, процессы, перезапуски)¶

    Лучший способ избежать DoS-атак — ограничить ресурсы. Вы можете ограничить память, CPU, максимальное количество перезапусков (--restart=on-failure:<number_of_restarts>), максимальное количество файловых дескрипторов (--ulimit nofile=<number>) и максимальное количество процессов (--ulimit nproc=<number>).

    Дополнительную информацию об ulimits см. в документации

    Это также можно сделать для Kubernetes: Назначение ресурсов памяти контейнерам и подам, Назначение ресурсов CPU контейнерам и подам и Назначение расширенных ресурсов контейнеру

    ПРАВИЛО #8 - Настройте файловую систему и тома в режим только для чтения¶

    Запускайте контейнеры с файловой системой только для чтения с помощью флага --read-only. Например:

    docker run --read-only alpine sh -c 'echo "whatever" > /tmp'

    Если приложению внутри контейнера нужно временно что-то сохранить, используйте флаг --read-only совместно с --tmpfs следующим образом:

    docker run --read-only --tmpfs /tmp alpine sh -c 'echo "whatever" > /tmp/file'

    Эквивалент в файле compose.yml Docker Compose:

    version: "3"
services:
  alpine:
    image: alpine
    read_only: true

    Эквивалент в Kubernetes в Security Context:

    apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: example
      image: gcr.io/google-samples/node-hello:1.0
      securityContext:
        readOnlyRootFilesystem: true

    Кроме того, если том монтируется только для чтения, монтируйте его как только для чтения. Это можно сделать, добавив :ro к -v следующим образом:

    docker run -v volume-name:/path/in/container:ro alpine

    Или с помощью опции --mount:

    docker run --mount source=volume-name,destination=/path/in/container,readonly alpine

    ПРАВИЛО #9 - Интегрируйте инструменты сканирования контейнеров в CI/CD-конвейер¶

    CI/CD-конвейеры — важнейшая часть жизненного цикла разработки программного обеспечения и должны включать различные проверки безопасности, такие как проверки линтера, статический анализ кода и сканирование контейнеров.

    Многих проблем можно избежать, следуя некоторым лучшим практикам при написании Dockerfile. Однако добавление линтера безопасности как шага в конвейер сборки может существенно помочь в предотвращении дальнейших проблем. Некоторые часто проверяемые моменты:

    • Убедитесь, что директива USER указана
    • Убедитесь, что версия базового образа зафиксирована
    • Убедитесь, что версии пакетов ОС зафиксированы
    • Избегайте использования ADD в пользу COPY
    • Избегайте curl bashing в директивах RUN

    ПРАВИЛО #10 - Поддерживайте уровень журналирования демона Docker на уровне info¶

    По умолчанию демон Docker настроен с базовым уровнем журналирования info. Это можно проверить, посмотрев в файл конфигурации демона /etc/docker/daemon.json на наличие ключа log-level. Если ключ отсутствует, уровень журналирования по умолчанию — info. Кроме того, если демон Docker запущен с опцией --log-level, значение ключа log-level в файле конфигурации будет переопределено. Чтобы проверить, запущен ли демон Docker с другим уровнем журналирования, можно использовать следующую команду:

    ps aux | grep '[d]ockerd.*--log-level' | awk '{for(i=1;i<=NF;i++) if ($i ~ /--log-level/) print $i}'

    Установка подходящего уровня журналирования настраивает демон Docker для записи событий, которые вы захотите проанализировать позднее. Базовый уровень журналирования info и выше будет фиксировать все журналы, кроме отладочных. Если это не требуется, не следует запускать демон Docker на уровне журналирования debug.

    Правило #11 - Запускайте Docker в безкорневом режиме¶

    Безкорневой режим обеспечивает работу демона Docker и контейнеров под непривилегированным пользователем. Это означает, что даже если злоумышленник вырвется из контейнера, у него не будет root-привилегий на хосте, что существенно сокращает поверхность атаки. Это отличается от режима userns-remap, где демон по-прежнему работает с root-привилегиями.

    Оцените конкретные требования и состояние безопасности вашей среды, чтобы определить, является ли безкорневой режим лучшим выбором для вас. Для сред, где безопасность является первостепенной задачей и ограничения безкорневого режима не мешают операционным требованиям, это настоятельно рекомендуемая конфигурация. В качестве альтернативы рассмотрите использование Podman вместо Docker.

    Безкорневой режим позволяет запускать демон Docker и контейнеры не от имени root для снижения потенциальных уязвимостей в демоне и среде выполнения контейнеров. Безкорневой режим не требует root-привилегий даже во время установки демона Docker при соблюдении предварительных условий.

    Подробнее о безкорневом режиме и его ограничениях, инструкции по установке и использованию см. на странице документации Docker.

    ПРАВИЛО #12 - Используйте Docker Secrets для управления конфиденциальными данными¶

    Docker Secrets предоставляет безопасный способ хранения и управления конфиденциальными данными, такими как пароли, токены и SSH-ключи. Использование Docker Secrets помогает избежать раскрытия конфиденциальных данных в образах контейнеров или в командах во время выполнения.

    docker secret create my_secret /path/to/super-secret-data.txt
docker service create --name web --secret my_secret nginx:latest

    Или для Docker Compose:

    version: "3.8"
secrets:
  my_secret:
    file: ./super-secret-data.txt
services:
  web:
    image: nginx:latest
    secrets:
      - my_secret

    Хотя Docker Secrets в целом обеспечивает безопасный способ управления конфиденциальными данными в средах Docker, этот подход не рекомендуется для Kubernetes, где секреты по умолчанию хранятся в открытом виде. В Kubernetes рассмотрите дополнительные меры безопасности, такие как шифрование etcd или сторонние инструменты. Подробнее см. в Шпаргалке по управлению секретами.

    ПРАВИЛО #13 - Усиливайте безопасность цепочки поставок¶

    Развивая принципы Правила #9, усиление безопасности цепочки поставок предполагает реализацию дополнительных мер для защиты всего жизненного цикла образов контейнеров от создания до развёртывания. Среди ключевых практик:

    • Происхождение образа: Документируйте происхождение и историю образов контейнеров для обеспечения прослеживаемости и целостности.
    • Генерация SBOM: Создавайте перечень компонентов программного обеспечения (SBOM) для каждого образа с указанием всех компонентов, библиотек и зависимостей для обеспечения прозрачности и управления уязвимостями.
    • Подпись образов: Цифровая подпись образов для проверки их целостности и подлинности, установление доверия к их безопасности.
    • Доверенный реестр: Хранение задокументированных, подписанных образов с их SBOM в безопасном реестре, обеспечивающем строгий контроль доступа и поддерживающем управление метаданными.
    • Безопасное развёртывание: Реализуйте политики безопасного развёртывания, такие как валидация образов, безопасность во время выполнения и непрерывный мониторинг, для обеспечения безопасности развёртываемых образов.

    Podman как альтернатива Docker¶

    Podman — совместимый с OCI инструмент управления контейнерами с открытым исходным кодом, разработанный Red Hat, предоставляющий интерфейс командной строки, совместимый с Docker, и настольное приложение для управления контейнерами. Он разработан как более безопасная и лёгкая альтернатива Docker, особенно для сред, где предпочтительны безопасные настройки по умолчанию. Среди преимуществ безопасности Podman:

    1. Бездемонная архитектура: В отличие от Docker, который требует центрального демона (dockerd) для создания, запуска и управления контейнерами, Podman напрямую использует модель fork-exec. Когда пользователь запрашивает запуск контейнера, Podman разветвляется от текущего процесса, а затем дочерний процесс выполняется в среде выполнения контейнера.
    2. Безкорневые контейнеры: Модель fork-exec обеспечивает способность Podman запускать контейнеры без необходимости root-привилегий. Когда пользователь без прав root инициирует запуск контейнера, Podman разветвляется и выполняется под правами пользователя.
    3. Интеграция с SELinux: Podman создан для работы с SELinux, что обеспечивает дополнительный уровень безопасности путём применения обязательного контроля доступа к контейнерам и их взаимодействию с хост-системой.
