    Шпаргалка по протоколу OAuth 2.0¶

    Эта шпаргалка описывает актуальные лучшие практики безопасности OAuth 2.0, основанные на его RFC. OAuth стал стандартом защиты API и основой для федеративного входа с использованием OpenID Connect. OpenID Connect 1.0 — это простой уровень идентификации поверх протокола OAuth 2.0. Он позволяет клиентам проверять идентичность конечного пользователя на основе аутентификации, выполненной сервером авторизации, а также получать базовую информацию профиля о конечном пользователе в совместимом и REST-подобном формате.

    Примечание: OAuth 2.0 поддерживает различные типы токенов для решения различных требований безопасности и реализации. Bearer-токены (RFC 6750) обеспечивают простоту и широкое распространение. Токены Proof of Possession (PoP) предлагают расширенную безопасность благодаря криптографической привязке между токенами и клиентами. Выбор типа токена зависит от требований безопасности вашего приложения, модели угроз и ограничений реализации.

    Терминология¶

    • Client (Клиент): Как правило, приложение, выполняющее запросы к защищённым ресурсам от имени владельца ресурса и с его авторизации. Термин «клиент» не подразумевает каких-либо конкретных характеристик реализации (например, выполняется ли приложение на сервере, настольном компьютере или других устройствах).
    • Authorization Server (Сервер авторизации, AS): Сервер, выдающий токены доступа клиенту после успешной аутентификации владельца ресурса и получения его согласия.
    • Resource Owner (Владелец ресурса, RO): Субъект, способный предоставить доступ к защищённому ресурсу. Когда владелец ресурса — человек, его называют конечным пользователем. Им также может быть организация или система.

    • Resource Server (Сервер ресурсов, RS): Сервер, хранящий защищённые ресурсы, способный принимать запросы к защищённым ресурсам и отвечать на них с использованием токенов доступа.

    • Access Tokens (Токены доступа): Обеспечивают абстракцию, заменяя различные конструкции авторизации (например, имя пользователя и пароль, утверждение) единым токеном, понятным серверу ресурсов. Эта абстракция позволяет выдавать токены доступа на короткий срок, а также освобождает сервер ресурсов от необходимости понимать широкий спектр схем аутентификации. Наиболее распространённый тип — bearer-токен (RFC 6750), который прост в реализации и интеграции, требуя только значения токена для доступа к API. Поскольку bearer-токен может использовать любой, кто им владеет, bearer-токены должны быть ограничены одной аудиторией (сервером ресурсов) для ограничения последствий утечки токена.

    • Refresh Tokens (Токены обновления) — учётные данные для получения токенов доступа. Выдаются клиенту сервером авторизации и используются для получения нового токена доступа, когда текущий стал недействительным или истёк, либо для получения дополнительных токенов доступа с идентичной или более узкой областью действия (токены доступа могут иметь меньший срок жизни и меньше прав, чем авторизовано владельцем ресурса). Токены обновления следует защищать с помощью механизмов привязки к отправителю (DPoP или mTLS) или ротации токенов обновления.

    • Proof of Possession (PoP) tokens (Токены с подтверждением владения): Токены доступа или токены обновления, криптографически привязанные к клиентам через механизмы, такие как DPoP (RFC 9449) или mTLS-привязанные токены доступа (RFC 8705). Эти токены привязаны к закрытому ключу клиента, и клиент должен демонстрировать владение этим закрытым ключом для использования токена. Такой подход обеспечивает дополнительную защиту в сценариях, где перехват токена вызывает обеспокоенность, при дополнительных требованиях к реализации управления ключами и генерации доказательств.

    Основные принципы OAuth 2.0¶

    1. Клиенты и сервер авторизации не должны раскрывать URL-адреса, которые перенаправляют браузер пользователя на произвольные URI, полученные из параметра запроса («открытые редиректоры»), что может позволить несанкционированную передачу кодов авторизации и токенов доступа.
    2. Клиенты, убедившиеся в том, что сервер авторизации поддерживает PKCE, могут полагаться на защиту CSRF, обеспечиваемую PKCE. В потоках OpenID Connect параметр «nonce» обеспечивает защиту CSRF. В противном случае для защиты CSRF необходимо использовать одноразовые CSRF-токены пользователя, переносимые в параметре «state», безопасно привязанные к пользовательскому агенту.
    3. Когда клиент OAuth может взаимодействовать с более чем одним сервером авторизации, клиенты должны использовать параметр «iss» (эмитент) в качестве контрмеры или на основе значения «iss» в ответе авторизации (например, утверждение «iss» в ID Token в OpenID).
    4. При отсутствии других вариантов защиты для клиентов OAuth, взаимодействующих с несколькими серверами авторизации, клиенты могут использовать отдельные URI перенаправления для идентификации конечных точек авторизации и токенов.
    5. Сервер авторизации избегает случайного перенаправления запроса, потенциально содержащего учётные данные пользователя.

    PKCE — механизм Proof Key for Code Exchange¶

    Публичные клиенты OAuth 2.0, использующие Authorization Code Grant, подвержены атаке перехвата кода авторизации. Proof Key for Code Exchange (PKCE, произносится «pixy») — это техника для защиты от угрозы перехвата кода авторизации.

    Изначально PKCE предназначался исключительно для защиты нативных приложений, но затем стал развёртываемой функцией OAuth. Он защищает не только от атак внедрения кода авторизации, но и защищает коды авторизации, созданные для публичных клиентов, так как PKCE гарантирует, что злоумышленник не сможет использовать похищенный код авторизации в конечной точке токена сервера авторизации без знания code_verifier.

    1. Клиенты предотвращают внедрение (воспроизведение) кодов авторизации в ответ на авторизацию с помощью потока PKCE. Кроме того, клиенты могут использовать параметр «nonce» OpenID Connect и соответствующее утверждение в ID Token. Задача PKCE или «nonce» OpenID Connect должна быть специфичной для транзакции и безопасно привязанной к клиенту и пользовательскому агенту, в котором была начата транзакция. Примечание: PKCE защищает коды авторизации; используйте токены с привязкой к отправителю для защиты токенов доступа и обновления.
    2. При использовании PKCE клиенты должны применять методы проверки PKCE, которые не раскрывают верификатор PKCE в запросе авторизации. В противном случае злоумышленники, способные читать запрос авторизации, смогут нарушить защиту PKCE. Серверы авторизации должны поддерживать PKCE.
    3. Если клиент отправляет действительный параметр PKCE «code_challenge» в запросе авторизации, сервер авторизации обеспечивает корректное использование «code_verifier» в конечной точке токена.
    4. Серверы авторизации смягчают атаки понижения PKCE, гарантируя, что запрос токена, содержащий параметр «code_verifier», принимается только в том случае, если в запросе авторизации присутствует параметр «code_challenge».

    Implicit Grant¶

    Implicit grant — это упрощённый поток кода авторизации, оптимизированный для клиентов, реализованных в браузере с использованием языка сценариев, такого как JavaScript. В неявном потоке вместо выдачи клиенту кода авторизации клиенту напрямую выдаётся токен доступа (как результат авторизации владельца ресурса). Тип предоставления называется неявным (implicit), поскольку промежуточные учётные данные (такие как код авторизации) не выдаются (и не используются впоследствии для получения токена доступа).

    1. Клиенты используют тип ответа «code» (тип предоставления кода авторизации) или любой другой тип ответа, при котором сервер авторизации выдаёт токены доступа в ответе на токен, например тип ответа «code id_token». Это позволяет серверу авторизации обнаруживать попытки воспроизведения со стороны злоумышленников и в целом сокращает поверхность атаки, поскольку токены доступа не раскрываются в URL-адресах. Это также позволяет серверу авторизации привязывать выданные токены к отправителю (например, с использованием механизмов PoP, таких как DPoP).

    Предотвращение воспроизведения токенов¶

    Безопасность токенов является критически важным аспектом реализаций OAuth 2.0. Токены с привязкой к отправителю устанавливают связь между токеном и клиентом. Токены Proof of Possession (PoP) — это особый тип токенов с привязкой к отправителю, использующих криптографическую привязку через закрытый ключ клиента. Эта привязка требует, чтобы клиент демонстрировал владение закрытым ключом при использовании токена, добавляя уровень безопасности через аутентификацию клиента на уровне использования токена.

    Сравнение механизмов PoP¶

    DPoP (Demonstration of Proof of Possession — RFC 9449):

    • Клиент генерирует пару открытый-закрытый ключ. Сервер авторизации может привязать токен доступа к открытому ключу клиента, например включив утверждение cnf (подтверждение) с отпечатком JWK (jkt), хотя это опционально и зависит от реализации. Для каждого API-запроса клиент включает доказательство владения закрытым ключом в виде JWT, подписанного этим закрытым ключом, который включает хэш токена доступа. Сервер ресурсов проверяет как токен доступа, так и доказательство DPoP (включая хэш токена), чтобы убедиться, что запрос исходит от законного держателя токена.
    • Не требует взаимной TLS-аутентификации; доказательство предоставляется через HTTP-заголовки DPoP; подходит для различных типов клиентов, включая браузеры и мобильные приложения; требует дополнительных криптографических операций для каждого запроса.

    Mutual TLS Certificate-Bound Access Tokens (RFC 8705):

    • Клиент аутентифицируется с помощью TLS-сертификата клиента во время TLS-рукопожатия (взаимная TLS-аутентификация, mTLS). Сервер авторизации привязывает токен доступа к отпечатку сертификата клиента через утверждение cnf. Сервер ресурсов проверяет, что сертификат, представленный во время TLS-рукопожатия, соответствует сертификату, привязанному к токену доступа.
    • Работает на транспортном уровне; использует существующую TLS-инфраструктуру; может использовать PKI или самоподписанные сертификаты для управления сертификатами; аутентификация происходит при установлении соединения; не требует генерации доказательств для каждого запроса.

    Когда использовать токены PoP¶

    Токены Proof of Possession особенно ценны в сценариях, требующих повышенных свойств безопасности токенов. Рассмотрите использование токенов PoP для:

    • Токенов доступа, которые необходимо использовать для более чем одной аудитории (сервера ресурсов), так как токены PoP можно безопасно использовать для нескольких аудиторий, в отличие от bearer-токенов, которые должны быть ограничены одной аудиторией
    • API, обрабатывающих конфиденциальные данные (финансовые, медицинские, персональные и т.д.), где полезны дополнительные уровни безопасности
    • Высокоценных транзакций (платежи, критические операции и т.д.), где криптографическая привязка к клиенту добавляет надёжность
    • Долгосрочных токенов, где расширенные периоды действия требуют дополнительных механизмов защиты
    • Межорганизационного доступа (B2B-интеграции), включающего несколько доменов безопасности
    • Мобильных и нативных приложений, где среда клиента может представлять дополнительные соображения безопасности
    • Распределённых архитектур, где токены пересекают несколько сетевых границ

    Выбор подхода к безопасности токенов должен учитывать требования безопасности приложения, существующую инфраструктуру, возможности клиента и операционные ресурсы.

    1. Для расширенной защиты от сценариев воспроизведения токенов серверы авторизации и ресурсов могут реализовывать механизмы привязки токенов доступа к отправителю, такие как Mutual TLS для OAuth 2.0 (mTLS — RFC 8705) или Demonstration of Proof of Possession (DPoP — RFC 9449). Эти механизмы криптографически привязывают токены к конкретным клиентам через доказательство владения закрытым ключом.
    2. Токены обновления привязаны к отправителю (с использованием DPoP или mTLS) или используют ротацию токенов обновления (выдача новых токенов обновления и немедленная инвалидация старых для обнаружения попыток воспроизведения). Примечание: Сочетание токенов обновления с привязкой PoP и ротацией обеспечивает эшелонированную защиту.

    Ограничение привилегий токенов доступа¶

    1. Привилегии, связанные с токеном доступа, должны быть ограничены минимумом, необходимым для конкретного приложения или варианта использования. Это предотвращает превышение клиентами привилегий, авторизованных владельцем ресурса. Это также предотвращает превышение пользователями своих привилегий, авторизованных соответствующей политикой безопасности. Ограничения привилегий также помогают снизить последствия утечки токенов доступа. Сочетайте с токенами с привязкой к отправителю для эшелонированной защиты.
    2. Токены доступа ограничены определёнными серверами ресурсов (ограничение аудитории), предпочтительно одним сервером ресурсов. Сервер авторизации должен связывать токен доступа с определёнными серверами ресурсов, и каждый сервер ресурсов обязан для каждого запроса проверять, предназначен ли переданный токен доступа для использования на данном конкретном сервере ресурсов. Если нет, сервер ресурсов должен отказать в выполнении соответствующего запроса. Клиенты и серверы авторизации могут использовать параметры «scope» и «resource» для определения сервера ресурсов, к которому они хотят получить доступ.
    3. Токены доступа ограничены определёнными ресурсами и действиями на серверах ресурсов или с ресурсами. Сервер авторизации должен связывать токен доступа с соответствующим ресурсом и действиями, и каждый сервер ресурсов обязан для каждого запроса проверять, предназначен ли переданный токен доступа для использования при данном конкретном действии над данным конкретным ресурсом. Если нет, сервер ресурсов должен отказать в выполнении соответствующего запроса. Клиенты и серверы авторизации могут использовать параметры «scope» и «authorization_details» для определения этих ресурсов и/или действий.

    Resource Owner Password Credentials Grant¶

    1. Тип предоставления Resource Owner password credentials не используется. Этот тип предоставления небезопасно раскрывает учётные данные владельца ресурса клиенту, увеличивая поверхность атаки приложения.

    Аутентификация клиента¶

    1. Серверы авторизации используют аутентификацию клиента там, где это возможно. Рекомендуется использовать асимметричные (основанные на открытом ключе) методы аутентификации клиента, такие как mTLS или «private_key_jwt» (OpenID Connect). При использовании асимметричных методов аутентификации клиента серверы авторизации не нуждаются в хранении чувствительных симметричных ключей, что делает эти методы более устойчивыми к нескольким типам атак.

    Другие рекомендации¶

    1. Серверы авторизации не позволяют клиентам влиять на их значение «client_id» или «sub», или любое другое утверждение, которое может быть перепутано с подлинным владельцем ресурса. Рекомендуется использовать сквозной TLS.
    2. Ответы на авторизацию не передаются через незашифрованные сетевые соединения. Серверы авторизации не должны разрешать URI перенаправления, использующие схему «http», кроме нативных клиентов, использующих Loopback Interface Redirection.
