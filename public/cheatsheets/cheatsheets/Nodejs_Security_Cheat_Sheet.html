    NodeJS Security Cheat Sheet¶

    Введение¶

    В этой шпаргалке перечислены действия, которые разработчики могут предпринять для создания безопасных приложений на Node.js. Каждый пункт содержит краткое пояснение и решение, специфичное для среды Node.js.

    Контекст¶

    Количество приложений на Node.js постоянно растёт, и они ничем не отличаются от приложений на других фреймворках и языках программирования — они также подвержены всем видам уязвимостей веб-приложений.

    Цель¶

    Цель данной шпаргалки — предоставить список лучших практик, которым следует придерживаться при разработке приложений на Node.js.

    Рекомендации¶

    Существует несколько рекомендаций для повышения безопасности ваших приложений на Node.js. Они разделены на следующие категории:

    • Application Security (Безопасность приложения)
    • Error & Exception Handling (Обработка ошибок и исключений)
    • Server Security (Безопасность сервера)
    • Platform Security (Безопасность платформы)

    Application Security¶

    Используйте плоские цепочки Promise¶

    Асинхронные функции обратного вызова (callback) — одна из сильнейших особенностей Node.js. Однако увеличение уровней вложенности внутри callback-функций может стать проблемой. Любой многоэтапный процесс может быть вложен на 10 и более уровней в глубину. Эта проблема называется «Pyramid of Doom» («Пирамида судьбы») или «Callback Hell» («Ад колбэков»). В таком коде ошибки и результаты теряются внутри callback-функций. Promise — хороший способ писать асинхронный код без погружения во вложенные пирамиды. Promise обеспечивает последовательное выполнение сверху вниз, оставаясь при этом асинхронным, и передаёт ошибки и результаты в следующую функцию .then.

    Ещё одно преимущество Promise — способ обработки ошибок. Если в классе Promise возникает ошибка, выполнение пропускает функции .then и вызывает первую найденную функцию .catch. Таким образом, Promise обеспечивает более надёжный перехват и обработку ошибок. В качестве принципа можно сделать так, чтобы весь асинхронный код (кроме эмиттеров) возвращал Promise. Следует отметить, что вызовы Promise также могут образовывать пирамиду. Чтобы полностью избежать «Callback Hell», следует использовать плоские цепочки Promise. Если используемый модуль не поддерживает Promise, можно преобразовать базовый объект в Promise с помощью функции Promise.promisifyAll().

    Следующий фрагмент кода является примером «Callback Hell»:

    function func1(name, callback) {
  // operations that takes a bit of time and then calls the callback
}
function func2(name, callback) {
  // operations that takes a bit of time and then calls the callback
}
function func3(name, callback) {
  // operations that takes a bit of time and then calls the callback
}
function func4(name, callback) {
  // operations that takes a bit of time and then calls the callback
}

func1("input1", function(err, result1){
   if(err){
      // error operations
   }
   else {
      //some operations
      func2("input2", function(err, result2){
         if(err){
            //error operations
         }
         else{
            //some operations
            func3("input3", function(err, result3){
               if(err){
                  //error operations
               }
               else{
                  // some operations
                  func4("input 4", function(err, result4){
                     if(err){
                        // error operations
                     }
                     else {
                        // some operations
                     }
                  });
               }
            });
         }
      });
   }
});

    Приведённый выше код можно безопасно переписать, используя плоскую цепочку Promise:

    function func1(name) {
  // operations that takes a bit of time and then resolves the promise
}
function func2(name) {
  // operations that takes a bit of time and then resolves the promise
}
function func3(name) {
  // operations that takes a bit of time and then resolves the promise
}
function func4(name) {
  // operations that takes a bit of time and then resolves the promise
}

func1("input1")
   .then(function (result){
      return func2("input2");
   })
   .then(function (result){
      return func3("input3");
   })
   .then(function (result){
      return func4("input4");
   })
   .catch(function (error) {
      // error operations
   });

    А также с использованием async/await:

    async function func1(name) {
  // operations that takes a bit of time and then resolves the promise
}
async function func2(name) {
  // operations that takes a bit of time and then resolves the promise
}
async function func3(name) {
  // operations that takes a bit of time and then resolves the promise
}
async function func4(name) {
  // operations that takes a bit of time and then resolves the promise
}

(async() => {
  try {
    let res1 = await func1("input1");
    let res2 = await func2("input2");
    let res3 = await func3("input2");
    let res4 = await func4("input2");
  } catch(err) {
    // error operations
  }
})();

    Устанавливайте ограничения на размер запросов¶

    Буферизация и разбор тел запросов могут быть ресурсоёмкими операциями. Если размер запросов не ограничен, злоумышленники могут отправлять запросы с большими телами, что приведёт к исчерпанию памяти сервера и/или заполнению дискового пространства. Вы можете ограничить размер тела запроса для всех запросов с помощью raw-body.

    const contentType = require('content-type')
const express = require('express')
const getRawBody = require('raw-body')

const app = express()

app.use(function (req, res, next) {
  if (!['POST', 'PUT', 'DELETE'].includes(req.method)) {
    next()
    return
  }

  getRawBody(req, {
    length: req.headers['content-length'],
    limit: '1kb',
    encoding: contentType.parse(req).parameters.charset
  }, function (err, string) {
    if (err) return next(err)
    req.text = string
    next()
  })
})

    Однако установка фиксированного ограничения размера для всех запросов может быть некорректным поведением, поскольку некоторые запросы могут содержать большой объём данных в теле — например, при загрузке файлов. Кроме того, ввод в формате JSON опаснее, чем multipart-ввод, поскольку разбор JSON является блокирующей операцией. Поэтому следует устанавливать ограничения размера запросов отдельно для разных типов контента. Это можно легко реализовать с помощью middleware express:

    app.use(express.urlencoded({ extended: true, limit: "1kb" }));
app.use(express.json({ limit: "1kb" }));

    Следует учитывать, что злоумышленники могут изменить заголовок Content-Type запроса и обойти ограничения размера. Поэтому перед обработкой запроса данные, содержащиеся в нём, должны быть проверены на соответствие типу контента, указанному в заголовках. Если проверка типа контента для каждого запроса существенно снижает производительность, можно проверять только определённые типы контента или запросы, превышающие заранее установленный размер.

    Не блокируйте цикл событий¶

    Node.js существенно отличается от обычных платформ приложений, использующих потоки. Node.js имеет однопоточную архитектуру, управляемую событиями. Благодаря этой архитектуре пропускная способность повышается, а модель программирования упрощается. Node.js реализован на основе неблокирующего цикла событий ввода-вывода. С этим циклом событий нет ожидания I/O или переключения контекста. Цикл событий ищет события и передаёт их функциям-обработчикам. Из-за этого, когда выполняются ресурсоёмкие операции JavaScript, цикл событий ждёт их завершения. Вот почему такие операции называются «блокирующими». Для решения этой проблемы Node.js позволяет назначать callback-функции для событий, заблокированных I/O. Таким образом, основное приложение не блокируется, а callback-функции выполняются асинхронно. Поэтому в качестве общего принципа все блокирующие операции должны выполняться асинхронно, чтобы не блокировать цикл событий.

    Даже если блокирующие операции выполняются асинхронно, приложение может работать не так, как ожидается. Это происходит, когда есть код вне callback-функции, который зависит от кода внутри callback-функции и должен выполняться после него. Например, рассмотрим следующий код:

    const fs = require('fs');
fs.readFile('/file.txt', (err, data) => {
  // perform actions on file content
});
fs.unlinkSync('/file.txt');

    В приведённом выше примере функция unlinkSync может выполниться раньше callback-функции, что приведёт к удалению файла до завершения желаемых действий с его содержимым. Подобные состояния гонки также могут влиять на безопасность вашего приложения. Примером может служить сценарий, при котором аутентификация выполняется в callback-функции, а аутентифицированные действия выполняются синхронно. Чтобы устранить такие состояния гонки, можно поместить все взаимозависимые операции в единую неблокирующую функцию. Таким образом можно гарантировать, что все операции выполняются в правильном порядке. Например, приведённый выше код можно переписать неблокирующим образом следующим образом:

    const fs = require('fs');
fs.readFile('/file.txt', (err, data) => {
  // perform actions on file content
  fs.unlink('/file.txt', (err) => {
    if (err) throw err;
  });
});

    В приведённом выше коде вызов удаления файла и другие операции с файлом находятся в одном и том же callback-е. Это обеспечивает правильный порядок выполнения операций.

    Выполняйте валидацию входных данных¶

    Валидация входных данных — важнейшая часть безопасности приложения. Её отсутствие может привести ко многим видам атак на приложение. К ним относятся SQL-инъекции, межсайтовый скриптинг (XSS), инъекции команд, включение локальных/удалённых файлов, отказ в обслуживании, обход каталогов, LDAP-инъекции и многие другие инъекционные атаки. Чтобы избежать этих атак, входные данные приложения должны быть предварительно очищены. Лучшая техника валидации — использование списка допустимых входных значений. Однако если это невозможно, входные данные сначала следует проверить на соответствие ожидаемой схеме, а опасные входные данные — экранировать. Для облегчения валидации входных данных в приложениях Node.js существуют такие модули, как validator и express-mongo-sanitize. Для получения подробной информации о валидации входных данных обратитесь к Input Validation Cheat Sheet.

    JavaScript — динамический язык, и в зависимости от того, как фреймворк разбирает URL, данные, которые видит код приложения, могут принимать самые разные формы. Вот несколько примеров после разбора строки запроса в express.js:

    URL Содержимое request.query.foo в коде
    ?foo=bar 'bar' (string)
    ?foo=bar&foo=baz ['bar', 'baz'] (array of string)
    ?foo[]=bar ['bar'] (array of string)
    ?foo[]=bar&foo[]=baz ['bar', 'baz'] (array of string)
    ?foo[bar]=baz { bar : 'baz' } (object with a key)
    ?foo[]baz=bar ['bar'] (array of string - postfix is lost)
    ?foo[][baz]=bar [ { baz: 'bar' } ] (array of object)
    ?foo[bar][baz]=bar { foo: { bar: { baz: 'bar' } } } (object tree)
    ?foo[10]=bar&foo[9]=baz [ 'baz', 'bar' ] (array of string - notice order)
    ?foo[toString]=bar {} (object where calling toString() will fail)

    Выполняйте экранирование выходных данных¶

    В дополнение к валидации входных данных следует экранировать весь HTML и JavaScript-контент, отображаемый пользователям через приложение, чтобы предотвратить атаки межсайтового скриптинга (XSS). Для экранирования выходных данных можно использовать библиотеки escape-html или node-esapi.

    Ведите журнал активности приложения¶

    Ведение журнала активности приложения является рекомендуемой хорошей практикой. Это упрощает отладку любых ошибок, возникающих во время выполнения приложения. Это также полезно с точки зрения безопасности, поскольку журналы могут использоваться при реагировании на инциденты. Кроме того, эти журналы можно использовать для питания систем обнаружения/предотвращения вторжений (IDS/IPS). В Node.js существуют такие модули, как Winston, Bunyan или Pino для ведения журнала активности приложения. Эти модули обеспечивают потоковую передачу и запросы к журналам, а также предоставляют способ обработки необработанных исключений.

    С помощью следующего кода можно записывать активность приложения как в консоль, так и в нужный файл журнала:

    const logger = new (Winston.Logger) ({
    transports: [
        new (winston.transports.Console)(),
        new (winston.transports.File)({ filename: 'application.log' })
    ],
    level: 'verbose'
});

    Можно задать различные транспорты, чтобы сохранять ошибки в отдельный файл журнала, а общие журналы приложения — в другой. Дополнительную информацию о ведении журналов безопасности можно найти в Logging Cheat Sheet.

    Мониторинг цикла событий¶

    Когда сервер приложения испытывает большую нагрузку по сети, он может не справляться с обслуживанием пользователей. По сути, это разновидность атаки Denial of Service (DoS). Модуль toobusy-js позволяет отслеживать цикл событий. Он отслеживает время ответа, и когда оно превышает определённый порог, этот модуль может сигнализировать о том, что сервер слишком занят. В этом случае можно прекратить обработку входящих запросов и отправлять сообщение 503 Server Too Busy, чтобы приложение оставалось отзывчивым. Пример использования модуля toobusy-js показан здесь:

    const toobusy = require('toobusy-js');
const express = require('express');
const app = express();
app.use(function(req, res, next) {
    if (toobusy()) {
        // log if you see necessary
        res.status(503).send("Server Too Busy");
    } else {
    next();
    }
});

    Принимайте меры против брутфорс-атак¶

    Брутфорс — распространённая угроза для всех веб-приложений. Злоумышленники могут использовать брутфорс как атаку на угадывание пароля для получения паролей учётных записей. Поэтому разработчики приложений должны принимать меры против брутфорс-атак, особенно на страницах входа. В Node.js для этой цели доступно несколько модулей. Express-bouncer, express-brute и rate-limiter — лишь некоторые примеры. В зависимости от ваших потребностей и требований следует выбрать один или несколько из этих модулей и использовать их соответствующим образом. Модули express-bouncer и express-brute работают аналогично. Они увеличивают задержку для каждого неудачного запроса и могут быть настроены для конкретного маршрута. Эти модули можно использовать следующим образом:

    const bouncer = require('express-bouncer');
bouncer.whitelist.push('127.0.0.1'); // allow an IP address
// give a custom error message
bouncer.blocked = function (req, res, next, remaining) {
    res.status(429).send("Too many requests have been made. Please wait " + remaining/1000 + " seconds.");
};
// route to protect
app.post("/login", bouncer.block, function(req, res) {
    if (LoginFailed){  }
    else {
        bouncer.reset( req );
    }
});

    const ExpressBrute = require('express-brute');

const store = new ExpressBrute.MemoryStore(); // stores state locally, don't use this in production
const bruteforce = new ExpressBrute(store);

app.post('/auth',
    bruteforce.prevent, // error 429 if we hit this route too often
    function (req, res, next) {
        res.send('Success!');
    }
);

    Помимо express-bouncer и express-brute, модуль rate-limiter также может помочь в предотвращении брутфорс-атак. Он позволяет указать, сколько запросов может сделать конкретный IP-адрес за определённый период времени.

    const limiter = new RateLimiter();
limiter.addLimit('/login', 'GET', 5, 500); // login page can be requested 5 times at max within 500 seconds

    Использование CAPTCHA — ещё один распространённый механизм защиты от брутфорса. Для Node.js разработаны соответствующие модули. Широко используемый в приложениях Node.js модуль — svg-captcha. Его можно использовать следующим образом:

    const svgCaptcha = require('svg-captcha');
app.get('/captcha', function (req, res) {
    const captcha = svgCaptcha.create();
    req.session.captcha = captcha.text;
    res.type('svg');
    res.status(200).send(captcha.data);
});

    Блокировка учётной записи — рекомендуемое решение для защиты легитимных пользователей от злоумышленников. Блокировка учётной записи возможна с помощью многих модулей, например mongoose. Вы можете обратиться к этой записи в блоге, чтобы узнать, как реализована блокировка учётной записи в mongoose.

    Используйте Anti-CSRF токены¶

    Межсайтовая подделка запросов (CSRF) направлена на выполнение авторизованных действий от имени аутентифицированного пользователя без его ведома. CSRF-атаки, как правило, выполняются для запросов, изменяющих состояние — например, изменение пароля, добавление пользователей или размещение заказов. Csurf — это middleware для express, которое использовалось для защиты от CSRF-атак. Однако недавно в этом пакете была обнаружена уязвимость безопасности. Команда разработчиков не устранила обнаруженную уязвимость и пометила пакет как устаревший (deprecated), рекомендуя использовать любой другой пакет для защиты от CSRF.

    Для получения подробной информации об атаках межсайтовой подделки запросов (CSRF) и методах защиты от них обратитесь к Cross-Site Request Forgery Prevention.

    Удаляйте ненужные маршруты¶

    Веб-приложение не должно содержать страниц, которые не используются пользователями, поскольку это может увеличить поверхность атаки. Поэтому все неиспользуемые API-маршруты должны быть отключены в приложениях Node.js. Особенно это актуально для таких фреймворков, как Sails и Feathers, поскольку они автоматически генерируют конечные точки REST API. Например, в Sails, если URL не совпадает с пользовательским маршрутом, он может совпасть с одним из автоматических маршрутов и всё равно сгенерировать ответ. Это может приводить к последствиям от утечки информации до выполнения произвольных команд. Поэтому перед использованием таких фреймворков и модулей важно знать, какие маршруты они генерируют автоматически, и удалять или отключать эти маршруты.

    Предотвращайте загрязнение HTTP-параметров¶

    HTTP Parameter Pollution (HPP) — атака, при которой злоумышленники отправляют несколько HTTP-параметров с одинаковым именем, что приводит к непредсказуемой интерпретации их приложением. Когда отправляется несколько значений параметра, Express помещает их в массив. Для решения этой проблемы можно использовать модуль hpp. При использовании этот модуль будет игнорировать все значения, переданные для параметра в req.query и/или req.body, и выбирать только последнее переданное значение параметра. Использование:

    const hpp = require('hpp');
app.use(hpp());

    Возвращайте только необходимые данные¶

    Информация о пользователях приложения является одной из наиболее критичных сведений о приложении. Таблицы пользователей обычно включают поля: ID, имя пользователя, полное имя, адрес электронной почты, дату рождения, пароль и в некоторых случаях номера социального страхования. Поэтому при запросе и использовании объектов пользователей необходимо возвращать только нужные поля, поскольку в противном случае может произойти раскрытие персональных данных. То же самое относится и к другим объектам, хранящимся в базе данных. Если вам нужно только определённое поле объекта, следует возвращать только конкретные требуемые поля. Например, можно использовать функцию, подобную следующей, когда нужно получить информацию о пользователе. Таким образом можно возвращать только те поля, которые нужны для конкретной операции. Иными словами, если нужно только перечислить имена пользователей, не следует возвращать их адреса электронной почты или номера кредитных карт вместе с именами.

    exports.sanitizeUser = function(user) {
  return {
    id: user.id,
    username: user.username,
    fullName: user.fullName
  };
};

    Используйте дескрипторы свойств объектов¶

    Свойства объектов имеют три скрытых атрибута: writable (если false, значение свойства не может быть изменено), enumerable (если false, свойство не может использоваться в циклах for) и configurable (если false, свойство не может быть удалено). При определении свойства объекта через присваивание эти три скрытых атрибута по умолчанию устанавливаются в true. Эти свойства можно задать следующим образом:

    const o = {};
Object.defineProperty(o, "a", {
    writable: true,
    enumerable: true,
    configurable: true,
    value: "A"
});

    Кроме того, существуют специальные функции для атрибутов объектов. Object.preventExtensions() предотвращает добавление новых свойств к объекту.

    Используйте списки управления доступом¶

    Авторизация предотвращает выполнение пользователями действий, выходящих за рамки их разрешений. Для этого пользователи и их роли должны быть определены с учётом принципа наименьших привилегий. Каждая роль пользователя должна иметь доступ только к тем ресурсам, которые ей необходимы. Для приложений Node.js можно использовать модуль acl, который реализует ACL (список управления доступом). С помощью этого модуля можно создавать роли и назначать пользователей этим ролям.

    Разрешения (Permissions)¶

    Начиная с Node.js v20, доступна модель разрешений (Permission Model) для ограничения привилегий приложения. Начиная с Node.js v23.5.0, модель считается стабильной и может быть включена с помощью флага --permission (более ранние версии требуют --experimental-permission).

    Использование¶

    node --permission [--allow-<type>=...] app.js

    Примеры¶

    Используйте только --permission, чтобы по умолчанию ограничить все разрешения:

    node --permission index.js

    Используйте --allow‑fs‑read, чтобы указать, какие файлы или каталоги Node.js имеет право читать. Это особенно полезно для предотвращения уязвимостей Local File Inclusion (LFI):

    node --permission --allow-fs-read=/uploads/ index.js

    Используйте --allow-fs-write, чтобы указать, куда Node.js имеет право записывать файлы:

    node --permission --allow-fs-write=/uploads/ index.js

    Несанкционированный доступ вызывает ошибку времени выполнения:

    Error: Access to this API has been restricted
code: 'ERR_ACCESS_DENIED'
permission: 'FileSystemRead'
resource: '/path/to/file'

    Другие флаги:

    • --allow-child-process — разрешает использование API child_process
    • --allow-worker — разрешает использование API worker_threads
    • --allow-addons — разрешает загрузку нативных аддонов
    • --allow-wasi — разрешает использование модулей WASI

    Важное замечание: Символические ссылки следуются даже в том случае, если они указывают за пределы разрешённых путей. Это означает, что относительные символические ссылки могут обходить ограничения и предоставлять непреднамеренный доступ. Для обеспечения безопасности убедитесь, что ни один из разрешённых путей не содержит относительных символических ссылок при использовании модели разрешений.

    Подробнее см. в официальной документации.

    Error & Exception Handling¶

    Обрабатывайте uncaughtException¶

    Поведение Node.js по умолчанию при необработанных исключениях — вывод текущего стека вызовов с последующим завершением потока. Однако Node.js позволяет настраивать это поведение. Он предоставляет глобальный объект process, доступный всем приложениям Node.js. Это объект EventEmitter, и в случае необработанного исключения генерируется событие uncaughtException, которое поступает в основной цикл событий. Для задания пользовательского поведения при необработанных исключениях можно привязаться к этому событию. Однако возобновление работы приложения после такого необработанного исключения может привести к дальнейшим проблемам. Поэтому, чтобы не пропустить ни одного необработанного исключения, следует привязаться к событию uncaughtException и освободить все выделенные ресурсы — дескрипторы файлов, хэндлы и тому подобное — перед завершением процесса. Возобновление работы приложения настоятельно не рекомендуется, поскольку приложение будет находиться в неизвестном состоянии. Важно отметить, что при отображении сообщений об ошибках пользователю в случае необработанного исключения не следует раскрывать подробную информацию, например трассировку стека. Вместо этого пользователям следует показывать пользовательские сообщения об ошибках, чтобы не допустить утечки информации.

    process.on("uncaughtException", function(err) {
    // clean up allocated resources
    // log necessary error details to log files
    process.exit(); // exit the process to avoid unknown state
});

    Прослушивайте ошибки при использовании EventEmitter¶

    При использовании EventEmitter ошибки могут возникать в любом месте цепочки событий. Как правило, если в объекте EventEmitter возникает ошибка, вызывается событие error, аргументом которого является объект Error. Однако если к этому событию error не привязаны слушатели, объект Error, переданный в качестве аргумента, выбрасывается и становится необработанным исключением. Иными словами, если не обрабатывать ошибки внутри объекта EventEmitter должным образом, эти необработанные ошибки могут привести к аварийному завершению вашего приложения. Поэтому при использовании объектов EventEmitter всегда следует прослушивать события error.

    const events = require('events');
const myEventEmitter = function(){
    events.EventEmitter.call(this);
}
require('util').inherits(myEventEmitter, events.EventEmitter);
myEventEmitter.prototype.someFunction = function(param1, param2) {
    //in case of an error
    this.emit('error', err);
}
const emitter = new myEventEmitter();
emitter.on('error', function(err){
    //Perform necessary error handling here
});

    Обрабатывайте ошибки в асинхронных вызовах¶

    Ошибки, возникающие в асинхронных callback-функциях, легко пропустить. Поэтому в качестве общего принципа первым аргументом асинхронных вызовов должен быть объект Error. Кроме того, маршруты express обрабатывают ошибки самостоятельно, но следует всегда помнить, что ошибки, возникающие в асинхронных вызовах внутри маршрутов express, не обрабатываются, если объект Error не передаётся первым аргументом.

    Ошибки в этих callback-функциях могут передаваться по цепочке столько раз, сколько необходимо. Каждый callback, которому была передана ошибка, может проигнорировать её, обработать или передать дальше.

    Server Security¶

    Устанавливайте флаги cookie надлежащим образом¶

    Как правило, информация о сессии передаётся с помощью cookie в веб-приложениях. Однако ненадлежащее использование HTTP cookie может сделать приложение уязвимым к различным атакам на управление сессиями. Для каждого cookie можно установить определённые флаги, чтобы предотвратить подобные атаки. Флаги httpOnly, Secure и SameSite очень важны для сессионных cookie. Флаг httpOnly запрещает доступ к cookie со стороны клиентского JavaScript. Это эффективная контрмера против XSS-атак. Флаг Secure позволяет cookie передаваться только при использовании HTTPS. Флаг SameSite может предотвратить отправку cookie в межсайтовых запросах, что помогает защититься от атак Cross-Site Request Forgery (CSRF). Помимо этих флагов, существуют и другие — domain, path и expires. Их правильная настройка рекомендуется, однако они в основном связаны с областью видимости cookie, а не с безопасностью cookie. Пример использования этих флагов приведён в следующем примере:

    const session = require('express-session');
app.use(session({
    secret: 'your-secret-key',
    name: 'cookieName',
    cookie: { secure: true, httpOnly: true, path: '/user', sameSite: true}
}));

    Используйте соответствующие заголовки безопасности¶

    Существует несколько заголовков безопасности HTTP, которые помогают предотвратить некоторые распространённые векторы атак. Пакет helmet может помочь установить эти заголовки:

    const express = require("express");
const helmet = require("helmet");

const app = express();

app.use(helmet()); // Add various HTTP headers

    Функция верхнего уровня helmet является обёрткой вокруг 14 меньших middleware. Ниже приведён список заголовков безопасности HTTP, поддерживаемых middleware helmet:

    • Strict-Transport-Security: HTTP Strict Transport Security (HSTS) указывает браузерам, что доступ к приложению возможен только через HTTPS-соединения. Для использования в приложении добавьте следующий код:
    app.use(helmet.hsts()); // default configuration
app.use(
  helmet.hsts({
    maxAge: 123456,
    includeSubDomains: false,
  })
); // custom configuration
    • X-Frame-Options: определяет, может ли страница загружаться через элемент <frame> или <iframe>. Разрешение встраивания страницы в фрейм может привести к атакам Clickjacking.
    app.use(helmet.frameguard()); // default behavior (SAMEORIGIN)
    • X-XSS-Protection: останавливает загрузку страниц при обнаружении отражённых атак межсайтового скриптинга (XSS). Этот заголовок устарел в современных браузерах, а его использование может привести к дополнительным проблемам безопасности на стороне клиента. Поэтому рекомендуется установить заголовок X-XSS-Protection: 0, чтобы отключить XSS Auditor и не позволять ему использовать поведение браузера по умолчанию при обработке ответа.
    app.use(helmet.xssFilter()); // sets "X-XSS-Protection: 0"

    Для современных браузеров рекомендуется внедрить надёжную политику Content-Security-Policy, как подробно описано в следующем разделе.

    • Content-Security-Policy: Content Security Policy разработана для снижения риска таких атак, как Cross-Site Scripting (XSS) и Clickjacking. Она позволяет загружать контент только из списка источников, который вы определяете. В ней есть несколько директив, каждая из которых запрещает загрузку определённого типа контента. Подробное описание каждой директивы и порядок её использования можно найти в Content Security Policy Cheat Sheet. Эти настройки можно реализовать в приложении следующим образом:
    app.use(
  helmet.contentSecurityPolicy({
    // the following directives will be merged into the default helmet CSP policy
    directives: {
      defaultSrc: ["'self'"],  // default value for all directives that are absent
      scriptSrc: ["'self'"],   // helps prevent XSS attacks
      frameAncestors: ["'none'"],  // helps prevent Clickjacking attacks
      imgSrc: ["'self'", "'http://imgexample.com'"],
      styleSrc: ["'none'"]
    }
  })
);

    Поскольку это middleware выполняет очень мало проверок, рекомендуется использовать инструменты проверки CSP, такие как CSP Evaluator.

    • X-Content-Type-Options: Даже если сервер устанавливает правильный заголовок Content-Type в ответе, браузеры могут попытаться определить MIME-тип запрошенного ресурса самостоятельно. Этот заголовок является способом остановить такое поведение и указать браузеру не изменять MIME-типы, указанные в заголовке Content-Type. Его можно настроить следующим образом:
    app.use(helmet.noSniff());
    • Cache-Control и Pragma: Заголовок Cache-Control можно использовать для предотвращения кэширования браузерами определённых ответов. Это следует делать для страниц, содержащих конфиденциальную информацию о пользователе или приложении. Однако отключение кэширования для страниц, не содержащих конфиденциальной информации, может существенно снизить производительность приложения. Поэтому кэширование следует отключать только для страниц, возвращающих конфиденциальную информацию. Соответствующие параметры и заголовки кэширования можно легко задать с помощью пакета nocache:
    const nocache = require("nocache");

app.use(nocache());

    Приведённый выше код соответствующим образом устанавливает заголовки Cache-Control, Surrogate-Control, Pragma и Expires.

    • X-Download-Options: Этот заголовок предотвращает выполнение загруженных файлов в контексте сайта в Internet Explorer. Это достигается с помощью директивы noopen. Это можно сделать с помощью следующего фрагмента кода:
    app.use(helmet.ieNoOpen());
    • X-Powered-By: Заголовок X-Powered-By используется для информирования о том, какая технология используется на стороне сервера. Это излишний заголовок, приводящий к утечке информации, поэтому его следует удалить из вашего приложения. Для этого можно использовать hidePoweredBy следующим образом:
    app.use(helmet.hidePoweredBy());

    Также можно указать в этом заголовке ложные сведения об используемых технологиях. Например, даже если ваше приложение не использует PHP, можно установить заголовок X-Powered-By таким образом, чтобы казалось, что оно его использует.

    app.use(helmet.hidePoweredBy({ setTo: 'PHP 4.2.0' }));

    Platform Security¶

    Поддерживайте пакеты в актуальном состоянии¶

    Безопасность вашего приложения напрямую зависит от того, насколько безопасны сторонние пакеты, используемые в приложении. Поэтому важно поддерживать пакеты в актуальном состоянии. Следует отметить, что Использование компонентов с известными уязвимостями по-прежнему входит в OWASP Top 10. Можно использовать OWASP Dependency-Check, чтобы проверить, имеет ли какой-либо из пакетов, используемых в проекте, известную уязвимость. Также можно использовать Retire.js для проверки JavaScript-библиотек с известными уязвимостями.

    Начиная с версии 6, npm представил команду audit, которая предупреждает об уязвимых пакетах:

    npm audit

    npm также представил простой способ обновления затронутых пакетов:

    npm audit fix

    Существует ещё несколько инструментов для проверки зависимостей. Более полный список можно найти в Vulnerable Dependency Management CS.

    Не используйте опасные функции¶

    Существуют некоторые функции JavaScript, которые являются опасными и должны использоваться только там, где это необходимо или неизбежно. Первый пример — функция eval(). Эта функция принимает строковый аргумент и выполняет его как любой другой исходный код JavaScript. В сочетании с пользовательским вводом это поведение по своей сути приводит к уязвимости удалённого выполнения кода. Аналогично, вызовы child_process.exec также очень опасны. Эта функция действует как интерпретатор bash и передаёт свои аргументы в /bin/sh. Внедряя данные в эту функцию, злоумышленники могут выполнять произвольные команды на сервере.

    В дополнение к этим функциям, некоторые модули требуют особой осторожности при использовании. Например, модуль fs обрабатывает операции с файловой системой. Однако если в этот модуль передаётся ненадлежащим образом очищенный пользовательский ввод, ваше приложение может стать уязвимым к атакам включения файлов и обхода каталогов. Аналогично, модуль vm предоставляет API для компиляции и запуска кода в контекстах V8 Virtual Machine. Поскольку по своей природе он может выполнять опасные действия, его следует использовать внутри песочницы.

    Нельзя однозначно утверждать, что эти функции и модули вообще не следует использовать, однако их следует применять осторожно, особенно при работе с пользовательским вводом. Кроме того, существуют другие функции, которые могут сделать ваше приложение уязвимым.

    Избегайте «злых» регулярных выражений¶

    Regular Expression Denial of Service (ReDoS) — это атака типа «отказ в обслуживании», которая эксплуатирует тот факт, что большинство реализаций регулярных выражений могут попадать в крайние ситуации, приводящие к их работе очень медленно (в зависимости от размера входных данных — экспоненциально). Затем злоумышленник может заставить программу, использующую регулярное выражение, попасть в эти крайние ситуации, и та будет зависать на очень долгое время.

    Regular Expression Denial of Service (ReDoS) — это тип атаки «отказ в обслуживании» с использованием регулярных выражений. Некоторые реализации регулярных выражений (Regex) вызывают крайние ситуации, которые делают приложение очень медленным. Злоумышленники могут использовать такие реализации regex, чтобы заставить приложение попасть в эти крайние ситуации и зависать на длительное время. Такие регулярные выражения называются «злыми», если приложение может зависнуть на специально созданном вводе. Как правило, эти регулярные выражения эксплуатируются с помощью группировки с повторением и чередования с перекрывающимися вариантами. Например, следующее регулярное выражение ^(([a-z])+.)+[A-Z]([a-z])+$ может использоваться для указания имён классов Java. Однако очень длинная строка (aaaa...aaaaAaaaaa...aaaa) также может соответствовать этому регулярному выражению. Существуют инструменты для проверки того, может ли регулярное выражение потенциально вызвать отказ в обслуживании. Один из примеров — vuln-regex-detector.

    Запускайте линтеры безопасности¶

    При разработке кода помнить все советы по безопасности действительно сложно. Также практически невозможно обязать всех членов команды соблюдать эти правила. Именно для этого существуют инструменты Static Analysis Security Testing (SAST). Эти инструменты не выполняют ваш код, а просто ищут паттерны, которые могут содержать риски безопасности. Поскольку JavaScript является динамическим и слабо типизированным языком, инструменты линтинга действительно необходимы в жизненном цикле разработки программного обеспечения. Правила линтинга следует периодически пересматривать, а результаты — проверять. Ещё одним преимуществом этих инструментов является возможность добавлять пользовательские правила для паттернов, которые вы считаете опасными. ESLint и JSHint — широко используемые инструменты SAST для линтинга JavaScript.

    Используйте строгий режим¶

    В JavaScript есть ряд небезопасных и опасных устаревших возможностей, которые не следует использовать. Для устранения этих возможностей ES5 включил строгий режим для разработчиков. В этом режиме ошибки, которые ранее были молчаливыми, теперь выбрасываются. Он также помогает JavaScript-движкам выполнять оптимизации. В строгом режиме ранее принимаемый некорректный синтаксис приводит к реальным ошибкам. Из-за этих улучшений всегда следует использовать строгий режим в своём приложении. Чтобы включить строгий режим, достаточно написать "use strict"; в начале кода.

    Следующий код сгенерирует ReferenceError: Can't find variable: y в консоли, что не будет отображаться без использования строгого режима:

    "use strict";

func();
function func() {
  y = 3.14;   // This will cause an error (y is not defined)
}
