    Шпаргалка по Laravel¶

    Введение¶

    Данная шпаргалка содержит советы по безопасности для разработчиков, создающих приложения на Laravel. Её цель — охватить все распространённые уязвимости и способы обеспечения безопасности Laravel-приложений.

    Фреймворк Laravel предоставляет встроенные функции безопасности и спроектирован безопасным по умолчанию. Однако он также обеспечивает дополнительную гибкость для сложных вариантов использования. Это означает, что разработчики, незнакомые с внутренними механизмами Laravel, могут попасть в ловушку, используя сложные функции небезопасным образом. Данное руководство призвано помочь разработчикам избежать распространённых ошибок и создавать Laravel-приложения безопасным образом.

    Основы¶

    • Убедитесь, что приложение не находится в режиме отладки в производственной среде. Для отключения режима отладки установите переменную среды APP_DEBUG в значение false:
    APP_DEBUG=false
    • Убедитесь, что ключ приложения сгенерирован. Laravel-приложения используют ключ приложения для симметричного шифрования и хешей SHA256, таких как шифрование cookies, подписанные URL, токены сброса пароля и шифрование данных сессии. Для генерации ключа приложения можно выполнить команду Artisan key:generate:
    php artisan key:generate

    • Убедитесь, что конфигурация PHP безопасна. Дополнительную информацию о безопасных настройках PHP можно найти в Шпаргалке по конфигурации PHP.

    • Установите безопасные права доступа к файлам и каталогам Laravel-приложения. В целом, все каталоги Laravel должны иметь максимальный уровень разрешений 775, а неисполняемые файлы — 664. Исполняемые файлы, такие как Artisan или скрипты развёртывания, должны иметь максимальный уровень разрешений 775.

    • Убедитесь, что приложение не имеет уязвимых зависимостей.

    Безопасность Cookies и управление сессиями¶

    По умолчанию Laravel настроен безопасным образом. Однако если вы изменяете конфигурацию cookies или сессий, убедитесь в следующем:

    • Включите промежуточное ПО шифрования cookies, если вы используете хранилище сессии cookie или если вы сохраняете какие-либо данные, которые не должны быть читаемы или изменяемы клиентами. В целом, это должно быть включено, если только ваше приложение не имеет очень специфического варианта использования, требующего отключения. Для включения этого промежуточного ПО просто добавьте промежуточное ПО EncryptCookies в группу промежуточного ПО web в вашем классе App\Http\Kernel:
    /**
 * Группы промежуточного ПО маршрутов приложения.
 *
 * @var array
 */
protected $middlewareGroups = [
    'web' => [
        \App\Http\Middleware\EncryptCookies::class,
        ...
    ],
    ...
];
    • Включите атрибут HttpOnly для сессионных cookies через файл config/session.php, чтобы сессионные cookies были недоступны для JavaScript:
    'http_only' => true,
    • Если вы не используете регистрацию маршрутов для поддоменов в Laravel-приложении, рекомендуется установить атрибут domain cookie в null, чтобы только тот же источник (исключая поддомены) мог устанавливать cookie. Это можно настроить в файле config/session.php:
    'domain' => null,
    • Установите атрибут cookie SameSite в значение lax или strict в файле config/session.php для ограничения cookies контекстом первой стороны или того же сайта:
    'same_site' => 'lax',
    • Если ваше приложение работает только по HTTPS, рекомендуется установить параметр конфигурации secure в файле config/session.php в значение true для защиты от атак «человек посередине». Если ваше приложение работает как по HTTP, так и по HTTPS, рекомендуется установить это значение в null, чтобы атрибут secure устанавливался автоматически при обслуживании запросов HTTPS:
    'secure' => null,
    • Убедитесь, что у вас небольшое значение тайм-аута бездействия сессии. OWASP рекомендует тайм-аут бездействия 2–5 минут для высокоценных приложений и 15–30 минут для приложений с низким уровнем риска. Это можно настроить в файле config/session.php:
    'lifetime' => 15,

    Также можно обратиться к Руководству по безопасности cookies для получения дополнительной информации о безопасности cookies и атрибутах cookies, упомянутых выше.

    Аутентификация¶

    Охранники и провайдеры¶

    В основе средств аутентификации Laravel лежат «охранники» и «провайдеры». Охранники определяют, как пользователи аутентифицируются для каждого запроса. Провайдеры определяют, как пользователи извлекаются из постоянного хранилища.

    Laravel поставляется с охранником session, поддерживающим состояние с использованием хранилища сессий и cookies, и охранником token для API-токенов.

    Для провайдеров Laravel поставляется с провайдером eloquent для получения пользователей с использованием Eloquent ORM и провайдером database для получения пользователей с использованием построителя запросов к базе данных.

    Охранники и провайдеры можно настроить в файле config/auth.php. Laravel также предоставляет возможность создания пользовательских охранников и провайдеров.

    Стартовые наборы¶

    Laravel предлагает широкий спектр официальных стартовых наборов приложений со встроенными функциями аутентификации:

    1. Laravel Breeze: Простая, минимальная реализация всех функций аутентификации Laravel, включая вход, регистрацию, сброс пароля, верификацию email и подтверждение пароля.
    2. Laravel Fortify: Безголовый бэкенд аутентификации, включающий вышеперечисленные функции аутентификации наряду с двухфакторной аутентификацией.
    3. Laravel Jetstream: Стартовый набор приложения, предоставляющий интерфейс на основе функций аутентификации Laravel Fortify.

    Рекомендуется использовать один из этих стартовых наборов для обеспечения надёжной и безопасной аутентификации в ваших Laravel-приложениях.

    Пакеты аутентификации API¶

    Laravel также предлагает следующие пакеты аутентификации API:

    1. Passport: Провайдер аутентификации OAuth2.
    2. Sanctum: Провайдер аутентификации по API-токенам.

    Стартовые наборы, такие как Fortify и Jetstream, имеют встроенную поддержку Sanctum.

    Массовое назначение¶

    Массовое назначение — распространённая уязвимость в современных web-приложениях, использующих ORM, такой как Eloquent ORM Laravel.

    Массовое назначение — это уязвимость, при которой шаблон ORM используется для изменения элементов данных, которые пользователь обычно не должен иметь возможности изменять.

    Рассмотрим следующий код:

    Route::any('/profile', function (Request $request) {
    $request->user()->forceFill($request->all())->save();

    $user = $request->user()->fresh();

    return response()->json(compact('user'));
})->middleware('auth');

    Приведённый маршрут профиля позволяет вошедшему в систему пользователю изменять информацию профиля.

    Однако предположим, что в таблице пользователей есть столбец is_admin. Вероятно, вы не хотите, чтобы пользователь мог изменять значение этого столбца. Однако приведённый код позволяет пользователям изменять любые значения столбцов в своей строке таблицы пользователей. Это уязвимость массового назначения.

    Laravel по умолчанию имеет встроенные функции для защиты от этой уязвимости. Убедитесь в следующем для обеспечения безопасности:

    • Уточняйте разрешённые параметры для обновления с помощью $request->only или $request->validated вместо $request->all.
    • Не снимайте защиту с моделей и не устанавливайте переменную $guarded в пустой массив. Делая это, вы фактически отключаете встроенную защиту Laravel от массового назначения.
    • Избегайте использования методов, таких как forceFill или forceCreate, обходящих механизм защиты. Однако вы можете использовать эти методы, если передаёте валидированный массив значений.

    SQL-инъекция¶

    Атаки SQL-инъекций, к сожалению, довольно распространены в современных web-приложениях и предполагают предоставление злоумышленниками вредоносных данных запроса для вмешательства в SQL-запросы. В этом руководстве рассматриваются SQL-инъекции и способы их предотвращения специально для Laravel-приложений. Также можно обратиться к Шпаргалке по предотвращению SQL-инъекций для получения дополнительной информации, не специфичной для Laravel.

    Защита Eloquent ORM от SQL-инъекций¶

    По умолчанию Eloquent ORM Laravel защищает от SQL-инъекций путём параметризации запросов и использования SQL-привязок. Например, рассмотрим следующий запрос:

    use App\Models\User;

User::where('email', $email)->get();

    Приведённый код выполняет следующий запрос:

    select * from `users` where `email` = ?

    Таким образом, даже если $email является ненадёжными данными пользовательского ввода, вы защищены от атак SQL-инъекций.

    SQL-инъекция в сырых запросах¶

    Laravel также предлагает выражения сырых запросов и сырые запросы для построения сложных запросов или запросов, специфичных для базы данных, которые не поддерживаются из коробки.

    Хотя это отлично для гибкости, необходимо всегда использовать SQL-привязки данных для таких запросов. Рассмотрим следующий запрос:

    use Illuminate\Support\Facades\DB;
use App\Models\User;

User::whereRaw('email = "'.$request->input('email').'"')->get();
DB::table('users')->whereRaw('email = "'.$request->input('email').'"')->get();

    Обе строки кода фактически выполняют один и тот же запрос, который уязвим к SQL-инъекции, поскольку не использует SQL-привязки для ненадёжных данных пользовательского ввода.

    Приведённый код выполняет следующий запрос:

    select * from `users` where `email` = "значение параметра запроса email"

    Всегда помните об использовании SQL-привязок для данных запросов. Можно исправить приведённый код, внеся следующее изменение:

    use App\Models\User;

User::whereRaw('email = ?', [$request->input('email')])->get();

    Также можно использовать именованные SQL-привязки:

    use App\Models\User;

User::whereRaw('email = :email', ['email' => $request->input('email')])->get();

    SQL-инъекция в именах столбцов¶

    Никогда не следует позволять данным пользовательского ввода определять имена столбцов, на которые ссылаются запросы.

    Следующие запросы могут быть уязвимы к SQL-инъекции:

    use App\Models\User;

User::where($request->input('colname'), 'somedata')->get();
User::query()->orderBy($request->input('sortBy'))->get();

    Важно учитывать, что хотя Laravel имеет некоторые встроенные функции, такие как оборачивание имён столбцов, для защиты от вышеуказанных уязвимостей SQL-инъекций, некоторые движки баз данных (в зависимости от версий и конфигураций) всё ещё могут быть уязвимы, поскольку привязка имён столбцов не поддерживается базами данных.

    В лучшем случае это может привести к уязвимости массового назначения, а не к SQL-инъекции, поскольку вы могли ожидать определённый набор значений столбцов, но поскольку они не валидируются, пользователь может использовать другие столбцы.

    Всегда валидируйте пользовательский ввод в подобных ситуациях:

    use App\Models\User;

$request->validate(['sortBy' => 'in:price,updated_at']);
User::query()->orderBy($request->validated()['sortBy'])->get();

    SQL-инъекция в правилах валидации¶

    Некоторые правила валидации имеют возможность указывать имена столбцов базы данных. Такие правила уязвимы к SQL-инъекции аналогично SQL-инъекции в именах столбцов, поскольку построение запросов выполняется схожим образом.

    Например, следующий код может быть уязвимым:

    use Illuminate\Validation\Rule;

$request->validate([
    'id' => Rule::unique('users')->ignore($id, $request->input('colname'))
]);

    За кулисами приведённый код инициирует следующий запрос:

    use App\Models\User;

$colname = $request->input('colname');
User::where($colname, $request->input('id'))->where($colname, '<>', $id)->count();

    Поскольку имя столбца определяется пользовательским вводом, это аналогично SQL-инъекции в именах столбцов.

    Межсайтовый скриптинг (XSS)¶

    XSS-атаки — это инъекционные атаки, при которых вредоносные скрипты (например, фрагменты кода JavaScript) внедряются в доверенные web-сайты.

    Шаблонизатор Blade Laravel имеет операторы вывода {{ }}, автоматически экранирующие переменные с использованием PHP-функции htmlspecialchars для защиты от XSS-атак.

    Laravel также предлагает отображение неэкранированных данных с использованием синтаксиса {!! !!}. Это не должно использоваться с ненадёжными данными, иначе приложение будет подвержено XSS-атаке.

    Например, если в каком-либо шаблоне Blade есть что-то подобное, это приведёт к уязвимости:

    {!! request()->input('somedata') !!}

    Однако это безопасно:

    {{ request()->input('somedata') }}

    Для получения дополнительной информации о предотвращении XSS, не специфичной для Laravel, можно обратиться к Шпаргалке по предотвращению межсайтового скриптинга.

    Неограниченная загрузка файлов¶

    Атаки с неограниченной загрузкой файлов предполагают загрузку злоумышленниками вредоносных файлов для компрометации web-приложений. В этом разделе описывается, как защититься от таких атак при создании Laravel-приложений. Также можно обратиться к Шпаргалке по загрузке файлов для получения дополнительной информации.

    Всегда валидируйте тип и размер файла¶

    Всегда валидируйте тип файла (расширение или MIME-тип) и размер файла, чтобы избежать DoS-атак на хранилище и удалённого выполнения кода:

    $request->validate([
    'photo' => 'file|size:100|mimes:jpg,bmp,png'
]);

    DoS-атаки на хранилище эксплуатируют отсутствие валидации размера файла и загружают массивные файлы для создания отказа в обслуживании (DoS) путём исчерпания дискового пространства.

    Атаки с удалённым выполнением кода предполагают сначала загрузку вредоносных исполняемых файлов (например, PHP-файлов), а затем запуск вредоносного кода путём посещения URL файла (если он публичный).

    Обе эти атаки можно избежать с помощью простой валидации файлов, как описано выше.

    Не полагайтесь на пользовательский ввод для определения имён файлов или путей¶

    Если приложение позволяет пользовательским данным формировать путь загрузки файла, это может привести к перезаписи критически важного файла или сохранению файла в нежелательном месте.

    Рассмотрим следующий код:

    Route::post('/upload', function (Request $request) {
    $request->file('file')->storeAs(auth()->id(), $request->input('filename'));

    return back();
});

    Этот маршрут сохраняет файл в каталог, специфичный для идентификатора пользователя. Здесь используются данные пользовательского ввода filename, что может привести к уязвимости, так как имя файла может быть что-то вроде ../2/filename.pdf. Это загрузит файл в каталог пользователя с идентификатором 2 вместо каталога текущего вошедшего пользователя.

    Для исправления следует использовать PHP-функцию basename для удаления информации о каталоге из входных данных filename:

    Route::post('/upload', function (Request $request) {
    $request->file('file')->storeAs(auth()->id(), basename($request->input('filename')));

    return back();
});

    По возможности избегайте обработки ZIP или XML файлов¶

    XML-файлы могут подвергнуть приложение широкому спектру атак, таких как XXE-атаки, атака «миллиард смехов» и другие. При обработке ZIP-файлов вы можете быть подвержены DoS-атакам с ZIP-бомбой.

    Обратитесь к Шпаргалке по безопасности XML и Шпаргалке по загрузке файлов для получения дополнительной информации.

    Path Traversal (обход каталога)¶

    Атака path traversal направлена на доступ к файлам путём манипуляции данными запроса с последовательностями ../ и их вариациями или с использованием абсолютных путей к файлам.

    Если пользователям разрешено скачивать файлы по имени файла, вы можете быть уязвимы, если входные данные не очищаются от информации о каталоге.

    Рассмотрим следующий код:

    Route::get('/download', function(Request $request) {
    return response()->download(storage_path('content/').$request->input('filename'));
});

    Здесь имя файла не очищается от информации о каталоге, поэтому некорректное имя файла, например ../../.env, может раскрыть учётные данные приложения потенциальным злоумышленникам.

    Аналогично неограниченной загрузке файлов, следует использовать PHP-функцию basename для удаления информации о каталоге:

    Route::get('/download', function(Request $request) {
    return response()->download(storage_path('content/').basename($request->input('filename')));
});

    Открытое перенаправление¶

    Атаки открытого перенаправления сами по себе не очень опасны, но они позволяют проводить фишинговые атаки.

    Рассмотрим следующий код:

    Route::get('/redirect', function (Request $request) {
   return redirect($request->input('url'));
});

    Этот код перенаправляет пользователя на любой внешний URL, предоставленный пользовательским вводом. Это позволяет злоумышленникам создавать внешне безопасные URL, например https://example.com/redirect?url=http://evil.com. Например, злоумышленники могут использовать URL такого типа для подделки писем сброса пароля и заманивания жертв для раскрытия учётных данных на сайте злоумышленника.

    Межсайтовая подделка запроса (CSRF)¶

    Межсайтовая подделка запроса (CSRF) — это тип атаки, происходящей, когда вредоносный web-сайт, электронное письмо, блог, мгновенное сообщение или программа заставляет web-браузер пользователя выполнить нежелательное действие на доверенном сайте, когда пользователь аутентифицирован.

    Laravel предоставляет защиту CSRF из коробки с промежуточным ПО VerifyCSRFToken. В целом, если это промежуточное ПО находится в группе web в вашем классе App\Http\Kernel, вы должны быть хорошо защищены:

    /**
 * Группы промежуточного ПО маршрутов приложения.
 *
 * @var array
 */
protected $middlewareGroups = [
    'web' => [
        ...
         \App\Http\Middleware\VerifyCsrfToken::class,
         ...
    ],
];

    Далее, для всех форм POST-запросов можно использовать директиву Blade @csrf для генерации скрытых полей токена CSRF:

    <form method="POST" action="/profile">
    @csrf

    <!-- Эквивалентно... -->
    <input type="hidden" name="_token" value="{{ csrf_token() }}" />
</form>

    Для AJAX-запросов можно настроить заголовок X-CSRF-Token.

    Laravel также предоставляет возможность исключения определённых маршрутов из защиты CSRF с использованием переменной $except в классе промежуточного ПО CSRF. Как правило, следует исключать только stateless маршруты (например, API или webhook) из защиты CSRF. Если исключены другие маршруты, это может привести к уязвимостям CSRF.

    Инъекция команд¶

    Уязвимости инъекции команд предполагают выполнение shell-команд, построенных с неэкранированными данными пользовательского ввода.

    Например, следующий код выполняет whois для предоставленного пользователем доменного имени:

    public function verifyDomain(Request $request)
{
    exec('whois '.$request->input('domain'));
}

    Приведённый код уязвим, поскольку данные пользователя не экранируются должным образом. Для этого можно использовать PHP-функции escapeshellcmd и/или escapeshellarg.

    Другие инъекции¶

    Атаки инъекции объектов, инъекции eval-кода и перехвата переменных extract предполагают десериализацию, оценку или использование функции extract для ненадёжных данных пользовательского ввода.

    Некоторые примеры:

    unserialize($request->input('data'));
eval($request->input('data'));
extract($request->all());

    В целом, избегайте передачи ненадёжных входных данных в эти опасные функции.

    Ограничение частоты запросов¶

    Laravel предоставляет встроенные механизмы для защиты маршрутов от чрезмерных запросов и потенциального злоупотребления.

    Два основных способа реализации ограничения частоты запросов:

    1. Промежуточное ПО throttle — встроенное промежуточное ПО, которое можно применять непосредственно к маршрутам или группам маршрутов.
    2. RateLimiter::for() — позволяет определять пользовательские правила ограничения частоты запросов с большей гибкостью.

    Ниже основные способы эффективного применения ограничения частоты запросов:

    1. Для отдельного маршрута¶

    Применение лимита непосредственно к одному маршруту с использованием промежуточного ПО throttle:

    Route::get('/profile', function () {
    return 'User profile';
})->middleware('throttle:10,1'); // 10 запросов в минуту

    2. Для группы маршрутов¶

    Применение лимита к группе маршрутов:

    Route::middleware('throttle:20,1')->group(function () {
    Route::get('/posts', fn () => 'Posts');
    Route::get('/comments', fn () => 'Comments');
});

    3. Пользовательский ограничитель частоты¶

    Определение пользовательского ограничителя частоты в RouteServiceProvider с использованием RateLimiter::for():

    use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('custom-limit', function ($request) {
    return Limit::perMinute(5)->by($request->user()?->id ?: $request->ip());
});

    Применение пользовательского ограничителя к маршрутам:

    Route::middleware('throttle:custom-limit')->get('/dashboard', fn () => 'Dashboard');

    4. Глобальное ограничение API / Web¶

    Laravel позволяет применять глобальное ограничение частоты запросов к целым группам маршрутов, таким как api или web, включая промежуточное ПО throttle в Kernel.php (обратите внимание, что группа api ограничена по частоте по умолчанию).

    protected $middlewareGroups = [
    'api' => [
        'throttle:60,1', // 60 запросов в минуту глобально для API
        // ...
    ],

    'web' => [
        'throttle:30,1', // 30 запросов в минуту глобально для web
        // ...
    ],
];

    Подробнее см. в официальной документации Laravel по ограничению частоты запросов.

    Заголовки безопасности¶

    Следует рассмотреть добавление следующих заголовков безопасности в web-сервер или промежуточное ПО Laravel-приложения:

    • X-Frame-Options
    • X-Content-Type-Options
    • Strict-Transport-Security (только для приложений HTTPS)
    • Content-Security-Policy

    Дополнительную информацию см. в проекте OWASP Secure Headers.
