    Application Logging Vocabulary Cheat Sheet¶

    Данный документ предлагает стандартный словарь для логирования событий безопасности. Цель — упростить мониторинг и оповещение: если разработчики перехватывают ошибки и записывают их в лог с использованием этого словаря, качество мониторинга и оповещений можно повысить, просто отслеживая наличие этих терминов.

    Overview¶

    Каждый год IBM Security заказывает Ponemon Institute опрос компаний по всему миру, посвящённый инцидентам безопасности, методам снижения ущерба и связанным затратам; его результатом является отчёт Cost of a Data Breach Report.

    Помимо миллионов долларов потерь от утечек данных, отчёт констатирует, что среднее время обнаружения утечки по-прежнему составляет около 200 дней. Очевидно, что улучшение мониторинга приложений и своевременное оповещение об аномальном поведении позволит сократить время выявления атаки и реагирования на неё.

    IBM Cost of a Data Breach Study 2025, Fig.4, pg.12, [https://www.ibm.com/reports/data-breach]

    Данный стандарт логирования призван определить конкретные ключевые слова, которые при последовательном применении в программном обеспечении позволят командам отслеживать соответствующие события во всех приложениях и оперативно реагировать в случае атаки.

    Assumptions¶

    • Группы наблюдаемости/SRE обязаны поддерживать использование данного стандарта и поощрять его применение разработчиками.
    • Реагирование на инциденты должно либо принимать эти данные, либо предоставлять средства, с помощью которых другие команды мониторинга смогут направлять уведомления об оповещениях, желательно программным способом.
    • Архитекторы обязаны поддерживать, принимать и развивать данный стандарт.
    • Разработчики должны принять данный стандарт и начать его внедрение (это требует знаний и готовности понимать потенциальные атаки и перехватывать соответствующие ошибки в коде).

    Getting Started¶

    Напомним, что цель логирования — возможность оповещения о конкретных событиях безопасности. Разумеется, первый шаг к логированию таких событий — грамотная обработка ошибок: если вы не перехватываете события, у вас нет данных для записи в лог.

    Identifying Events¶

    Для лучшего понимания логирования событий безопасности полезно иметь общее представление о моделировании угроз, даже если это простой подход из следующих вопросов:

    1. Что может пойти не так?
    • Заказы: может ли кто-то оформить заказ от имени другого человека?
    • Аутентификация: могу ли я войти в систему под чужим аккаунтом?
    • Авторизация: могу ли я просмотреть чужой аккаунт?
    1. Что произойдёт, если это случится?
    • Заказы: я оформил заказ от чужого имени... на заброшенный склад в Нью-Джерси. Упс.
    • Затем похвастался этим на 4Chan.
    • Затем рассказал об этом в New York Times.
    1. Кто может намеренно это сделать?
    • Преднамеренные атаки хакеров.
    • Сотрудник, «проверяющий», как работает система.
    • Некорректно написанный API, выполняющий действия, не предусмотренные автором.

    Implementation¶

    Для некоторых языков существуют библиотеки, упрощающие внедрение данного словаря логирования в приложения:

    • Python: lucabello/owasp-logger
    • C#/.NET: byteguard-hq/byteguard-security-logger

    Format¶

    ПРИМЕЧАНИЕ: Все даты должны логироваться в формате ISO 8601 со смещением UTC для обеспечения максимальной переносимости

    {
    "datetime": "2021-01-01T01:01:01-0700",
    "appid": "foobar.netportal_auth",
    "event": "AUTHN_login_success:joebob1",
    "level": "INFO",
    "description": "User joebob1 login successfully",
    "useragent": "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_14_6) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/78.0.3904.108 Safari/537.36",
    "source_ip": "165.225.50.94",
    "host_ip": "10.12.7.9",
    "hostname": "portalauth.foobar.com",
    "protocol": "https",
    "port": "440",
    "request_uri": "/api/v2/auth/",
    "request_method": "POST",
    "region": "AWS-US-WEST-2",
    "geo": "USA"
}

    The Vocabulary¶

    Далее перечислены различные типы событий, которые необходимо фиксировать. Для каждого типа события указан префикс, например «authn», а также дополнительные данные, которые могут быть включены для этого события.

    Фрагменты полного формата лога приведены для примера, однако полная запись события должна следовать формату, указанному выше.

    Примечание о конфиденциальности данных:

    Все поля, логируемые после типа события, следует считать необязательными. Организации, внедряющие данный метод логирования, должны соотносить ценность логируемых полей с ответственностью за сохранность этих данных как распорядителя информации. Например: логирование IP-адреса пользователя может быть полезным для обнаружения инцидентов и реагирования, однако в сочетании с другими данными оно может считаться персонально идентифицирующей информацией, подпадающей под регуляторные требования или запросы на удаление.

    Authentication [AUTHN]¶

    authn_login_success[:userid]¶

    Description Все события входа должны фиксироваться, включая успешные.

    Level: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_login_success:joebob1",
    "level": "INFO",
    "description": "User joebob1 login successfully",
    ...
}

    authn_login_successafterfail[:userid,retries]¶

    Description Пользователь успешно вошёл в систему после предшествующих неудачных попыток.

    Level: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_login_successafterfail:joebob1,2",
    "level": "INFO",
    "description": "User joebob1 login successfully",
    ...
}

    authn_login_fail[:userid]¶

    Description Все события входа должны фиксироваться, включая неудачные.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_login_fail:joebob1",
    "level": "WARN",
    "description": "User joebob1 login failed",
    ...
}

    authn_login_fail_max[:userid,maxlimit(int)]¶

    Description Все события входа должны фиксироваться, включая неудачные.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_login_fail_max:joebob1,3",
    "level": "WARN",
    "description": "User joebob1 reached the login fail limit of 3",
    ...
}

    authn_login_lock[:userid,reason]¶

    Description Если функция блокировки аккаунта после x попыток или по иным условиям существует, блокировка должна логироваться с соответствующими данными.

    Level: WARN

    Reasons:

    • maxretries: Достигнуто максимальное количество попыток
    • suspicious: На аккаунте обнаружена подозрительная активность
    • customer: Клиент запросил блокировку своего аккаунта
    • other: Прочее

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_login_lock:joebob1,maxretries",
    "level": "WARN",
    "description": "User joebob1 login locked because maxretries exceeded",
    ...
}

    authn_password_change[:userid]¶

    Description Каждое изменение пароля должно логироваться, включая идентификатор пользователя, для которого оно выполнялось.

    Level: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_password_change:joebob1",
    "level": "INFO",
    "description": "User joebob1 has successfully changed their password",
    ...
}

    authn_password_change_fail[:userid]¶

    Description Неудачная попытка изменения пароля. Может также инициировать другие события, например authn_login_lock.

    Level: CRITICAL

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_password_change_fail:joebob1",
    "level": "CRITICAL",
    "description": "User joebob1 failed to change their password",
    ...
}

    authn_impossible_travel[:userid,region1,region2]¶

    Description Когда пользователь, авторизованный в одном городе, неожиданно появляется в другом, слишком далёком, чтобы туда можно было добраться за разумное время, — это зачастую указывает на возможный захват аккаунта.

    Level:: CRITICAL

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "authn_impossible_travel:joebob1,US-OR,CN-SH",
    "level": "CRITICAL",
    "description": "User joebob1 has accessed the application in two distant cities at the same time",
    ...
}

    authn_token_created[:userid, entitlement(s)]¶

    Description Создание токена для доступа к сервису должно фиксироваться.

    Level:: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "aws.foobar.com",
    "event": "authn_token_created:app.foobarapi.prod,create,read,update",
    "level": "INFO",
    "description": "A token has been created for app.foobarapi.prod with create,read,update",
    ...
}

    authn_token_revoked[:userid,tokenid]¶

    Description Токен был отозван для указанного аккаунта.

    Level:: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "aws.foobar.com",
    "event": "authn_token_revoked:app.foobarapi.prod,xyz-abc-123-gfk",
    "level": "INFO",
    "description": "Token ID: xyz-abc-123-gfk was revoked for user app.foobarapi.prod",
    ...
}

    MCP Servers [MCP]¶

    Данный раздел посвящён вопросам, связанным с использованием MCP-серверов — как в продуктивных приложениях, так и на корпоративном уровне.

    mcp_prompt_injection[:userid]¶

    Description Когда MCP-клиент или MCP-сервер обнаруживает признаки prompt injection (например, инструкции игнорировать системные/разработческие сообщения, попытки переопределить политики инструментов, запросы на раскрытие секретов или попытки принудить к вызову инструментов за пределами предусмотренной задачи), действие должно быть заблокировано или ограничено, а событие — зафиксировано для расследования.

    ПРИМЕЧАНИЕ: Избегайте логирования полного содержимого prompt/tool I/O. Предпочтительнее логировать категорию обнаружения или идентификатор правила, целевой инструмент/сервер и идентификаторы запроса для обеспечения расследования без создания вторичного риска утечки конфиденциальных данных или log injection.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",

    mcp_resource_exhaustion[:userid]¶

    Description Когда MCP-клиент или MCP-сервер обнаруживает паттерн запросов, направленный на исчерпание ресурсов (например, необычно большие промпты, многократные повторные попытки, циклы вызовов инструментов или иное поведение, приводящее к чрезмерному расходу токенов и затратам), активность должна быть прекращена или ограничена, а попытка — зафиксирована.

    ПРИМЕЧАНИЕ: Избегайте логирования полных промптов или входных/выходных данных инструментов. Предпочтительнее логировать измеренное потребление (токены входящие/исходящие), пороги политик, идентификаторы запросов и задействованный инструмент/модель.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",

    "event": "mcp_resource_exhaustion:joebob1",

    mcp_tool_poisoning[:userid]¶

    Description Когда MCP-клиент или MCP-сервер обнаруживает, что инструмент может быть вредоносным или подменённым (например, неожиданные изменения инструмента, сбои проверки подписи/хэша, подозрительные метаданные инструмента или инструмент из маркетплейса агентов/инструментов с минимальной валидацией), инструмент должен быть заблокирован или помещён в карантин, а попытка — зафиксирована.

    ПРИМЕЧАНИЕ: Экосистемы инструментов и маркетплейсы агентов могут способствовать быстрому распространению сторонних инструментов с относительно слабой валидацией. Настоятельно рекомендуется использовать внутренний маркетплейс или хэшированный список разрешённых инструментов.

    Level: CRITICAL

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "sequence_fail:joebob1",
    "level": "CRITICAL",
    "description": "User joebob1 has reached a part of the application out of the normal application flow.",
    ...
}

    Session Management [SESSION]¶

    session_created:[userid]¶

    Description При создании новой аутентифицированной сессии она может логироваться, а её активность — отслеживаться.

    Level: INFO

    Example:

        {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "session_created:joebob1",
    "level": "INFO",
    "description": "User joebob1 has started a new session",
    ...
}

    session_renewed:[userid]¶

    Description Когда пользователь получает предупреждение об истечении/отзыве сессии и выбирает её продление, эта активность должна логироваться. Кроме того, если система содержит строго конфиденциальные данные, продление сессии может потребовать дополнительной верификации.

    Level: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "session_renewed:joebob1",
    "level": "INFO",
    "description": "User joebob1 was warned of expiring session and extended.",
    ...
}

    session_expired:[userid,reason]¶

    Description При истечении сессии, особенно аутентифицированной или содержащей конфиденциальные данные, это событие может логироваться с пояснительными данными. Код причины может быть любым, например: logout, timeout, revoked и т.д. Сессии никогда не должны удаляться — вместо этого при необходимости отзыва они должны переводиться в статус истёкших.

    Level: INFO

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "session_expired:joebob1,revoked",
    "level": "INFO",
    "description": "User joebob1 session expired due to administrator revocation.",
    ...
}

    session_use_after_expire:[userid]¶

    Description В случае попытки пользователя получить доступ к системе с истёкшей сессией полезно зафиксировать это событие, особенно в сочетании с последующей неудачной попыткой входа. Это может указывать на попытку захвата сессии или непосредственный доступ к устройству/браузеру другого человека со стороны злоумышленника.

    Level: CRITICAL

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "session_use_after_expire:joebob1",
    "level": "CRITICAL",
    "description": "User joebob1 attempted access after session expired.",
    ...
}

    System Events [SYS]¶

    sys_startup:[userid]¶

    Description При первом запуске системы полезно зафиксировать этот факт — даже если система является бессерверной или контейнерной — особенно если есть возможность записать пользователя, инициировавшего запуск.

    Level: WARN

    "description": "User joebob1 spawned a new instance",

    sys_shutdown:[userid]¶

    Level: WARN

    Example:

    {

    "event": "sys_shutdown:joebob1",

    sys_restart:[userid]¶

    Description При перезапуске системы полезно зафиксировать это событие — даже если система является бессерверной или контейнерной — особенно если есть возможность записать пользователя, инициировавшего перезапуск.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "sys_restart:joebob1",
    "level": "WARN",

    sys_crash[:reason]¶

    Description Если возможно перехватить нестабильное состояние системы, приводящее к её краху, логирование этого события может быть полезным — особенно если событие вызвано атакой.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "sys_crash:outofmemory,
    "level": "WARN",
    "description": "The system crashed due to Out of Memory error.",
    ...
}

    sys_monitor_disabled:[userid,monitor]¶

    Description Если ваши системы содержат агенты, отвечающие за целостность файлов, ресурсы, логирование, антивирусную защиту и т.д., особенно важно знать, были ли они остановлены и кем.

    Level: WARN

    Example:

    "description": "User joebob1 has disabled CrowdStrike",
    ...
}

    sys_monitor_enabled:[userid,monitor]¶

    User Management [USER]¶

    user_created:[userid,newuserid,attributes[one,two,three]]¶

    Description При создании новых пользователей полезно логировать специфику события создания — особенно если новые пользователи могут создаваться с правами администратора.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "user_created:joebob1,user1,admin:create,update,delete",
    "level": "WARN",
    "description": "User joebob1 created user1 with admin:create,update,delete privilege attributes",
    ...
}

    user_updated:[userid,onuserid,attributes[one,two,three]]¶

    Description При обновлении пользователей полезно логировать специфику события обновления — особенно если пользователям могут назначаться права администратора.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "user_updated:joebob1,user1,admin:create,update,delete",
    "level": "WARN",
    "description": "User joebob1 updated user1 with attributes admin:create,update,delete privilege attributes",
    ...
}

    user_archived:[userid,onuserid]¶

    Description Всегда предпочтительнее архивировать пользователей, а не удалять их — если только это не является обязательным требованием. При архивировании пользователей полезно логировать специфику этого события. Злонамеренный пользователь может использовать данную функцию для отказа в обслуживании легитимным пользователям.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "user_archived:joebob1,user1",
    "level": "WARN",
    "description": "User joebob1 archived user1",
    ...
}

    user_deleted:[userid,onuserid]¶

    Description Всегда предпочтительнее архивировать пользователей, а не удалять их — если только это не является обязательным требованием. При удалении пользователей полезно логировать специфику этого события. Злонамеренный пользователь может использовать данную функцию для отказа в обслуживании легитимным пользователям.

    Level: WARN

    Example:

    {
    "datetime": "2019-01-01 00:00:00,000",
    "appid": "foobar.netportal_auth",
    "event": "user_deleted:joebob1,user1",
    "level": "WARN",
    "description": "User joebob1 has deleted user1",
    ...
}

    Exclusions¶

    Не менее важно, что вы НЕ логируете, наряду с тем, что логируете. Приватная или секретная информация, исходный код, ключи, сертификаты и т.д. никогда не должны попадать в логи.

    Для полного обзора элементов, которые следует исключить из логирования, см. OWASP Logging Cheat Sheet.
