    Памятка по безопасной загрузке файлов¶

    Введение¶

    Загрузка файлов становится всё более неотъемлемой частью любого приложения, где пользователь может загружать фотографию, резюме или видео, демонстрирующее рабочий проект. Приложение должно уметь отклонять поддельные и вредоносные файлы, чтобы обеспечить безопасность приложения и пользователей.

    Кратко, для реализации безопасной загрузки файлов следует придерживаться следующих принципов:

    • Составьте список разрешённых расширений. Разрешайте только безопасные и критически важные для бизнеса расширения
      • Убедитесь, что валидация ввода применяется до проверки расширений.
    • Проверяйте тип файла; не доверяйте заголовку Content-Type, так как он может быть подделан
    • Изменяйте имя файла на сгенерированное приложением
    • Ограничьте длину имени файла. Если возможно, ограничьте разрешённые символы
    • Установите ограничение на размер файла
    • Разрешайте загрузку файлов только авторизованным пользователям
    • Храните файлы на отдельном сервере. Если это невозможно, храните их за пределами webroot
      • При публичном доступе к файлам используйте обработчик, сопоставляющий идентификаторы с именами файлов внутри приложения (someid -> file.ext)
    • Проверяйте файл с помощью антивируса или в изолированной среде (sandbox), если это доступно, чтобы убедиться, что он не содержит вредоносных данных
    • Пропускайте файл через CDR (Content Disarm & Reconstruct), если это применимо к данному типу (PDF, DOCX и т.д.)
    • Убедитесь, что используемые библиотеки безопасно настроены и поддерживаются в актуальном состоянии
    • Защитите форму загрузки файлов от атак CSRF

    Угрозы при загрузке файлов¶

    Для оценки и точного определения необходимых мер контроля важно понимать, с чем вы сталкиваетесь. Следующие разделы должны продемонстрировать риски, связанные с функциональностью загрузки файлов.

    Вредоносные файлы¶

    Злоумышленник загружает файл с вредоносными намерениями, например:

    1. Эксплуатация уязвимостей в парсере файлов или модуле обработки (например, эксплойт ImageTrick, XXE)
    2. Использование файла для фишинга (например, форма для заявлений о приёме на работу)
    3. Отправка ZIP-бомб, XML-бомб (также известных как атака «миллиард смехов») или просто огромных файлов с целью заполнить хранилище сервера, что нарушает и повреждает доступность сервера
    4. Перезапись существующего файла в системе
    5. Активное содержимое на стороне клиента (XSS, CSRF и т.д.), которое может угрожать другим пользователям, если файлы общедоступны.

    Публичное получение файлов¶

    Если загруженный файл общедоступен, возникают дополнительные угрозы:

    1. Публичное раскрытие других файлов
    2. Организация DoS-атаки путём запроса большого количества файлов. Запросы небольшие, но ответы значительно больше
    3. Содержимое файла, которое может считаться незаконным, оскорбительным или опасным (например, персональные данные, защищённые авторским правом данные и т.д.), что превращает вас в хранилище подобных вредоносных файлов.

    Защита при загрузке файлов¶

    Не существует универсального решения для валидации пользовательского контента. Ключом к тому, чтобы сделать процесс загрузки более сложным и ограниченным потребностями и требованиями сервиса, является применение комплексного подхода (defence in depth). Реализация нескольких техник является ключевым и рекомендуемым подходом, так как ни одна техника сама по себе не достаточна для защиты сервиса.

    Валидация расширений¶

    Убедитесь, что валидация происходит после декодирования имени файла и что установлен надлежащий фильтр для предотвращения известных обходов, например:

    • Двойные расширения, например, .jpg.php, что легко обходит regex \.jpg
    • Нулевые байты, например, .php%00.jpg, где .jpg усекается и .php становится новым расширением
    • Неправильный общий regex, который недостаточно протестирован и проверен. Воздерживайтесь от написания собственной логики, если у вас нет достаточных знаний в этой области.

    Для правильного разбора и обработки расширения обратитесь к Памятке по валидации ввода.

    Список разрешённых расширений¶

    Используйте только критически важные для бизнеса расширения, не допуская каких-либо ненужных расширений. Например, если система требует:

    • загрузки изображений — разрешите один тип, согласованный для соответствия бизнес-требованиям;
    • загрузки резюме — разрешите расширения docx и pdf.

    Исходя из потребностей приложения, обеспечьте использование наименее опасных и наиболее низкорисковых типов файлов.

    Блокировка расширений¶

    Определите потенциально опасные типы файлов и заблокируйте расширения, которые вы считаете вредными для вашего сервиса.

    Обратите внимание, что блокировка определённых расширений сама по себе является слабым методом защиты. В статье об уязвимости неограниченной загрузки файлов описано, как злоумышленники могут попытаться обойти такую проверку.

    Валидация Content-Type¶

    Content-Type для загружаемых файлов предоставляется пользователем и поэтому не может считаться надёжным, так как его легко подделать. Хотя на него не следует полагаться в целях безопасности, он обеспечивает быструю проверку для предотвращения случайной загрузки пользователями файлов неверного типа.

    Помимо определения расширения загружаемого файла, его MIME-тип может быть проверен для быстрой защиты от простых атак загрузки файлов.

    Это предпочтительно делать с использованием подхода на основе белого списка; в противном случае можно использовать подход на основе чёрного списка.

    Валидация сигнатуры файла¶

    В сочетании с валидацией Content-Type можно проверить и верифицировать сигнатуру файла на соответствие ожидаемому типу файла.

    Этот метод не следует использовать самостоятельно, так как его обход весьма распространён и прост.

    Безопасность имени файла¶

    Имена файлов могут подвергать систему опасности различными способами: через использование недопустимых символов или специальных и ограниченных имён файлов. Для Windows обратитесь к следующему руководству MSDN. Для более широкого обзора различных файловых систем и особенностей работы с файлами обратитесь к странице Wikipedia о именах файлов.

    Во избежание вышеупомянутой угрозы необходимо использовать случайную строку в качестве имени файла, например генерировать UUID/GUID. Если имя файла требуется по бизнес-нуждам, следует применять надлежащую валидацию ввода для векторов атак на стороне клиента (например, активное содержимое, приводящее к XSS и CSRF-атакам) и на стороне сервера (например, перезапись или создание специальных файлов). Ограничения на длину имени файла следует учитывать исходя из системы хранения файлов, так как у каждой системы своё ограничение длины имени файла. Если имена файлов пользователей необходимы, рассмотрите реализацию следующего:

    • Установите максимальную длину
    • Ограничьте символы конкретным допустимым подмножеством, например буквенно-цифровыми символами, дефисом, пробелами и точками
      • Рекомендуется сообщать пользователю, каким должно быть допустимое имя файла.
      • Ограничьте использование ведущих точек (скрытые файлы) и последовательных точек (обход директорий).
      • Ограничьте использование ведущего дефиса или пробелов для более безопасного использования скриптов оболочки при обработке файлов.
      • Если это невозможно, заблокируйте опасные символы, которые могут угрожать фреймворку и системе, хранящей и использующей файлы.

    Валидация содержимого файла¶

    Как упоминалось в разделе Публичное получение файлов, содержимое файлов может содержать вредоносные, неприемлемые или незаконные данные.

    В зависимости от ожидаемого типа можно применять специальную валидацию содержимого файла:

    • Для изображений применение техник перезаписи изображений уничтожает любой вид вредоносного содержимого, внедрённого в изображение; это можно сделать через рандомизацию.
    • Для документов Microsoft использование Apache POI помогает валидировать загружаемые документы.
    • ZIP-файлы не рекомендуются, так как они могут содержать файлы любых типов, и связанных с ними векторов атак очень много.

    Служба загрузки файлов должна позволять пользователям сообщать о незаконном содержимом, а владельцам авторских прав — сообщать о нарушениях.

    При наличии достаточных ресурсов следует проводить ручную проверку файлов в изолированной среде перед их публикацией.

    Добавление автоматизации в процесс проверки может быть полезным, но это трудоёмкий процесс, который следует тщательно изучить перед использованием. Некоторые сервисы (например, Virus Total) предоставляют API для проверки файлов по известным хэшам вредоносных файлов. Некоторые фреймворки могут проверять и валидировать необработанный тип содержимого на соответствие заранее определённым типам файлов, например библиотека ASP.NET Drawing Library. Остерегайтесь угроз утечки данных и сбора информации публичными сервисами.

    Место хранения файлов¶

    Место хранения файлов должно выбираться исходя из требований безопасности и бизнеса. Следующие пункты расставлены по приоритету безопасности и являются включающими:

    1. Храните файлы на отдельном хосте, что обеспечивает полное разделение обязанностей между приложением, обслуживающим пользователя, и хостом, обрабатывающим загрузку файлов и их хранение.
    2. Храните файлы за пределами webroot, где разрешён только административный доступ.
    3. Храните файлы внутри webroot и устанавливайте для них только права на запись. - Если требуется доступ на чтение, необходимо установить надлежащие средства контроля (например, внутренний IP, авторизованный пользователь и т.д.)

    Хранение файлов продуманным образом в базах данных является одной дополнительной техникой. Иногда она используется для автоматических процессов резервного копирования, защиты от атак на файловую систему и решения проблем с разрешениями. В то же время это открывает возможность для проблем с производительностью (в некоторых случаях), требований к хранению для базы данных и её резервных копий, а также для SQLi-атак. Это рекомендуется только при наличии DBA в команде и при условии, что этот процесс демонстрирует улучшение по сравнению с хранением в файловой системе.

    Некоторые файлы отправляются по электронной почте или обрабатываются сразу после загрузки и не хранятся на сервере. Необходимо применять меры безопасности, описанные в этой памятке, до выполнения каких-либо действий с ними.

    Права пользователей¶

    Перед предоставлением доступа к какой-либо службе загрузки файлов должна проводиться надлежащая проверка на двух уровнях для пользователя, загружающего файл:

    • Уровень аутентификации
      • Пользователь должен быть зарегистрированным или идентифицируемым пользователем, чтобы установить ограничения на его возможности загрузки
    • Уровень авторизации
      • Пользователь должен иметь соответствующие права для доступа к файлам или их изменения

    Права доступа к файловой системе¶

    Установите права доступа к файлам согласно принципу наименьших привилегий.

    Файлы следует хранить таким образом, чтобы обеспечить:

    • Только авторизованные системные пользователи могут читать файлы
    • Для файла установлены только необходимые режимы
      • Если требуется выполнение, перед запуском файла необходимо его проверить — это обязательная рекомендация безопасности, чтобы убедиться в отсутствии макросов или скрытых скриптов.

    Ограничения на загрузку и скачивание¶

    Приложение должно устанавливать надлежащие ограничения размера для службы загрузки, чтобы защитить ёмкость файлового хранилища. Если система будет извлекать или обрабатывать файлы, ограничение размера файла следует применять после декомпрессии и использовать безопасные методы для вычисления размера zip-файлов. Подробнее об этом см. руководство по безопасному извлечению файлов из ZipInputStream, потока ввода Java для обработки ZIP-файлов.

    Приложение должно также устанавливать надлежащие ограничения запросов для службы скачивания, если она доступна, для защиты сервера от DoS-атак.
