    Query Parameterization Cheat Sheet¶

    Введение¶

    SQL Injection — одна из наиболее опасных веб-уязвимостей. Настолько опасная, что она занимала #1 место в OWASP Top 10 версии 2013 года и версии 2017 года. По состоянию на 2021 год она занимает #3 в OWASP Top 10.

    Это серьёзная угроза, поскольку SQL Injection позволяет злоумышленнику изменить структуру SQL-запроса веб-приложения таким образом, чтобы похитить данные, изменить их или потенциально обеспечить инъекцию команд в операционную систему.

    Данная шпаргалка является производной от Шпаргалки по предотвращению SQL Injection.

    Примеры параметризованных запросов¶

    Наилучшим способом предотвращения SQL Injection является использование параметризованных запросов. Следующая таблица демонстрирует на реальных примерах кода, как создавать параметризованные запросы на большинстве распространённых веб-языков. Цель этих примеров — показать веб-разработчику, как избежать SQL Injection при построении запросов к базе данных в веб-приложении.

    Обратите внимание, что многие клиентские фреймворки и библиотеки предлагают параметризацию запросов на стороне клиента. Зачастую такие библиотеки просто строят запросы путём конкатенации строк перед отправкой сырых запросов на сервер. Убедитесь, что параметризация запросов выполняется на стороне сервера!

    Примеры подготовленных выражений¶

    Использование встроенных возможностей Java¶

    String custname = request.getParameter("customerName");
String query = "SELECT account_balance FROM user_data WHERE user_name = ? ";
PreparedStatement pstmt = connection.prepareStatement( query );
pstmt.setString( 1, custname);
ResultSet results = pstmt.executeQuery( );

    Использование Java с Hibernate¶

    // HQL
@Entity // declare as entity;
@NamedQuery(
 name="findByDescription",
 query="FROM Inventory i WHERE i.productDescription = :productDescription"
)
public class Inventory implements Serializable {
 @Id
 private long id;
 private String productDescription;
}

// Use case
// This should REALLY be validated too
String userSuppliedParameter = request.getParameter("Product-Description");
// Perform input validation to detect attacks
List<Inventory> list =
 session.getNamedQuery("findByDescription")
 .setParameter("productDescription", userSuppliedParameter).list();

// Criteria API
// This should REALLY be validated too
String userSuppliedParameter = request.getParameter("Product-Description");
// Perform input validation to detect attacks
Inventory inv = (Inventory) session.createCriteria(Inventory.class).add
(Restrictions.eq("productDescription", userSuppliedParameter)).uniqueResult();

    // Input from CLI args but could be anything
let username = std::env::args().last().unwrap();

// Using build-in macros (compile time checks)
let users = sqlx::query_as!(
        User,
        "SELECT * FROM users WHERE name = ?",
        username
    )
    .fetch_all(&pool)
    .await
    .unwrap();

// Using built-in functions
let users: Vec<User> = sqlx::query_as::<_, User>(
        "SELECT * FROM users WHERE name = ?"
    )
    .bind(&username)
    .fetch_all(&pool)
    .await
    .unwrap();

    Примеры хранимых процедур¶

    SQL, написанный в веб-приложении, — не единственное место, где могут возникнуть уязвимости SQL Injection. Если вы используете хранимые процедуры и динамически формируете в них SQL-запросы, уязвимости SQL Injection могут появиться и там.

    Динамический SQL можно параметризовать с помощью переменных привязки (bind variables), чтобы обеспечить безопасность динамически создаваемого SQL.

    Ниже приведены примеры использования переменных привязки в хранимых процедурах для различных баз данных.

    Oracle с использованием PL/SQL¶

    Обычная хранимая процедура¶

    Динамический SQL не создаётся. Параметры, передаваемые в хранимые процедуры, автоматически привязываются к своему месту в запросе без каких-либо дополнительных действий:

    PROCEDURE SafeGetBalanceQuery(UserID varchar, Dept varchar) AS BEGIN
   SELECT balance FROM accounts_table WHERE user_ID = UserID AND department = Dept;
END;
    Хранимая процедура с использованием переменных привязки в SQL, запускаемом через EXECUTE¶

    Переменные привязки используются для указания базе данных, что входные данные для этого динамического SQL являются «данными», а не потенциально кодом:

    PROCEDURE AnotherSafeGetBalanceQuery(UserID varchar, Dept varchar)
          AS stmt VARCHAR(400); result NUMBER;
BEGIN
   stmt := 'SELECT balance FROM accounts_table WHERE user_ID = :1
            AND department = :2';
   EXECUTE IMMEDIATE stmt INTO result USING UserID, Dept;
   RETURN result;
END;

    SQL Server с использованием Transact-SQL¶

    Обычная хранимая процедура¶

    Динамический SQL не создаётся. Параметры, передаваемые в хранимые процедуры, автоматически привязываются к своему месту в запросе без каких-либо дополнительных действий:

    PROCEDURE SafeGetBalanceQuery(@UserID varchar(20), @Dept varchar(10)) AS BEGIN
   SELECT balance FROM accounts_table WHERE user_ID = @UserID AND department = @Dept
END
    Хранимая процедура с использованием переменных привязки в SQL, запускаемом через EXEC¶

    Переменные привязки используются для указания базе данных, что входные данные для этого динамического SQL являются «данными», а не потенциально кодом:

    PROCEDURE SafeGetBalanceQuery(@UserID varchar(20), @Dept varchar(10)) AS BEGIN
   DECLARE @sql VARCHAR(200)
   SELECT @sql = 'SELECT balance FROM accounts_table WHERE '
                 + 'user_ID = @UID AND department = @DPT'
   EXEC sp_executesql @sql,
                      '@UID VARCHAR(20), @DPT VARCHAR(10)',
                      @UID=@UserID, @DPT=@Dept
END
