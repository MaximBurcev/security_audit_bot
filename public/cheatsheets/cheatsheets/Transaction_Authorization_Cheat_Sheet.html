    Transaction Authorization Cheat Sheet¶

    Назначение и целевая аудитория¶

    В этом справочном листе рассматривается, как разработчики могут обеспечить безопасность авторизации транзакций и предотвратить её обход. Данные рекомендации предназначены для:

    • Банков — которые должны формировать функциональные и нефункциональные требования к авторизации транзакций.
    • Разработчиков — которым необходимо устранять уязвимости в механизмах авторизации транзакций.
    • Пентестеров — которые должны проверять, насколько защищена авторизация транзакций.

    Введение¶

    Как правило, мобильные и веб-приложения требуют от пользователей предоставления второго фактора, чтобы система могла проверить, авторизованы ли они для выполнения чувствительной операции (например, подтверждения банковского перевода). В данном документе такие действия называются авторизацией транзакций.

    Авторизация транзакций широко применяется в финансовых системах, однако необходимость в защищённых транзакциях привела к её распространению по всему интернету. Например, письмо, позволяющее пользователю разблокировать учётную запись с помощью секретного кода или ссылки с токеном, содержит авторизацию транзакции. Авторизация транзакции может быть реализована следующими методами:

    • Карточка с номером авторизации транзакции (TAN)
    • Одноразовый пароль на основе времени (OTP), например OATH TOTP (Time-based One-Time Password)
    • OTP, отправленный по SMS или предоставленный по телефону
    • Цифровая подпись с помощью смарт-карты или смартфона
    • Токен типа «запрос-ответ», включая не подключённые к компьютеру устройства чтения карт или решения, сканирующие данные транзакции с экрана компьютера пользователя

    Некоторые из перечисленных методов авторизации транзакций могут быть реализованы в виде физического устройства или мобильного приложения.

    1. Функциональные требования¶

    1.1 Метод авторизации транзакции должен позволять пользователю идентифицировать и подтвердить существенные данные транзакции¶

    Поскольку разработчики не могут предполагать, что компьютер пользователя защищён, внешний компонент авторизации должен проверять данные типовой транзакции.

    При создании компонентов авторизации транзакций разработчики должны применять принцип What You See Is What You Sign («Что видишь, то и подписываешь»). Метод авторизации должен позволять пользователю идентифицировать и подтвердить данные, существенные для конкретной транзакции. Например, в случае банковского перевода пользователь должен иметь возможность видеть целевой счёт и сумму.

    При определении того, какие данные транзакции являются существенными, разработчики должны опираться на:

    • Реальный риск
    • Технические возможности и ограничения выбранного метода авторизации
    • Положительный пользовательский опыт

    Например, если SMS-сообщение подтверждает существенные данные транзакции, разработчик может передать пользователю целевой счёт, сумму и тип перевода. Однако требовать от пользователя ввода этих данных в не подключённое CAP-устройство чтения неудобно. В таких случаях разработчику, вероятно, следует ограничиться минимальным объёмом существенных данных транзакции (например, частичным номером целевого счёта и суммой) для подтверждения.

    В целом пользователь должен проверить все существенные данные транзакции в рамках процесса авторизации. Если процесс транзакции требует от пользователя ввода данных в внешнее устройство, пользователю должен быть предъявлен запрос на подтверждение конкретного значения (например, номера целевого счёта). Отсутствие понятного запроса легко эксплуатируется с помощью методов социальной инженерии и вредоносного ПО, как описано ниже в разделе 1.4. Подробнее о проблемах перегрузки ввода см. здесь.

    1.2 Смена токена авторизации должна подтверждаться с использованием текущего токена авторизации¶

    Если пользователь может изменить токен авторизации через интерфейс приложения, он должен подтвердить эту операцию с помощью текущих учётных данных авторизации (аналогично процедуре смены пароля). Например: при смене номера телефона для получения SMS-кодов авторизационный SMS-код должен быть отправлен на текущий номер телефона.

    1.3 Смена метода авторизации должна подтверждаться с использованием текущего метода авторизации¶

    Некоторые приложения позволяют пользователю выбирать способ авторизации транзакций. В таких случаях разработчик должен убедиться, что приложение может подтвердить выбранный пользователем метод авторизации, чтобы предотвратить его изменение вредоносным ПО на наиболее уязвимый метод. Кроме того, приложение должно информировать пользователя о возможных угрозах, связанных с выбранным методом авторизации.

    1.4 Пользователи должны легко отличать процесс аутентификации от процесса авторизации транзакции¶

    Поскольку разработчики должны препятствовать авторизации пользователями мошеннических операций, приложения не должны требовать от пользователя одинаковых действий при аутентификации и при авторизации транзакции. Рассмотрим следующий пример:

    1. Приложение использует один и тот же метод для аутентификации пользователя и для авторизации транзакции (например, с помощью OTP-токена).
    2. Вредоносное ПО может использовать атаку «человек посередине», чтобы показать пользователю ложное сообщение об ошибке при вводе учётных данных, вынудив повторить процедуру аутентификации. Первые учётные данные будут использованы вредоносным ПО для аутентификации, вторые — для авторизации мошеннической транзакции. Даже схемы «запрос-ответ» могут быть использованы в таком сценарии, поскольку вредоносное ПО может подставить запрос из мошеннической транзакции и обманом получить от пользователя ответ. Подобные сценарии атак широко применяются в атаках вредоносного ПО на системы электронного банкинга.

    Для предотвращения таких атак разработчики могут обеспечить отличие действий при аутентификации от действий при авторизации транзакции:

    • Используя разные методы для аутентификации и для авторизации
    • Применяя разные действия во внешнем компоненте безопасности (например, используя разные режимы работы в CAP-устройстве чтения)
    • Отображая пользователю чёткое сообщение о том, что именно он «подписывает» (принцип «Что видишь, то и подписываешь»)

    Методы социальной инженерии могут применяться вопреки методам аутентификации и авторизации операций, однако приложение не должно упрощать реализацию подобных сценариев атак.

    1.5 Каждая транзакция должна авторизоваться с использованием уникальных учётных данных авторизации¶

    Если приложение запрашивает учётные данные авторизации транзакции только один раз (например, статический пароль, код из SMS или ответ токена), пользователь сможет авторизовать любую транзакцию в течение всей сессии или повторно использовать те же учётные данные при необходимости. В таком сценарии злоумышленники могут использовать вредоносное ПО для перехвата учётных данных и последующей авторизации любой транзакции без ведома пользователя.

    2. Нефункциональные требования¶

    2.1 Авторизация должна выполняться и проверяться на стороне сервера¶

    Как и все прочие средства защиты, авторизация транзакций должна обеспечиваться на стороне сервера. Никогда не должно быть возможности повлиять на результат авторизации путём изменения данных, передаваемых от клиента к серверу:

    • Подмена параметров, содержащих данные транзакции
    • Добавление/удаление параметров, отключающих проверку авторизации
    • Намеренное вызывание ошибки

    Для обеспечения управления данными исключительно на стороне сервера следует применять лучшие практики безопасного программирования, такие как:

    • Запрет по умолчанию (Default deny)
    • Исключение отладочного функционала из production-кода

    Следует также рассмотреть дополнительные меры защиты от подмены данных, например шифрование данных для обеспечения конфиденциальности и целостности с последующей расшифровкой и проверкой на стороне сервера.

    2.2 Метод авторизации должен определяться на стороне сервера¶

    Если пользователю доступно несколько методов авторизации транзакций, серверная сторона должна обеспечивать выполнение транзакции с использованием выбранного пользователем метода авторизации или метода, установленного политиками приложения. В противном случае вредоносное ПО могло бы понизить метод авторизации до наименее защищённого. Разработчики должны сделать невозможным изменение выбранного метода авторизации путём манипуляций с параметрами, передаваемыми клиентом.

    Разработчикам следует проявлять особую осторожность, если требуется добавить новый метод авторизации, повышающий уровень безопасности. К сожалению, разработчики нередко реализуют новый метод авторизации поверх старой кодовой базы. Такой подход небезопасен: злоумышленник может манипулировать клиентом, чтобы успешно авторизовать транзакцию, отправив параметры с использованием старого метода, даже если приложение уже перешло на новый метод.

    2.3 Данные для верификации транзакции должны формироваться на стороне сервера¶

    Если разработчики решают программно передавать существенные данные транзакции в компонент авторизации, им необходимо принять дополнительные меры для предотвращения каких-либо изменений данных транзакции на стороне клиента в момент авторизации. Все существенные данные транзакции должны быть проверены пользователем, сформированы и сохранены на сервере, а затем переданы в компонент авторизации без какой-либо возможности их подмены на стороне клиента.

    Если разработчики собирают существенные данные транзакции на стороне клиента и передают их на сервер, вредоносное ПО может подменить эти данные и отобразить в компоненте авторизации фиктивные данные транзакции.

    2.4 Приложение должно препятствовать подбору учётных данных авторизации методом перебора¶

    Разработчики должны убедиться, что их приложение исключает возможность перебора учётных данных в точке, где они передаются на сервер для верификации. После установленного числа неудачных попыток авторизации весь процесс авторизации транзакции должен быть перезапущен. Кроме того, существуют и другие методы предотвращения перебора и защиты от атак на основе автоматизации — см. OWASP Authentication Cheat Sheet.

    2.5 Приложение должно контролировать допустимые переходы между состояниями транзакции¶

    Авторизация транзакции, как правило, выполняется в несколько этапов, например:

    1. Пользователь вводит данные транзакции.
    2. Пользователь запрашивает авторизацию у приложения.
    3. Приложение инициализирует механизм авторизации.
    4. Пользователь проверяет/подтверждает данные транзакции.
    5. Пользователь предоставляет учётные данные авторизации.
    6. Приложение проверяет авторизацию и выполняет транзакцию.

    Разработчики должны обеспечить, чтобы бизнес-логика авторизации транзакции выполнялась строго последовательно, не позволяя пользователям (или злоумышленникам) выполнять шаги в произвольном порядке или пропускать их. Это должно защищать от таких техник атак, как:

    • Перезапись данных транзакции до ввода пользователем учётных данных авторизации
    • Пропуск этапа авторизации транзакции

    (см. требование 15.1 OWASP ASVS).

    2.6 Данные транзакции должны быть защищены от изменения¶

    Разработчики не должны допускать возможности изменения данных транзакции злоумышленниками после их первоначального ввода пользователем. Слабые реализации могут позволить вредоносному ПО:

    1. Повторно выполнить первый шаг из раздела 2.5 (отправку данных транзакции) в фоновом режиме до того, как пользователь введёт учётные данные авторизации, и тем самым подменить реквизиты транзакции на мошеннические.
    2. Создать и добавить новые параметры данных транзакции в HTTP-запрос, выполняющий авторизацию транзакции. В таком случае плохо реализованный процесс авторизации транзакции может авторизовать исходную транзакцию, а затем выполнить мошенническую (частный пример уязвимости Time of Check to Time of Use).

    Существует несколько способов предотвратить изменение данных транзакции в процессе авторизации:

    1. При изменении данных транзакции код может аннулировать ранее введённые данные авторизации (например, сформированный OTP) и запрос (challenge).
    2. Изменение данных транзакции может инициировать сброс процесса авторизации.
    3. Любая попытка изменить данные транзакции после их ввода пользователем является атакой на систему и должна быть зафиксирована, отслеживаться и тщательно расследоваться.

    2.7 Конфиденциальность данных транзакции должна быть обеспечена на всех этапах взаимодействия клиента и сервера¶

    Процесс авторизации транзакции должен обеспечивать конфиденциальность данных транзакции, которые пользователь будет авторизовывать (т.е. на шагах 2 и 4 раздела 2.5).

    2.8 Система должна проверять каждое исполнение транзакции и убеждаться в наличии надлежащей авторизации¶

    Конечный результат процесса ввода и авторизации транзакции (как описано в разделе 2.5) также называется исполнением транзакции. Непосредственно перед исполнением транзакции должен существовать финальный контрольный рубеж, проверяющий, была ли транзакция надлежащим образом авторизована пользователем. Этот контроль должен быть неотделим от исполнения и предотвращать такие атаки, как:

    • Time of Check to Time of Use (TOCTOU) — пример в разделе 2.6
    • Пропуск проверки авторизации в процессе ввода транзакции (см. раздел 2.5)

    2.9 Учётные данные авторизации должны быть действительны только в течение ограниченного времени¶

    В ряде атак учётные данные авторизации пользователя передаются вредоносным ПО на командный сервер (C&C) и затем используются с машины, находящейся под управлением злоумышленника. Зачастую этот процесс выполняется злоумышленником вручную. Чтобы усложнить проведение подобных атак, сервер должен разрешать авторизацию транзакции только в ограниченном временном окне — между формированием запроса (challenge или OTP) и завершением авторизации. Кроме того, такие меры помогают предотвратить атаки на исчерпание ресурсов. Временной интервал должен быть тщательно подобран так, чтобы не нарушать нормальную работу пользователей.

    2.10 Учётные данные авторизации должны быть уникальны для каждой операции¶

    Для предотвращения атак повторного воспроизведения (replay attacks) каждый набор учётных данных авторизации должен быть уникальным для каждой операции. Эти учётные данные могут формироваться различными способами в зависимости от используемого механизма. Например, разработчики могут использовать метку времени, порядковый номер или случайное значение в подписанных данных транзакции или в составе запроса.

    Примечания¶

    Ниже приведены дополнительные вопросы, которые следует учитывать при реализации авторизации транзакций, однако они выходят за рамки данного справочного листа:

    • Какие транзакции требуют авторизации? Все или только некоторые? Каждое приложение уникально, и владелец приложения должен решить, нужна ли авторизация для всех транзакций или только для части из них. Разработчикам следует провести анализ рисков, оценить риск-экспозицию конкретного приложения и принять во внимание другие защитные меры, реализованные в приложении.
    • Рекомендуется использовать криптографические операции для защиты транзакций и обеспечения их целостности, конфиденциальности и неотрекаемости.
    • Крайне важно обеспечить надлежащее выпускание и защиту ключей подписи устройства в процессе «сопряжения» (pairing), равно как и сам протокол подписи. Вредоносное ПО может пытаться подменить, внедрить или похитить ключи подписи.
    • Осведомлённость пользователей: например, при использовании методов авторизации транзакций, когда пользователь вводит существенные данные транзакции в компонент авторизации (например, внешнее специализированное устройство или мобильное приложение), пользователей следует обучать переписывать данные транзакции из доверенного источника, а не с экрана компьютера.
    • Существуют антивирусные решения, защищающие от подобных угроз, однако эти решения не могут быть эффективными на 100% и должны применяться лишь в качестве дополнительного уровня защиты.
    • Защита ключей подписи с помощью второго фактора, такого как пароли, биометрия и т.д., или использование защищённых элементов (TEE, TPM, смарт-карта).
