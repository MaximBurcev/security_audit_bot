    Symfony Cheat Sheet¶

    Введение¶

    Данный cheat sheet призван предоставить разработчикам советы по безопасности при создании приложений на фреймворке Symfony. В нём рассматриваются распространённые уязвимости и лучшие практики для обеспечения безопасности ваших Symfony-приложений.

    Хотя Symfony поставляется со встроенными механизмами безопасности, разработчики должны знать о потенциальных уязвимостях и лучших практиках, чтобы создаваемые ими приложения были безопасными. Это руководство охватывает типичные проблемы безопасности, подчёркивая важность понимания функций безопасности Symfony и их эффективного использования. Независимо от того, являетесь ли вы новичком в Symfony или опытным разработчиком, стремящимся укрепить практики безопасности, этот документ служит ценным ресурсом. Следуя изложенным здесь рекомендациям, вы сможете повысить безопасность своих Symfony-приложений и создать более безопасную цифровую среду для пользователей и данных.

    Основные разделы¶

    Cross-Site Scripting (XSS)¶

    Cross-Site Scripting (XSS) — это тип атаки, при которой вредоносный JavaScript-код внедряется в отображаемую переменную. Например, если значение переменной name — <script>alert('hello')</script>, и мы отображаем её в HTML так: Hello {{name}}, внедрённый скрипт будет выполнен при рендеринге HTML.

    Symfony по умолчанию поставляется с шаблонами Twig, которые автоматически защищают приложения от XSS-атак, используя экранирование вывода для преобразования переменных, содержащих специальные символы, путём обёртывания переменной конструкцией {{ }}.

    <p>Hello {{name}}</p>
{# если 'name' равно '<script>alert('hello!')</script>', Twig выведет:
'<p>Hello &lt;script&gt;alert(&#39;hello!&#39;)&lt;/script&gt;</p>' #}

    Если вы отображаете переменную, которой доверяете и которая содержит HTML-содержимое, можно использовать фильтр raw в Twig для отключения экранирования вывода.

    <p>{{ product.title|raw }}</p>
{# если 'product.title' равно 'Lorem <strong>Ipsum</strong>', Twig выведет
именно это вместо 'Lorem &lt;strong&gt;Ipsum&lt;/strong&gt;' #}

    Ознакомьтесь с документацией Twig по экранированию вывода, чтобы узнать, как отключить экранирование вывода для конкретного блока или всего шаблона.

    Для получения другой информации о предотвращении XSS, не специфичной для Symfony, вы можете обратиться к Cross Site Scripting Prevention Cheatsheet.

    Cross-Site Request Forgery (CSRF)¶

    Компонент Symfony Form автоматически включает CSRF-токены в формы, обеспечивая встроенную защиту от CSRF-атак. Symfony автоматически проверяет эти токены, что исключает необходимость ручного вмешательства для защиты вашего приложения.

    По умолчанию CSRF-токен добавляется как скрытое поле с именем _token, но это можно настроить для каждой формы отдельно:

    use Symfony\Component\Form\AbstractType;
use Symfony\Component\OptionsResolver\OptionsResolver;

class PostForm extends AbstractType
{

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults([
            // ...
            'csrf_protection' => true,  // включить/отключить CSRF-защиту для этой формы
            'csrf_field_name' => '_csrf_token',
            'csrf_token_id'   => 'post_item', // изменить произвольную строку для генерации токена
        ]);
    }

}

    Если вы не используете Symfony Forms, вы можете генерировать и проверять CSRF-токены самостоятельно. Для этого необходимо установить компонент symfony/security-csrf.

    composer install symfony/security-csrf

    Включите/отключите CSRF-защиту в файле config/packages/framework.yaml:

    framework:
    csrf_protection: ~

    Далее рассмотрим HTML Twig-шаблон, в котором CSRF-токен генерируется функцией Twig csrf_token():

    <form action="{{ url('delete_post', { id: post.id }) }}" method="post">
    <input type="hidden" name="token" value="{{ csrf_token('delete-post') }}">
    <button type="submit">Delete post</button>
</form>

    Затем вы можете получить значение CSRF-токена в контроллере с помощью функции isCsrfTokenValid():

    use App\Entity\Post;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Annotation\Route;

class ExampleController extends AbstractController
{

    #[Route('/posts/{id}', methods: ['DELETE'], name: 'delete_post')]
    public function delete(Post $post, Request $request): Response
    {
        $token = $request->request->get('token')
        if($this->isCsrfTokenValid($token)) {
            // ...
        }

        // ...
    }
}

    Дополнительную информацию о CSRF, не связанную с Symfony, можно найти в Cross-Site Request Forgery (CSRF) Cheat Sheet.

    SQL Injection¶

    SQL Injection — это тип уязвимости безопасности, возникающий, когда злоумышленник способен манипулировать SQL-запросом таким образом, что он может выполнять произвольный SQL-код. Это может позволить злоумышленникам просматривать, изменять или удалять данные в базе данных, что потенциально ведёт к несанкционированному доступу или потере данных.

    Symfony, особенно при использовании с Doctrine ORM (Object-Relational Mapping), обеспечивает защиту от SQL injection с помощью параметров подготовленных выражений. Благодаря этому ошибочно написать незащищённые запросы сложнее, однако это всё ещё возможно. Следующий пример показывает небезопасное использование DQL:

    use Doctrine\ORM\EntityManagerInterface;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

class ExampleController extends AbstractController {

    public function getPost(Request $request, EntityManagerInterface $em): Response
    {
        $id = $request->query->get('id');

        $dql = "SELECT p FROM App\Entity\Post p WHERE p.id = " . $id . ";";
        $query = $em->createQuery($dql);
        $post = $query->getSingleResult();

        // ...
    }
}

    Примеры ниже показывают правильные способы защиты от SQL Injection:

    • Использование встроенного метода репозитория сущностей
    $id = $request->query->get('id');
$post = $em->getRepository(Post::class)->findOneBy(['id' => $id]);
    • Использование языка Doctrine DQL
    $query = $em->createQuery("SELECT p FROM App\Entity\Post p WHERE p.id = :id");
$query->setParameter('id', $id);
$post = $query->getSingleResult();
    • Использование DBAL Query Builder
    $qb = $em->createQueryBuilder();
$post = $qb->select('p')
            ->from('posts','p')
            ->where('id = :id')
            ->setParameter('id', $id)
            ->getQuery()
            ->getSingleResult();

    Для получения дополнительной информации о Doctrine вы можете обратиться к их документации. Вы также можете обратиться к SQL Injection Prevention Cheatsheet для получения информации, не специфичной ни для Symfony, ни для Doctrine.

    Command Injection¶

    Command Injection происходит, когда вредоносный код внедряется в систему приложения и выполняется. Для получения дополнительной информации обратитесь к Command Injection Defense Cheat Sheet.

    Рассмотрим следующий пример, в котором файл удаляется с помощью функции exec() без какого-либо экранирования ввода:

    use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\AsController;
use Symfony\Component\Routing\Annotation\Route;

#[AsController]
class ExampleController
{

    #[Route('/remove_file', methods: ['POST'])]
    public function removeFile(Request $request): Response
    {
        $filename =  $request->request->get('filename');
        exec(sprintf('rm %s', $filename));

        // ...
    }
}

    В приведённом коде нет валидации пользовательского ввода. Представьте, что могло бы произойти, если бы пользователь предоставил вредоносное значение вроде test.txt && rm -rf .. Чтобы снизить этот риск, рекомендуется использовать нативные PHP-функции, в данном случае unlink(), или метод remove() компонента Symfony Filesystem вместо exec().

    Для получения информации о конкретных PHP-функциях для работы с файловой системой, подходящих для вашего случая, вы можете обратиться к документации PHP или документации компонента Symfony Filesystem.

    Open Redirection¶

    Open Redirection — это уязвимость безопасности, возникающая, когда веб-приложение перенаправляет пользователей на URL, указанный в непроверенном параметре. Злоумышленники используют эту уязвимость для перенаправления пользователей на вредоносные сайты.

    В приведённом фрагменте PHP-кода:

    use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\MapQueryParameter;
use Symfony\Component\Routing\Annotation\Route;

class ExampleController extends AbstractController
{

    #[Route('/dynamic_redirect', methods: ['GET'])]
    public function dynamicRedirect(#[MapQueryParameter] string $url): Response
    {
        return $this->redirect($url);
    }
}

    Функция контроллера перенаправляет пользователей на основе параметра запроса url без надлежащей валидации. Злоумышленники могут создавать вредоносные URL, ведя ничего не подозревающих пользователей на вредоносные сайты. Для предотвращения открытых перенаправлений всегда проверяйте и очищайте пользовательский ввод перед перенаправлением, и избегайте прямого использования недоверенного ввода в функциях перенаправления.

    Уязвимости при загрузке файлов¶

    Уязвимости при загрузке файлов — это проблемы безопасности, возникающие, когда приложение не проверяет должным образом и не обрабатывает загружаемые файлы. Важно обеспечить безопасную обработку загрузок файлов для предотвращения различных типов атак. Вот некоторые общие рекомендации для снижения этого риска в Symfony:

    Проверка типа и размера файла¶

    Всегда проверяйте тип файла на стороне сервера, чтобы принимались только разрешённые типы файлов. Также рассмотрите ограничение размера загружаемых файлов для предотвращения атак типа "отказ в обслуживании" и обеспечения наличия достаточных ресурсов сервера для обработки загрузок.

    Пример с PHP Attributes:

    use Symfony\Component\HttpFoundation\File\UploadedFile;
use Symfony\Component\Validator\Constraints\File;

class UploadDto
{
    public function __construct(
        #[File(
            maxSize: '1024k',
            mimeTypes: [
                'application/pdf',
                'application/x-pdf',
            ],
        )]
        public readonly UploadedFile $file,
    ){}
}

    Пример с Symfony Form:

    use Symfony\Component\Form\AbstractType;
use Symfony\Component\Form\Extension\Core\Type\FileType;
use Symfony\Component\Form\FormBuilderInterface;
use Symfony\Component\Validator\Constraints\File;

class FileForm extends AbstractType
{
    public function buildForm(FormBuilderInterface $builder, array $options)
    {
        $builder
            ->add('file', FileType::class, [
                'constraints' => [
                    new File([
                        'maxSize' => '1024k',
                        'mimeTypes' => [
                            'application/pdf',
                            'application/x-pdf',
                        ],
                    ]),
                ],
            ]);
    }
}

    Использование уникальных имён файлов¶

    Убедитесь, что каждый загружаемый файл имеет уникальное имя, чтобы предотвратить перезапись существующих файлов. Вы можете использовать комбинацию уникального идентификатора и оригинального имени файла для создания уникального имени.

    Безопасное хранение загружаемых файлов¶

    Храните загружаемые файлы вне публичной директории для предотвращения прямого доступа. Если вы используете публичную директорию для их хранения, настройте веб-сервер для запрета доступа к директории загрузок.

    Обратитесь к File Upload Cheatsheet для получения дополнительной информации.

    Обход директорий¶

    Атака обхода директорий (path traversal) направлена на получение доступа к файлам и директориям, хранящимся на сервере, путём манипуляции входными данными, которые ссылаются на файлы с последовательностями "../" точка-точка-слэш и их вариациями или с использованием абсолютных путей к файлам. Для получения дополнительной информации обратитесь к OWASP Path Traversal.

    Вы можете защитить своё приложение от атаки обхода директорий, проверив, является ли абсолютный путь к запрашиваемому файлу корректным, или удалив информацию о директории из имени файла.

    • Проверьте существование пути с помощью PHP-функции realpath и убедитесь, что он ведёт в директорию хранилища
    use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\MapQueryParameter;
use Symfony\Component\Routing\Annotation\Route;

class ExampleController extends AbstractController
{

    #[Route('/download', methods: ['GET'])]
    public function download(#[MapQueryParameter] string $filename): Response
    {
        $storagePath = $this->getParameter('kernel.project_dir') . '/storage';
        $filePath = $storagePath . '/' . $filename;

        $realBase = realpath($storagePath);
        $realPath = realpath($filePath);

        if ($realPath === false || !str_starts_with($realPath, $realBase))
        {
            //Обход директорий обнаружен!
        }

        // ...

    }
}
    • Удалите информацию о директории с помощью PHP-функции basename
    // ...

$storagePath = $this->getParameter('kernel.project_dir') . '/storage';
$filePath = $storagePath . '/' . basename($filename);

// ...

    Уязвимости зависимостей¶

    Уязвимости зависимостей могут подвергнуть ваше приложение различным рискам, поэтому крайне важно придерживаться лучших практик. Поддерживайте все компоненты Symfony и сторонние библиотеки в актуальном состоянии.

    Composer — менеджер зависимостей для PHP — упрощает обновление PHP-пакетов:

    composer update

    При использовании множества зависимостей некоторые из них могут содержать уязвимости безопасности. Для решения этой проблемы Symfony поставляется с Symfony Security Checker. Этот инструмент специально проверяет файл composer.lock в вашем проекте для выявления известных уязвимостей безопасности в установленных зависимостях и устранения потенциальных проблем безопасности в вашем Symfony-проекте.

    Для использования Security Checker выполните следующую команду с помощью Symfony CLI:

    symfony check:security

    Cross-Origin Resource Sharing (CORS)¶

    CORS — это функция безопасности, реализованная в веб-браузерах для контроля того, как веб-приложения в одном домене могут запрашивать и взаимодействовать с ресурсами, размещёнными на других доменах.

    В Symfony вы можете управлять политиками CORS с помощью nelmio/cors-bundle. Этот бандл позволяет точно контролировать правила CORS без изменения настроек сервера.

    Для установки с помощью Composer выполните:

    composer require nelmio/cors-bundle

    Для пользователей Symfony Flex установка автоматически генерирует базовый файл конфигурации в директории config/packages. Ознакомьтесь с примером конфигурации для маршрутов с префиксом /API.

    # config/packages/nelmio_cors.yaml
nelmio_cors:
    defaults:
        origin_regex: true
        allow_origin: ['*']
        allow_methods: ['GET', 'OPTIONS', 'POST', 'PUT', 'PATCH', 'DELETE']
        allow_headers: ['*']
        expose_headers: ['Link']
        max_age: 3600
    paths:
        '^/api': ~  # ~ означает, что конфигурация для этого пути наследуется от defaults

    Заголовки безопасности¶

    Рекомендуется усилить безопасность вашего Symfony-приложения, добавив в ответы следующие важные заголовки безопасности:

    • Strict-Transport-Security
    • X-Frame-Options
    • X-Content-Type-Options
    • Content-Security-Policy
    • X-Permitted-Cross-Domain-Policies
    • Referrer-Policy
    • Clear-Site-Data
    • Cross-Origin-Embedder-Policy
    • Cross-Origin-Opener-Policy
    • Cross-Origin-Resource-Policy
    • Cache-Control

    Для получения более подробной информации об отдельных заголовках обратитесь к проекту OWASP secure headers.

    В Symfony вы можете добавлять эти заголовки вручную или автоматически, прослушивая ResponseEvent для каждого ответа, или настроив веб-серверы, такие как Nginx или Apache.

    use Symfony\Component\HttpFoundation\Request;

$response = new Response();
$response->headers->set('X-Frame-Options', 'SAMEORIGIN');

    Управление сессиями и Cookie¶

    По умолчанию сессии настроены безопасно и включены. Однако ими можно управлять вручную в файле config/packages/framework.yaml под ключом framework.session. Убедитесь, что в конфигурации сессии установлены следующие параметры.

    Убедитесь, что cookie_secure явно не установлен в false (по умолчанию он равен true). Установка http only в true означает, что cookie не будет доступен через JavaScript.

    cookie_httponly: true

    Установите короткое время жизни сессии (TTL). Согласно рекомендациям OWASP, стремитесь к TTL сессии 2-5 минут для приложений с высокой ценностью и 15-30 минут для приложений с меньшим риском.

    cookie_lifetime: 5

    Рекомендуется установить cookie_samesite в значение lax или strict, чтобы предотвратить отправку cookie из запросов cross-origin. lax разрешает отправку cookie при "безопасных" навигациях верхнего уровня и запросах с того же сайта. При strict отправка любого cookie невозможна, если HTTP-запрос не с того же домена.

    cookie_samesite: lax|strict

    Установка cookie_secure в значение auto гарантирует, что cookie отправляются только через защищённые соединения: true для HTTPS и false для HTTP.

    cookie_secure: auto

    OWASP предоставляет более общую информацию о сессиях в Session Management Cheat Sheet. Вы также можете обратиться к Cookie Security Guide.

    В Symfony сессиями управляет сам фреймворк, используя механизмы обработки сессий Symfony, а не обработку сессий PHP по умолчанию через директиву session.auto_start = 1 в файле php.ini. Директива session.auto_start = 1 в PHP используется для автоматического запуска сессии при каждом запросе, минуя явные вызовы session_start(). Однако при использовании Symfony для управления сессиями рекомендуется отключить session.auto_start, чтобы предотвратить конфликты и непредвиденное поведение.

    Аутентификация¶

    Symfony Security предоставляет надёжную систему аутентификации, включающую провайдеры, файрволлы и контроль доступа для обеспечения безопасной и контролируемой среды доступа. Настройки аутентификации можно конфигурировать в файле config/packages/security.yaml.

    • Провайдеры

      Аутентификация Symfony опирается на провайдеры для получения информации о пользователях из различных источников хранения, таких как базы данных, LDAP или пользовательские источники. Провайдеры получают пользователей на основе определённого свойства и загружают соответствующий объект пользователя.

      В примере ниже представлен Entity User Provider, который использует Doctrine для получения пользователя по уникальному идентификатору.

      providers:
    app_user_provider:
        entity:
            class: App\Entity\User
            property: email

    • Файрволлы

      Symfony использует файрволлы для определения конфигурации безопасности для различных частей приложения. Каждый файрволл определяет конкретный набор правил и действий для входящих запросов. Они защищают различные секции приложения, указывая, какие маршруты или URL защищены, какие механизмы аутентификации используются и как обрабатывается несанкционированный доступ. Файрволл может быть связан с конкретными шаблонами, методами запросов, контролем доступа и провайдерами аутентификации.

      firewalls:
    dev: # отключить безопасность для маршрутов в среде разработки
        pattern: ^/(_(profiler|wdt)|css|images|js)/
        security: false
    admin: # обработка аутентификации для маршрутов с шаблоном /admin
        lazy: true
        provider: app_user_provider
        pattern: ^/admin
        custom_authenticator: App\Security\AdminAuthenticator
        logout:
            path: app_logout
            target: app_login
    main: # основной файрволл, охватывающий все оставшиеся маршруты
        lazy: true
        provider: app_user_provider

    • Контроль доступа

      Контроль доступа определяет, какие пользователи могут получить доступ к конкретным частям приложения. Эти правила состоят из шаблонов путей и требуемых ролей или разрешений. Правила контроля доступа конфигурируются под ключом access_control.

      access_control:
    - { path: ^/admin, roles: ROLE_ADMIN } # доступ разрешён только пользователям с ролью ROLE_ADMIN
    - { path: ^/login, roles: PUBLIC_ACCESS } # этот маршрут доступен всем

    Раскрытие информации при обработке ошибок¶

    Symfony имеет надёжную систему обработки ошибок. По умолчанию Symfony-приложения настроены на отображение подробных сообщений об ошибках только в среде разработки в целях безопасности. В производственной среде отображается общая страница ошибки. Система обработки ошибок Symfony также позволяет настраивать страницы ошибок на основе различных HTTP-кодов состояния, обеспечивая удобный пользовательский опыт в корпоративном стиле. Кроме того, Symfony записывает подробную информацию об ошибках в журналы, помогая разработчикам эффективно выявлять и устранять проблемы.

    Для получения дополнительной информации об обработке ошибок, не связанной с Symfony, обратитесь к Error Handling Cheat Sheet.

    Конфиденциальные данные¶

    В Symfony лучший способ хранения конфигураций, таких как API-ключи и т. д., — использование переменных среды, которые зависят от расположения приложения. Для обеспечения безопасности конфиденциальных значений Symfony предоставляет систему управления секретами, в которой значения дополнительно кодируются с использованием криптографических ключей и хранятся как секреты.

    Рассмотрим пример, в котором API_KEY хранится как секрет:

    Для генерации пары криптографических ключей выполните следующую команду. Файл приватного ключа является строго конфиденциальным и не должен фиксироваться в репозитории.

    bin/console secrets:generate-keys

    Эта команда создаст файл для секрета API_KEY в директории config/secrets/env(dev|prod|etc.)

    bin/console secret:set API_KEY

    Вы можете получать доступ к значениям секретов в своём коде так же, как к переменным среды. Очень важно отметить, что если существуют переменные среды и секреты с одинаковыми именами, значения переменных среды всегда переопределяют секреты.

    Для получения дополнительной информации обратитесь к документации Symfony по секретам.

    Резюме¶

    • Убедитесь, что приложение не работает в режиме отладки на продакшене. Для отключения режима отладки установите переменную среды APP_ENV в значение prod:

      APP_ENV=prod

    • Убедитесь, что конфигурация PHP безопасна. Вы можете обратиться к PHP Configuration Cheat Sheet для получения дополнительной информации о настройках безопасной конфигурации PHP.

    • Убедитесь, что SSL-сертификат правильно настроен на вашем веб-сервере, и настройте его для принудительного использования HTTPS путём перенаправления HTTP-трафика на HTTPS.

    • Реализуйте заголовки безопасности для повышения уровня защищённости вашего приложения.

    • Убедитесь, что права доступа к файлам и директориям установлены правильно для минимизации рисков безопасности.

    • Реализуйте регулярное резервное копирование производственной базы данных и критически важных файлов. Создайте план восстановления для быстрого восстановления приложения в случае возникновения проблем.

    • Используйте средства проверки безопасности для сканирования зависимостей с целью выявления известных уязвимостей.

    • Рассмотрите возможность настройки инструментов мониторинга и механизмов отчётности об ошибках для быстрого выявления и устранения проблем в производственной среде. Изучите такие инструменты, как Blackfire.io.
