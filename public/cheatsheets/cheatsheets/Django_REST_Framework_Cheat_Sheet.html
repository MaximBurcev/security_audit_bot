    Шпаргалка по Django REST Framework (DRF)¶

    Введение¶

    Данная шпаргалка содержит рекомендации по безопасности Django REST Framework для разработчиков. Это базовый набор руководящих принципов для разработчиков Django REST, которым необходимо защитить ключевые аспекты приложения.

    Что такое view в Django?¶

    View в Django — это Python-класс или функция, возвращающая web-ответ после получения web-запроса. Этот ответ может быть простым HTTP-ответом, HTML-шаблоном или HTTP-редиректом, перенаправляющим пользователя на другую страницу.

    Настройки¶

    Для настройки Django REST Framework (DRF) необходим доступ к пространству имён REST_FRAMEWORK. Как правило, оно находится в файле settings.py. С точки зрения безопасности наиболее значимыми параметрами являются:

    DEFAULT_AUTHENTICATION_CLASSES¶

    Список классов аутентификации, используемых по умолчанию для определения того, какой пользователь аутентифицирован при обращении к свойствам request.user или request.auth. Это классы 'rest_framework.authentication.SessionAuthentication' (аутентификация через сессию) и 'rest_framework.authentication.BasicAuthentication' (базовая аутентификация).

    DEFAULT_PERMISSION_CLASSES¶

    Список классов разрешений, определяющих набор разрешений по умолчанию, которые Django проверяет перед доступом к view. Поскольку значение по умолчанию — 'rest_framework.permissions.AllowAny', это означает, что если класс разрешений по умолчанию не изменён, каждый имеет доступ ко всем view по умолчанию.

    DEFAULT_THROTTLE_CLASSES¶

    Список классов ограничения запросов, определяющих набор ограничений по умолчанию, проверяемых в начале обработки view. По умолчанию ограничение запросов не настроено, так как класс по умолчанию пуст.

    DEFAULT_PAGINATION_CLASS¶

    Класс по умолчанию для пагинации наборов запросов. В Django пагинация отключена по умолчанию. Без надлежащей пагинации могут возникнуть проблемы или атаки типа «отказ в обслуживании» (DoS) при наличии большого объёма данных.

    OWASP API Security Top 10 (2019)¶

    OWASP API Security Top 10 — список наиболее критичных рисков безопасности для API, разработанный Open Worldwide Application Security Project (OWASP). Он помогает организациям выявлять и приоритизировать наиболее значимые риски для их API, чтобы можно было внедрить соответствующие меры контроля для их снижения.

    В этом разделе используется версия API Security Top 10 2019 года. Лучший подход к защите web API — начать с верхней угрозы (A1 ниже) и двигаться вниз. Это обеспечивает наибольшую эффективность времени, затрачиваемого на безопасность, поскольку сначала охватываются наиболее серьёзные угрозы. После изучения Top 10 рекомендуется оценить другие угрозы или провести профессиональный тест на проникновение.

    API1:2019 Нарушение авторизации на уровне объектов¶

    При использовании разрешений на уровне объектов убедитесь, что доступ к объекту проверяется с помощью метода .check_object_permissions(request, obj).

    Пример:

    def get_object(self):
    obj = get_object_or_404(self.get_queryset(), pk=self.kwargs["pk"])
    self.check_object_permissions(self.request, obj)
    return obj

    НЕ переопределяйте метод get_object() без проверки того, должен ли запрос иметь доступ к этому объекту.

    API2:2019 Нарушение аутентификации пользователей¶

    Для предотвращения нарушений аутентификации используйте параметр DEFAULT_AUTHENTICATION_CLASSES с правильными классами для вашего проекта и обеспечьте аутентификацию для каждой непубличной конечной точки API. Не переопределяйте класс аутентификации в представлении на основе класса (переменная authentication_classes) или функции (декоратор authentication_classes), если вы не уверены в правильности изменения и не понимаете его последствий.

    API3:2019 Избыточное раскрытие данных¶

    Для предотвращения этой проблемы отображайте только минимально необходимый объём информации. Убедитесь, что вы проверяете сериализатор и отображаемую информацию. Если сериализатор наследуется от ModelSerializer, НЕ используйте свойство Meta exclude.

    API4:2019 Отсутствие ресурсов и ограничения частоты запросов¶

    Для предотвращения этой проблемы настройте параметр DEFAULT_THROTTLE_CLASSES и НЕ переопределяйте класс ограничения в представлении на основе класса (переменная throttle_classes) или функции (декоратор throttle_classes), если вы не уверены в правильности изменения и не понимаете его последствий.

    ДОПОЛНИТЕЛЬНО: По возможности реализуйте ограничение частоты запросов с помощью WAF или аналогичного инструмента. DRF должен быть последним уровнем ограничения запросов.

    API5:2019 Нарушение авторизации на уровне функций¶

    Для устранения этой проблемы измените значение по умолчанию ('rest_framework.permissions.AllowAny') параметра DEFAULT_PERMISSION_CLASSES. Используйте параметр DEFAULT_PERMISSION_CLASSES с правильными классами для вашего проекта.

    НЕ используйте rest_framework.permissions.AllowAny, за исключением публичных конечных точек API, и НЕ переопределяйте класс авторизации в представлении на основе класса (переменная permission_classes) или функции (декоратор permission_classes), если вы не уверены в правильности изменения и не понимаете его последствий.

    API6:2019 Массовое назначение¶

    Для предотвращения этой проблемы используйте Meta.fields (подход с допустимым списком) при работе с ModelForms. НЕ используйте Meta.exclude (подход с запрещённым списком) или ModelForms.Meta.fields = "__all__".

    API7:2019 Неправильная конфигурация безопасности¶

    Для устранения этой проблемы необходимо иметь повторяемый процесс ужесточения настроек, обеспечивающий быстрое и лёгкое развёртывание правильно защищённой среды. Используйте автоматизированный процесс для непрерывной оценки эффективности конфигурации и настроек во всех средах.

    НЕ используйте пароли по умолчанию. Установите настройки Django DEBUG и DEBUG_PROPAGATE_EXCEPTIONS в значение False. Убедитесь, что API доступен только через указанные HTTP-методы. Все остальные HTTP-методы должны быть отключены. Установите SECRET_KEY в случайное значение и НИКОГДА не вшивайте секреты в код.

    ОБЯЗАТЕЛЬНО проверяйте, фильтруйте и санируйте все данные, предоставленные клиентом, или другие данные из интегрированных систем.

    API8:2019 Инъекции¶

    SQLi¶

    Для предотвращения этой проблемы используйте параметризованные запросы. Будьте осторожны при использовании опасных методов, таких как raw(), extra() и пользовательский SQL (через cursor.execute()). НЕ добавляйте пользовательский ввод в опасные методы (raw(), extra(), cursor.execute()).

    RCE¶

    Для устранения этой проблемы используйте Loader=yaml.SafeLoader для YAML-файлов. НЕ загружайте YAML-файлы, управляемые пользователем, с помощью метода load().

    Также НЕ добавляйте пользовательский ввод в опасные методы (eval(), exec() и execfile()) и НЕ загружайте pickle-файлы, управляемые пользователем, включая метод pandas pandas.read_pickle().

    API9:2019 Ненадлежащее управление активами¶

    Для предотвращения этой проблемы создайте инвентарь всех хостов API. В этом инвентаре документируйте важные аспекты каждого хоста. Сосредоточьтесь на версии API и среде API (например, production, staging, test, development) и определите, кто должен иметь сетевой доступ к хосту (например, публичный, внутренний, партнёры). Убедитесь, что все аспекты вашего API задокументированы: аутентификация, ошибки, редиректы, ограничение частоты запросов, политика CORS и конечные точки, включая их параметры, запросы и ответы.

    API10:2019 Недостаточное ведение журналов и мониторинг¶

    Для обеспечения надлежащего ведения журналов и возможностей мониторинга выполните следующее:

    --Регистрируйте все неудачные попытки аутентификации, запреты доступа и ошибки валидации входных данных с достаточным контекстом пользователя для идентификации подозрительных или вредоносных аккаунтов.

    --Создавайте журналы в формате, пригодном для использования системой управления журналами, и включайте достаточно деталей для идентификации злоумышленника.

    --Обрабатывайте журналы как конфиденциальные данные, обеспечивая их целостность в состоянии покоя и при передаче.

    --Настройте систему мониторинга для непрерывного контроля инфраструктуры, сети и работы API.

    --Используйте систему управления информацией и событиями безопасности (SIEM) для агрегации и управления журналами всех компонентов стека API и хостов.

    --Настройте пользовательские панели мониторинга и оповещения, позволяющие обнаруживать подозрительные действия и реагировать на них на более ранних этапах.

    --Обеспечьте эффективный мониторинг и оповещение, чтобы подозрительные действия обнаруживались и обрабатывались своевременно.

    НЕ следует:

    --Регистрировать общие сообщения об ошибках, например: Log.Error("Error was thrown"); вместо этого регистрируйте трассировку стека, сообщение об ошибке и идентификатор пользователя, вызвавшего ошибку.

    --Регистрировать конфиденциальные данные, такие как пароли пользователей, API-токены или персональные данные (PII).

    Другие риски безопасности¶

    Ниже приведён список рисков безопасности для API, не рассматриваемых в OWASP API Security Top 10.

    Ошибки бизнес-логики¶

    Следует учитывать возможные ошибки бизнес-логики, приводящие к уязвимостям безопасности. Поскольку ошибки бизнес-логики трудно или невозможно обнаружить с помощью автоматизированных инструментов, лучшими способами предотвращения таких ошибок являются: использование моделей угроз, проведение проверок безопасности при проектировании, проведение код-ревью, парное программирование и написание модульных тестов.

    Управление секретами¶

    Секреты никогда не должны быть вшиты в код. Лучшая практика — использовать менеджер секретов. Для получения дополнительной информации см. OWASP Шпаргалку по управлению секретами.

    Обновление Django и DRF и процесс обновления зависимостей¶

    Все приложения имеют зависимости, и эти зависимости могут содержать уязвимости. Хорошей практикой является аудит зависимостей, используемых в проекте. В целом важно иметь процесс обновления зависимостей. Примерный процесс может определять три механизма для инициирования обновления:

    --Каждый месяц/квартал зависимости обновляются в целом. --Каждую неделю рассматриваются важные уязвимости безопасности и при необходимости инициируется обновление. --В ИСКЛЮЧИТЕЛЬНЫХ случаях могут потребоваться экстренные обновления.

    Команда безопасности Django располагает информацией о том, как Django раскрывает проблемы безопасности.

    При рассмотрении библиотеки оцените её «состояние безопасности»: как часто она обновляется, есть ли известные уязвимости, активно ли сообщество? и т.д. Некоторые инструменты помогут с этой задачей (например, Snyk Advisor).

    Инструменты SAST¶

    Существует несколько отличных инструментов статического анализа безопасности с открытым исходным кодом для Python, заслуживающих внимания:

    Bandit — Bandit — инструмент для поиска распространённых проблем безопасности в Python. Bandit обрабатывает каждый файл, строит из него абстрактное синтаксическое дерево (AST) и запускает соответствующие плагины против узлов AST. По завершении сканирования всех файлов Bandit генерирует отчёт. Bandit изначально был разработан в рамках OpenStack Security Project и впоследствии перенесён в PyCQA.

    Semgrep — Semgrep — быстрый движок статического анализа с открытым исходным кодом для поиска ошибок, обнаружения уязвимостей в сторонних зависимостях и соблюдения стандартов кода. Разработан компанией «Return To Corporation» (обычно называемой r2c) и контрибьюторами открытого исходного кода. Работает на основе правил, которые могут быть ориентированы на безопасность, лучшие практики языка или что-то другое. Создавать правила несложно, а semgrep очень мощный. Для Django существует 29 правил.

    PyCharm Security — Pycharm-security — плагин для PyCharm или JetBrains IDE с плагином Python. Плагин анализирует Python-код на наличие распространённых уязвимостей безопасности и предлагает исправления. Также может запускаться из Docker-контейнера. Имеет около 40 проверок, часть из которых специфична для Django.
