    Шпаргалка по документированию архитектуры безопасности на основе микросервисов¶

    Введение¶

    Архитектура микросервисов всё шире применяется для проектирования и реализации прикладных систем как в облачной, так и в локальной инфраструктуре. Существует множество задач безопасности, которые необходимо решить на этапах проектирования и реализации приложения. Для решения некоторых из них необходимо собирать специфическую для безопасности информацию об архитектуре приложения. Цель данной статьи — предложить конкретный подход к сбору информации об архитектуре на основе микросервисов для обеспечения безопасности приложения.

    Контекст¶

    При обеспечении безопасности приложений на основе архитектуры микросервисов архитекторы/инженеры безопасности обычно сталкиваются со следующими вопросами (в основном упоминаемыми в OWASP Application Security Verification Standard Project в разделе V1 "Architecture, Design and Threat Modeling Requirements"):

    1. Моделирование угроз и применение принципа минимальных привилегий:
      • Какие области действия или API-ключи минимально необходимы микросервису для доступа к API других микросервисов?
      • Какие разрешения минимально необходимы микросервису для доступа к базе данных или очереди сообщений?
    2. Анализ утечки данных:
      • Какие хранилища или очереди сообщений содержат чувствительные данные?
      • Читает/записывает ли микросервис данные из/в конкретную базу данных или очередь сообщений?
      • Какие микросервисы вызываются конкретным микросервисом? Какие данные передаются между микросервисами?
    3. Анализ поверхности атаки:
      • Какие конечные точки микросервисов необходимо тестировать при тестировании безопасности?

    В большинстве случаев существующая документация по архитектуре приложений не подходит для ответа на эти вопросы. В следующих разделах предлагается, какую архитектурную информацию, специфическую для безопасности, можно собрать для ответа на указанные вопросы.

    Цель¶

    Цели данной шпаргалки — объяснить, какую специфическую для безопасности архитектурную информацию можно собрать для ответа на указанные вопросы, и предложить конкретный подход к сбору информации об архитектуре на основе микросервисов для обеспечения безопасности приложения.

    Предложение¶

    Сбор информации о строительных блоках¶

    Идентификация и описание сервисов, реализующих функциональность приложения¶

    Сервисы, реализующие функциональность приложения, воплощают один или несколько бизнес-процессов или функциональных возможностей (например, хранение данных клиентов, хранение и отображение каталога товаров). Соберите информацию по параметрам, указанным ниже, для каждого такого сервиса.

    Название параметра Описание
    Название сервиса (ID) Уникальное название или ID сервиса
    Краткое описание Краткое описание бизнес-процесса или функциональности, реализованной микросервисом
    Ссылка на репозиторий исходного кода Укажите ссылку на репозиторий исходного кода сервиса
    Команда разработчиков Укажите команду разработчиков, разрабатывающую данный микросервис
    Определение API Если микросервис предоставляет внешний интерфейс, укажите ссылку на описание интерфейса (например, спецификацию OpenAPI). Рекомендуется определить используемую схему безопасности, например, определить области действия или API-ключи, необходимые для вызова конкретной конечной точки (например, смотрите).
    Описание архитектуры микросервиса Укажите ссылку на диаграмму архитектуры микросервиса, описание (при наличии)
    Ссылка на runbook Укажите ссылку на runbook микросервиса

    Идентификация и описание инфраструктурных сервисов¶

    Инфраструктурные сервисы, включая удалённые, могут реализовывать аутентификацию, авторизацию, регистрацию и обнаружение сервисов, мониторинг безопасности, журналирование и т.д. Соберите информацию по параметрам, указанным ниже, для каждого инфраструктурного сервиса.

    Название параметра Описание
    Название сервиса (ID) Уникальное название или ID сервиса
    Краткое описание Краткое описание функциональности, реализованной сервисом (например, аутентификация, авторизация, регистрация и обнаружение сервисов, журналирование, мониторинг безопасности, API-шлюз).
    Ссылка на репозиторий исходного кода Укажите ссылку на репозиторий исходного кода сервиса (при наличии)
    Ссылка на документацию сервиса Укажите ссылку на документацию сервиса, включающую определение API сервиса, руководство по эксплуатации/runbook и т.д.

    Создание графического представления архитектуры приложения¶

    Рекомендуется создать графическое представление архитектуры приложения (строительных блоков и связей, определённых выше) в форме графа вызовов сервисов или диаграммы потоков данных. Для этого можно использовать специальные программные инструменты (например, Enterprise Architect) или язык DOT. Пример использования языка DOT можно посмотреть здесь.

    Использование собранной информации в практиках безопасной разработки¶

    Собранная информация может быть полезна для практик безопасности приложений, например при определении требований безопасности, моделировании угроз или тестировании безопасности. В следующих разделах приведены примеры мероприятий, связанных с обеспечением безопасности архитектуры приложения (а также их соответствие проектам OWASP), и советы по их реализации с использованием собранной выше информации.
