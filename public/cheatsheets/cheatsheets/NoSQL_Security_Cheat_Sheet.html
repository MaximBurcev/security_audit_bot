    NoSQL Security Cheat Sheet¶

    Введение¶

    NoSQL-базы данных (MongoDB, CouchDB, Cassandra и др.) лежат в основе многих современных приложений благодаря гибким схемам данных и горизонтальному масштабированию. Однако их отличающиеся модели запросов и особенности развёртывания создают больше рисков безопасности по сравнению с реляционными базами данных. Этот шпаргалочный лист содержит рекомендации по снижению рисков при использовании NoSQL-систем.

    Угрозы и типичные уязвимости¶

    • NoSQL Injection — небезопасное построение объектов запросов или строк запросов из недоверенных входных данных.
    • Открытые интерфейсы управления — административные GUI, порты базы данных или REST-эндпоинты, доступные из интернета.
    • Слабая или отсутствующая аутентификация и авторизация — открытый доступ по умолчанию или избыточные привилегии для клиентов.
    • Незащищённое сетевое взаимодействие — отсутствие TLS, открытые порты, недостаточная сетевая сегментация.
    • Небезопасные настройки по умолчанию — стандартные учётные записи администратора, пароли по умолчанию, незащищённые конфигурации.
    • Неудовлетворительные модели контроля доступа — грубые роли, допускающие горизонтальное злоупотребление.
    • Небезопасная сериализация / десериализация — удалённое выполнение кода через небезопасную десериализацию объектов.
    • Некорректно настроенный CORS / публичные API — API случайно разрешают кросс-доменные запросы или открытый доступ.
    • Утечка учётных данных и секретов — жёстко закодированные учётные данные БД в коде, образах контейнеров, логах CI.
    • Незащищённые резервные копии — бэкапы, хранящиеся в незашифрованном виде или публично доступные.
    • Риски цепочки поставок / зависимостей — уязвимые драйверы, ORM/ODM или плагины.

    Принципы безопасного проектирования¶

    • Считайте все входные данные недоверенными — валидируйте, санируйте и нормализуйте их.
    • Применяйте принцип минимальных привилегий — ограниченные роли для пользователей, сервисов и операторов.
    • Глубокая эшелонированная защита — комбинируйте сетевые средства контроля, аутентификацию, валидацию входных данных и мониторинг.
    • Безопасные настройки по умолчанию — меняйте стандартные порты и учётные записи, включайте аутентификацию и TLS по умолчанию.
    • Автоматизируйте управление секретами и их ротацию — используйте хранилища секретов и краткосрочные учётные данные.
    • Мониторинг и аудит — ведите журналы доступа и выявляйте аномалии.

    Практические меры защиты и примеры¶

    Предотвращение NoSQL-инъекций¶

    Небезопасный вариант (построение фильтра на основе строк — Node.js / MongoDB):

    // ОПАСНО: построение запроса из недоверенных входных данных
const q = "{ name: ‘" + req.query.name + "’ }";
const filter = eval("(" + q + ")"); // НИКОГДА так не делайте
db.collection(‘users’).find(filter)

    Безопасный вариант (использование объектов запроса драйвера / параметризация):

    // БЕЗОПАСНО: позвольте драйверу управлять структурой запроса
const filter = { name: req.query.name };
db.collection(‘users’).find(filter)

    Безопасный вариант (вайтлистинг для операторов):

    // Отклоняйте инъекции операторов, запрещая $ в ключах или значениях операторов
if (JSON.stringify(req.body).includes(‘"$’)) throw Error("Invalid input");

    Примечания:

    • Не принимайте от клиента необработанные JSON-фрагменты для выполнения в качестве запросов.
    • Запрещайте контролируемые клиентом операторы запросов (такие как $where, $regex или $expr), если они строго не требуются и не проверяются.
    • Для текстовых параметров поиска используйте безопасные API драйвера (например, $text с контролируемыми входными данными).

    Использование безопасных паттернов драйвера / ODM¶

    • Отдавайте предпочтение высокоуровневым API (ODM/ORM), которые безопасно строят запросы (например, Mongoose, Spring Data, паттерны драйвера Datastax).
    • Избегайте функциональности, аналогичной .eval(), и выполнения произвольных запросов из недоверенных данных.
    • Санируйте и валидируйте любые необработанные выражения перед передачей в БД.

    Пример — безопасное использование PyMongo¶

    from pymongo import MongoClient
client = MongoClient(uri, tls=True)
collection = client.mydb.users
user = collection.find_one({"email": email_input})

    Аутентификация и авторизация¶

    • Включайте аутентификацию (не запускайте базы данных без аутентификации).
    • Используйте управление доступом на основе ролей (RBAC), принцип минимальных привилегий для сервисных учётных записей.
    • Используйте отдельных пользователей для администрирования, резервного копирования, доступа только для чтения и работы приложения.
    • Используйте федеративные удостоверения или краткосрочные учётные данные там, где это поддерживается (например, AWS IAM -> DynamoDB).

    Безопасность сети и транспортного уровня¶

    • Привязывайте сервисы к внутренним интерфейсам, а не к 0.0.0.0.
    • Используйте сетевую сегментацию / приватные подсети и группы безопасности.
    • Обеспечивайте TLS (шифрование при передаче) для подключений драйверов и административных консолей.
    • Отключайте удалённое управление или ограничивайте его доступом только из административных сетей / VPN.

    Ужесточение конфигурации¶

    • Меняйте порты по умолчанию и отключайте тестовых / демонстрационных пользователей.
    • Отключайте или ограничивайте функции, выполняющие код на сервере (например, MongoDB db.eval, серверные скрипты).
    • Требуйте TLS для внутренних ссылок репликации там, где это поддерживается.

    Управление секретами¶

    • Не хардкодируйте учётные данные БД — используйте менеджер секретов (Vault, AWS Secrets Manager, Azure Key Vault).
    • Избегайте встраивания учётных данных в образы контейнеров или переменные окружения в логах CI.
    • Регулярно ротируйте учётные данные и используйте эфемерные токены там, где это возможно.

    Логирование, мониторинг и аудит¶

    • Включайте аудит-логирование (попытки подключения, действия администраторов, неудачные аутентификации).
    • Отправляйте логи в защищённую от подделки SIEM-систему.
    • Настраивайте оповещения об аномальных паттернах (всплески запросов, медленные запросы, массовый экспорт данных).
    • Отслеживайте подозрительные команды (например, действия администраторов, $where, задания map-reduce).

    Резервные копии и снимки¶

    • Шифруйте резервные копии в состоянии покоя и при передаче.
    • Ограничивайте доступ к хранилищу резервных копий.
    • Очищайте резервные копии от персональных данных (PII) в соответствии с требованиями политики.
    • Регулярно проверяйте процедуры восстановления.

    Краткий контрольный список безопасности NoSQL¶

    • Включить аутентификацию и RBAC
    • Обеспечить TLS для взаимодействия клиентов и узлов
    • Привязать БД к внутренним IP / использовать приватные сети
    • Использовать сервисные учётные записи с минимальными привилегиями
    • Запретить контролируемые клиентом операторы запросов, если они не прошли валидацию
    • Избегать выполнения произвольных запросов / eval на сервере
    • Хранить учётные данные в менеджере секретов и ротировать их
    • Ужесточить конфигурацию (отключить небезопасные настройки по умолчанию)
    • Шифровать и защищать резервные копии
    • Вести мониторинг / аудит доступа к БД и действий администраторов
    • Своевременно обновлять БД и драйверы

    Что делать и чего избегать¶

    Делайте:

    • Используйте объекты запросов драйвера вместо построения строк запросов.
    • Валидируйте и применяйте вайтлистинг к полям (столбцам/ключам), передаваемым пользователями.
    • Ограничивайте доступ к интерфейсам управления и требуйте MFA для административного доступа.
    • Автоматизируйте тестирование безопасности в CI/CD-пайплайнах.

    Не делайте:

    • Не открывайте порты БД / административные консоли в публичный интернет.
    • Не принимайте от клиентов необработанные JSON-запросы и не выполняйте eval недоверенных строк.
    • Не используйте учётные записи root / admin БД для подключений приложения.
    • Не полагайтесь исключительно на сетевые средства контроля для защиты плохо написанных запросов.

    Примеры опасных паттернов (кратко)¶

    • Разрешение клиенту передавать { "$where": "this.balance > 0" } → удалённое выполнение кода или значительная нагрузка на CPU.
    • Конкатенация пользовательских данных в строки языка запросов или команды оболочки для инструментов БД.
    • Эксплуатация MongoDB без защиты (без аутентификации), слушающей на публичном IP-адресе.
